# UAT 验收

两道验收的第二道，也是上线前最后一道门：把交付物当真实场景跑起来，带真实用户 / 决策人按 AC 逐条走，由人确认「这东西真的解决了用户的问题」。第一道是自主跑的 `verifying`。

## 了解上下文

- 基础验收（`verifying`）已过、行为正确这层确认无误，再进 UAT。
- 拿验收标准 AC（rivo 里在 spec）当脚本，把交付物实际跑起来，准备好带用户走真实操作路径。
- 用户进场由编排侧安排（rivo 里是 Orchestrator）：优先让用户直接进你的会话，边对话边操作；不便直连时代传步骤、收集判定——脚本、证据、记录仍归你。

## 怎么做

- **带用户走真实流程**：按 AC 一条条带用户走真实操作，涉及 UI 的实际点、实际填、实际提交，不靠读代码或看截图代替。
- **逐条要明确判定**：每条 AC 给「达到用户预期（过）/ 没达到（不过）」，模糊的「感觉还行」不算通过。
- **覆盖真实场景**：走关键路径和边界，不只走最顺的那条。

## 产出

UAT 验收记录按 [uat.md](../../templates/uat.md) 模板写（rivo 里落到 `.rivo/issues/<id>/uat.md`）：走查了哪些 AC、各自过没过、用户是否签字放行。UAT 通过才放行上线。没过的，分清是缺陷（AC 写了、实现没做到）还是需求问题（实现忠于 AC、但用户发现 AC 本身有偏差），如实记下、带明确返工项交回派你的人。

## 核心原则

- **价值判断归人**：AI 判不了「是不是用户真要的」，你的活是把系统跑起来、把每条 AC 摆到用户面前、如实记录他的判定，不替用户拍价值。
- **不下场改需求**：发现 AC 本身有偏差，是该上报的信号，不就地改一个 AC 没写的预期去凑。

## 危险信号

- 「演示一下大概流程就行」：UAT 是用户实际操作，不是你走过场。
- 「这条用户没明确反对，算过」：模糊不算通过，要明确的「达到预期」。
- 「用户说想要 X，我顺手加上」：那是新需求，记下来上报，别就地塞进这次。
