# 架构决策

记录一个重要选择为什么成立、付出什么代价，以及何时需要重新考虑。需求、设计和实施阶段都可以调用。

开始时声明：“正在使用 rivo:architecture-decisions，比较并记录这项重要选择。”

**未获批准的推荐仍是提议。用户接受方案不代表系统已经实现该方案。**

## 何时调用

涉及以下重要选择时，加载本技能并独立记录 ADR：对象或模块的职责边界、共享接口承诺、数据的业务含义、状态与生命周期归属，以及难以撤回的迁移或依赖选择。

常规命名、局部实现和不影响这些约定的调整，留在 plan 中。不要为每个函数建立 ADR，也不要把重要模型选择只藏在技术方案的一句话里。

## 工作步骤

1. **界定问题。** 说明要决定什么、适用范围、已有约定和实际限制。查证关键事实，分清事实与假设。
2. **比较可行方案。** 现状能满足需求时也纳入比较。用同一场景解释各方案的行为、成本、依赖与迁移后果，不编造陪衬选项。
3. **检验模型。** 用正常场景和相关反例检查职责、关系与生命周期，说明哪些规则共享、哪些差异必须保留。需要图示时加载 using-archify，在讨论中展示 SVG。
4. **取得决定。** 给出建议和理由，等待用户对重要取舍作出决定。已有明确批准或委托继续沿用，不重复确认。
5. **记录并交回当前阶段。** 每个决定独立记录，指出哪些 Spec 或 plan 内容受影响。阶段完整结论获批后，再同步正文中的结论与主要理由。局部决定获批不代表可以提前写入整份 Spec 或 plan。

用户只要求记录已有决定时，直接整理其依据。补写的选项分析要标明是事后分析，不能冒充当时讨论过的过程。关键事实仍未证实时，记录影响并继续调查，不替用户批准推荐方案。

## 文档输出

写作前加载可用的 writing-clearly-and-concisely。默认每个决定写入 `.rivo/issues/<slug>/adr/<编号>-<主题>.md`，使用 Markdown。已有 ADR 或项目命名约定直接沿用，不为改格式拆散历史记录。

单独记录、没有所属需求的决定，保存到 `.rivo/decisions/`。用户指定路径优先。跨仓库决定沿用本任务集中保存材料的位置，写入时创建目录。

正文读起来应是一份完整的理由说明。资料链接用于追溯，不能要求读者跳回 Spec 才知道在决定什么。

```markdown
# <编号>：<选择主题>

状态：提议／接受／已替代
日期与确认或委托依据：<真实依据>

## 背景与问题
具体场景、要作出的决定、适用范围和已经核实的限制。

## 可行选项
各选项如何处理同一个场景，行为、成本和依赖有何差异。
涉及结构或流程时嵌入 SVG，在正文解释决定所依赖的关系。

## 决定与理由
采用什么、为什么适合当前约束、放弃了什么。
尚未批准时说明推荐和未决问题，不写成已接受。

## 后果与重新考虑条件
收益、代价、迁移影响和适用边界。
哪些新事实或需求变化会使当前决定失效。

## 依据
需求、讨论、工程证据和相关旧决定的必要来源。
```

替代旧决定时保留原理由，注明新旧编号及替代原因。不要把 ADR 状态变成另一套任务进度管理。

## 完成条件

问题、选项、理由和后果完整，状态与真实批准一致，相关正文已同步。返回决定和文件位置；需要更新的材料尚未处理时明确说明。单独记录任务到此结束，不自动启动完整需求流程。
