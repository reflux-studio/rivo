# 架构决策

开始时声明：“正在使用 rivo:architecture-decisions，比较或记录当前重要选择。”同一阶段已经说明过，就不重复。

调查、比较并记录重要的架构选择。需求、设计和实施阶段都可以使用。已有结论就记录下来，还没决定就先调查和比较。

## 何时值得单独处理

以下问题需要仔细比较或长期保留理由时，单独写一份决策记录（ADR）：

- 各模块负责什么，哪些规则或模型可以共享。
- 接口承诺什么，数据代表什么，依赖哪些能力。
- 哪些安排一旦采用就难以改变。

常规选择留在 Spec 或 plan 中，不为每个函数和分支创建 ADR。

Spec 和 plan 说明概念、规则、结构及已知业务事实。ADR 解释为什么选择这个方案，以及会有什么后果。

## 形成决定

1. 查明要解决什么问题，适用于哪里，已有决定和实际限制是什么。分清事实、假设和个人偏好。
2. 比较真正可行且有差异的方案，现状可行时也列入比较。不要为了衬托推荐方案编造其他选项。核实关键假设，说明各方案的行为、成本、依赖和迁移影响。
3. 涉及模型时，用已有场景和反例检查各方案。说明哪些规则共用、哪些差异要保留，以及增加抽象后是否更难理解。
4. 提出推荐及其依据。重要取舍需要用户判断且没有既有决定时，展示具体后果并等待回应；已有结论直接沿用。
5. 保存决定或提议，核对相关 Spec、plan 和当前知识，说明哪些内容需要更新。方案被接受不代表能力已经实现。

需要图示才能判断时使用可用的绘图能力，沿用当前任务的图源与确认版本；结构对比可参考 [架构图协作参考](../requirements-definition/references/architecture-diagrams.md)。短小选择可用场景表和文字说明。

## 文档输出

写文档时，如果有 `writing-clearly-and-concisely` 技能，就加载并使用。

默认保存到目标项目的 `.rivo/issues/<slug>/ADR.md`。

- 同一需求使用已有目录；单独记录决定时，按主题给目录命名。
- 用户或项目指定了路径，就按指定路径保存。已有记录直接修改原文件。
- 输入资料放在哪里，不影响保存位置。涉及多个仓库时，沿用本任务选定的项目集中保存文档。

每个决定有固定编号和自己的状态，默认追加到同一个文件。项目习惯按编号分文件时，沿用这个习惯。替代已接受的决定时，保留旧理由，并写明新旧记录的关系。

## 文档内容

采用 MADR 的背景、选项、决定和后果结构，记录状态与来源。下方模板可直接使用。

```markdown
# <稳定编号>：<选择主题>
状态：提议／接受／已替代
日期与确认或委托依据：
相关需求、设计与证据：

## 背景与问题
需要决定什么，适用范围、事实与约束是什么。

## 考虑的选项
真实可行的选择及其差异，必要的验证或场景检验。

## 决定与理由
采用什么及其依据；待定时明确写出推荐和未决问题。

## 后果与重新考虑条件
收益、代价、适用边界；哪些证据或变化会促使重看。
替代旧决定时注明双方编号与新依据。
```

## 返回结果

检查来源、方案差异、状态和后果是否写对。没有得到用户确认或委托的建议，仍标为提议。

返回结论、文件位置、未决问题和需要更新的材料。如果这是交付中的一步，回到原问题继续；如果用户只要求记录决定，交付后结束。不要自动重做需求或设计阶段。
