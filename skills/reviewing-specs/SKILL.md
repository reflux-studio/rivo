# 评审需求文档

一份需求文档只有两种失败方式：读的人理解错了要做什么，或者验收的人无法判断做没做到。评审就是在开工之前找出这两种失败。

## 工作流程

### 1. 建立评审依据

- 若项目里维护着长期文档（项目定位、用户与价值一类），先读——需求应当服务于项目的定位。
- 找到这份文档的来源输入：原始诉求、工单里的用户原话。理解它想解决什么，再开始挑毛病。
- 个人偏好不构成依据。依据只有三样：来源输入、长期文档、下面的清单。

### 2. 通读抓理解

- 通读一遍后，尝试一句话复述：给谁、解决什么问题、做成什么样算成功。
- 复述不出来，这本身就是最严重的一条意见——问题陈述不合格。

### 3. 逐节过检查清单

按下面的清单逐节检查。清单与需求文档的产出结构（见 writing-specs）成对维护：那边加一节，这边加一组检查。

### 4. 组织意见

按「意见的写法」成文。

### 5. 交付

发现如何呈现，取决于你对这份文档的位置：

- **有裁决权**（团队产物的把关评审）：给出结论——通过，或不通过附阻塞项。阻塞项清零才能通过。若这单工作有工单目录，意见存入其中的 `reviews/`。
- **无裁决权**（外来的 PRD、别人写的文档）：同一份发现转为改进建议和澄清问题清单，交给能回答的人。

## 检查清单

### 问题陈述

- [ ] 说清了谁遇到什么问题、不解决的代价是什么？
- [ ] 有证据支撑，还是凭感觉断言？

### 目标与非目标

- [ ] 目标是结果还是产出？「缩短首次配置时间」是结果，「做一个配置向导」是产出。
- [ ] 每个目标可衡量吗？
- [ ] 有非目标吗？没有非目标的文档等于没有边界。
- [ ] 每个非目标有理由吗？

### 需求与用户故事

- [ ] 从用户视角描述，还是夹带了实现方式？出现具体 UI 组件或技术选型即为越界。
- [ ] 分了优先级吗？全是 P0 等于没有 P0。
- [ ] 用户故事有收益（「以便……」）吗？颗粒度小到能独立交付吗？

### 验收标准

- [ ] 逐条编号了吗？
- [ ] 每条可独立操作、可判真假吗？
- [ ] 覆盖了错误情况和边界情况吗？有「不应该发生什么」的负面用例吗？
- [ ] 有模糊词吗？「快速」「友好」「直观」——写了等于没写。
- [ ] 是不是把需求换个说法又抄了一遍？验收标准要给出判定的操作和预期，不是复述。

### 成功指标

- [ ] 指标具体可衡量吗？「提升体验」这类写了等于没写。
- [ ] 有目标值、衡量方法和评估时点吗？

### 待解决问题

- [ ] 都是真开放的问题吗？背景信息能回答的不该出现在这里。
- [ ] 每个都标了谁来回答、是否阻塞开工吗？

### 时间线考量

- [ ] 硬性截止日期是真实存在的承诺，还是拍出来的？
- [ ] 对其他工作的依赖标出来了吗？
- [ ] 一次做不完的需求，有分期建议吗？

### 整体

- [ ] 前后自洽吗？目标、需求、验收标准之间有没有互相打架？
- [ ] 比例失衡吗？小需求配大文档，和大需求配薄文档一样是问题。
- [ ] 有空节吗？没有内容的节是噪音。

## 意见的写法

- 每条意见给三样：**位置**（哪一节哪一条）、**问题**（是什么）、**为什么**（违反清单哪条、会导致什么后果）。能给改法就给改法。
- 分级：**阻塞**（不改就会导致理解错误或无法验收）与**建议**（改了更好）分开列，不把口味包装成阻塞。
- 「这里不好」不是意见；「AC-3 用了『快速响应』，无法判真假，建议改为『搜索结果在 1 秒内返回』」才是。
- 好的地方点出来——确认「这部分可靠」和指出问题同样有信息量。

## 输出

```markdown
## 需求文档评审：[文档名]

### 结论
[把关：通过 / 不通过；反馈：总体评估一两句]

### 阻塞项
| # | 位置 | 问题 | 为什么 |
|---|------|------|--------|
| 1 | [节/条] | [描述] | [依据与后果] |

### 建议项
| # | 位置 | 建议 | 理由 |
|---|------|------|------|

### 澄清问题（反馈场景）
1. [问题] —— [为什么需要答案、该由谁答]

### 可靠的部分
- [确认没问题的节，一句话]
```

## 注意事项

- 评审产出意见，不产出修改——改是作者的事。
- 复述测试（工作流程第 2 步）是性价比最高的一步，不要跳过。
- 清单管得住下限，管不住「这需求值不值得做」——价值判断不在评审范围内。
