# 架构图协作与留存

需求定义或技术设计需要展示结构变化时读取。图的长期现状维护由 [knowledge-management](../../knowledge-management/SKILL.md) 负责。本参考约定 Rivo 的协作与材料归属；实际绘图前仍需加载已安装的 Archify 技能，按其版本读取匹配 schema、示例及校验要求。

## 图源与展示产物

类型化 JSON 是可维护的图源。Archify 将其渲染为自包含 HTML，内嵌 SVG 与交互；HTML 是阅读和协作入口，图片是按需导出产物。不要手改生成的 HTML 来代替修改 JSON，也不要把 HTML 当作图片生成后的废弃入口。

已核实 Archify 2.16 的 `compare architecture` 接收两份架构 JSON，生成一个包含 Before / Delta / After 切换的 HTML，默认展示 Delta，并写入相邻的 compare 回执。它按组件和关系的稳定 ID 对齐，边界身份由 kind 与 label 派生；不要重编已有对象 ID、无故改边界名称或通过重新布局制造无意义差异。

## 取得并固定 before

1. 从项目全局知识导航进入相关模块，找到当前架构 JSON、适用范围、来源及版本；核对代码或运行证据。不能仅凭历史方案或图片推定当前实现。
2. 图源过时时，先依据事实校正现状。没有图源时从调查建立；只有图片时重建并核实 JSON，不能声称已找回原始图源。无法查明的部分保留未知，不伪造 before。
3. 将核实的现状复制到本次需求目录作为 `before.architecture.json`，记录知识库来源版本或哈希，以及核实依据。一次讨论期间保持 before 不变。
4. 复制 before 为 `target.architecture.json` 后演进，保留相同对象的 ID 与尽可能稳定的布局。基线本身发现错误时，保留原版本，说明修正依据，生成新的基线版本并重新检查受影响结论。

## 候选图用于作出决定

target 在讨论中是提议，确认后才成为已接受的方案。按 schema 支持的标题或标签明确标注“候选”与当前假设，在展示时说明哪些是既有事实、哪些是建议、哪些尚未定；不向 JSON 添加未经 schema 支持的状态字段。

尚未确定某条审批链或职责归属时，先围绕当前选择绘制一个有依据的候选；有实质不同的方案时，保留各候选图源，依次在同一个 compare 阅读入口展示与 before 的差异，说明当前展示的是哪一案。没有依据的细节暂不展开，不能把不同方案同时画成都会实施，也不能把猜测写进 before。

“target 尚未确认”不属于工具不可用、没有基线或无需图示，不能因此降级为 ASCII 后推迟到技术设计。先展示本轮需要判断的候选，接收反馈后再改 target；图参与决定的形成，不只是决定后的附件。

## 随讨论更新 target

每轮形成需要用户判断的架构变化时，修改 target、按 Archify 要求验证，再执行对比。以下 `<archify-root>` 和材料路径由当前安装及项目约定确定：

```bash
node <archify-root>/bin/archify.mjs compare architecture \
  before.architecture.json target.architecture.json compare.html \
  --quality showcase --json
```

使用相同的展示入口，成功后在宿主支持的预览中刷新或重新打开，展示新增、移除和修改的关系及其后果。仅写出文件路径不等于已向用户展示；无法预览时说明限制并提供可访问产物或替代呈现，不勾选已展示。

生成期间使用固定输入，避免一边改 JSON 一边对比。命令失败时保留诊断，原路径可能仍是上一份成功产物，不能当成本轮 target 展示或验收。compare 有自己的校验和回执，不能把单图 `deliver` 当作对比命令。

Archify 2.16 的 `preview` 仅监听一份 JSON，不提供双输入 compare watch。Rivo 默认由 AI 每轮重新 compare 并刷新同一入口，不声称保存后会自动刷新。单图主动预览按 Archify 约定启动与停止；升级后先核实能力再改变此行为。

## 确认与技术设计承接

用户确认时，在对应 Spec、ADR 或技术方案中记录图源版本或哈希、确认依据与阅读入口。通过可恢复的版本控制修订或需求内不可变快照保留该版 JSON、compare HTML 和回执；只有哈希而没有可恢复内容不足以保存确认结果。

技术设计继承同一需求的 before/target 和确认记录，继续深化 target。工作入口可以更新，已确认版本保留不动。图成为方案的一部分，相关文档引用它，不能等方案结束才补一张没有参与讨论的图。

## 能力边界与替代

- `compare` 在已核实版本只支持 architecture。流程、时序、数据流和生命周期使用对应单图能力与显式变化说明；需要架构对比时补充真实的组件关系视图，不能把任意类型 JSON 塞进 architecture。不得将替代图标为 compare 已完成。
- 两份架构没有任何共同组件 ID 时 compare 会拒绝。全新系统展示 target 与新建范围说明，不添加虚假共同节点来绕过校验。
- Archify 不可用时说明原因，以 Mermaid、表格或文字继续，记录替代方式。用户明确不需要图或不存在相关变化时不强制绘图。
- compare 描述编写的架构快照差异，不证明代码已经实现目标。目标中的计划能力不可冒充已核实源码证据。

## 检查证据与清理

`visual-check` 是检查工具：在产物旁生成四张尺寸／主题截图、一个联系表 HTML 和一个 JSON 回执；成功后的保留是为了检查证据。按已安装 Archify 的交付约定完成实际视觉检查，不能把截图生成成功当成视觉审阅通过。对 compare 页面还需检查其切换视图和 Delta，不假定单图检查覆盖了全部交互。

材料按用途管理：

| 材料 | 留存方式 |
| --- | --- |
| before、target、已确认快照 | 留在本次需求材料，交付后随需求归档 |
| compare HTML、compare 回执 | 保留可读入口与可追溯的确认版本 |
| visual-check 截图、联系表、检查回执 | 检查完成后，将需留存的一组证据放入 `evidence/`；保留产物哈希与来源对应关系 |
| 无需留存的本轮辅助文件 | 检查完成且确认没有引用后，按本轮实际生成清单清理 |

移动证据时成组维护截图、联系表及回执的相对链接，不能留下指向已删除截图的页面。不清理未解决失败的诊断、既有审阅记录或其他任务文件；不得用全项目 `*.visual-check.*` 通配删除。若保存过确认版本，后续运行检查不得覆盖那一版证据。临时渲染目录由 Archify 管理，不额外修改其安装目录。

## 交付后维护

实施和验证完成后，通过 knowledge-management 对照实际交付修订最终图源，核实偏差、版本与影响范围，再将 JSON 维护回项目知识库，并更新当前阅读入口和导航。具体回写及并发基线检查遵循 [知识组织参考](../../knowledge-management/references/knowledge.md)。用户确认的 target 在交付核实前仅是方案，不替换系统现状。
