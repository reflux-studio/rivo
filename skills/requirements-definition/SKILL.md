# Requirements Definition

与用户形成能解释真实场景、支撑验收的需求约定，并直接保存结果。已有 PRD、知识和决定直接承接；只要求评审、整理或先出草稿时按该范围完成，不重新启动整套讨论。

## 协作方式

围绕当前最重要的问题调查、提出解释或候选、接收回应，再更新结论。发现足以讨论的问题就展示依据和具体后果，不等全量调查或完整 Spec 写完。需要用户判断且没有既有决定时，等待回应后再推进依赖部分；独立调查可以继续。

已有确认不重复询问。未知业务规则不由代码或 AI 推测决定，能自行查明的技术事实也不转交用户。用户明确要求"先出草稿"时可以先整理，但区分事实、提议和未决项。讨论中可保存局部结论；完整草稿和问题清单不能代替用户尚未参与的讨论。

## 核实现状与范围

从相关项目知识、PRD、设计稿及代码核实用户路径、现有能力和限制。区分业务希望怎样、系统实际怎样与尚待验证的推测；历史方案不自动代表现状。引用已有权威来源，指出材料之间的矛盾及影响。

明确目标、非目标、角色、入口、可观察行为和验收。涉及界面时讨论信息层级、操作位置、状态反馈和异常恢复；无界面任务描述调用方行为。技术约束影响需求成立时说明其用户后果，必要时做小实验，不提前展开全部实现细节。

## 从场景建立模型

在含义已清楚时也检查：多个场景是否表达同一业务动作、关系或约束？哪些区别来自真实业务，哪些只是入口或现有代码组织造成的？先解释概念和生命周期，再考虑表、类或服务。

提出有依据的共同规则，用已有场景及能区分候选解释的反例检验它。说明模型解释了什么、消除了哪些人为例外、哪些差异仍需保留。没有足够共性时沿用现有模型，不为减少分支而统一独立规则。

例如，四个账号操作可能共享“设置指定账号为主账号”。仍需核实主账号的所属范围、有效条件和生效时点；各入口的权限或审批差异可以保留。让用户判断具体行为与边界，不要求用户凭空设计模型。

将确认的概念、关系、约束、场景和适用边界直接写入 Spec。重要模型选择的理由可留在本文件；值得单独推演或长期追踪时，可使用 architecture-decisions 形成 ADR。建模不以是否生成 ADR 为完成标志。

## 方向与展示

影响需求行为、成本或协作承诺的方向选择在当前问题中比较，给出成立条件、代价及建议。例如立即生效还是审批后生效需要在这里对齐，具体存储与重试机制由技术设计展开。

存在影响判断的结构变化时，使用可用的 Archify，并按 [架构图协作参考](references/architecture-diagrams.md) 固定 before、展示候选 target、随讨论刷新同一 compare 入口。图在需要判断的当轮展示，保留已确认版本。工具不可用时说明限制并采用可读替代；用户明确不需要图或没有相关变化时无需绘制。

## Output Location

默认写入本次目标项目根目录的 `.rivo/issues/<slug>/spec.md`，同一需求沿用已有 slug。用户指定位置或项目配置（CLAUDE.md 等）中声明的路径优先；已有文件的位置不构成约定；修订已有文件时原位更新。输入 PRD 所在目录不决定输出位置，目录不存在时按需创建。跨仓库任务选定并说明一个主交付根目录，后续产物沿用。

## Spec Structure

按实际问题裁剪以下结构，不用空章节凑完整度。开头写明草稿／部分确认／已确认、来源和确认依据；图示附入口及可恢复的确认版本。

```markdown
# <需求名称>

## 背景与范围
现状及依据、目标、非目标、角色与约束。

## 概念与规则
核心解释：哪些概念或动作共同解释本次场景。
关系与约束：对象关系、状态变化、操作前后必须成立的条件。
场景检验：规则怎样解释原始场景，什么反例能检验它。
适用边界：必须保留的差异、尚未确定的含义。

## 行为与交互
场景、前置条件、操作、预期结果；相关页面或调用方表现。

## 验收
情境或输入、预期行为、验证方式；适用的质量要求及依据。

## 重要选择与未决项
选择及理由，相关 ADR（如有）；未决问题、影响范围与解决方式。
```

## 完成与交接

关键问题讨论后回述约定，取得或引用已有确认，直接写入并核对 Spec。检查概念与场景能否对上、验收是否具体、提议是否被误写为事实、重要选择的理由是否留存。文字先给结论，再给依据；用实际对象说明，删去重复 PRD 和泛泛承诺。

需求与必要方向明确、关键可行性有依据时交付。阻塞项只阻塞受影响范围，不能标为全部确认。需要完整交付时，将 Spec、来源、确认依据、图源和未决项交给技术设计；已有充分实施依据的小改动无需补造方案。只要求评审或整理时返回本次结果。
