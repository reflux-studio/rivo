# Requirements Definition

开始时声明：“正在使用 rivo:requirements-definition，核实现状、对齐需求和验收。”同一阶段已声明时不重复。写作时使用可用的 `writing-clearly-and-concisely` 技能。

与用户明确场景、规则和验收，写入 `spec.md` 并完成自审。承接已有 PRD、知识和决定，文档深度随需求规模调整。

## 工作步骤

在主任务清单中追踪以下步骤，沿用已有进度。无任务工具时用对话短清单。

- 核实相关知识、现状和已有材料，确认影响范围。
- 对尚需用户判断的业务问题展示依据、后果和建议，等待回应后继续依赖部分。
- 需要架构选择时展示候选变化并比较。
- 回述收敛结论，引用已有确认或委托；尚未决定的内容明确标注。
- 写入 spec.md。
- 自审并修正 Spec，核对规则、场景、验收和确认状态。
- 交付需求结论，或衔接技术设计。

整理已有结论时直接写入 Spec 并自审。用户只要求评审时，返回发现、依据和建议。

## 协作方式

围绕当前问题调查、提出解释、展示依据与后果，接收回应后更新结论。取得足够依据就展开讨论。需要用户判断的问题，等待回应后再推进依赖部分；独立调查继续。

沿用已有确认。AI 查证技术事实，向用户说明待定业务规则的选项与后果。讨论记录区分事实、提议和未决项，重要判断须有确认或委托依据。

## 核实现状与范围

从相关项目知识、PRD、设计稿及代码核实用户路径、现有能力和限制。区分业务希望怎样、系统实际怎样与尚待验证的推测；历史方案不自动代表现状。引用已有权威来源，指出材料之间的矛盾及影响。

明确目标、非目标、角色、入口、可观察行为和验收。涉及界面时讨论信息层级、操作位置、状态反馈和异常恢复；无界面任务描述调用方行为。技术约束影响需求成立时说明其用户后果，必要时做小实验，不提前展开全部实现细节。

## 从场景建立模型

在含义已清楚时也检查：多个场景是否表达同一业务动作、关系或约束？哪些区别来自真实业务，哪些只是入口或现有代码组织造成的？先解释概念和生命周期，再考虑表、类或服务。

提出有依据的共同规则，用已有场景及能区分候选解释的反例检验它。说明模型解释了什么、消除了哪些人为例外、哪些差异仍需保留。用业务证据判断哪些规则共享、哪些独立。

例如，四个账号操作可能共享“设置指定账号为主账号”。仍需核实主账号的所属范围、有效条件和生效时点；各入口的权限或审批差异可以保留。向用户展示具体行为与边界，帮助其判断模型。

将确认的概念、关系、约束、场景、适用边界和选择理由写入 Spec。需要集中比较或长期追踪的重要选择，使用 architecture-decisions 记录 ADR。

## 方向与展示

影响需求行为、成本或协作承诺的方向选择在当前问题中比较，给出成立条件、代价及建议。例如立即生效还是审批后生效需要在这里对齐，具体存储与重试机制由技术设计展开。

存在影响判断的结构变化时，使用可用的 Archify，并按 [架构图协作参考](references/architecture-diagrams.md) 固定 before、展示候选 target、随讨论刷新同一 compare 入口。图在需要判断的当轮展示，保留已确认版本。工具不可用时说明限制并采用可读替代；用户明确不需要图或没有相关变化时无需绘制。

## Output Location

默认写入本次目标项目根目录的 `.rivo/issues/<slug>/spec.md`，同一需求沿用已有 slug。用户指定或项目配置声明的路径优先；修订已有文件时原位更新。输入 PRD 所在目录不决定输出位置，写入时创建目录。跨仓库任务选定并说明一个主交付根目录，后续产物沿用。

## Spec Structure

用以下结构组织内容，简明写清每项结论。开头写明草稿／部分确认／已确认、来源和确认依据；图示附入口及可恢复的确认版本。

```markdown
# <需求名称>

## 背景与范围
现状及依据、目标、非目标、角色与约束。

## 概念与规则
核心解释：哪些概念或动作共同解释本次场景。
关系与约束：对象关系、状态变化、操作前后必须成立的条件。
场景检验：规则怎样解释原始场景，什么反例能检验它。
适用边界：必须保留的差异、尚未确定的含义。

## 行为与交互
场景、前置条件、操作、预期结果；相关页面或调用方表现。

## 验收
情境或输入、预期行为、验证方式；适用的质量要求及依据。

## 重要选择与未决项
选择及理由，相关 ADR（如有）；未决问题、影响范围与解决方式。
```

## Spec 自审

写完 Spec 后，由当前代理重新通读并检查：

1. **完整性：** 目标、范围、场景和验收是否齐全？清除占位符、空章节和“待补充”。
2. **一致性：** 同一概念和规则是否前后一致？逐个用场景检验规则，修正矛盾。
3. **明确性：** 行为、边界和验收能否得到唯一解释？技术事实自行核实；业务歧义带着选项和后果交给用户判断。
4. **范围与依据：** 需求是否足以形成一个连贯的交付计划？结论是否有来源，确认状态是否准确？

直接修正发现的文档问题。待定业务决定写明影响，取得回应后更新相关内容。自审完成后交接 Spec，并简述修正和剩余未决项。

## 完成与交接

交付保存后的 Spec、来源、确认依据、图示入口和自审结论。影响设计的业务问题须先解决；其他未决项明确记录处理方式。

完整交付继续加载 technical-design，声明用途并传递 Spec。用户指定的需求评审或整理请求，在交付本次结果后结束。
