# 需求定义

和用户一起理清需求，写成 `spec.md`，交给子代理和用户审阅。已有 PRD、项目知识和确认过的决定都可以作为起点。任务小就写短，步骤仍要走完。

开始时说明：“正在使用 rivo:requirements-definition，核实现状、讨论需求和验收。”同一阶段已经说明过，就不重复。

## 工作步骤

把以下步骤加入主任务清单，已有进度直接沿用。没有任务工具时，在对话中列出短清单。

1. 阅读相关资料，核实现状和影响范围。
2. 梳理问题之间的依赖，逐轮讨论，每轮带上依据、建议和后果。
3. 需要选择架构方向时，展示候选方案并比较。
4. 展示完整需求结论和相关图示，说明还有哪些问题未定，等待用户批准。
5. 获批后写入 `spec.md`。
6. 启动审阅子代理，修复发现的问题，复审直到通过；遇到反复无进展的问题，按[审阅与分歧](../using-rivo/SKILL.md#审阅与分歧)处理。
7. 请用户审阅 Spec，收到通过的回应后再进入技术设计。

用户明确要求把已确认的结论写入 Spec 时，直接按这些结论写入，再完成子代理和用户审阅。用户只要求评审时，返回问题、依据和建议。

## 决策树协作

用决策树整理问题：一个决定会影响哪些后续决定？在当前任务清单和讨论记录中记下依赖、依据和状态，无需新增文档。

### 1. 找出先要决定的事

从目标、场景和已有材料中找出会影响模型、行为或验收的问题。说明哪些必须先解决，只讨论与本次需求有关的内容。

### 2. 准备本轮问题

本轮只问前提已经明确的问题。互不依赖的问题可以一起问；需要用到本轮答案的问题，留到下一轮。

每个问题都要让用户看懂：

- 哪个场景需要作出决定？依据是什么，资料是否有矛盾？
- 有哪些选择，各自会带来什么结果？
- 推荐哪一个，为什么？

展示相关模型和图示。用户确认前，推荐答案仍是建议。

### 3. 根据回答更新问题

等用户回答后，更新概念、规则和下一轮问题。用户修改上层模型时，先回述各对象负责什么、如何关联、状态由谁维护，再用场景检查自己是否理解正确。随后检查受影响的下层决定；未受影响的确认继续沿用。

例如，先确定“一次活动只有一条审批链，还是每个模板各有一条”，再讨论驳回会影响哪些填写记录。驳回范围确定后，再讨论整体状态和重新提交的流程。下一轮问什么，由答案决定，不按固定题数或轮数结束。

### 4. 确认完整结论

检查相关分支是否都已解决，再展示完整结论和剩余问题，请用户确认双方理解一致。用户批准后才能写 Spec。

事实由 AI 查代码、读资料或做实验来核实，能查明的内容不让用户猜。调查期间，可以继续讨论不依赖该事实的问题。

暂时没有能问的问题，不代表讨论结束。检查是否还在等待调查结果或外部决定，并说明哪些后续问题因此无法推进。核心业务规则未定时，需求仍未完成；和用户确定如何解决，或调整范围，不能只把它放进“产品确认清单”就宣布定稿。

## 核实现状与范围

阅读相关项目知识、PRD、设计稿和代码，核实用户路径、现有能力和限制。分清用户希望怎样、系统实际怎样、哪些还只是推测。结论引用已有权威来源。历史方案不能直接当作现状；资料有矛盾时，指出原始来源和影响。

把以下内容说清楚：

- 目标与非目标：本次解决什么，不解决什么。
- 角色与入口：谁在什么地方使用。
- 行为与验收：用户会看到什么结果，怎样判断做对了。
- 约束：哪些现有条件限制了需求。

有界面时，讨论信息层级、操作位置、状态反馈和异常恢复。没有界面时，描述调用方的行为。技术限制会影响需求时，说明它对用户的影响，必要时做小实验；完整实现方案留到技术设计阶段。

## 从场景建立模型

检查不同场景是否在表达同一个动作、关系或约束。哪些差异来自业务，哪些只是入口不同或现有代码的写法不同？先讲清概念和生命周期，再考虑表、类和服务。

提出共同规则后，用已有场景和反例验证。说明这条规则能解释什么、减少了哪些人为例外、哪些差异仍然要保留。共享还是分开，应有业务依据。

例如，四个账号操作可能都在“设置指定账号为主账号”。还要核实主账号属于哪个范围、满足什么条件、何时生效；各入口的权限和审批差异可以保留。把具体行为展示给用户判断。

将确认后的概念、关系、约束、场景、适用范围和选择理由写入 Spec。重要选择需要集中比较或长期记录时，使用 architecture-decisions 保存 ADR。

## 展示方向与图示

会影响需求行为、成本或团队承诺的选择，在需求阶段讨论。说明各方案适用的条件、代价和建议。例如，立即生效还是审批后生效要在这里确定；怎样存储和重试留到技术设计。

梳理实体关系、系统协作、流程或状态时，使用 Archify 展示现状和候选方案。按[架构图协作参考](references/architecture-diagrams.md)保存图源和版本，在讨论对应问题时展示，并随用户回答更新。

未安装 Archify 时，说明“当前环境未安装 Archify，使用 Mermaid 替代”，然后继续。按实际选择写 ASCII、Mermaid 或 PlantUML，无需征求降级许可。已经安装但无法使用时，说明实际原因。用户明确不需要图时，遵从用户要求。

## 文档输出

写文档时，如果有 `writing-clearly-and-concisely` 技能，就加载并使用。

默认保存到目标项目的 `.rivo/issues/<slug>/spec.md`。`<slug>` 是这项需求的目录名，同一需求始终用同一个目录。

- 用户或项目指定了路径，就按指定路径保存。
- 已有 Spec 时，直接修改原文件。缺少目录时，在写入时创建。
- PRD 放在哪里，不影响 Spec 的保存位置。
- 涉及多个仓库时，选一个项目集中保存需求材料，并告诉用户选了哪里。后续文档也放在那里。

## 文档内容

开头说明需求来源，分清已确认的结论和未决问题。图示附上阅读入口，以及能恢复的已确认版本。

```markdown
# <需求名称>

## 背景与范围
现状与依据、目标、非目标、角色和约束。

## 概念与规则
核心概念和动作，以及它们如何解释本次场景。
对象之间的关系、状态变化、操作前后必须满足的条件。
用哪些场景和反例验证了规则，哪些差异需要保留。
适用范围和仍未确定的含义。

## 行为与交互
场景、前置条件、操作、预期结果，以及页面或调用方的表现。

## 验收
情境或输入、预期行为、验证方式，以及质量要求和依据。

## 重要选择与未决项
选择和理由，相关 ADR（如有）。
未决问题、影响范围，以及如何解决。
```

## 子代理审阅

写完 Spec 后，加载 [Spec 审阅提示词](references/spec-document-reviewer-prompt.md)。填入 Spec 路径、需求来源、用户确认过的决定和相关图示，启动独立审阅子代理。

审阅者读取文档和依据，将报告写入本需求的 `reviews/spec-<round>.md`，返回 `Approved` 或 `Issues Found`。发现问题时，指出位置，并说明为什么会影响技术设计。

- 主代理修复问题后，启动新的审阅子代理，提供修订后的文档和前轮报告，复审直到通过；遇到反复无进展的问题，按[审阅与分歧](../using-rivo/SKILL.md#审阅与分歧)处理。
- 措辞偏好和可选改进不阻塞通过。
- 修复会改变已确认的规则、范围或验收时，先带着证据和后果请用户决定，再修改并复审。

用户只要求修改表述时，直接修改文档并重新审阅；结论有变化时，回到对应讨论。

## 交付与下一步

交付 Spec、来源、确认依据、图示入口和子代理审阅结论。影响设计的业务问题必须先解决，其他未决项写明处理方式。

子代理通过后，请用户审阅 Spec。只有用户也审阅通过，才能加载 technical-design，说明用途并传递 Spec 和批准依据。用户只要求需求评审或整理时，完成本次结果就结束。
