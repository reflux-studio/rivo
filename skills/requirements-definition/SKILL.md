# Requirements Definition

与用户共同查清问题，形成明确的需求约定与有依据的架构方向。调查、澄清、可行性验证和重要选择围绕当前问题交替推进；接口字段、模块实现机制和迁移步骤由 technical-design 展开。

## Checklist

用宿主任务工具建立以下清单，再开始调查；已有清单补齐沿用。无任务工具时保留对话短清单。

- 核实相关知识与实现，确认现状、影响范围和已有能力。
- 对齐目标、非目标、角色、行为、UI 形态、约束和验收。
- 比较影响需求成立的重要架构选择，验证关键可行性。
- 随讨论展示关键变化，记录确认对应的图源版本。
- 按需保存 Spec 和 ADR，核对依据、确认状态和未决项。
- 交付需求与方向结论，或衔接技术设计。

按请求深度裁剪：只调查保留调查与交付；没有重要取舍不制造 ADR；无需图示时说明原因。调查、讨论和展示可以交替发生。只有实际完成才勾选，展示须有已展示的产物，保存须已加载对应写作技能并完成核对。具体问题放在当前项下，不替换展示与保存责任。

## 查证现状

从项目知识导航找到相关主题，通过 [knowledge-management](../knowledge-management/SKILL.md) 查找和核实结论、现状图源及适用版本，再沿受影响的用户路径核查代码、入口、状态、调用和结果。已有 PRD、设计稿和决定直接承接，不重做已完成的调查。

准备复用某项能力时，确认实际语义、业务差异、依赖和限制，不凭名称判断可行。能从代码或资料查明的事实由 AI 调查，不转交用户。区分业务要求、实现事实与待验证推测，结论附来源，证据不足时说明缺口和确认方式。

## 定义需求与方向

每轮呈现已有依据、本次需要决定的问题、建议及具体后果。聚焦影响范围、行为、结构、成本或协作承诺的选择；独立且容易的问题可合并。需要人判断时展开真正的讨论，已有决定和委托直接沿用，不用一次生成文档代替对齐。

明确目标、非目标、角色、可观察行为与验收。涉及页面时明确入口、信息层级、操作位置、状态反馈与异常恢复。术语或规则有歧义时使用 [domain-modeling](../domain-modeling/SKILL.md)。

比较有实质差异的做法，包括沿用现状：获得什么、改变什么、影响谁、代价和成立条件是什么。架构选型按需要发生，不是每个需求的必经步骤。关键机制可以调查或做小实验，深度以能判断方向是否可行为准。

例如，提交后立即完成还是异步处理会改变需求和验收，需要在这里对齐；消费者如何组织、重试数据怎样存储，则交给技术设计。将尚未成立的技术假设及其用户后果保持可见。

## 展示变化

流程、生命周期、跨模块调用、数据流或职责划分有实质变化，且用户需要基于此判断时，加载 Archify，并读取 [架构图协作参考](references/architecture-diagrams.md)。先取得核实后的 before，再演进 target；架构对比使用一个 compare HTML 中的 Before / Delta / After，在需要判断的当轮更新展示。

不支持 compare 的图型、无可比较基线或工具不可用时，按参考中的能力边界处理并说明替代方式。用户明确不需要图或没有相关变化时不强制绘制。UI 形态结合设计稿或原型。

## 保存与衔接

实际加载 [write-spec](../write-spec/SKILL.md) 保存需求约定，按需加载 [write-adr](../write-adr/SKILL.md) 保存重要选择。传入结论、来源、确认或委托依据、未决项、图源版本和目标位置。草稿可随讨论保存，写作交回后继续原问题。ADR 可以在任何阶段独立产生或修订。

新证据与已确认结论不符时，说明原约定、证据、后果和建议，在既有委托内处理；未获决定只暂停依赖部分。修订受影响的 Spec、ADR 和图源时保留旧理由及确认版本，不把新结论改写成原本约定。

本阶段完成标准：需求与所需架构方向已确认，关键可行性有依据，图示和材料与确认版本对应；接口和模块实现细节允许留给下一阶段。仍有阻塞选择时说明影响，不标为全部完成。

需要展开方案且有授权时加载 [technical-design](../technical-design/SKILL.md)，传入 Spec、相关 ADR、before/target、确认记录、可行性依据及未决项。已有足够实施依据的小改动可直接衔接 [incremental-delivery](../incremental-delivery/SKILL.md)，无需补造详细设计。只要求调查或评审时交付结果，不自行进入实施。
