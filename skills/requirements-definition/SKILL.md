# 需求定义

把用户要解决的问题说清楚，让技术设计有可靠依据。先对齐现状，再讨论目标；用户批准完整结论后才能写入 `spec.md`。

开始时声明：“正在使用 rivo:requirements-definition，核实现状、讨论本期需求和验收。”

**不得把读过资料当作现状已对齐，把局部回答当作完整批准，或把未决核心规则写成待办后结束需求阶段。**

## 工作清单

使用宿主任务工具为以下步骤建立任务，完成条件成立后再勾选。没有任务工具时在会话中维护短清单。

1. **明确本期范围。** 回述本次要交付什么、哪些属于后续工作，沿用用户已经明确的边界。
2. **调查实际现状。** 围绕本期场景查清实际行为、工程机制和限制，为需求讨论提供依据。
3. **呈现并对齐现状。** 加载 using-archify，展示本期相关的现状图及依据，说明未知之处。收到用户确认或纠正后才能结束此项。
4. **逐轮讨论需求。** 按决定之间的依赖展开场景、规则和验收，记录未解决的问题及其影响。
5. **呈现并对齐目标。** 总结完整需求，用图示对比现状与目标，讲清变化和理由，等待用户批准。
6. **写入 Spec。** 按获批结论写正文、嵌入 SVG，重要选择加载 architecture-decisions 并保存独立 ADR。
7. **独立审阅与修复。** 使用本技能的 Spec 审阅提示词启动子代理，解决实质问题，再由新的审阅者复审。
8. **用户审阅与交接。** 展示文件及审阅结果，收到用户通过的回应后才能进入技术设计。

用户只要求评审时，返回问题、依据和建议。明确要求整理已有结论时，核对其范围与批准依据后写入，再完成文档审阅；不重演已经完成的讨论。

## 核实现状

调查要回答：我们对问题和现状的理解是否成立，本次准备改变哪些行为。阅读本期涉及的 PRD、设计稿、项目知识和实现，沿真实场景从入口追到最终结果，查清参与方、接口、数据转换、权限、配置和外部依赖中影响结果的机制。不能只确认“存在这个能力”，把关键限制留到技术设计再查。

例如，需求要求附件进入档案，就要查清当前附件由谁上传、怎样转换和保存、何时归档。调查深度以能解释本期行为为准，不提前穷尽所有候选实现，也不因读过足够多文件就结束调查。

区分用户要求、已核实事实和推测。代码里有类型、接口或组件，不代表业务已经使用；关键关系要有实际调用、配置或运行证据。历史方案只能提供线索，材料冲突时回查原始来源。查不到就说明搜索范围和具体影响，不把“尚未找到”扩大成“整个系统不存在”。能查明的事实由 AI 调查，不让用户猜代码。

小问题直接查证，需要独立探索的问题使用共享的[调研提示词](../../references/investigation-prompt.md)委派。带上已有发现与证据，说明还缺什么、会影响哪个判断。主代理核对返回结果、处理冲突，继续本阶段的讨论；不为每次调查另建清单或报告。

展示现状时解释真实链路和限制，图中只放当前事实。用户纠正或讨论扩大范围后，补查受影响的问题并修正相关结论。用户认可不能代替工程查证；能解释本期主要场景、关键判断有依据、未知的影响明确后，再进入现状对齐。影响核心规则的缺口按本阶段要求解决，不因列为待办就宣布现状已查清。

调查发现先用于讨论。需求结论获批后，把理解业务和后续设计所需的现状、机制与限制写入 Spec，并在相关主题末保留证据位置和适用版本。调查现有存储方式不等于决定新增结构怎样存储，实现选择留给技术设计。

## 决策树协作

决策树用于组织问题，不要求画成决策树图。先找出会影响后续判断的决定，再逐轮展开。

### 准备本轮问题

只讨论本次范围内、前提已经明确的问题。每个问题先说明场景和依据，再比较可行选择的行为、代价与后果，最后给出建议。不要让用户审批常规文件命名和目录安排。

使用宿主的结构化提问工具。紧密相关的问题围绕同一个决定讨论；互不依赖的问题可以合并，不能用一次问卷代替后续推演。图示应解释当前对象或流程，不能用问题依赖图代替系统现状图。

### 根据回答推进

收到回答后，回述由此确定的规则，更新概念和后续问题，再检查正常、拒绝、重复操作等与本需求有关的场景。上层模型改变时，重看受影响的下层决定；仍有效的批准继续沿用。

例如，先明确审批以整次活动还是每个模板为单位，再讨论驳回影响哪些填写结果。不能在审批单位未定时，直接把整次活动退回写成既定行为。

没有新问题可问时，检查是否还在等待调查或外部决定。涉及范围、核心对象、业务行为或验收的未决问题会阻塞定稿；和用户确定解决方式或调整本期范围。不要仅列入“产品待确认”就继续写最终 Spec。

### 呈现完整目标

按用户场景讲清角色、入口、操作、结果与异常反馈，说明目标相对现状改变了什么。用 using-archify 展示目标 SVG 和现状对比，用户确认前保持“候选”含义。

重要的对象职责、共享规则和生命周期选择必须加载 architecture-decisions 比较并记录。先在正文说清选择与理由，再用 ADR 保留详细取舍。

最后展示完整结论及剩余限制，等待明确批准。不要按固定问题数或轮数宣布讨论完成。

## 文档输出

写作前加载可用的 writing-clearly-and-concisely。使用 Markdown，默认保存到目标项目的 `.rivo/issues/<slug>/spec.md`。同一需求沿用原目录，已有文件原位修改；用户或项目指定路径时按指定位置保存。跨仓库任务选一个项目集中保存材料，并说明位置。输入 PRD 的目录不决定输出位置，写入时再创建目录。

Spec 应让不了解对话的设计者读懂业务。按下面的内容展开，标题可以贴合需求，但不能遗漏实际涉及的规则。用完整句子解释对象与行为，用表格整理重复结构，用具体场景消除歧义。图嵌在对应解释旁，图中的关键规则也写进正文。

```markdown
# <需求名称>

## 背景与本期范围
谁遇到什么问题，当前如何处理，本期要改变什么。
明确包含和不包含的工作，以及影响本期的后续约束。
沿本期场景说明当前入口、参与方和结果，嵌入现状 SVG。
解释影响业务行为或后续方案选择的关键机制与限制，保留必要依据。
描述当前实现，不提前规定新增实现；不搬入与这些判断无关的代码和配置细节。

## 目标与业务规则
解释核心对象各自代表什么、归谁管理、如何关联。
逐项说明允许和禁止的操作、成立条件、状态变化及影响范围。
用具体例子说明规则；嵌入目标或流程 SVG，并解释变化。

## 场景与交互
按角色和操作展开：前置条件、输入、预期结果、可见反馈。
写清本次涉及的拒绝、撤销、重复操作和异常恢复。
界面需求说明信息和操作位置；无界面需求说明调用方行为。

## 验收标准
每个场景写明输入或条件、可观察结果、验证方式。
质量要求给出明确标准和依据，不写“正常”“合理”“体验良好”。

## 重要决定与剩余问题
在此说明决定和主要理由，独立 ADR 保存完整取舍。
剩余问题写明具体影响和处理方式，不得掩盖阻塞设计的规则缺口。
资料来源集中列在相关章节末尾或文末，不用链接代替正文解释。
```

Spec 确定业务含义，不提前指定数据库字段或逐步开发操作。不得因追求简短，把正文写成只剩术语和规则编号的索引。

## 独立审阅

写完后读取 [Spec 审阅提示词](references/spec-document-reviewer-prompt.md)，提供 Spec、原始请求、PRD、关键调查依据、用户决定和 SVG 图源。审阅者独立读取材料，将报告写入 `reviews/spec-<round>.md`，注明被审版本。

实质问题修复后启动新的审阅者复审，提供当前文件和前轮报告。措辞偏好不阻塞通过；改变业务规则、范围或验收的修复先取得用户决定，再修改文档。同一问题没有新进展时停止重复复审，查清证据或请用户裁决模型分歧。

## 完成条件

Spec 的规则足以支持技术设计，阻塞问题已解决，独立审阅通过，用户已审阅通过。全部成立后，才能加载 technical-design；只要求需求评审或整理的任务，到此交付并结束。
