# 撰写产品方案

撰写功能规格说明书或产品需求文档（PRD）：读它的人不需要再问「到底要做什么」，验收的人拿它就能逐条判断「做没做到」。

## 工作流程

### 1. 理解功能

询问用户想要规格化的内容。可以接受以下任何形式：

- 一个功能名称（「SSO 支持」）
- 一个问题陈述（「企业客户一直在要求集中式身份验证」）
- 一个用户请求（「用户希望把数据导出为 CSV」）
- 一个模糊的想法（「新用户流失得想想办法」）
- 一条缺陷的修复预期（「超时后应该提示重试而不是白屏」）
- 一份现成的需求文档（公司的 PRD、客户交来的需求）

同时判断规模：这个需求里有多少个真正需要决策的点？文档的深度与决策量成正比——一句话的需求配一句话的方案加一两条验收标准，不要为小需求生成大文档。

方向本身还悬着的——值不值得做、往哪个方向做——先用 product-brainstorming 探索定向；这份技能在方向已定之后，把它落成文档。

输入是现成的需求文档时，先消化再转写：先走 critiquing-prds 找出缺口和歧义，列成澄清问题拿去和需求方对齐；答案回来后转写成自己的 spec——引用原文而不重抄、补齐带编号的验收标准、把与原文的差异明确标注出来。

### 2. 收集背景信息

向用户询问以下内容。要以对话的方式进行——不要一次性抛出所有问题，先问最重要的，随着交流逐步补充细节；上下文里已经有答案的不要再问：

- **用户问题**：这解决了什么问题？谁遇到了这个问题？
- **目标用户**：这个功能服务于哪些用户群体？
- **成功指标**：我们如何知道这个功能是否奏效？
- **约束条件**：技术约束、时间线、法规要求、依赖关系。
- **过往经验**：之前是否尝试过？是否有现成的解决方案？

### 3. 利用已有的信息源

- 若项目里维护着长期文档（项目定位、架构说明、设计规范一类），先读它们，方案不与它们冲突。
- 若已连接项目管理或工单工具：搜索相关的工单、史诗任务或功能；提取现有的需求或验收标准；识别与其他工作项的依赖关系。
- 若已连接知识库：搜索相关的调研文档、既往规格或设计文档；提取相关的用户研究发现；查找相关的会议记录或决策记录。
- 若已连接设计工具：提取相关的原型图、线框图或设计探索；搜索与该功能相关的设计系统组件。
- 若这些工具都没有连接，完全基于用户提供的信息和代码库现状推进。不要要求用户连接工具——直接使用现有信息。

### 4. 生成 PRD

按以下部分生成结构化的 PRD。每个部分应包含的内容，详见下文的 **PRD 结构**：

- **问题陈述**：用户问题、受影响的人群，以及不解决该问题的影响（两三句话）
- **目标**：3-5 个具体的、可衡量的、与用户或业务指标挂钩的成果
- **非目标**：3-5 项明确不在范围内的内容，并简要说明理由
- **用户故事**：标准格式（「作为一名 [用户类型]，我希望 [能力]，以便 [收益]」），按角色分组
- **需求**：分为必须实现（P0）、最好实现（P1）和未来考虑（P2），每项均附验收标准
- **成功指标**：先导指标（变化较快）和滞后指标（随时间变化），并设定具体目标值
- **待解决问题**：标注负责解答方（工程、设计、法务、数据）的未决问题
- **时间线考量**：硬性截止日期、依赖关系及分阶段计划

规模小的需求用最小形态：问题陈述加验收标准即可，其余节没有内容就不写——空节是噪音，不是完整性。

### 5. 审阅与迭代

生成 PRD 后：

- 询问用户是否有部分需要调整，主动提出可以扩展特定部分。
- 把你拿不准、需要用户拍板的点单独列出来，不要藏在正文里。
- 主动提出可以创建后续产物（设计说明、工程任务拆解）。
- 若这单工作有自己的工单目录，文档存为其中的 `spec.md`；否则按用户指定的位置保存。

## PRD 结构

### 问题陈述

- 用两三句话描述用户问题。
- 谁遇到这个问题，频率如何。
- 不解决它的代价是什么：用户痛点、业务影响、竞争风险。
- 用证据支撑：用户研究、支持数据、指标或客户反馈。

### 目标

- 该功能应实现的 3-5 个具体、可衡量的成果。
- 每个目标都应回答：「我们如何知道这算成功？」
- 区分用户目标（用户获得什么）和业务目标（业务获得什么）。
- 目标应是结果而非产出：「将首次获得价值的时间缩短 50%」，而不是「构建新用户引导向导」。

### 非目标

- 该功能明确不会做的 3-5 件事。
- 本版本范围之外的相邻能力。
- 对每个非目标简要说明为何不在范围内：影响不够大、过于复杂、属于独立计划、时机尚早。
- 非目标可以防止实施过程中的范围蔓延，并对外设定预期。

### 用户故事

用标准格式撰写：「作为一名 [用户类型]，我希望 [能力]，以便 [收益]」。

指导原则：

- 用户类型应具体到有意义的程度（「企业管理员」而非单纯的「用户」）。
- 能力描述应说明用户想完成什么，而非如何实现。
- 收益部分应解释「为什么」——这带来了什么价值。
- 包含边缘情况：错误状态、空状态、边界条件。
- 如果该功能服务于多种角色，应包含不同的用户类型。
- 按优先级排序——最重要的故事排在最前面。

示例：

- 「作为一名团队管理员，我希望为我的组织配置 SSO，以便团队成员可以使用企业凭证登录」
- 「作为一名团队成员，我希望被自动重定向到公司的 SSO 登录页，以便不需要记住另一个密码」
- 「作为一名团队管理员，我希望看到哪些成员已通过 SSO 登录，以便验证部署是否成功」

### 需求

**必须实现（P0）**：没有这些，功能无法上线，它们代表功能的最小可行版本。判断方法：如果砍掉这项，功能是否还能解决核心问题？如果不能，它就是 P0。

**最好实现（P1）**：能显著改善体验，但核心用例没有它们也能运作。通常成为上线后的快速迭代项。

**未来考虑（P2）**：本期明确不做，但设计时不要堵死它的路。记录它们可以防止后续出现让它们难以实现的架构决策。

对每项需求：

- 清晰、无歧义地描述预期行为，不规定实现方式。
- 包含验收标准（见下文）。
- 注明技术考量或约束条件。
- 标注对其他系统或工作的依赖。

### 成功指标

- 先导指标和滞后指标各选关键的几项，给出具体目标值、衡量方法和评估时点（详见下文「成功指标定义」）。

### 待解决问题

- 在实施之前或过程中需要解答的问题。
- 为每个问题标注应由谁解答：工程、设计、法务、数据、用户。
- 区分阻塞性问题（开工前必须解答）和非阻塞性问题（可在实施中解决）。

### 时间线考量

- 硬性截止日期：合同承诺、活动、合规日期。
- 对其他工作或发布计划的依赖。
- 如果功能过大无法一次发布，给出建议的分期计划。

## 用户故事撰写

好的用户故事具备以下特点（INVEST）：

- **独立（Independent）**：可以独立开发和交付。
- **可协商（Negotiable）**：细节可以讨论，故事不是一份合同。
- **有价值（Valuable）**：为用户（而不仅仅是团队）带来价值。
- **可估算（Estimable）**：能够大致估算工作量。
- **小颗粒（Small）**：可以在一个迭代周期内完成。
- **可测试（Testable）**：有明确的方式验证其是否有效。

### 用户故事的常见错误

- 太过模糊：「作为用户，我希望产品更快」——具体是什么应该更快？
- 解决方案先行：「作为用户，我希望有一个下拉菜单」——应描述需求本身，而非 UI 组件。
- 没有收益：「作为用户，我希望点击一个按钮」——为什么？这能实现什么？
- 颗粒度过大：「作为用户，我希望管理我的团队」——应拆解为具体的能力项。
- 内部视角：「作为工程团队，我们希望重构数据库」——这是一项任务，不是用户故事。

## 需求分类

### MoSCoW 框架

- **必须有（Must have）**：没有这些，功能就不可行。不可协商。
- **应该有（Should have）**：重要，但对上线而言不是关键。高优先级的快速跟进项。
- **可以有（Could have）**：时间允许则做。砍掉不会延误交付。
- **暂不会有（Won't have，本次）**：明确不在范围内。未来版本可能重新考虑。

### 分类小贴士

- 对 P0 要严格。必须实现的清单越精简，交付和学习的速度就越快。
- 如果所有东西都是 P0，那就等于没有 P0。挑战每一个「必须」：「没有这个，我们真的不上线吗？」
- P1 应该是你确信近期会构建的内容，而不是愿望清单。
- P2 是架构层面的保险——即使当下不构建，它们也在指导设计决策。

## 成功指标定义

### 先导指标

上线后变化较快的指标（数天到数周）：

- **采用率**：尝试使用该功能的合格用户占比。
- **激活率**：完成核心操作的用户占比。
- **任务完成率**：成功达成目标的用户占比。
- **完成时间**：核心工作流所需的时长。
- **错误率**：用户遇到错误或卡死的频率。
- **使用频率**：用户返回使用该功能的频率。

### 滞后指标

需要较长时间才能体现的指标（数周到数月）：

- **留存影响**：该功能是否提升了用户留存？
- **收入影响**：该功能是否推动了升级、扩展或新增收入？
- **满意度变化**：该功能是否改善了用户对产品的感受？
- **支持负担**：该功能是否减少了支持请求？

### 设定目标值

- 目标应具体：「30 天内达到 50% 采用率」，而非「较高的采用率」。
- 基于可比功能、行业基准或明确假设来设定。
- 设定一个「成功」门槛和一个「进阶」目标。
- 定义衡量方法：用什么工具、什么查询、什么时间窗口。
- 明确评估时间点：上线后 1 周、1 个月还是 1 个季度。

## 验收标准

逐条编号（AC-1、AC-2……），后续的测试记录按编号逐条引用。使用 Given/When/Then 格式或清单格式：

**Given/When/Then**：

- Given（给定）[前提条件或背景]
- When（当）[用户执行的操作]
- Then（那么）[预期结果]

示例：

- Given 管理员已为其组织配置了 SSO
- When 团队成员访问登录页面
- Then 他们被自动重定向到该组织的 SSO 提供商页面

**清单格式**：

- [ ] 管理员可以在组织设置中输入 SSO 提供商 URL
- [ ] 团队成员在登录页看到「使用 SSO 登录」按钮
- [ ] 账户不存在时，SSO 登录创建新账户
- [ ] 邮箱匹配时，SSO 登录关联到现有账户
- [ ] SSO 登录失败时显示清晰的错误提示

### 验收标准小贴士

- 覆盖正常流程、错误情况和边缘情况。
- 明确预期行为本身，而非实现方式。
- 包含不应该发生的情况（负面测试用例）。
- 每条标准都可独立验证。
- 避免模糊词汇：「快速」「友好」「直观」——写出可判定的具体含义（「首屏在 2 秒内可交互」）。

## 范围管理

### 识别范围蔓延

以下情况即为范围蔓延：

- 规格定稿后需求不断增加。
- 「小」的增补累积成明显更大的项目。
- 在构建没有用户要求过的功能（「顺便做一下……」）。
- 交付日期不断推迟，却没有明确的重新界定范围。
- 只增加需求而不删减任何内容。

### 防止范围蔓延

- 在每份规格里明确写出非目标。
- 任何范围增加都必须伴随范围削减或时间线延长。
- 在规格里清楚区分本期和下期。
- 对照原始问题陈述审视规格——是否每一项都服务于该问题？
- 为调研设定时间盒：「如果两天内无法搞清楚 X，就砍掉它」。
- 建一个「待议」清单，存放好想法但暂不纳入范围。

## 输出格式

使用带清晰标题的 Markdown。保持文档易于浏览——读者应该能只看标题和加粗文字就了解大意。

## 注意事项

- 对范围要有主见。宁可要一份精简、界定清晰的规格，也不要宽泛模糊的。
- 如果想法对一份规格而言过大，建议分期，先为第一期撰写规格。
- 成功指标应具体可衡量，不要模糊（「提升用户体验」）。
- 非目标与目标同样重要，它们防止实施过程中的范围蔓延。
- 待解决问题应是真正开放的——不要包含从背景信息就能回答的问题。
- 定稿后再改，改动要重新走评审，不口头补充新说法。
