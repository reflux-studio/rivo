# Requirements Clarification

与用户确定本次要交付什么、在什么条件下怎样工作。产出足以指导设计的需求与交互约定，以及有来源的现状判断。

现状调研为需求澄清提供事实依据，也可在后续决策、设计和实施中继续，不单独设为必须完成的阶段。

## 查清相关现状

从已有知识导航、PRD、设计稿和相关代码进入，按当前问题取用材料。沿受影响的用户路径核查入口、状态、调用和结果；准备依赖某项能力时，确认它的实际语义和限制，不凭组件名或接口存在就认定可以复用。

区分业务要求、观察到的实现行为和待验证推测。结论附相关来源；调查深度以支撑当前判断为准，后续设计发现新的依赖时继续调查。新项目从现有业务过程和外部约束开始，不虚构代码基线。

## 围绕问题逐步澄清

先呈现查明的现状、本次变化和会影响范围或行为的缺口，再讨论当前能决定的问题。给出建议、依据和不同选择的具体后果；前提未定的后续问题暂留待定。同一轮可合并相互独立且容易回答的问题，不预设轮数，也不穷举无关边界。

能从代码或资料查明的事实由 AI 调查。业务选择请用户判断；资料不足时说明缺少什么，保留待确认项，不用默认值代替决定。已有决定和明确委托直接沿用。

PRD 或设计稿缺位时，提出需求补充、交互草图或优化建议，区分建议与已确认要求。涉及页面时明确入口、信息层级、操作位置、状态反馈及异常恢复。术语或业务规则有歧义时，通过具体场景澄清；建模不作为每次调研的独立前置任务。

## 形成 Spec

使用 [需求与交互模板](references/spec.md)，或沿用已有 PRD 并补充差异。Spec 描述目标、非目标、可观察行为、UI 形态、规则、约束和验收场景；组件拆分、文件路径、表结构与实现算法留给技术设计。现状代码路径可以作为调查依据引用。

草稿和调查记录可以随讨论保存，标明状态。先让影响范围、行为和验收的未决选择得到确认或明确委托，再将相关部分作为设计依据；不把一份完整草稿当成已经对齐。未决项写明影响什么、由谁或通过什么方式解决，独立部分可继续推进。

## 呈现变化

优先复用现有设计稿与流程图。流程或状态变化难以用文字判断时，使用可用的 Archify 技能呈现现状与目标对比；按实际工具能力表达新增、调整和保留的部分。没有图表工具时用 Mermaid、表格或文字完成讨论。UI 布局用设计稿或原型表达，概念模拟不当成运行证据。

## 后续衔接

需求已明确时，有重要架构取舍就进入 [architecture-decisions](../architecture-decisions/SKILL.md)；方向已有充分依据则直接进入 [system-design](../system-design/SKILL.md)。待定行为只阻塞依赖它的部分。只要求需求澄清时交付 Spec 与未决项；长任务把已定结论、当前阶段和下一步同步到已有进度记录。
