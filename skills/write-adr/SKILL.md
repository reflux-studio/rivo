# Write ADR

记录一项值得长期解释的重要决定。可以独立调用，不要求先有 Spec、技术方案或进入某个阶段。接收结论或候选、事实来源、约束、取舍、状态依据及位置。

## 写作与核对

1. 读取 [ADR 模板](references/adr.md)，查找相关旧决定及稳定编号，确认本次是新增、修订还是替代。
2. 按模板记录问题、约束、可行候选、选择理由、代价和重新考虑条件；已形成决定时开头一句话说明采用什么。
3. 对照模板和原始材料核对结构、事实、备选及确认依据，检查新旧编号关系与受影响引用。
4. 交回位置、状态、主要变化和未决项。被调用时继续原问题；独立写作完成后结束，不启动完整交付。

保留模板主结构，细节按内容裁剪；用户指定其他格式时按其要求。被调用时嵌入当前清单项，不另建竞争清单。

## 决定与状态

备选来自调查，不为填表制造陪衬。选择尚未形成时可记录候选、建议和未决项，将结论标为待定、状态保留提议；只有真实确认或既有委托支持时才能标为接受。不通过写文档替用户作出缺失的决定。

决定需要进一步讨论时交回调用方；独立请求按问题使用 [requirements-definition](../requirements-definition/SKILL.md) 处理需求与方向，或 [technical-design](../technical-design/SKILL.md) 处理具体设计选择，不重跑整套流程。

改变决定时保留原理由、替代编号、新证据与后果，不能把旧决定改写成从未发生。引用相关图源及确认版本，常规实现细节留在技术方案中。ADR 被接受不代表该能力已经实现。
