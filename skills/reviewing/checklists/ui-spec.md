# ui-spec 评审清单

判定：这份 UI 规格能不能进入实现。

对照材料：待审 ui-spec；需求 spec（UI 该覆盖的场景与状态）；设计系统契约 DESIGN.md（现有组件清单、token、模式）；设计稿——有就逐视图打开核对，没有则 ui-spec 应标「无稿，直接设计」。

## spec 覆盖性

- spec 涉及 UI 的场景、状态（空 / 错误 / 权限 / 边界）、用户故事，ui-spec 是否都有对应视图与状态？
- 有没有 spec 没要的视图 / 交互？
- 「审稿结论」（覆盖缺口 / 越界）是否都闭环，没悬着？

## 组件设计合理性

- 该复用 DESIGN.md 现有组件的，有没有无理由新增？
- 新增组件有没有给出「现有的为什么替代不了」？
- 有没有绕过设计系统的硬编码样式（不引用 token）？

复用优先，但不强行复用：把不同设计模式硬塞进一个组件，比新增更糟，会埋维护债。

## 状态与交互完整性

- 每个视图的正常 / 空 / 加载 / 错误 / 无权限 / 边界各态是否都定了？
- 关键操作的交互与流转有没有断链？

## 设计稿忠实度

- 每个视图是否记了设计稿来源（节点 / 链接 / 文件），让实现能回查精确样式？
- 有稿的逐视图打开核对：ui-spec 是否忠实表达了稿件，有没有漏读、误读、擅自简化？偏离稿件又没记进「视觉偏离」的，标出。

## 本类产物的危险信号

- 「ui-spec 自己说覆盖了，那就覆盖了」：有稿必须打开稿核对，自述不算证据。
- 「新增组件比翻库快」：先查 DESIGN.md 现有的能不能用。
- 「能复用就复用」：先确认是不是同一设计模式，还是为省事硬凑。
