# plan 评审清单

判定：这份技术方案能不能进入实现。底线是**照着能不能直接施工**——实现者照它干活，不该回头猜接口、字段、错误码。

对照材料：待审 plan；需求 spec（方案要落的目标与边界）；全局契约 PROJECT.md（技术栈）、CONVENTIONS.md（规约）、ARCHITECTURE.md（架构边界）；前端再加 ui-spec 和 DESIGN.md；用户提供的原始技术材料（有才核）。

## 与 spec 对齐

- 是否覆盖 spec 全部目标？有没有 spec 没要的实现（过度设计）？
- 是否引入 spec 标「非目标」的内容？有 → 高危。
- spec 的核心场景与边界，方案是否都有对应处理？
- spec 的性能 / 可用性等 NFR，方案设计撑不撑得住？

## 根因成立性（缺陷工单才有）

- 根因有没有复现测试背书？标「推断」的，推理链是否扎实、有没有更简单的解释没被排除？
- 修复方案是否对准根因，而不是只压症状？

## 合规（架构 / 规约 / 技术栈）

- 是否遵循 ARCHITECTURE 的模块边界与分层？突破是否记为架构决策并给足理由？
- 新引入的组件 / 库 / 中间件是否在 PROJECT 技术栈内？超出是否给了选型理由、替代、风险？
- 命名、目录、错误码格式等是否与 CONVENTIONS 一致？
- 对外接口变更是否影响 ARCHITECTURE 记录的下游调用方？兼容策略是否明确？

## 可实施性

- 跨界接口是否有完整请求 / 响应 / 错误示例？错误码是否枚举？
- 核心算法或状态流转是否用伪代码 / 状态图讲清？
- 新增 / 变更字段的类型、约束、索引是否完整？数据迁移是否说明新旧并存与废弃节点？
- 写操作是否定义幂等键？外部调用是否有超时 / 重试 / 降级？
- （前端）ui-spec 提的新增组件，plan 是否定了 Props / 事件 / 类型契约？复用组件是否对齐 DESIGN.md？

## 非功能与风险

- 鉴权、防刷、敏感数据处理是否与 ARCHITECTURE 安全基线一致？
- 关键日志 / 指标 / 告警是否定义、符合项目约定？
- 有上线风险的，是否有灰度与可执行的回滚步骤？

## 内部一致性

- 技术决策一节是否记了「决策 → 理由 → 放弃的替代 → 风险」？关键决策有无论证？
- 影响面清单是否与总体设计、组件设计自洽，无遗漏改动点？

## 本类产物的危险信号

- 「设计挺漂亮，过」：漂亮不等于能施工，逐条量「照这个能不能直接写」。
- 「这库应该没问题」：超出技术栈的依赖必须有选型理由和退路。
- 「影响面大概就这些」：拿 plan 自己的影响面清单逐项反查，别信「大概」。
