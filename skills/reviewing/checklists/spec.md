# spec 评审清单

判定：这份需求规格能不能放行进入技术方案。底线是**可测试**——每条需求都得能写成一条「做到没有」可判定的测试，否则就是问题。

对照材料：待审 spec；外部 PRD / 原始材料（spec 的「来源材料」里列了才核）。

## 结构完整性

- 按 spec 模板核对，背景与问题、目标与非目标、功能需求、验收标准这几节缺不得；其余小节模板允许按需取用，只标「该有而没有」的：需求明明涉及（有数据实体、有状态流转、有外部依赖）却整节空缺。
- 残留占位符（形如 `[...]`、`[示例:...]`）→ 标出。

## WHAT-not-HOW（实现泄漏）

逐节扫，出现以下任一即高危并引原文：技术栈 / 框架 / 库名；表名、字段名 / 类型、索引；接口签名、URL、具体算法或数据结构；「调用 X 服务」「用 Y 中间件」这类实现手段。

> spec 只回答做什么 / 为什么，以上都属于技术方案。

## 可测试性（逐条 FR / NFR）

对每条需求自问：能否照原文写出一个能判定通过 / 不通过的测试？

- 含不可验证措辞（快、稳定、友好、高效、合理、尽量、灵活、流畅 等）→ 标出。
- 一条捆绑多个行为（「并」「且」「同时」串多个动作）→ 标出，要求拆成单一可验证行为。
- 用「应该」「可以」「最好」代替「应 / 必须」→ 标出。

## 触发与条件明确（逐条 FR，NFR 不适用）

EARS 句式是写作工具，不逐条核句式归类；要审的是句式想保证的东西——每条 FR 的触发时机、前置条件、适用状态是否明确，读的人能否无歧义判断「什么时候该发生什么」。

- 触发不明（看不出何时生效、是持续状态还是一次性事件）→ 标出。
- 错误处理混在正常行为里、没写成独立的条件分支 → 标出。

## 验收标准 AC

- 每条是否有 `AC-NNN` 编号且连续不重复？缺编号 → 高危，下游全靠编号追溯，断一条整链断。
- 是否同时覆盖正常路径 + 至少一条错误 / 边界路径？只有正常路径 → 标出。
- 每条是否 Given / When / Then、描述可观察的外部行为（而非内部状态）？
- 每条能否追溯到至少一条 FR？找不到 → 标出（需求缺失）。

## 成功标准

- 每条 SC 是否含数值阈值或客观可判定条件？无法度量 → 标出。
- 是否为业务 / 用户指标而非技术指标（技术指标归 NFR）？

## 范围与未决

- 非目标是否明确写出？缺失 → 标出。
- 残留 `[NEEDS CLARIFICATION: ...]` 按可关闭性分两类：当下能关的 → 高危，进技术方案前必须澄清；依赖外部、当下无法关的 → 核对是否标了阻塞方与影响面（标了降中危、当前置依赖跟踪；没标仍高危）。

## 内部一致性

- FR 之间有无相互矛盾。
- NFR 存在时，各项是否都满足上面「可测试性」的要求。
- 成功标准是否与目标对齐（有目标无对应 SC，或反之）。
- AC、FR、目标三者是否自洽。

## 辅助章节

- 领域模型与核心实体（涉及数据时）：是否只描述概念、属性、关系，没泄漏表结构、字段类型、索引？
- 假设与依赖：是否列出、是否合理？spec 明显依赖某些外部条件却没声明的 → 标出要求补。

## 与来源材料一致（有外部 PRD / 原始材料时）

- 来源的每个功能点、关键分支、异常场景，spec 是否都覆盖（翻成 FR / AC）或在「非目标」明确排除？漏 → 高危，列出来源位置。
- spec 有没有来源没有、也无澄清出处的内容（凭空发挥）？有 → 标出。

## 本类产物的危险信号

- 「这条没编号但意思清楚」：AC 缺编号就是断链，必标。
- 「PRD 写过了，spec 没写也行」：有来源就逐点核覆盖，漏的算高危。
