# 代码评审清单

判定：本次代码改动（git diff）写得对不对、能不能放行。从局部到全局过三遍，一遍都别跳。

对照材料：本次 git diff；需求 spec、技术方案 plan、代码规约 CONVENTIONS.md；前端再加 ui-spec 和 DESIGN.md。

## 第一遍 · spec 合规（忠不忠于约定）

- spec 的每条 AC，变更中是否有对应实现、行为是否相符？逐条判定：✅ 通过（行为完全符合）/ ⚠️ 有缺陷（行为偏离但功能在）/ ❌ 未实现（不符或缺失）。AC 没有「差不多」，偏差就是缺陷。
- 有没有实现 AC 没要的东西（过度实现）？
- AC 的错误 / 边界路径是否也实现了，而不止正常路径？
- 架构、接口契约、数据结构是否和 plan 对得上？入参 / 出参 / 错误码是否一致？偏离是否记了理由？
- 改动范围是否超出方案描述的文件与模块？
- （前端）是否按 ui-spec 组合实现、复用 DESIGN.md 已有组件而非重写？新增组件是否符合 plan 的 Props 契约？数据是否匹配契约接口？模拟数据是否按要求删除？

## 第二遍 · 代码质量（写得好不好）

- **正确性**：逻辑是否成立；分支、边界（空 / 零 / 极值 / 越界）、异常路径是否兜住；并发时序有无竞态，外部调用失败 / 超时 / 重试是否处理；连接、文件、锁是否正确释放。
- **安全**：外部输入是否校验；有无注入、越权、鉴权缺位；敏感数据是否明文传输 / 存储，密钥 / 凭证有无硬编码。
- **测试**：核心逻辑与关键边界是否有覆盖；测的是真实行为还是 mock，断言是否有效，有没有为覆盖率凑数。
- **规范与简洁**：命名、目录、错误处理是否遵循 CONVENTIONS；有无重复、过度抽象；有没有顺手改了无关代码。

## 第三遍 · 终审（局部看不见的全局问题）

默认各处改动之间有缝，直到逐项证明衔接无误。

- **衔接**：一处的函数签名 / 数据结构 / 错误码，别处调用是否对得上？有无重复逻辑或同一概念多个命名？共享资源（配置、迁移、环境变量）的改动是否相互兼容？
- **AC 全集复核**：全部 AC 拼起来，有没有哪条端到端仍走不通（每处局部都对，串起来断了）？
- **整体回归**：本次变更对既有功能的影响面是否都验证？plan「现状与影响面」逐项反查；全量测试是否通过、输出是否干净。
- **全局遗漏**：plan 的改动点、数据迁移、配置 / 环境变更有没有漏实现？有无遗留的模拟数据、调试代码、TODO？

## 本类产物的危险信号

- 「读着没问题，过」：找不到问题常是没找对地方，三遍逐一过完、别跳。
- 「局部都对，整体应该没事」：局部对、串起来断是终审专抓的，必做。
