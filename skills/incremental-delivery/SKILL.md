# Incremental Delivery

主线程组织任务和用户协作，每个任务由新的执行者实施，再由新的独立审阅者检查。将影响理解和决定的新发现带回讨论。

## 角色与任务

执行者只完成被委托的任务，不嵌套派发；审阅者独立检查，不修改被审实现或契约。已有授权和任务边界由主线程传入。

主线程按可验证的能力或关键机制拆分工作，保留可运行的业务路径。先处理影响后续结构的假设；当前任务细化到可执行，远期任务保留目标与依赖。

派发前使用 [任务简报](references/task-brief.md) 提供适用需求、决定、设计、方法与当前工作区。长任务保存进度和材料入口，不能只依赖对话记忆。没有相关模型或 ADR 的任务无需补造文档。

## 实施与审阅循环

1. **派发执行。** 为当前任务启动新执行者，使用 [执行者提示词](references/implementer-prompt.md) 注入所需上下文。可用时选择不继承全历史的委托方式；否则明确本轮边界。
2. **接收结果。** 核对完成内容、验证、自审与未决项。“已实现”表示待审，不等于交付完成。缺上下文时补充，重要决定缺失时处理依赖。
3. **独立审阅。** 为新任务启动不同于执行者的新审阅者，使用 [审阅者提示词](references/reviewer-prompt.md)，检查需求与契约、工程质量、验收证据。
4. **修复或对齐。** 实现缺陷按原要求修复，重要分歧带回用户。修复后复审受影响部分，可沿用原审阅者并更新材料。
5. **完成当前任务。** 验收有依据、阻塞项已处理后记录结果，再推进下一任务。

默认一次推进一个执行任务及其审阅。确实互不依赖且写入不冲突的任务可并行；共同契约先明确。审阅固定代码版本，避免一边改写一边宣称通过。

适用行为使用 TDD，其他任务采用合适的验证方式。尊重用户明确的验证范围，报告实际证据及限制，不伪造独立审阅或测试结果。

## 碰撞处理

与已确认需求、ADR、技术方案或相关知识不符的发现，都应向用户说明原预期、证据、后果和处理依据：

- 原规则仍有效：作为实现缺陷修复，无需重复审批。
- 重要规则、设计选择或协作承诺需要改变：按既有委托处理；未获决定时暂停依赖部分，继续独立工作。
- 无法判断：先调查或实验，不把证据不足变成用户批准猜测的问题。

使用 [审阅与碰撞记录](references/review-report.md) 留下依据。决定变化后更新相关材料和任务上下文，核对受影响的已完成工作；不能只改文档让实现看起来正确。

连续修复没有新证据时，重新调查原因或调整任务划分，避免机械重试。

## 终审与恢复

任务完成后另派独立审阅者检查整项交付的组合行为、原始目标、兼容性和发布依赖。主线程处理阻塞项并完成授权范围内的交接，将新知识交回项目知识维护。

恢复时重读当前任务与进度，核对最新依据、工作区、在途代理和未决决定，判断下一步是执行、审阅还是修复，不重做已完成任务。

宿主没有子代理能力时，采用明确标注的单代理执行与自审；用户要求独立审阅作为完成条件时，该项保持未完成。

## 后续衔接

完成审阅、适用验证与授权交接后，回到主线程复盘偏差和经验，通过 [knowledge-management](../knowledge-management/SKILL.md) 维护可复用知识，再归档交付材料。遗留事项保留状态、影响与后续安排。碰撞按问题来源回到需求澄清、架构决策或技术设计，并更新当前任务和进度；子代理交回结果，由主线程负责阶段推进。
