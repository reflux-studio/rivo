# 增量交付

开始时声明：“正在使用 rivo:incremental-delivery，完成当前实施、审阅或验证任务。”同一阶段已经说明过，就不重复。

按需求和方案完成实现，并验证结果。主代理安排任务、和用户讨论；执行者实现并自查；独立审阅者检查完整改动和证据。发现新问题可以修改模型，但要先和用户讨论对已确认行为的影响。

## 本次范围

用户要求完整实施时，按下面的步骤推进。只要求审阅或验证时，检查指定范围并返回结论和证据。

## 工作步骤

把以下步骤加入主任务清单，已有进度直接沿用。没有任务工具时，在对话中列出短清单。

- 核对需求、plan、重要决定及相关知识，细化当前任务范围。
- 为当前任务启动执行者，提供简报和工作区。
- 接收实现和自审结果。**已实现表示待审，不等于已完成。**
- 启动独立审阅者检查改动、需求与契约、工程质量和证据。
- 处理发现，完成修复与复审。**阻塞验收的缺陷、契约分歧和必要证据缺口处理后才能完成；可选改进不阻塞。**
- 所有任务完成后终审组合行为和原始目标。
- 交付结论，检查跨需求知识是否需要更新。

每个交付切片都是一部分可以单独验证的功能。完成实现、审阅和修复后，再推进下一项，并更新清单。

## 准备与任务划分

实施前读取 Spec 和 plan，检查：

- 文档是否通过子代理审阅和用户审阅。
- 用户是否已授权实施。
- 相关图源、项目知识和重要约定是否明确。

缺少文档或用户审阅结果时，回到对应阶段补齐。不能因为文件已经存在，或子代理说通过了，就直接开工。

各切片共用本需求的 Spec 和 plan。按其中的约定和依赖，细化当前切片的范围、输入输出和验证方式。这些约定包括接口、共享状态、事件顺序和协作要求等。需要重新划分时，说明原因；涉及重要取舍，先取得用户批准再修改 plan。

按可以运行和验证的能力拆任务，先验证会影响后续结构的假设。任务简报可以放在当前工具的任务记录中；需要保存为文件时，使用[任务简报](references/task-brief.md)。写清规则、各项约定和版本，不要只让执行者翻整段聊天记录。

在主任务清单中更新各切片的实施、审阅和验证状态。

## 实施与审阅

1. 为当前任务启动新的执行者，按 [执行者提示词](references/implementer-prompt.md) 提供简报、工作区、授权与适用方法。执行者只负责本任务，不嵌套派发。
2. 接收实现、验证和自审结果，核对依赖及未决项；已实现表示待审。
3. 启动不同于执行者的审阅者，按 [审阅者提示词](references/reviewer-prompt.md) 检查真实改动、需求与契约、工程质量和验收证据。固定被审版本，审阅者不修改被审代码和约定。
4. 处理发现，完成必要修复与复审后再结束当前任务。每轮复审启动新的审阅者，提供更新后的依据和前轮报告。
5. 所有任务完成后独立终审组合行为、原始目标、兼容和发布依赖，完成适用验证及授权范围内的交接。

默认逐个推进任务。任务确实独立、不会同时修改同一内容时，可以并行，但要先确定各任务共同遵守的约定。

交给子代理的改动包含未提交或未跟踪文件时，提供快照或等效差异。多个仓库分别记录版本，不必为了审阅而提交代码。

适用行为采用 TDD，先加载 test-driven-development 并声明用途；出现待定位的异常时加载 systematic-debugging 并声明用途。其他部分采用与改动相称的验证。

反复复审仍没有进展时，按[审阅与分歧](../using-rivo/SKILL.md#审阅与分歧)处理。模型决策和重大不可逆操作先请用户确认，再推进。

## 实现中的模型检验

新增多个特殊分支、重复维护同一规则或连续修复同类问题时，检查是否存在更合适的操作、关系或状态归属。对照 Spec 和 plan 的模型，提出候选并用真实场景或反例检验；真实业务差异和独立变化边界应保留。

行为不变、已有授权内的局部结构改进可直接实施并验证。候选改变了业务含义、重要契约或协作承诺时，说明原理解、证据、后果和建议，回到受影响的需求或设计问题。未获决定只暂停依赖部分。可选抽象偏好不作为强制重构或交付阻塞项。

对已获批准的变化更新相关 Spec、plan、图源及任务依据；重要选择使用 architecture-decisions 比较并记录 ADR。文档修订后完成对应子代理审阅；改变规则或重要方案的修订交给用户审阅后再继续依赖它的实施。保留原理由，重新检查受影响的已完成任务，不能只改文档让偏差看起来正确。

## 文档输出

写文档时，如果有 `writing-clearly-and-concisely` 技能，就加载并使用。

代码和测试在各自项目中修改。文档沿用本需求的 `.rivo/issues/<slug>/` 目录：

- 审阅记录：`reviews/<task>-<round>.md`，按任务和审阅轮次命名。
- 需要保存的任务简报：`tasks/<task>.md`。
- 需要保留的日志、截图和验证证据：`evidence/`。

用户或项目指定了路径，就按指定路径保存。已有文档直接修改原文件，但每轮审阅要单独留记录，不能覆盖前轮证据。

告诉执行者和审阅者具体保存位置，缺少目录时在写入时创建。输入资料放在哪里，不影响输出位置。

## 审阅记录

每轮记录以下内容，按实际范围裁剪：

- 审阅方式、范围及被审代码和契约版本。
- 需求与契约、工程质量、验收证据的判断及依据。
- 发现的位置、具体影响、类型和处理建议；无发现时说明检查范围。
- 实际运行的检查、结果及未覆盖部分。
- 后续动作；复审补充旧发现的处理结论。

完整模板和向用户说明问题的示例见[审阅记录](references/review-report.md)。分清实现缺陷、需要用户决定的规则或设计问题、证据缺口和可选改进。代码质量合格，不代表它符合已约定的行为。

## 交付结果

交付时说明改了什么、最终版本是什么、审阅和验证结果如何，以及还有哪些外部依赖、发布或交接没有完成。

环境错误不算行为测试失败，模拟验证也不代表真实集成。如果证据无法访问或版本对不上，要明确说明。

检查受影响的跨需求知识是否需要更新，有变化时加载 knowledge-management 并声明用途，对照实现维护当前模型和架构图源。没有新知识不制造总结。确认所有交付事项及引用可迁移后，可将本需求材料归档到 `.rivo/archived/<slug>/`，同步修复链接；用户指定的归档位置优先。未完成事项不能靠归档表示完成。
