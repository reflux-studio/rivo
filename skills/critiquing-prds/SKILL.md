# 消化外来需求文档

消化一份别人写的需求文档：找出缺口和歧义，列出澄清问题，判断够不够开工。产出反馈和问题清单，不做放行或打回的裁决。把关团队自己的需求文档用 reviewing-specs。

## 工作流程

### 1. 理解意图

- 通读一遍，一句话复述：给谁、解决什么问题、做成什么样算成功。复述不出来，记为头号澄清问题。
- 若项目里维护着长期文档（项目定位一类），对照它——外来需求和项目方向冲突的地方，单独标出来。

### 2. 找缺口与歧义

- **缺口**：该有而没有的——验收标准缺失或不可测、边界情况没提（空状态、权限差异、错误处理）、非目标没划（范围没有边界）。
- **歧义**：一句话能读出两种做法的——「支持批量操作」是多选后统一操作，还是逐条快捷操作？把两种读法都写出来，让对方选。
- **越界**：文档规定了实现方式的——指定了 UI 组件、指定了技术选型——标出来，确认那是硬需求还是随手的建议。

### 3. 标可行性存疑点

- 你能识别但无权判定的技术疑点——「实时同步到第三方」的延迟要求现实吗、「导出全量历史」的数据量扛得住吗——列出来，交给工程侧做可行性评估（方法见 architecture-brainstorming）。

### 4. 产出

- **澄清问题清单**：逐条编号，每条写明为什么需要答案、该由谁回答；区分「不答无法开工」和「可以边做边澄清」。
- **反馈意见**：改进建议，语气是同行，不是裁判。
- **可开工判断**：够，或不够——不够就点名缺哪几个答案。
- 这是过程性产出，不设固定文件名：有工单目录顺手存进去，没有就在对话里直接交付。

### 5. 衔接转写

澄清的答案回来后，按 writing-specs 的转写路径落成自己的需求文档：引用原文而不重抄、补齐带编号的验收标准、把与原文的差异明确标注出来。

## 注意事项

- 你没有裁决权。「这需求不合理」要写成「这里与 X 冲突，建议确认」——判断留给能拍板的人。
- 反馈是问题和建议的清单，不是文档的改写版——重新排版不算反馈。
- 澄清问题宁少而锐：十个泛泛的问题，不如三个躲不开的。
