# 设计评审、视觉还原和交互验收

在产品需求明确后，完成设计评审、视觉还原和交互验收。

若 [using-rivo](../using-rivo/SKILL.md) 总纲尚未在上下文中，先读它。

## 获取必要的上下文

0. 读 `.rivo/issues/$issue_id/handoff.md`（如有），定位现状与细读范围
1. 读 `.rivo/PROJECT.md`、`.rivo/ARCHITECTURE.md` 了解项目信息和现有架构
2. 读 `.rivo/DESIGN.md` 了解项目现有设计规约与现有组件目录
3. 读 `.rivo/issues/$issue_id` 目录下的 `prd.md` 和 `spec.md` 了解现有需求
4. 读 `.rivo/issues/$issue_id/assets` 下的设计稿，或上下文中的 Figma 链接、设计文件、截图
5. 扫 `.rivo/learnings/` 中与本需求或当前阶段相关的学习经验
6. 若 `ui-plan.md` / `ui-contract.md` 已存在，本次是变更模式：在原文件与已实现 UI 的基础上增量修改受影响的部分，保留未被波及的内容

## 设计稿评审

没有设计稿时跳过本环节。

使用 **review** 技能，完成设计稿评审。设计稿不是你产出的，不必跨厂商，选视觉理解能力强的模型即可。

> 审查项提示词：[ui-reviewer.md](prompts/ui-reviewer.md)

总结问题，等用户提供新设计稿后重新评审，直至通过。

## 视觉还原

将产品需求转化为可精确还原的 UI 方案，并确保还原结果与设计稿（或设计意图）一致

### 起草视觉还原计划

读 [ui-plan.md](templates/ui-plan.md) 模板，回答以下问题：

1. **复用清单**：本次会用到哪些已有组件？（基础 UI 组件 + 业务组件）
2. **新增清单**：本次需要新建哪些组件？每个新组件的名称、Props 草案、存放路径，并说明为什么不能用现有组件替代。
3. **组件树**：每个页面的组件层级结构。页面 → 区块 → 组件 → 基础组件，标注复用/新建。

将文件写入 `.rivo/issues/$issue_id/ui-plan.md`

### UI 还原

基于上下文、设计稿与视觉还原计划，在实际项目中逐个还原 UI 组件与页面整体样式。

> **注意事项**：
>
> 1. 用到 shadcn/kibo-ui 等组件库时，用 CLI 拉取对应组件，不手写。
> 2. 代码遵循 `PROJECT.md` / `ARCHITECTURE.md` 的目录结构、命名与路由规范。
> 3. 模拟数据放在组件同目录的 `__mocks__/` 或项目约定的目录。
> 4. 覆盖所有相关状态：正常态、空态、加载态、错误态、权限受限态等，不只画正常态。
> 5. 必要时附加状态 / 视角切换工具，方便后续走查。

### 走查

如果检测到 devtools MCP 或其他支持浏览器操作的插件，启动开发服务器，对照本次设计产物做初步 AI 走查。

这一环节主要关注宏观的交互链路、整体布局、状态切换等，发现任何问题请自行修复，确认无误后提醒用户完成人工视觉走查。

接收并修复用户提出的问题，直至用户宣布通过

### 产出 UI 契约

用户走查完成后，读 [ui-contract.md](templates/ui-contract.md) 模板，基于已实现的 UI 代码产出契约文档。

将文件写入 `.rivo/issues/$issue_id/ui-contract.md`

## 收尾

用 **handoff** 技能更新交接纪要，提交 `feat: ui $issue_id`。

全部完成后，提示用户执行 `/rivo:plan` 进入技术方案设计。

## 核心原则

- **忠实还原** —— 像素、间距、状态都对齐设计稿或设计意图，不自由发挥。
- **眼见为实** —— UI 的正确性在屏幕上，必须把项目跑起来实地看，不靠读代码确认。
- **遵循设计系统** —— 颜色、间距、字号引用 DESIGN.md 的 token，不硬编码、不自创。
- **只做 UI 层** —— 还原阶段只写组件、样式、布局，不接真实数据、不碰业务逻辑。

## 危险信号

- 「设计稿只画了正常态，那就只还原正常态」—— 状态以 PRD 为准反查，空、加载、错误、权限态都要覆盖。
- 「代码看着对，开发服务器就先不起了」—— UI 正确性在屏幕上，不跑起来看就不算走查。
- 「这个间距差不多，先硬编码上去」—— 绕过设计系统的硬编码迟早失控，一律引 token。
