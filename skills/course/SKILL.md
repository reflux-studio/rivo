# 编写技术方案

开始时声明：“正在使用 rivo:writing-designs，整理或修订这份技术方案。”

技术方案面向评审者、开发者和协作方。忠实写出用户主导形成的方案及理由，让用户能据此向同事解释和讨论，也让协作方能开发、联调、测试部署和发布。AI 负责组织表达、核对一致性，不在成文时接管设计。

**方案结论经用户确认后才写入 plan。文档修改后必须重新独立审阅和交给用户审阅；旧通过结论不能覆盖新稿。** 用户已经要求整理确认过的方案，或明确给出了修改决定时，沿用这项授权。

## 核对本次输入

读取请求、PRD、会话决定、已有 plan、note、ADR 和评审意见，核对用户已选做法、选择理由、明确不做的工作，以及 AI 尚未获采纳的建议。已有材料可以来自任何流程，不要求先补一份 Spec，也不重跑已经完成的讨论。

区分表达问题与设计问题。段落组织、措辞和重复内容可以直接重写；缺少技术事实时加载 investigating；需要改变业务规则、职责、数据含义或共同契约时，加载 discussing-designs 讨论受影响的问题，取得决定后再写。不要以“整理文档”为由替用户作选择。

用宿主任务工具建立或沿用清单：核对输入、整合正文与图、检查一致性、独立审阅、用户审阅。没有任务工具时在会话中列短清单。写完本次要求的文档就交回结果，写作本身不授权实施。

## 组织整篇方案

先解释需求与整体变化，再按功能或设计主题展开，最后说明跨主题的影响、验证和发布。一个主题在一处讲完整，不按“模型、接口、模块改动”反复重讲同一设计。

以下内容构成完整方案的阅读顺序，标题贴合实际需求，不为无关机制凑章节：

```markdown
# <需求名称>：技术方案

## 需求与本期范围
为什么做、本期功能点、关键规则、明确不做的工作，以及验收结果。
已有 PRD 不逐段复述；补充本次讨论确定的含义与范围。

## 现状与总体方案
说明与本次改动有关的现状、准备怎样改、为什么这样做。
交代涉及的系统、职责和外部依赖，嵌入现状与目标图。

## <功能或设计主题>
连续解释本主题的行为、数据、接口与关键机制。
提供完整字段表、必要的目录结构、核心伪代码和配置或消息示例。
说明重要取舍及主要理由，ADR 保存完整比较。

## 影响面与外部协同
说明受影响的调用方、共享能力、数据、权限和兼容要求。
写清协作方责任、对接契约、环境配置和就绪条件。

## 验证与发布
用业务场景说明如何验证本次变化和关键失败路径。
给出部署依赖、配置、数据处理、生效检查和回滚办法。

## 待决问题与依据
说明剩余问题影响什么、何时必须解决，以及已批准的延后安排。
必要资料集中列在主题末或文末。
```

## 内容取舍与写法

**保留协作所需的具体内容。** 字段名、类型、接口签名、JSON 配置、消息体、XXL-JOB 参数和部署操作，只要开发者或协作方需要对照使用，就写在方案相应主题中。目录结构说明组件职责；核心伪代码解释算法、时序或失败处理。不能为了缩短篇幅把这些内容移入 AI 的任务文件。

例如，配置任务内部怎样读取文件属于 note；本期上线要执行哪个任务、传什么参数、按何顺序执行及检查生效，属于发布方案。逐文件编码步骤和子代理分工属于 task。

现状只保留解释本次设计需要的部分。源码追踪、备选试验和工程注意事项整合进 note；方案写出由这些事实得到的设计结论和必要限制。未改变的机制也可能决定新契约，不能一概删除。

**字段集中成表，一行一个字段。** 把名称、类型、含义、归属或变化分别成列，不把多个变量名挤在一个格子。单元格用短语或一句短句，不主动换行；需要解释原因、例外或多步操作时，在相邻段落展开。一百个字段可以有一百行，完整不等于难读。

代码块应增加信息。字段表说明属性，JSON 说明嵌套和实际交付形态，伪代码说明核心逻辑；不要用三种形式机械重复同一份字段定义。可复制的配置和示例不得含未说明的占位值。

正文保留完整含义，链接只用于查证，不让读者沿章节或其他文档跳转才能理解。必要时短述共用约定，完整契约在一处定义。图中的关键关系也用文字说明，AI 只读 Markdown 仍能理解设计。

结构、流程或状态需要图示时，加载 using-archify 生成并展示 SVG，嵌在对应说明旁。重要选择加载 architecture-decisions，正文写清主要理由，独立 ADR 保存比较和后果。继续使用可用的 writing-clearly-and-concisely。

## 修订已有方案

收到评审建议或新事实后，核对当前文件和用户决定，确定受影响的主题、图、契约、任务和已完成实现。事实有疑问就调用 investigating，不把同事建议直接当作事实或已批准决定。

重新组织受影响的段落、字段表和图；原结构已经不合适时，重写整篇。正文表达当前方案，删除失效解释，不累计“补充”“注意”让读者自行消解矛盾。保留 ADR 的原始理由和历轮审阅记录。

**每次修订后，检查整体一致性并重新独立审阅，再交用户审阅当前稿。** 文字修订检查含义是否保持；设计变化同时核对功能、契约、外部协作和相关实现。反复审阅无进展时查证或请用户裁决模型分歧，不不断追加说明来绕过问题。

用户确认后，检查这次修改是否改变实施依据。已有任务受到影响时，通过 planning-tasks 更新并复审；已实现行为受到影响时，安排重新验证。只改表达且含义不变，就交付审阅后的方案，不额外创建任务。仍然成立的决定和无关工作继续沿用。

## 审阅与完成

写完先自查范围、矛盾、遗漏、未决项、图表与示例一致性。然后读取 [技术方案审阅提示词](references/plan-reviewer-prompt.md)，为每轮启动新的独立审阅者，提供原始请求、用户决定、当前 plan、note、ADR 和图源。报告写入 `reviews/plan-<round>.md`，注明被审内容的提交或快照。

修复后复审，不能自行把自查当成独立通过。交给用户完整文档和审阅结果，重点讲清本次如何表达其决定、修订改变了什么，以及尚待判断的地方；不能只丢文件链接求批准。已充分讨论的内容不重讲，关闭提问或沉默不是批准。核心规则和契约缺口必须解决，用户允许延后的验证保留时点和失败影响，不写成已验证。

当前稿独立审阅通过、用户审阅通过后，本次方案工作完成。已有实施准备请求时加载 planning-tasks；只要求文档，到此交付。方案获批本身不等于实施授权。

## 保存位置

默认保存到目标项目的 `.rivo/issues/<slug>/plan.md`，沿用已有目录，用户或项目指定位置优先。跨仓库集中保存方案，输入 PRD 所在目录不决定输出位置。原位更新当前方案，审阅报告逐轮保留。

## 常见错误（Red Flags）

| 你在想 | 应当怎么做 |
| --- | --- |
| “为了方案完整，替用户补一个决定” | 将缺口带回讨论，未经采纳的建议不写成定论。 |
| “技术细节都给 AI 看，移到 task” | 保留开发、联调和发布共同需要的契约。 |
| “为了简洁，一格列完十个字段” | 一字段一行，把解释移到表外。 |
| “只补一句就能修正前面的方案” | 重写受影响内容并检查相关定义。 |
| “只改了文档，不用重新审阅” | 对当前稿和变化影响重新审阅。 |
