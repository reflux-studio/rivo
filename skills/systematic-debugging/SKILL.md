# Systematic Debugging

从可观察的分歧找原因，修复导致问题的机制。

## 建立事实

明确预期、实际结果、发生条件和影响范围。检查版本、配置、输入及近期变化，寻找最小可复现路径。已有日志、数据和测试可以提供线索，但要区分事实与解释。

如果预期本身有冲突，先明确业务规则；不能把现有行为或某个测试当成天然正确的答案。

## 缩小范围

沿输入、状态变化、边界调用和输出定位首次偏离。提出能被证伪的假设，选择可以区分它们的检查；每次改变尽量少的变量。

```text
预期 → 实际：定义分歧
       ↓
最近变化 → 版本、配置、依赖、输入
       ↓
假设 → 设计能区分它们的检查
       ↓
缩小 → 定位首次偏离的位置
       ↓
验证 → 确认根因，排除巧合
```

复现失败时缩小范围并说明限制，不靠连续猜测扩大改动。涉及外部系统时验证其实际契约。避免在日志中泄露敏感内容或为了诊断修改无关数据。

## 修复与解释

验证原因后实施范围内的最小修复，保留针对原始问题的回归验证，并检查相关边界。临时缓解与根因修复分别说明。

若问题推翻重要设计假设，解释因果链和受影响的决定；需要改变业务或协作契约时先讨论。用户需要理解时，以这次具体分歧追到关键代码，帮助更新其预期。

报告已证实原因、修复、验证和未排除的因素。没有足够证据时保持假设状态，不把一次成功运行写成问题永久消失。
