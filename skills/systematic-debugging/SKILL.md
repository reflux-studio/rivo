# 系统化排障

先用证据检验原因假设，再做针对性修复。为验证假设做的实验性修改要与正式修复区分，用完即删。

## 流程

### 1. 复现问题

- 记录触发条件、预期结果、实际结果和影响范围
- 检查相关版本、配置、输入和最近的改动，尽量构造最小复现
- 现象和解释分开写：一条可疑日志不等于原因已经确认
- 现有代码和失败测试只证明当前现象，不代表业务原本应该怎样

### 2. 定位原因

1. 沿输入、状态变化、跨模块调用和输出，找到最早出错的位置
2. 提出可以验证的原因假设
3. 选择能区分这些假设的检查，一次只改变一个变量
4. 假设不成立就继续调查，不靠扩大修改范围碰运气

卡住时：
- 无法复现：说明限制，缩小调查范围
- 连续尝试没有新证据：重新检查假设和观察位置
- 怀疑外部依赖：核实它的实际行为

### 3. 修复与验证

- 在授权范围内做根因修复，区分临时缓解和正式修复
- 为原问题保留回归验证证据；原来通过的测试不能证明本轮修改正确
- 如果证据表明原有的设计方案或任务约定本身有误，暂停依赖该约定的修复，报告原约定、证据和具体后果

### 4. 报告结果

- 证实的原因（指出预期行为与实际行为在哪一步出现分叉）
- 改动与验证结果
- 仍未排除的因素
