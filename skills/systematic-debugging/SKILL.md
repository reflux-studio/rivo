# 系统化排障

开始时说明正在使用 `rivo:systematic-debugging`，并用一句话说明本次要做什么。同一项工作中不重复声明。

先用证据检验原因假设，再做针对性修复。为检验假设而做的实验性改动，要与正式修复区分。

从"本来应该怎样"和"实际发生了什么"的差异入手。排障进度沿用当前任务。用户只要求定位时，返回原因和证据即可。

## 流程

### 1. 复现问题

- 记录发生条件、预期结果、实际结果和影响范围
- 检查相关版本、配置、输入和最近的改动
- 尽量找到最小复现
- 现象和解释分开写：一条可疑日志不等于原因已确认
- 现有代码和失败测试只证明现象，不证明业务应该怎样

### 2. 定位原因

1. 沿输入、状态变化、跨模块调用和输出，找到最早出错的位置
2. 提出可以验证的原因假设
3. 选择能区分这些假设的检查，一次只改变一个相关变量
4. 假设不成立就继续调查

卡住时：
- 无法复现：说明限制，缩小调查范围
- 连续尝试没有新证据：重新检查假设和观察位置，不靠扩大修改碰运气
- 怀疑外部依赖：核实它的实际行为

需要补查项目机制时，加载 investigating。需要解释调用或状态时，加载 writing-clearly 画一张基于证据的图。

### 3. 修复与验证

- 在授权范围内做针对性修复
- 为原问题保留回归证据
- 区分临时缓解和根因修复
- 原来通过的测试和审阅不能证明本轮修改正确

如果证据表明 ADR、plan.md 或任务中的约定有误，暂停依赖该约定的修复，向主代理报告原约定、证据和具体后果；单独排障时交给用户决定。

### 4. 报告结果

- 证实的原因
- 改动与验证结果
- 仍未排除的因素

解释原因时，指出预期行为与实际行为在哪一步出现差异，并说明相关代码和状态。实施任务中的排障结果交给主代理，继续原任务的验证与审阅。
