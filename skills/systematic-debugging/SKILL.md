# 系统化排障

开始时声明："正在使用 rivo:systematic-debugging，从证据定位当前异常。"同一阶段说明过就不重复。

**核心原则：** 没有证据支持原因之前，不做猜测性修复。

从"本来应该怎样"和"实际发生了什么"的差异入手。本技能是方法技能：进度沿用当前任务，结果交回当前任务。用户只要求定位时，返回原因和证据即可。

## 流程

### 1. 复现问题

- 记录发生条件、预期结果、实际结果和影响范围
- 检查相关版本、配置、输入和最近的改动
- 尽量找到最小复现
- 现象和解释分开写：一条可疑日志不等于原因已确认
- 现有代码和失败测试只证明现象，不证明业务应该怎样

### 2. 定位原因

1. 沿输入、状态变化、跨模块调用和输出，找到最早出错的位置
2. 提出可以验证的原因假设
3. 选择能区分这些假设的检查，一次只改变一个相关变量
4. 假设不成立就继续调查

卡住时：
- 无法复现：说明限制，缩小调查范围
- 连续尝试没有新证据：重新检查假设和观察位置，不靠扩大修改碰运气
- 怀疑外部依赖：核实它的实际行为

需要补查项目机制时，加载 investigating。需要解释调用或状态时，加载 writing-clearly 画一张基于证据的图。

### 3. 修复与验证

- 在授权范围内做针对性修复
- 为原问题保留回归证据
- 区分临时缓解和根因修复
- 原来通过的测试和审阅不能证明本轮修改正确

原因指向约定本身有误时（ADR、plan.md 或任务契约），停下，带着原约定、证据和具体后果交回当前任务；单独排障时交给用户决定。

### 4. 交回结果

- 证实的原因
- 改动与验证结果
- 仍未排除的因素

需要帮助用户理解时，沿这次的差异解释关键代码和状态变化。在 implementing-plans 中时，交回它按当前环节继续。

## 常见错误

| 你在想 | 应当怎么做 |
| --- | --- |
| "大概是这个原因，先改了试试" | 先用证据确认原因。 |
| "改了好几处，总有一处能修好" | 一次只改一个变量。 |
| "测试通过了，修好了" | 确认测试能重现原问题。 |
| "约定写错了，顺手改掉" | 带证据交回当前任务或用户。 |
