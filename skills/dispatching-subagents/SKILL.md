# 委派子代理

主会话负责拆分边界、提供上下文、协调依赖和核验结果；子代理完成边界清楚的任务，返回可检查的证据。

## 流程

### 1. 判断是否值得委派

- 问题或交付结果能独立描述、所需输入已经齐备、完成标准可检查时，才适合委派
- 隔离上下文、独立审视或并行执行的收益，应当超过传递材料、等待和整合的成本
- 需要边做边探索方向、多处紧密耦合，或需要人随时交互确认的工作，留在当前主会话直接完成

当前环境没有子代理工具时，直接由主会话继续不依赖独立视角的工作；如果某项工作要求独立审阅而无法委派，如实说明缺口，不把主会话自查算作独立审阅。

### 2. 选择执行配置

先看用户偏好、项目的 `AGENTS.md` 或 `CLAUDE.md`，以及宿主实际提供的子代理工具和配置。项目已指定分工时直接沿用。

- 有选择空间时：目标明确、步骤机械、容易验证的任务选低开销配置；复杂判断、高错误代价和关键审阅选可靠的配置
- 只使用宿主真实支持且允许选择的配置，不虚构模型名或参数，也不切换主会话模型

### 3. 写清委派契约

派发时把子代理完成任务所需的材料一次给齐，不假设它拥有主会话的聊天上下文：

| 内容 | 要交代什么 |
| --- | --- |
| 目标与完成标准 | 要回答的问题或交付结果，怎样才算做完 |
| 输入与参考材料 | 需求依据、相关文档或参考代码路径、已有证据（区分已知事实与待验证假设） |
| 范围与限制 | 工作目录、可读与可写范围、允许和禁止的操作 |
| 依赖与边界 | 上游输入、共用契约、与其他任务的分界，什么情况下应停下交回主会话 |
| 返回要求 | 结论或实际改动、运行过的验证命令与输出、未覆盖部分与受阻原因 |

如果委派的是独立审阅，交给没有参与该方案编写或代码实现的子代理，并提供原始要求、真实改动差异（如 `git diff`）和验证材料，不只给执行者的口头摘要。

### 4. 隔离并行工作

- 只并行互不依赖的任务；共用的接口契约或前置基础先定好，再派发依赖它的任务
- 划清写入范围：每个可写文件或目录由一个子代理负责；有重叠时串行，或用独立工作树隔离后由主会话整合
- 数据库、端口、服务配置和测试数据不能互相干扰，无法隔离时串行
- 保留工作区已有改动，不覆盖他人的未提交文件

### 5. 核验结果与处理受阻

- 查看实际文件、差异和命令输出，核对结论是否对应当前代码版本，不把子代理一句“已完成”当作事实
- 按受阻原因处理：
  - 缺少信息或材料：补齐上下文后继续；需要用户拍板时只暂停依赖该答案的工作
  - 环境或权限受阻：说明故障和解除条件，先推进不受影响的任务
  - 超出子代理能力：拆小任务、换更可靠的配置，或收回主会话直接完成；用同一配置重复盲试不算处理
