# 评审技术方案

评审团队产出的技术方案：抽查现状断言、按清单逐节检查，给出通过或不通过的结论。重点盯两类问题——照着施工会做错的（现状失真、设计漏洞），和照着没法施工的（粒度不够、影响面没交代）。

## 工作流程

### 1. 建立评审依据

- 读上游输入：需求文档的验收标准、缺陷的复现记录与修复预期，或技术任务的完成标准——方案的每个部分都应能追溯到它们。
- 若项目里维护着长期架构文档，先读，方案不应与它冲突；冲突而有理由的，理由要写在方案里。
- 个人偏好不构成依据。依据只有三样：上游输入、长期文档、下面的清单。

### 2. 通读抓理解

- 通读一遍后，尝试复述：这个方案用什么思路解决什么问题、动了哪几块。
- 复述不出来，本身就是最严重的一条意见。

### 3. 抽查现状断言

- 现状梳理是方案的地基——现状错，方案全错。挑两三处关键断言（「X 模块目前如何工作」「Y 接口被谁调用」），打开代码核实。
- 抽查不符的，标阻塞，并且对其余断言降低信任、加大抽查。

### 4. 逐节过检查清单

按下面的清单逐节检查。清单与技术方案的产出结构（见 writing-plans）成对维护：那边加一节，这边加一组检查。

### 5. 组织意见与交付

按「意见的写法」（见 reviewing-specs，两边同一套写法）成文。给出结论——通过，或不通过附阻塞项。阻塞项清零才能通过。若这单工作有工单目录，意见存入其中的 `reviews/`。

## 检查清单

### 背景与目标

- [ ] 能追溯到上游输入吗？验收标准、修复预期或完成标准，哪个都不挂靠的方案在解决谁的问题？

### 现状梳理

- [ ] 是核实过的事实，还是想当然？（按工作流程第 3 步抽查）
- [ ] 与本次改动相关的约束和既有模式都提到了吗？

### 方案概述

- [ ] 有组件图或数据流图吗？
- [ ] 假设写明了吗？每个假设成立吗——错误的假设是返工的头号来源。

### 详细设计

- [ ] 粒度到「照着能写代码」了吗？接口、数据模型定义完整吗？
- [ ] 每一条验收标准都有对应的实现路径吗？逐条对照。
- [ ] 错误处理定义了吗——每类失败发生时系统怎么表现？

### 影响面分析

- [ ] 波及的文件、模块、接口、数据列全了吗？可以抽查：对改动点搜一遍引用。
- [ ] 兼容性和回滚交代了吗？
- [ ] 不可逆变更标出来了吗？数据迁移、对外接口变更、技术栈更换——漏标即阻塞。

### 取舍与备选

- [ ] 有命名的备选吗？只有一个方案等于没有探索。
- [ ] 胜出理由成立吗？「什么变难了」写得诚实吗？

### 实施步骤

- [ ] 每一步有可验证的检查点吗？
- [ ] 步骤顺序有依赖倒置吗？

### 未决问题

- [ ] 都是真开放的问题吗？标了谁来回答、是否阻塞开工吗？

### 整体

- [ ] 前后自洽吗？概述、详细设计、实施步骤之间有没有互相打架？
- [ ] 过度设计了吗？为不存在的场景写灵活性、为一次性逻辑建抽象，和设计不足一样是问题。
- [ ] 比例失衡吗？有空节吗？

## 输出

```markdown
## 技术方案评审：[方案名]

### 结论
[通过 / 不通过]

### 阻塞项
| # | 位置 | 问题 | 为什么 |
|---|------|------|--------|
| 1 | [节/条] | [描述] | [依据与后果] |

### 建议项
| # | 位置 | 建议 | 理由 |
|---|------|------|------|

### 现状抽查记录
- [抽查了哪几处断言，核实结果]

### 可靠的部分
- [确认没问题的节，一句话]
```

## 注意事项

- 评审产出意见，不产出修改——改是作者的事。
- 现状抽查是这份清单里唯一要打开代码的步骤，也是最值钱的步骤，不要跳过。
- 清单管的是方案作为文档的质量；「这个方向本身对不对」的争论属于探索（architecture-brainstorming），别在评审里打方向仗——发现方向性疑点，标出来交上游裁决。
