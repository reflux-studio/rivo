# Writing Docs

将讨论结论按模板整理为交付文档。接收结论、来源、确认依据、未决项与目标位置；独立调用时从已有材料取得。

每次写作按以下顺序完成：读取对应模板和已有文档 → 按模板写入 → 对照模板核对结构与内容 → 交回位置和未决项。写入后必须完成核对。缺少内容依据时回到讨论，不在写作中补出缺失的决定。

被 brainstorming 或其他技能调用时，写作步骤嵌入调用方的当前清单项，不另建竞争清单。独立调用时可按上述顺序建立短清单。

## 文档类型与模板

| 需要保存什么 | 模板 |
| --- | --- |
| 需求、行为、UI 形态与验收约定 | [需求与交互模板](references/spec.md) |
| 值得长期解释的重要决定与取舍 | [ADR 模板](references/adr.md) |
| 足以供团队评审的完整技术方案 | [技术方案模板](references/system-design.md) |

新建或实质修订前，读取对应模板；更新时同时读取目标文档。采用模板的元信息、章节顺序和表格字段，不凭记忆另拟结构。用户指定其他格式时按其要求。

## 各类文档要点

### Spec

记录目标、非目标、角色、可观察行为、UI 形态、业务规则、约束与验收。已有 PRD 在对应章节引用，只写澄清、差异和遗漏。组件拆分和实现算法由技术方案承载。区分草稿、部分确认与已确认，附真实依据。技术限制应解释对用户行为的影响，不把实现选择写成需求前提。

### ADR

开头一句话说明选择，交代问题、约束、事实、可行备选、理由、代价及重新考虑条件。备选来自调查，不为填表制造陪衬。区分提议、接受与已替代，保留编号关系。决定变化时保留原理由，说明新证据及受影响材料。常规选择留在技术方案中，不为记录制造决定。

### 技术方案

先用一小段讲清总体做法和主要变化，再按真实模块展开改动、复用、数据流、接口与关键机制。需求引用 Spec，取舍引用 ADR，接口以权威契约为准。复杂模块可拆附属文档，主方案保留完整流程和验证安排。不能因当前仓库或执行职责遗漏外部依赖。实施任务拆分由 incremental-delivery 负责。

## 核对

对照模板检查元信息、章节和字段。核对内容是否忠实于讨论：验收是否对应行为、确认与建议是否分明、是否夹带未决定的实现设计。事实缺口保持可见，不靠编造填齐。

## 合理化预防

| 想法 | 实际 |
| --- | --- |
| "模板太重，简化一下结构" | 读模板，按范围裁剪细节，不删主结构 |
| "这个决定显而易见，不需要 ADR" | 有真实取舍才写 ADR，但不因嫌麻烦跳过 |
| "讨论还没完，先把已有的写上" | 可以保存草稿，但标明状态，不伪装成已确认 |
| "核对没问题，可以勾选了" | 逐项对照模板和讨论，实际核对后才勾选 |

## 后续衔接

交回文档位置、主要变化和未决项，由调用方继续。独立写作请求完成后结束，不自行启动设计或实施。
