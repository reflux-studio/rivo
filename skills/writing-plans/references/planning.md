# 拆解实施方案（task.md）

在 `plan.md` 获用户批准后，趁当前会话上下文完整，紧接着写出 `task.md`。

`task.md` 有两个作用：一是把方案拆成可以逐项实施和走查的任务，二是记录每项任务跑通后的样板位置和实测结论，方便换新会话或交子代理时接力。

## 拆分方法

- **按可走查的完整结果拆**：每项任务交付一条从入口到结果能独立验证或演示的功能切片，不按“先写完所有后端、再写所有前端”水平切分。
- **第一项任务先跑通样板**：把决定后续代码结构、或者首次建立页面组件样式的任务排在最前面，跑通并校准后再展开同类任务。
- **涉及上百个文件的机械重构按“扩、迁、删”拆**：无法在单次任务里一步到位的全仓机械改动，拆成“先并存新结构 → 分批迁移调用方 → 清理旧结构”。
- **不重抄 PRD 细则**：常规按钮显隐和表单校验直接标明“见 PRD 第几节”；这里重点写清涉及的仓库、参照样板路径、前端设计稿节点和必须复用的组件库。
- **不写逐行编码教程**：列出相关目录、样板和必守契约即可，具体写法由执行者读代码后决定。

## 结构

顶部放一张简短的任务总览表，下面每项任务单列一节，方便实施中逐项填写进展与踩坑记录：

```markdown
# <需求名称>：实施方案

依据：plan.md <版本>，adr/<编号范围>，PRD <位置>，设计稿 <位置>。

## 仓库与共同约定

- 仓库与分支：<各仓库路径、worktree、分支起点、提交与推送授权边界>
- 工程与组件约定：<必读的 AGENTS.md、项目组件库要求、构建与测试命令>
- 共用契约：<plan.md 相关章节；跨仓库 SDK 同步或类型生成要求>

## 任务总览

| 任务 | 对应模块 | 依赖 | 状态 |
| --- | --- | --- | --- |
| T1 <名称> | <F1 等> | 无 | `[ ]` |
| T2 <名称> | <F2 等> | T1 | `[ ]` |

---

### T1 <任务名称>

- **交付结果与验收**：<做完后能观察或检查到什么；对应 plan.md 与 PRD 哪一节>
- **参照与约定**：
  - 仓库与范围：<具体仓库和目录>
  - 参照样板：<后端参照类或模块；前端参照页面与必须复用的组件>
  - 设计稿对应：<设计稿节点或 research/ 中的组件映射笔记，无界面则略>
  - 特有契约：<本任务需要注意的接口、状态或边界>
- **进展与实测结论**：<实施时填写：已完成提交、实测踩到的坑、组件真实用法，供后续任务接力>
- **独立审阅**：<审阅报告路径，未修的 P1、P2 及拒绝意见的理由>
```

## 自查

- 逐节对照 `plan.md` 和发布计划，每个模块、契约和跨仓同步动作都已落入某项任务
- 涉及界面的任务都已写明参照页面、组件库要求和设计稿位置
- 任务之间没有矛盾的约定

覆盖完整后交出 `task.md`，方案阶段结束。
