# 接收审阅意见

审阅者依据提供的材料独立检查方案，也可能因材料缺失或理解偏差提出不成立的意见。主代理先核实每条意见，再决定如何处理。

## 分级

| 级别 | 含义 | 处理 |
| --- | --- | --- |
| P0 | 照方案做会做错或做不下去；遗漏需求；与 ADR、用户决定矛盾 | 必须修 |
| P1 | 影响评审、开发或联调的质量，但不会做错 | 默认修；修复代价明显高于收益时可不修，写明理由 |
| P2 | 瑕疵，不影响理解和执行 | 不必修，顺手能改的改 |

结论：没有 P0 即为通过。

## 核实与处理

回到方案、ADR、笔记和代码核实每条意见：

| 核实结果 | 处理 |
| --- | --- |
| 问题属实 | 按级别处理，修复按 writing-clearly 的修订原则 |
| 缺少上下文造成的误会 | 拒绝，写明理由和证据 |
| 设计没错，文字让人误解 | 重写原句，设计不变 |
| 同意问题，不同意级别 | 按你认为的级别处理，写明理由 |

- 修复需要新的或改变的 ADR，或需要用户补定核心设计：按 SKILL.md「何时回到 converging」处理
- 把 P0 挪进待决问题不算修复
- 修完检查同一处改动是否波及其他主题、表格和图

## 复核

有 P0 时，修完交给同一个审阅者增量复核：
- 宿主支持时续用原审阅者的会话，把修复内容、拒绝的意见和理由发给它。它已经读过方案，复核只看改动和波及范围
- 无法续用时，派新的审阅者，附上前轮报告，只复核修复和波及范围
- 审阅者对拒绝的意见仍然坚持，或意见涉及 ADR 的决定：交用户裁决

每轮复核的结论追加到同一份报告末尾：第几轮、对应的方案版本、看了哪些修复、结论、仍坚持的意见。

复核通过为止。同一个问题反复修不好时，停下分析原因，报给用户。

## 用户和团队的意见

1. 核实意见依据的现状、代码行为或约束是否属实，查不清的加载 investigating
2. 把核实结果和建议交给用户
3. 是否采纳由用户决定。同事的建议在用户采纳前不写进方案
