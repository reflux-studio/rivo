# 接收审阅意见

审阅者刻意不带会话上下文，才看得见惯性忽略的问题。代价是它的意见不一定成立，分级也可能偏差，所以每条先核实再处理。

## 核实与处理

回到方案、ADR、笔记和代码核实每条意见：

| 核实结果 | 处理 |
| --- | --- |
| 问题属实 | 按 writing-clearly 的修订原则修复 |
| 缺少上下文造成的误会 | 拒绝，写明理由和证据 |
| 设计没错，文字让人误解 | 重写原句，设计不变 |
| 同意问题，不同意级别 | 修复，写明分级异议，交下一轮复核 |
| 只是措辞偏好 | 不改 |

- 修复需要新的或改变的 ADR：按 SKILL.md「何时回到 converging」处理
- 修完检查同一处改动是否波及其他主题、表格和图

## 是否重审

有阻塞问题：
1. 不论修复、拒绝还是下调分级，都派新的审阅者全量重审
2. 被拒绝的意见和分级异议连同理由交它复核
3. 审阅者接受理由，这条即告处理
4. 仍然坚持，或涉及 ADR 的决定：交用户裁决，之后不再重复提出

没有阻塞问题：
- 本轮通过
- 非阻塞问题改完不再审阅，被拒绝的也不再复核

## 三轮上限

同一份方案连续三轮未通过，停下，不开第四轮：
1. 回看三轮报告，分析问题为什么反复出现
2. 根因是修订方式在制造新问题（例如插补丁句、只改症状处）：说明根因和改法，用户知情后继续
3. 其他根因（漏掉分叉、ADR 矛盾、方向有误、方案不可行）：由用户决定下一步
4. 用户决定或知情后，重新计轮

## 用户和团队的意见

1. 核实意见依据的现状、代码行为或约束是否属实，查不清的加载 investigating
2. 把核实结果和建议交给用户
3. 是否采纳由用户决定。同事的建议在用户采纳前不写进方案
