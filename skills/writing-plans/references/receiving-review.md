# 接收审阅意见

独立审阅者刻意不带会话上下文，才看得见惯性忽略的问题；代价是它提出的问题不一定成立，分级也可能偏差。审阅轮次靠核实后再修来收敛。

## 逐条核实

对报告里的每一条意见，先回到方案、ADR、笔记和代码核实，再选一种处理：

| 核实结果 | 处理 |
| --- | --- |
| 问题属实 | 按写作标准中的修订原则修复 |
| 因缺少上下文产生的误会 | 拒绝，写明理由和证据 |
| 设计没错，但文字让人误解 | 改写表达，设计保持不变 |
| 同意问题，不同意级别 | 按修订原则修复，并写明分级异议的理由，交给下一轮复核 |

意见指出某个关键取舍没有对应的 ADR，或者修复需要改变某份 ADR 的决定时，按 SKILL.md「何时回到 converging」处理。修复要落实到方案本身，改完后检查同一处改动是否波及其他主题、表格和图。

## 是否需要重审

报告里有阻塞问题时，不论主代理修复、拒绝还是下调分级，都由新的审阅者全量重审，并带着理由复核被拒绝的意见和分级异议。审阅者接受理由的，这条意见即告处理；仍然坚持的，或者意见涉及某份 ADR 的决定，交给用户裁决，此后的审阅不再重复提出。用户支持主代理的，该意见即告处理，这一轮没有其他阻塞问题即为通过。

报告里没有阻塞问题，本轮即为通过。非阻塞问题改完后不再审阅；被拒绝的非阻塞意见不再复核。

## 三轮上限

同一份方案连续三轮审阅未通过，停下来，不开第四轮。回看三轮报告，分析问题为什么反复出现，把分析报给用户：

- 根因是修订方式在制造新问题，例如往原文里插补丁句、只改症状处而不重写段落：说明根因和改法，用户知情后继续。
- 其他根因，例如讨论漏掉了分叉、ADR 之间有矛盾、方向本身有误、方案内容不可行：由用户决定下一步。

用户决定或知情后，重新计轮。

## 用户和团队的评审意见

用户自审或团队评审带回的意见，同样先核实事实：意见依据的现状、代码行为或约束是否属实，查不清的加载 investigating。把核实结果和建议交给用户；是否采纳、是否改变决定，由用户决定。同事的建议在用户采纳之前不写进方案。
