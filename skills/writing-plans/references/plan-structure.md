# 技术方案模板

团队每次评审都在同一个位置找到同一类信息，读过几次就能扫一眼看懂。默认使用下面六章，顺序固定；团队有自己的模板时用团队的。

```markdown
# <需求名称>技术方案

状态：草稿

## 1. 需求背景
<为什么做；必要的现状与约束；需求来源；本期不做的事>

## 2. 需求总览
| ID | 模块 | 本期交付结果 | 涉及系统与边界 |
| --- | --- | --- | --- |
| F1 | <模块名称> | <可观察的结果> | <范围> |

## 3. 总体设计
<各模块怎样配合：系统分工、主要数据流、跨模块共用的定义、关键选择的理由>

## 4. 详细设计
### F1 <与总览一致的模块名称>
<本模块怎样工作：行为、数据、接口、权限、失败处理和验证>

## 5. 三方库／三方接口
<本期接入或变更的依赖：版本、能力边界、鉴权、环境和联调条件>

## 6. 发布计划
<部署与配置顺序、初始数据或迁移、联调与验收检查、生效观察、回滚>

## 修订记录
| 版本 | 日期 | 改动与理由 | 关联 ADR |
| --- | --- | --- | --- |
```

## 各章写什么

| 章节 | 回答的问题 | 写法 |
| --- | --- | --- |
| 需求背景 | 为什么做 | 只保留影响本次判断的现状 |
| 需求总览 | 本期交付什么 | 沿用 note.md 需求总览的模块 ID 和名称 |
| 总体设计 | 模块怎样配合 | 建立整体认识，不逐节复述详细设计；复杂关系配图，分清现状与目标 |
| 详细设计 | 每个模块怎样工作 | 按模块展开，子章节与总览一一对应 |
| 三方库／三方接口 | 依赖有哪些确定的接入条件 | 集中给出接入信息；业务上怎样使用写在详细设计 |
| 发布计划 | 怎样安全生效并证明结果正确 | 写实际的上线次序和成功、失败的判断 |

- **章节固定，内容随需求**：小需求缩短正文。没有新增依赖时，第 5 章写一句“本期无新增或变更”
- **固定的是位置**：段落、图表数量和模块内的小标题按解释需要组织

## 详细设计

- **一个模块讲完整**：入口、权限、提交、存储和展示写在同一个模块里。不拆成“前端设计”“后端设计”两章让读者自己拼
- **共用定义集中写**：跨模块共用的字段、状态和接口在总体设计里定义一次，各模块说明怎样使用
- **契约写实际定义**：协作方要实现或联调的内容，给出类型、基数、约束和输入输出
- **附表属于方案**：字段很多时放进 `assets/` 下的附表，正文说明用途、关键规则和位置。附表与方案一起审阅
- **初始状态与外部入口**：写清上线当天已有数据处于什么状态，外部参与者从哪个接口进入
- **查证过程留在 note.md**：方案只保留最终采用的定义

## 状态与修订记录

顶部一行写状态，区分待确认的稿子和获批的版本：

| 时点 | 状态行 |
| --- | --- |
| 第一次批准前 | `状态：草稿` |
| 有核心设计缺口、用户要先看稿 | `状态：草稿（设计未完成）` |
| 用户批准 | `状态：定稿 v1.0` |
| 批准后修订并经用户确认 | `状态：定稿 v1.1`，次版本号递增 |

修订记录每个版本一行，第一次批准时加第一行。正文不记录修改过程。
