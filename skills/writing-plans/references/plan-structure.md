# 方案结构

plan.md 交给用户自审，常常还要拿去团队评审。目标是：没参与讨论的同事读完，能解释整个设计、判断取舍是否合理，并知道自己怎样接入。写法按 writing-clearly，本文件说明章节安排、设计主线的写法和修订记录。

## 章节

按下面的顺序组织全文。标题贴合实际需求，与本需求无关的章节不写。

```markdown
# <需求名称>：技术方案

状态：草稿

## 需求与本期范围
## 总体设计
## <设计主线>
## 各仓库改动汇总
## 影响面
## 验证与发布
## 待决问题
## 修订记录
```

| 章节 | 写什么 |
| --- | --- |
| 需求与本期范围 | 为什么做、本期做哪些事、关键规则和验收结果、明确不做的事。已有 PRD 只补充讨论中确定的含义和范围。 |
| 总体设计 | 先写本次有哪些业务变化、涉及的系统各自承担什么、哪些链路复用、哪些新增；再写支撑这些变化的关键机制和主要取舍，完整比较留在 ADR。跨主线的结构变化也写在这里，例如新增服务或包、调整前端路由或共享状态、改变宿主接入方式。架构或主链路有变化时配图。注明所依据的知识库版本。 |
| 设计主线 | 每条主线一节，写法见下文。 |
| 各仓库改动汇总 | 按仓库或模块列出改动项及所属主线，供分工查阅。这里只做索引，设计和理由留在主线里。 |
| 影响面 | 受影响的调用方、共享能力、数据、权限和兼容要求；协作方的责任、对接契约、环境配置和就绪条件。 |
| 验证与发布 | 用业务场景说明怎样验证本次变化和关键失败路径；部署依赖、配置、数据处理、生效检查和回滚办法。 |
| 待决问题 | 剩余问题影响什么、何时必须解决、用户同意的延后安排；没有时省略本节。会改变主流程、跨系统契约或数据落点的问题是核心设计缺口，按 writing-plans 的“核心设计缺口”处理，不放在这里了事。 |

## 设计主线

先从需求中找出几条设计主线。一条主线是一项业务行为从发起到结果的完整路径，或一类数据从采集、保存到展示的完整链路。按主线组织详细设计，不按调查顺序，也不按前端、后端或仓库拆开：同一功能的权限、提交、审批、生效和展示分散在几节里，读者就得自己拼出设计。

每条主线在一处讲完整。先写**行为**：谁在什么条件下做了什么，经过哪些系统，各阶段数据在哪里，成功和失败各有什么结果；跨系统的流程配时序图或流程图。现有模型的介绍不算行为，放进数据或总体设计。行为还要回答两件容易漏的事：
- **上线时的初始状态**：上线当天已有数据、账号和配置处于什么状态，第一次能否走通。例如新流程要求某种角色才能发起，而存量里还没有这种角色，就要写清第一个角色从哪来
- **外部参与者的入口**：供应商、客户等外部账号怎样进入内部流程，调用哪个接口，权限在哪里校验再按主线涉及的功能点展开。存储、接口、服务端逻辑和页面都是同一条主线里的功能点，前端不单独成章：

| 功能点 | 写什么 |
| --- | --- |
| 数据与存储 | 新增和改动的结构，逐字段写出名称、类型、基数、枚举、来源和约束；迁移和存量数据的处理 |
| 接口与契约 | 接口路径、入参、出参、错误码、消息体、跨系统的键名对应。前后端共用这一份，前端部分不再重写 |
| 服务端逻辑 | 状态流转、校验、并发与幂等、定时任务和失败处理 |
| 页面与交互 | 入口在哪，经过哪些页面或弹窗；加载、为空、失败、无权限时各显示什么；接口的每个错误码在页面上怎样呈现 |
| 组件与状态 | 新增和复用哪些组件、放在哪个目录；数据取自哪个接口，何时请求、何时刷新；状态放在组件、全局还是 URL |
| 权限与可见性 | 谁能看到、谁能操作；前端的显示判定和服务端校验用同一口径 |
| 取舍 | 为什么这样做，引用对应的 ADR |
| 改动点 | 落到哪些类、组件、配置和模块 |

主线不涉及的功能点不写。前端部分写到能照着开发和联调即可：页面、组件、数据来源、状态和权限写清楚，不必逐个组件列出 props。页面上的数据要写明来源和必要的转换：来自服务端的要能对应到接口契约，对应不上说明契约缺了一块；用户输入、URL 参数、本地配置和计算得出的数据各自说明即可，不必为它们增加接口字段。

契约要完整交付。条目很多时（例如几十个字段），可以放进需求目录下随方案维护的附表，正文链接过去并说明分组；附表与方案同一版本、一起审阅。附表的列与正文要求相同，字段表要有类型、基数、枚举值、约束和跨系统的键名，开发能照着写出配置和代码。只列路径或落点的是索引，不是契约。只写“另出清单”却不交付，同样算作契约缺失。

机制写不写，看删掉之后读者是否还能理解、评审或正确实现这个设计。影响契约或实现正确性的机制写进主线，例如序列化让两处的字段路径不同；查找代码的过程、排除过的猜测留在 note.md。

开发、联调和发布要对照使用的具体内容留在方案里：字段名、类型、接口签名、配置、消息体、定时任务参数和部署操作。

## 完整主线示例

虚构需求：店长可以把某一天的营业时间临时改掉，区域经理审批后生效。范围只有一天、一家门店，链路很短，但每一处契约都要写全。

note.md 和 ADR 中按调查顺序记着这些事实与决定：
- 营业时间存在 `store.business_hours`，结构是 `[{"open": "HH:mm", "close": "HH:mm"}]`，门店本地时间，不跨日；门店时区存在 `store.timezone`
- POS 和外卖平台每 10 分钟调用 `GET /stores/{storeId}/hours?date=YYYY-MM-DD` 拉取，响应是 `{"date", "hours"}`
- 审批中心按模板里配置的地址回调业务方，载荷 `{"approvalId", "result": "APPROVED" | "REJECTED", "decidedAt"}`，`decidedAt` 为 ISO 8601 带时区；同一结果可能回调多次，业务方返回 200 即停止重试
- ADR-002：临时时间单独存表，不改写常规营业时间；同一门店同一天最多一条待审批或已生效的申请
- ADR-003：只能申请明天及以后的日期；门店服务在生效日 00:00（门店时区）前没有收到通过回调的申请作废，不顺延。审批通过后外部平台要到下一次拉取才看到新时段，最多晚 10 分钟，这个延迟可以接受
- 门店后台的营业时间页在 `pages/store-hours/`，时段编辑组件 `HoursEditor` 的值结构与 `store.business_hours` 相同；只有该门店的店长能编辑营业时间，服务端按角色校验

写进方案时，从店长的操作开始，把存储、拉取、回调这些事实放到行为发生的位置：

```markdown
## 门店申请临时营业时间

### 行为

店长在门店后台选一天、填写当天的营业时段并提交，门店服务创建申请并在审批中心发起审批。区域经理通过后，这一天的营业时间改用申请里的时段；驳回则申请关闭，营业时间不变。POS 和外卖平台仍按原方式拉取，接口响应结构不变，不需要改动。

![申请经审批中心回调生效，拉取接口在当天返回临时时段](assets/temp-hours/flow.svg)

日期按门店时区计算，只能申请明天及以后的日期。申请是否生效以门店服务收到回调的时间为准：生效日 00:00 前收到通过回调的申请生效，之后才收到的作废，店长需要重新申请。审批中心的 `decidedAt` 只说明经理何时审批，不代表门店服务已经知道结果，所以不用它判断。外部平台在申请生效后的下一次拉取看到新时段，最多晚 10 分钟（ADR-003 接受这个延迟）。

### 数据

新增表 `store_temp_hours`，常规营业时间不改（ADR-002）。

| 字段 | 类型 | 约束与说明 |
| --- | --- | --- |
| id | bigint | 主键 |
| store_id | bigint | 门店 |
| date | date | 生效日期，门店本地日期 |
| hours | json | 与 `store.business_hours` 相同：至少 1 段 `{"open": "HH:mm", "close": "HH:mm"}`，`open < close`，段间不重叠 |
| status | varchar | PENDING / APPROVED / REJECTED / VOIDED |
| approval_id | varchar | 审批中心单号，唯一 |

同店同日只能有一条 PENDING 或 APPROVED 记录，写入时加锁检查。

### 接口

`POST /stores/{storeId}/temp-hours`（新增）

请求：`{"date": "2026-10-01", "hours": [{"open": "10:00", "close": "18:00"}]}`

| 结果 | 响应 |
| --- | --- |
| 创建成功，已发起审批 | `201 {"id": 123, "status": "PENDING"}` |
| date 不是明天或以后 | `422 {"code": "TOO_LATE"}` |
| hours 不符合上表约束 | `422 {"code": "INVALID_HOURS"}` |
| 同店同日已有 PENDING 或 APPROVED | `409 {"code": "DUPLICATE"}` |
| 调用者不是该门店店长 | `403` |

`GET /stores/{storeId}/temp-hours`（新增）：返回今天及以后的申请，按日期升序，`200 [{"id", "date", "hours", "status"}]`。权限同上。

`POST /approval-callbacks/temp-hours`（新增，配置在审批模板里）

按 `approvalId` 找到申请，状态映射如下，所有情况都返回 `200 {}`：

| 申请当前状态 | 回调 | 结果 |
| --- | --- | --- |
| PENDING | APPROVED，收到时早于生效日 00:00 | APPROVED |
| PENDING | APPROVED，收到时已到或晚于生效日 00:00 | VOIDED |
| PENDING | REJECTED | REJECTED |
| 其他 | 任意 | 不变，属于重复回调 |

`GET /stores/{storeId}/hours?date=`（修改）：该门店该日期有 APPROVED 记录时返回它的 hours，否则返回 `store.business_hours`。响应仍是 `{"date", "hours"}`。

### 页面

营业时间页新增「临时调整」按钮，只对该门店店长显示，与提交接口的权限一致。按钮打开 `TempHoursDialog`：选一个日期，时段编辑复用 `HoursEditor`。提交失败时弹窗不关闭，按错误码提示：`TOO_LATE` 为“只能申请明天及以后的日期”，`INVALID_HOURS` 标出不合法的时段，`DUPLICATE` 为“这一天已有申请”。提交成功后关闭弹窗，刷新申请列表。

页面下方新增 `TempHoursList`，数据取自申请列表接口，打开页面和提交成功时各请求一次，不轮询，审批结果在刷新页面后可见。列表为空时不显示这一块。两个组件放在 `pages/store-hours/components/`，状态留在页面内，不进全局 store。

### 改动点

门店服务：新表与迁移、提交接口、申请列表接口、回调接口、查询接口的覆盖逻辑。门店后台：`TempHoursDialog`、`TempHoursList`，营业时间页接入两者。审批中心：新增审批模板，审批人取门店所属区域经理，回调地址填上面的接口。
```

从材料到这一节：
- 方案分清了三个时间：经理审批的时间、门店服务收到回调的时间、外部平台拉到新时段的时间。生效判断用门店服务能确认的那个，外部平台的延迟由 ADR-003 明确接受，而不是默认它们相同
- “回调可能重复”成了状态映射表的最后一行，返回 200 是为了让审批中心停止重试
- 作废规则和同日唯一约束来自 ADR，不是写作时补定的
- 拉取机制只写一句“不需要改动”，它说明了外部系统为什么不用改
- 页面没有另起一章，就写在这条主线里：错误提示逐一对应接口的错误码，按钮的显示和接口用同一条权限规则。写申请列表时发现它需要一个接口，于是补进了接口一节
