# 技术方案模板

方案沿一条主线展开，团队每次评审都按同样的顺序读：

> 为什么做 → 本期做什么 → 整体怎样配合 → 各部分怎样实现 → 怎样发布

下面的骨架对应这条主线。本次需求还有别的内容要交代时，在合适的位置加章节，标题直接写内容是什么。团队有自己的模板时用团队的。

```markdown
# <需求名称>技术方案

| 项目 | 内容 |
| --- | --- |
| 状态 | 草稿 |
| <项目约定的元信息> | <内容> |

| 相关文档 | 位置 |
| --- | --- |
| <文档名称> | <链接> |

## 需求背景
<为什么做；本期的范围和不做的事>

## 需求总览
| ID | 模块 | 本期交付结果 | 涉及系统 |
| --- | --- | --- | --- |
| F1 | <模块名称> | <可观察的结果> | <系统> |

## 整体设计
<本期的完整做法：各系统的分工、主要数据流、跨模块共用的定义>

## 详细设计
### F1 <与总览一致的模块名称>
<本模块怎样工作：行为、数据、接口、权限、失败处理和验证>

## 发布计划
<部署与配置顺序、初始数据或迁移、联调与验收检查、生效观察、回滚>

## 修订记录
| 版本 | 日期 | 改动与理由 | 关联决定 |
| --- | --- | --- | --- |
```

## 方案写什么

方案只回答“本期怎么做”。读者没有参与讨论，也不了解现有代码，要能据此评审、开发、联调和发布。

| 内容 | 位置 |
| --- | --- |
| 本期采用的做法、协作方要对照实现的定义 | 方案正文和附件 |
| 现有系统怎样工作、怎样查到的 | `research/` 的调查笔记 |
| 为什么选这个做法、放弃了哪些选项 | `adr/` |

- **现状不进正文**：现有机制对本期构成约束时，写成本期要做的动作、要满足的条件和要验证的结果
- **理由不进正文**：方案陈述采用的做法，不重新论证
- **必要的背景与正文分开**：读者不知道就看不懂做法的背景，用一两句写在相邻的引用或提示块里
- **举证材料不进方案**：协作方要使用的接口路径、参数名和配置项写出实际定义；用来证明现状的文件名、方法名和行号留在调查笔记

## 各部分

- **顶部元信息**：用表格集中记录状态和项目约定的元信息，例如需求单、相关人员、时间节点。未知的写待定
- **相关文档登记一次**：产品需求、设计稿、方案附件等都列在顶部，正文用文档名称引用，不再重复介绍和链接
- **章节随内容增减**：接口定义、数据结构、依赖接入等内容，只属于一个模块的放在该模块下，多个模块共用且内容多的单列一章。不为凑齐章节写空内容
- **需求总览沿用已有编号**：模块的 ID、名称和顺序与 decisions.md 的范围一致
- **整体设计先讲完整做法**：先用一段话把本期怎样做串起来，再展开分工和数据流。复杂关系配图，分清现状与目标
- **一个模块讲完整**：入口、权限、提交、存储和展示写在同一个模块里，不拆成“前端设计”“后端设计”让读者自己拼
- **共用定义只写一处**：跨模块共用的定义在整体设计里写一次，各模块说明怎样使用
- **定义足以对接**：协作方要实现或联调的内容，给出类型、基数、约束和输入输出
- **初始状态与外部入口**：写清上线当天已有数据处于什么状态，外部参与者从哪个接口进入
- **发布安排可执行**：必须做的升级、配置和验证都排进顺序里，写明成功和失败怎样判断

## 附件

条目多、需要单独查阅的定义或图放进 `assets/`，在顶部的相关文档里登记，与方案一起审阅。

- **同一份定义只维护一处**：放进附件的内容，正文只说明用途和关键规则
- **附件写本期采用的定义**：调查中整理的现状对照留在 `research/`，不复制成附件

## 状态与修订记录

顶部元信息的“状态”区分待确认的稿子和获批的版本：

| 时点 | 状态 |
| --- | --- |
| 第一次批准前 | `草稿` |
| 有核心设计缺口、用户要先看稿 | `草稿（设计未完成）` |
| 用户批准 | `定稿 v1.0` |
| 批准后修订并经用户确认 | `定稿 v1.1`，次版本号递增 |

修订记录每个版本一行，第一次批准时加第一行。正文不记录修改过程。
