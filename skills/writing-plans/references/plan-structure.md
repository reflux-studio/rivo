# 方案结构

plan.md 交给用户自审，常常还要拿去团队评审。写法按 writing-clearly，本文件只规定方案的章节和修订记录。

## 章节

按下面的顺序组织全文。标题贴合实际需求，与本需求无关的章节不写。

```markdown
# <需求名称>：技术方案

状态：草稿

## 需求与本期范围
## 现状与总体方案
## <功能或设计主题>
## 影响面
## 验证与发布
## 待决问题
## 修订记录
```

| 章节 | 写什么 |
| --- | --- |
| 需求与本期范围 | 为什么做、本期做哪些事、关键规则和验收结果、明确不做的事。已有 PRD 只补充讨论中确定的含义和范围。 |
| 现状与总体方案 | 解释本次设计所需的现状，准备怎样改、为什么；涉及的系统、职责和外部依赖。注明所依据的知识库版本。 |
| 功能或设计主题 | 一个主题在一处讲完整：行为、数据、接口和关键机制连续写下来。重要取舍写出主要理由，完整比较留在 ADR。 |
| 影响面 | 受影响的调用方、共享能力、数据、权限和兼容要求；协作方的责任、对接契约、环境配置和就绪条件。 |
| 验证与发布 | 用业务场景说明怎样验证本次变化和关键失败路径；部署依赖、配置、数据处理、生效检查和回滚办法。 |
| 待决问题 | 剩余问题影响什么、何时必须解决、用户同意的延后安排；没有就写"无"。 |

开发、联调和发布要对照使用的具体内容留在方案里：字段名、类型、接口签名、配置、消息体、定时任务参数和部署操作。源码追踪和试验过程留在 note.md，方案只写由事实得出的设计结论。

## 修订记录

```markdown

| --- | --- | --- | --- |

| v1.1 | 2026-01-12 | 超时从 15 分钟改为 30 分钟：支付渠道通知延迟超出预期。 | 004 |
```
