# 技术方案模板

技术方案用来对齐架构、边界和关键契约，控制篇幅让没参与讨论的同事能在十分钟内读懂。主线如下：

> 为什么做与不做 → 交付总览 → 整体设计与参照样板 → 关键设计与契约 → 风险假设与发布

团队有自己的模板时用团队的。

```markdown
# <需求名称>技术方案

| 项目 | 内容 |
| --- | --- |
| 状态 | 草稿 |
| <项目约定的元信息> | <需求单、PRD 链接、设计稿链接、涉及仓库等> |

## 需求背景与范围
<为什么做；本期做什么，明确不做什么>

## 需求总览
| ID | 模块 | 本期交付结果 | 涉及系统 / 仓库 |
| --- | --- | --- | --- |
| F1 | <模块名称> | <可观察的结果> | <系统或仓库> |

## 整体设计
<用一两段话串起本期完整做法、各系统分工和主要数据流；复杂关系配图。>

- 参照样板与复用：<后端参照哪个已有模块或类，前端参照哪个已有页面和组件库>
- 方案取舍说明：<如果新增了服务、抽象层或同步机制，对比最简直接做法说明为什么值得>

## 关键设计与契约
### <按核心机制或模块展开>
<只写影响系统结构与协作边界的设计：数据模型、状态流转、职责划分、新增或改动的接口契约、关键失败处理和权限边界。>

## 关键假设与风险
<本方案最依赖的前提假设（如果该假设不成立会怎样），以及影响上线或跨团队协作的风险与应对。>

## 发布计划
<部署与配置顺序、初始数据或迁移任务、联调与生效检查、回滚方式>

## 修订记录
| 版本 | 日期 | 改动与理由 | 关联决定 |
| --- | --- | --- | --- |
```

## 方案写什么、不写什么

| 内容 | 放哪里 |
| --- | --- |
| 架构边界、数据模型、状态流转、新增或变更的接口契约、参照样板、发布顺序 | `plan.md`（长字段表放 `assets/`） |
| PRD 里已写明的按钮显隐条件、提示文案、常规表单校验 | 留在原 PRD，实施时直接对照 |
| 任务拆分、设计稿具体节点、组件映射引用、每项任务的实测踩坑记录 | `task.md` |
| 现有代码怎么工作、排查经过、源码行号举证、设计稿组件盘点 | `research/` |
| 为什么选这个方案、放弃了哪些备选方案 | `adr/` |

## 编写要求

- 已有接口如果只是照常调用或微调，一行写清路径、用途和变化即可，不逐个铺满四段套话；没有变化的章节直接略过
- 正文只写当前采用的做法，读起来像第一次就写对了；修改过程只进修订记录
- 状态区分：`草稿`、`草稿（设计未完成）`、`定稿 v1.0`；批准后局部修订递增为 `定稿 v1.1`
