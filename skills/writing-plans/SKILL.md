# 撰写技术方案

把「做什么」转化为「怎么做」：读方案的人不需要再问「从哪里下手」，照着实施步骤就能开工；评审的人能看到每个决策的备选与代价。

这份技能在关键决策已经收敛之后使用——方向或选型还悬着的，先用 architecture-brainstorming 探索定案；写作中发现有未收敛的重大决策，停下来回到探索，不要边写边拍。决策量小的方案不在此列：改法一眼可见时，决策与写作自然一体。

## 工作流程

### 1. 理解输入

- **功能需求**：输入是需求文档（含验收标准），涉及界面时还有界面设计方案。方案要覆盖每一条验收标准的实现路径。
- **缺陷**：输入是复现记录与修复预期。方案的核心是根因分析与修法；没做实验验证的根因，标注「推断」。
- **技术任务**：输入是目标与完成标准。方案的核心是技术路线与迁移策略。

同时判断规模：方案的深度与决策量成正比。改法一眼可见的需求，现状、改法、影响面各一句话就够，不要为小改动生成大文档。

### 2. 现状梳理

方案是长在现有代码上的，先弄清现状再设计：

- 相关模块现在怎么工作：入口、数据流、依赖关系。
- 已有的约束：技术栈、既定模式、性能基线。
- 若项目里维护着长期架构文档，先读它，方案不与它冲突；发现文档和代码不一致，以代码为准并把不一致指出来。
- 若已连接知识库，搜索既往的设计文档和决策记录，不要推翻早已论证过的结论。
- 若已连接项目管理或工单工具，检索相关工单，识别与其他在途工作的冲突。

### 3. 需求收集

- **功能性需求**：系统要做什么。
- **非功能性需求**：规模、延迟、可用性、成本。
- **约束条件**：时间线、现有技术栈、团队熟悉度。

### 4. 方案设计

高层设计：

- 组件划分与各自职责
- 数据流
- API 契约
- 存储方案选择

按需深入（涉及哪项写哪项）：

- 数据模型设计
- API 端点设计（REST、GraphQL、gRPC）
- 缓存策略
- 队列与事件设计
- 错误处理与重试逻辑

### 5. 影响面分析

- 改动会波及的文件、模块、接口和数据。
- 兼容性：对外接口是否变化、数据是否需要迁移、旧版本或存量数据怎么办。
- 回滚：出问题时怎么退回来。
- **不可逆变更醒目标注**：数据迁移、对外接口变更、更换技术栈——单独列出，用户确认之前不能实施。

### 6. 规模与可靠性（按需）

- 负载估算
- 水平扩展 vs 垂直扩展
- 故障转移与冗余
- 监控与告警

### 7. 取舍分析

- 每一个决策都有取舍，把它们摆到明面上。
- 考虑的维度：复杂度、成本、团队熟悉度、上市时间、可维护性。
- 给备选方案命名并如实分析——即使你已有倾向，明确的备选才让评审有的放矢。
- 探索阶段（architecture-brainstorming）已经做过的对比，把结论和关键依据落成维度表即可，不重开战场。

### 8. 拆解实施步骤

- 把方案拆成可依次执行的步骤，每步说明改什么、怎么验证。
- 步骤粒度以「照着能直接开工」为准。

## 产出结构

若这单工作有自己的工单目录，文档存为其中的 `plan.md`；否则按用户指定的位置保存。规模小的方案用最小形态：现状、改法、影响面各一句，其余节没有内容就不写。

### 背景与目标

- 一两句话：为什么做这件事，输入是哪份文档。
- 技术任务写清完成标准，方案的每个部分都要能追溯到它。

### 现状梳理

- 相关模块的现有工作方式，用事实描述，不夹评价。
- 与本次改动相关的既有约束和模式。

### 方案概述

- 组件图或数据流图（ASCII 图或文字描述）。
- 明确写出假设条件——错误的假设是返工的头号来源。

### 详细设计

- 数据模型、接口定义、组件契约，粒度到「照着能写代码」。
- 错误处理：每类失败发生时系统怎么表现。

### 影响面分析

- 波及范围、兼容性、回滚方式。
- 待用户确认的不可逆变更清单，单独成块、醒目。

### 取舍与备选

- 备选方案命名后逐个对比，用维度表：复杂度、成本、可扩展性、团队熟悉度、可维护性。
- 写明为什么选中的方案胜出，以及它输在哪里；顺带记下「什么变容易了、什么变难了、系统长大后要重新审视什么」。

### 实施步骤

- 有序步骤，每步一个可验证的检查点。

### 未决问题

- 只留真正开放的问题，标注该由谁回答、是否阻塞开工。

## 注意事项

- **约束先行**：「两周内要上线」「必须扛住 10K rps」——约束塑造答案，开头就写明。
- **给选项命名**：即使已有倾向，命名的备选才能得到平衡的分析。
- **非功能性需求和功能同等重要**：延迟、成本、团队专长、维护负担，和功能列表一样影响决策。
- **图示优于文字**：组件关系和数据流用 ASCII 图表达，一张图省十段话。
- **永远指出「系统长大后要重新审视什么」**：今天正确的决策会过期，把过期条件写下来。
- **值得超越本单记住的决策，复盘时沉淀进长期架构文档**；项目已有 `docs/adr/` 一类决策记录惯例的，按惯例追加，不另起炉灶。
- 定稿后再改，改动要重新走评审，不在代码里悄悄绕开。
