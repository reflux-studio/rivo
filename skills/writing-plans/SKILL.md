# 技术方案

开始时说明正在使用 `rivo:writing-plans`，并用一句话说明本次要做什么。同一项工作中不重复声明。

把已确认的做法和理由写成技术方案。写作中发现尚未决定的关键取舍时，加载 converging，与用户讨论后再继续。

plan.md 的读者：用户要据此向同事解释，团队要据此评审，开发、联调和发布要据此对照。

## 入口

| 从哪来 | 做什么 | 完成后 |
| --- | --- | --- |
| converging 讨论结束 | 写 plan.md，送审，交给用户 | 用户批准即完成 |
| 用户或团队带回评审意见 | 修订，向用户说明改动 | 用户批准即完成 |
| implementing-plans 需要修订方案 | 修订，向用户说明改动 | 用户确认后回到 implementing-plans，原实施授权继续有效 |

需要改变某份 ADR 的决定时，先用 converging 与用户讨论并更新记录，再修订方案。

## 流程

### 1. 写 plan.md

先核对讨论是否结束：note.md 的待决问题和每份 ADR 的“引出的问题”都已回答、被用户划出本期，或经用户同意延后并写明影响和解决时点。仍有核心设计缺口的，回到 converging；用户要先看未完成的稿子，按下文“核心设计缺口”处理。

读输入：
- PRD、已有方案和 note.md 中的调查结论
- ADR、note.md 的“已确认的方案细节”和会话中的决定，普通细节也要纳入正文
- 缺少技术事实时，加载 investigating 查清

成文：
- 位置：`.rivo/issues/<slug>/plan.md`，用户或项目指定了位置的以指定为准
- 加载 writing-clearly，按 [方案结构](references/plan-structure.md) 组织全文
- 用户同意进入写方案，就是这次写作的授权，不再逐条请示

### 2. 标记状态与版本

顶部一行写状态：

| 阶段 | 状态行 | 修订记录 |
| --- | --- | --- |
| 第一次批准前 | `状态：草稿` | 不记 |
| 有核心设计缺口，用户要先看稿 | `状态：草稿（设计未完成）` | 不记 |
| 批准 | `状态：定稿 v1.0` | 加第一行 |
| 批准后修改中 | `状态：草稿 v1.1` | — |
| 修改经用户确认 | `状态：定稿 v1.1` | 加一行：日期、改了什么、为什么、关联 ADR |

- 已授权提交时，每个版本单独提交一次，用户可以直接看 diff
- 状态行用于区分待确认稿和获批版本，实际进度仍需对照审阅记录与当前改动

### 3. 送审前自查

- 范围是否完整
- 每条设计主线从发起到结果能否走通，同一功能是否被拆散到多节
- 契约是否完整交付，附表是否已写好
- 有没有核心设计缺口被写成待决问题
- 前后是否矛盾
- 图、表、示例是否与正文一致
- 结构、流程或状态有变化的地方是否有 before/after 图
- 批量替换或改名后，全文搜索旧说法

自查不能代替独立审阅。

### 4. 独立审阅

首次定稿前做一次全量独立审阅，检查需求、决定、契约和验证安排。之后的修订由用户直接确认，以减少重复审阅。原审阅未覆盖的新改动，应在修订说明中交代影响范围和验证结果。

1. 派一个审阅者，按 [审阅提示词](references/plan-reviewer.md) 全量审阅整份方案
2. 报告写入 `reviews/plan-<n>.md`，n 递增，不覆盖旧报告
3. 按 [接收审阅意见](references/receiving-review.md) 核实和处理；有 P0 时修复后交同一审阅者增量复核

### 5. 交给用户和团队评审

审阅通过后，交出完整方案和一份说明：
- 方案怎样落实了用户的决定
- 如果是修订稿，说明改了什么、为什么，以及影响范围和验证结果
- 审阅中没修的 P1、P2，拒绝了哪些意见及理由
- 还需要用户判断的地方

说明聚焦本次改动和需要判断的事项，已确认的背景简要带过。

用户或团队带回意见时：
1. 按接收审阅意见先核实事实
2. 由用户决定是否采纳
3. 采纳的按 writing-clearly 的修订原则修订，向用户说明改了什么、为什么，由用户确认

### 6. 完成

用户明确批准后，本次方案工作完成。未回复或未提出意见不视为批准。
- 批准方案不等于授权实施
- 用户同时授权实施的，加载 implementing-plans；否则到此交付

## 核心设计缺口

会改变主流程、跨系统契约或数据落点的未定问题，是核心设计缺口。例如一项权限的承载与既有约束冲突、一个字段在哪一侧转换尚未决定。它们在讨论、写作或审阅中都可能出现。

- 列进待决问题不等于设计已经完成。发现后回到 converging，由用户决定
- 用户想先看稿再讨论时，可以成文和送审。状态行写 `状态：草稿（设计未完成）`，在待决问题开头列出未成立的设计：缺什么、阻塞哪条主线、影响哪些改动
- 这样的稿子可以审阅以发现更多问题，但缺口补齐前不能批准为定稿，也不能进入实施

## 何时回到 converging

遇到以下情况，回到 converging 交给用户决定，再修订方案：
- 核心设计缺口
- 达到 ADR 门槛、而用户没有做过决定的关键取舍
- 需要改变某份 ADR 的决定

某个关键取舍在 `adr/` 里找不到时，先查来源：
- 用户在讨论中决定过、只是漏记：加载 converging 补记
- AI 自己补定的：按用户没有做过决定处理

不涉及新的关键取舍或改变 ADR 决定时，直接在本技能内修订方案，向用户说明改动并取得确认。
