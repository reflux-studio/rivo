# 写技术方案、测试方案与任务清单

技术方案 `plan.md` 定下怎么改，测试方案 `test-plan.md` 定下怎么测、要守住哪些老功能，两份方案同级并列，各找独立审阅者检查后一并交给用户评审。批准后不换会话，趁上下文完整立即拆出下游的任务清单 `task.md`。

## 流程

### 1. 核对设计依据

- 读需求目录 `.rivo/issues/<slug>/` 下的 `decisions.md`、`adr/` 和 `research/` 调查笔记；如果还没有经过 `converging`（缺少 `decisions.md`，或范围与关键取舍还没定清楚），先提示用户是否要先进入 `converging`
- 核对后端参照哪个已有模块、前端参照哪个已有页面和组件库，以及已确认的验收标准和不能破坏的老功能
- 缺少会影响架构或测试预期的技术事实时，加载 `investigating` 查清；`decisions.md` 还有未决核心问题时，按下文「何时回到 converging」处理

### 2. 编写并审阅技术方案 `plan.md`

- 加载 `system-design`，写出 `.rivo/issues/<slug>/plan.md`（用户或项目指定的位置优先；附图与长字段表放 `assets/`）
- 首次定稿前按 `system-design` 委派独立审阅，报告写入 `reviews/plan-<n>.md`（`n` 递增，不覆盖旧报告）；属实的 P0 修完后交同一审阅者复核

### 3. 编写并审阅测试方案 `test-plan.md`

- 加载 `test-design`，同时对照 PRD、`decisions.md`（业务规则）以及 `plan.md`、`research/`（代码依赖与最脆弱假设），写出 `.rivo/issues/<slug>/test-plan.md`
- 按业务模块和老功能回归范围组织，统一用 `TC-01..` 编号，不绑定临时的任务序号；小改动精简为紧凑表格，不强求逐条铺开
- 首次定稿前按 `test-design` 委派独立审阅，报告写入 `reviews/test-plan-<n>.md`（`n` 递增）；属实的 P0 修完后交同一审阅者复核

### 4. 方案评审

两份方案各自通过独立审阅后，一并交给用户和团队评审，说明：
- 技术方案怎样落实了用户决定、参照了哪处现有实现，以及最依赖的前提假设
- 测试方案重点覆盖哪些边界、各层怎么测，以及圈出了哪些可能受影响的老功能
- 两份审阅中未修的 P1、P2，拒绝的意见及理由，以及仍需用户判断的地方

用户或团队带回意见时，先核实代码和事实，是否采纳由用户决定；未获用户采纳前不写进方案。

### 5. 方案批准后拆解 `task.md`

用户明确批准 `plan.md` 与 `test-plan.md` 后，将两份方案状态均改为 `定稿 v1.0`，不切换会话，立即拆出任务清单 `task.md`：

1. 按 [实施方案拆解方法](references/planning.md) 写出同目录下的 `task.md`
2. 在每项任务里列出要覆盖的 `TC-xx` 编号和对应的测试层级（单元测试、集成测试或端到端测试），并标出需要停下来请用户人工验收的任务；纯基建或数据库任务不打断用户，小需求不设实施中途的人工验收，全部做完再交用户一次验收
3. 核对整份 `plan.md`、`test-plan.md` 和发布准备都已覆盖后交出 `task.md`：
   - 用户已同时授权实施时，可在当前会话直接开始第一项任务，或提示用户压缩上下文／换新会话加载 `implementing-plans` 按序推进
   - 用户尚未授权实施时，到此交付

## 修订已有方案

方案批准前，按评审意见在原处直接修改。

方案批准并进入实施后，正文锁定：
- 发现契约、假设或测试预期与实际不符时，加载 `revising` 从受影响的最上游逐层修改，对应 `plan.md` 或 `test-plan.md` 次版本号加一，修改过程记入修订记录
- 如果中后期发现底层模型或整体思路走不通、需要大规模重构，不往原目录叠放平行方案；先暂停或收尾当前需求，另开独立的重构需求

## 何时回到 converging

写作中遇到会改变主流程、跨系统契约、核心数据落点或验收标准的未定问题，或者达到 ADR 门槛而用户还没拍板的取舍，加载 `converging` 交给用户决定后再继续。

用户想先看未完成的稿子时，状态标为 `草稿（设计未完成）` 并在正文标出缺口；这样的稿子不能批准定稿，也不能拆解 `task.md`。
