# 知识维护参考

先使用用户或项目指定的位置，其次使用已有知识库。需要新建时，保存到目标项目的 `.rivo/knowledge/`。将本次变化补入对应主题。

## 结论的依据

```markdown
结论与适用范围：
性质：业务约定／实现事实／待验证推断
理由、解释它的场景或反例：
来源：原始资料、ADR、相关代码或验证证据
版本或最近核实时间（影响时效时）：
```

一段内容可以共用来源。解释名词时，写清含义及它与其他概念的区别。方案、任务记录和测试原稿放在交付目录，知识文档通过链接引用。

## 架构图源

同一模块和范围的当前图源，只在一个位置维护，例如 `<topic>/architecture/current.architecture.json`。

在主题目录中链接 JSON 和内嵌的当前 SVG，并注明适用范围、实现版本或提交、最近核实的依据，以及来源需求。这些信息写在主题说明或 schema 支持的字段中，不随意增加 Archify JSON 字段。

交付后，按以下顺序更新知识库：

1. 对照实际实现与验证结果核实本次最终图源。已确认的 target 只是方案，未实施或未验证的能力不能写成现状；分阶段交付只更新实际完成的范围。
2. 比较知识库当前版本与本需求取得 before 时记录的来源版本或哈希。知识库已被其他需求更新时，核实差异，合并已实现的变化并保留无关内容；不能直接用旧基线衍生的 target 覆盖它。
3. 保存旧现状的可追溯历史，将核实后的 JSON 更新到唯一维护位置，保留已有对象的稳定 ID。结构变化时加载 using-archify，重新交付当前 SVG，核对图文与 JSON 一致。无法同步的展示入口明确标为旧版或待更新，不声称同步完成。
4. 更新主题导航、范围、实现版本、验证依据和来源链接，完成后才能将本需求材料归档。before、已确认目标及其 SVG 历史随需求归档，知识库保存当前现状并链接历史依据。

单独维护知识时，也要有实现依据。无法核实、版本有冲突或外部同步失败时，标为待更新。结构没有变化，就沿用图源，不必生成新版本。

## 替代与清理

1. 核实旧结论因何失效，以及是否仍适用于其他版本或范围。
2. 更新当前说明，保留旧理由与替代来源；无可靠历史记录时先归档有价值的旧内容。
3. 修复受影响导航、交叉引用和源材料链接。交付目录移动到归档后重新指向有效位置。

分清“已决定采用”和“已经实现并验证”。例如，目标流程虽然获批，但尚未实现，就不能将它写成当前流程。

项目已有 wiki、工程文档或知识索引时，在原位置维护这些信息。迁移范围遵循当前任务授权。
