# 知识维护参考

## 位置与结构

知识库的位置按以下顺序确定：

1. 用户或项目配置（例如 CLAUDE.md、AGENTS.md）指定的位置。
2. 项目已有的知识库或 wiki。
3. 都没有时，使用目标项目的 `.rivo/knowledge/`。

在已有位置上维护，不另建一份。写入外部系统需要相应的授权；本地草稿尚未同步时如实说明。需要写文件时才创建目录。

知识库由首页 `README.md` 和按主题分开的 `<主题>.md` 组成，图放在 `assets/` 下。已有知识库是单个多节的 README 时，本次涉及的主题写成主题文件，README 里原来承载这部分内容的位置改为导读和链接。由导航配置驱动的文档目录或外部 wiki，按其原有的组织方式补充页面和导航项。

## 怎样写

写法按 writing-clearly。知识库的读者是刚入职的同事，或替他分析项目的 AI，要能从首页读到任一主题，理解系统现在是什么样、为什么这样设计、改动时要守住哪些约束。

首页讲清系统全貌：它做什么、由哪些部分组成、一次典型的操作怎样流过这些部分，然后引到各个主题。每个主题先讲这部分负责什么，再讲它怎样工作、有哪些规则，以及规则背后的理由。

知识库记录现状。讨论过程、被放弃的方案和实施中踩过的坑留在归档的需求目录里；只有改动系统时必须知道的理由才写进正文。仍适用于其他版本或范围的旧规则保留，并写明适用范围。来源需求写在主题的引用块里。

## 只写已实现并核实的事实

知识库只写已经实现、并对照代码或运行结果核实过的事实。批准了但尚未实现的目标、ADR 和方案里的设想，都不能写成现状；分阶段交付时只写实际完成的范围。ADR、note.md、plan.md 和 task.md 的实施记录提供理由和线索，是否仍然成立以最新代码为准。无法核实的内容不写入，交给用户说明。

## 图源

同一模块和范围的当前图，只在知识库的一个位置维护，SVG 和它的图源放在一起，例如 `assets/<主题>/<图名>.svg` 与同名的 Archify 图源 `assets/<主题>/<图名>.architecture.json`；手写的 SVG 本身就是图源。主题文件嵌入 SVG，并在引用块里注明图的适用范围和来源需求。

收尾时先按实际实现核实本需求的 after 图，再更新知识库里的当前图，已有对象保留原来的 ID。结构没有变化时沿用原图。需求目录里的 before/after 图随需求一起归档，知识库只保存当前的图，旧的现状由归档材料和版本历史保留。

## 合并基线

更新前，比较知识库的当前版本与本需求或本次调查读取它时的版本。读取版本（提交号或修改时间）记录在 note.md，需求还会写进 plan.md 的现状一节。找不到读取版本时，按知识库的提交历史判断本需求开始后有哪些改动；判断不了，先问用户。

两个版本不同，说明其他需求已经改过知识库。核实这些改动，把本次的变化合并进去，保留其他需求写入的内容；不能用本次的 after 或笔记结论直接覆盖，它们是从旧基线推出来的。

## 来源链接

整理知识库时，来源里的原需求或调查链接指向它当前的位置 `.rivo/issues/<slug>/`，冷读时链接有效。目录移入 `.rivo/archived/<slug>/` 后，知识库里的来源引用、导航，以及其他 Rivo 文档中指向 `.rivo/issues/<slug>/` 的链接，全部改到新位置，并逐一确认链接有效。
