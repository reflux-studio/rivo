# 知识维护参考

知识根目录默认是目标项目根目录下的 `.rivo/knowledge/`；用户指定位置或项目配置（CLAUDE.md 等）中声明的路径优先；已有文件的位置不构成约定。优先维护已有主题，不从输入资料位置推导输出，也不为一次交付建立新的目录层级。

## 结论的依据

```markdown
结论与适用范围：
性质：业务约定／实现事实／待验证推断
理由、解释它的场景或反例：
来源：原始资料、ADR、相关代码或验证证据
版本或最近核实时间（影响时效时）：
```

无需为每句话重复元数据；同一段共用来源即可。名词解释聚焦含义和区别；详细方案、任务流水与测试原稿留在交付材料中，知识文档链接必要依据。

## 架构图源

同一模块、范围的当前图源只设一个维护位置，例如 `<topic>/architecture/current.architecture.json`。主题导航链接 JSON 和当前阅读入口，并标明范围、实现版本或提交、最近核实依据与来源需求。元信息放在主题说明或 schema 支持的字段中，不向 Archify JSON 随意增加字段。

交付后回写按以下顺序进行：

1. 对照实际实现与验证结果核实本次最终图源。已确认的 target 只是方案，未实施或未验证的能力不能写成现状；分阶段交付只更新实际完成的范围。
2. 比较知识库当前版本与本需求取得 before 时记录的来源版本或哈希。知识库已被其他需求更新时，核实差异，合并已实现的变化并保留无关内容；不能直接用旧基线衍生的 target 覆盖它。
3. 保存旧现状的可追溯历史，将核实后的 JSON 更新到唯一维护位置，保留已有对象的稳定 ID。必要时重新生成当前阅读入口，核对图文与 JSON 一致。无法同步的展示入口明确标为旧版或待更新，不声称同步完成。
4. 更新主题导航、范围、实现版本、验证依据和来源链接，完成后才能将本需求材料归档。before、已确认方案和 compare 历史随需求归档，知识库保存当前现状并链接历史依据。

独立维护同样需要实现依据；无法核实、存在基线冲突或外部同步受阻时保留待更新状态。没有结构变化时沿用图源，不为交付制造无意义版本。

## 替代与清理

1. 核实旧结论因何失效，以及是否仍适用于其他版本或范围。
2. 更新当前说明，保留旧理由与替代来源；无可靠历史记录时先归档有价值的旧内容。
3. 修复受影响导航、交叉引用和源材料链接。交付目录移动到归档后重新指向有效位置。

把“已决定采用”与“已经实施并验证”分别表达。例如通过审批的目标流程尚未实现时，不将它替换成现状流程。

项目已有 wiki、工程文档或知识索引时，映射这些信息即可，不建立竞争的副本。大量迁移按当前任务范围进行，不因为使用了本技能就重组整个知识库。
