# 收尾与项目知识

开始时声明："正在使用 rivo:knowledge-management，收尾本次交付或查阅、维护项目知识。"

**核心原则：** 知识库只写已实现并核实的现状，让新同事从首页读起就能理解系统。

动笔前：
- 加载 writing-clearly
- 读 [知识维护参考](references/knowledge.md)：位置、写法、合并基线、图源和来源链接

## 收尾流程

### 1. 确认验收

只有用户明确表示验收通过才开始，不论是 implementing-plans 交来，还是用户点名本技能或继续需求目录。
- 沉默、没提意见、"看起来不错"都不是验收
- 没有验收就请用户验收，先不动知识库

### 2. 整理进知识库

材料：本需求的 ADR、note.md、plan.md、task.md 实施记录和 before/after 图。

1. 按知识维护参考找到知识库，用合并基线确认其他需求在此期间的改动
2. 确定本需求涉及哪些主题
3. 已有主题在原文件里重写受影响的段落；新主题写成新文件
4. 在首页补上导读和链接

知识库的其余部分保持原样。整体改写需要用户单独指定。

### 3. 冷读检查

1. 派一个没有本次上下文的子代理，从首页读到本次改写的主题，用自己的话复述系统现状
2. 复述不出或复述错的地方，就是写得不可读的地方，改写后再冷读
3. 连续三次仍不对，停下把问题报给用户

### 4. 归档

1. 冷读通过后，把整个需求目录移入 `.rivo/archived/<slug>/`，包括 ADR、审阅报告、证据和图
2. 按知识维护参考修复指向它的链接

### 5. 向用户报告

- 改写或新增了哪些主题，首页补了什么
- 冷读检查的结果
- 目录归档到哪里，修复了哪些链接
- 仍未核实或需要用户决定的事项

收尾完成，本次交付即告结束。

## 单独调用

**查阅项目知识：**
- 从首页找到相关主题，回答并给出来源
- 结论会影响接下来的工作时，对照代码核实；不符的地方告诉用户，由用户决定是否修订

**整理单独调查的笔记**（`.rivo/issues/<topic>/note.md`）：
- 按收尾流程的第 2、3 步写入并冷读，不需要验收
- 调查目录是否归档由用户决定

**重写已有知识库：**
- 按用户给的范围，用 writing-clearly 重写，只改写法
- 原有内容逐条对照代码核实，不符的列给用户决定
- 写完做冷读检查

## 常见错误

| 你在想 | 应当怎么做 |
| --- | --- |
| "用户说挺好的，可以收尾了" | 请用户明确验收。 |
| "方案里写了，就当作现状写进去" | 只写已实现并对照代码核实的内容。 |
| "顺手把旧主题也改成新写法" | 只改本次涉及的主题。 |
| "直接用本次的 after 图覆盖知识库" | 先按合并基线合入其他需求的改动。 |
