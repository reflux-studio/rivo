# 维护项目知识

知识解释已经成立的机制、约束和理由。方案获批不等于已经实现；代码里存在一个类型，也不等于能力实际接入。写入前核实适用版本与行为。

## 确定本次范围

交付收尾沿用用户明确验收，不要求固定口令；没有验收则保留需求材料。单独查阅、整理调查或编辑知识按用户给的范围执行，不要求先验收一个不存在的交付。

按 [知识维护方法](references/knowledge.md) 找到项目已有知识位置和基线，加载 writing-clearly。保留现有阅读结构，不因它是一个 README 就拆文件。

## 更新与核实

读本次需求依据、有效决定、调查结果、方案、实施记录及证据，结合当前代码或运行结果确定实际变化。只能核实部分时只写已核实部分，报告剩余缺口；错误的旧说法不能因新结论尚未证实就继续当事实使用。

把当前知识与本次最初读取的版本比较，合并本次变化，保留其他工作已经写入的内容。已有主题在原处更新；只有形成能独立解释的新主题时才新建文件。核实事实的修正与改变业务决定分开：授权范围内可修正事实，不能借知识维护改变系统承诺。

写当前机制与修改时必须知道的理由，调查过程留在需求记录。图随实际实现更新；结构没变时沿用，不为了收尾另画一套。确认文字、图及其来源一致，文内不依靠来回跳转补足解释。

## 收尾

交付验收后的知识更新完成，将整个需求目录移到 `.rivo/archived/<slug>/`，保留决定、证据和各轮审阅。检查归档目标未被占用，不覆盖已有档案；修复指向旧位置的材料引用和导航。

单独调查目录是否归档按用户要求，不自行推断验收。外部知识系统写入需相应授权，只有本地草稿时说明尚未同步。

报告实际更新的主题、核实范围、归档位置及未完成事项。不能把没有确认的设想写成已完成，也不能把归档动作当作验证完成的证明。
