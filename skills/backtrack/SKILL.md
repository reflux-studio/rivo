# 回溯修复

下游发现上游错，不打补丁——回到根因所在那一层，按变更模式改源头，再向下逐级重放。工作流是单向的：clarify → ui-plan → plan → build。（verify 和 archive 不产出可重放的代码产物，因此不纳入回溯链路。）

若 [using-rivo](../using-rivo/SKILL.md) 总纲尚未在上下文中，先读它。

## 定位根因层

读 `.rivo/issues/$issue_id/` 下的产物，把缺陷现象对照工作流，定位它的根在哪一层——一个现象对应一个根因层。

| 缺陷现象 | 根因层 | 回退去向 |
| --- | --- | --- |
| 代码逻辑 / 边界错，但需求和方案都对 | build | build 层 |
| 某 AC 完全没实现——没被拆进任务 | plan | plan 层（补任务覆盖，再向下重放 build）|
| 架构 / 接口和 plan 对不上，或方案本身不可行 | plan | plan 层 |
| UI 与设计稿 / ui-contract 不符 | ui-plan | ui-plan 层 |
| AC 写错了、或需求本身理解偏了 | clarify | clarify 层 |
| 用户想要、但 PRD 从没约定的新诉求 | —— | 新开 issue，不混入本次回退 |

拿不准根在哪层，就从现象往上游一层层反推。

## 与用户确认

方向性的回退——改 spec、改需求、推翻方案——会牵动下游一大片，**先和用户确认，拿到明确指示再动**。

## 回到对应层

按定位结果，进对应层走变更模式：

- **clarify 层** —— 读 **clarify** 技能，以变更模式改 `prd.md` / `spec.md`，改完向下重放 ui-plan → plan → build。
- **ui-plan 层** —— 读 **ui-plan** 技能，以变更模式改 UI 还原与 `ui-contract.md`，改完向下重放 plan → build。
- **plan 层** —— 读 **plan** 技能，以变更模式改 `plan.md` / `tasks.md`，改完向下重放 build。
- **build 层** —— 读 **build** 技能，在现有实现上增量修复，保留能复用的部分。

## 向下重放

从被改的层开始，逐级向下重放。每一层的做法：

1. 用上游的变更结论对照自己当前产物，判断哪些部分不再成立。
2. 在原文件基础上修改受影响的章节，保留未被上游变更波及的内容。
3. 自审通过后再进入下一层。

**build 层特殊处理**：如果 build 已部分完成（部分 task 已提交），回退 plan 后重放时，只重新执行受影响或新增的 task，已完成且不受上游变更影响的 task 保留不动。但全局回归仍需覆盖全部 task。

重放到原先发现缺陷的那一层时，复验问题是否真的消失。

## 核心原则

- **回源头，不打补丁** —— 缺陷的根在哪层就回哪层改，不在发现它的地方硬补
- **一个现象一个根因层** —— 别同时往多层改，先定位再动手
- **方向性回退必须用户拍板** —— 改需求 / 推翻方案牵一发动全身，先确认
- **改完必须向下重放** —— 上游一动，下游全部据新结论复核，不假设旧产物还成立
- **重放是增量修改，非推倒重来** —— 只改被上游变更波及的部分，保留已完成的、不受影响的工作
- **新诉求新开 issue** —— PRD 没约定的是新需求不是缺陷，别混进本次回退

## 危险信号

- 「就在这层顺手把它改了吧」—— 根不在这层，补丁只会让工作流和源头脱节。
- 「改了 spec，下游应该不受影响吧」—— 上游一动就得向下重放，凭感觉跳过下游复核迟早出事。
- 「这缺陷看着像实现问题，回 build 就行」—— 多想一层：是不是 plan 没拆到、spec 没写到？别默认离自己最近那层。
- 「用户临时想加的，顺手在这轮一起返工了」—— 新诉求 = 新 issue，混进来就失控。
