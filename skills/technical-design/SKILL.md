# 技术设计

将已确认的业务规则展开成可以实施的技术方案。读者应能从 plan 中找到修改对象、共同契约、关键机制和验证要求，不必重新猜一次设计。

开始时声明：“正在使用 rivo:technical-design，形成可实施的技术方案。”

**先核实 Spec 已通过独立审阅和用户审阅。完整方案未经用户批准，不得写入 plan；plan 未经审阅和实施授权，不得开始实现。**

## 工作清单

使用宿主任务工具建立或沿用清单，没有任务工具时在会话中维护。

1. **核对输入与范围。** 读取 Spec、审阅报告和用户决定，确认本期边界，判断已有依据是否足以支持设计。
2. **明确设计问题。** 基于已有事实识别需要决定的职责、契约和实现选择，以及需要验证的假设。
3. **逐轮设计。** 先讨论对象职责和接口边界，再展开数据、状态、关键机制和切片。验证影响结构的假设。
4. **呈现完整方案。** 加载 using-archify，随讨论展示结构、时序或状态 SVG；总结整体变化、取舍和验证安排，等待用户批准。
5. **写入 plan。** 按获批方案写 Markdown，嵌入 SVG；重要选择加载 architecture-decisions，保存独立 ADR。
6. **独立审阅与修复。** 按 Plan 审阅提示词对照 Spec 和工程依据检查，修复后由新的审阅者复审。
7. **用户审阅与实施交接。** 展示方案和审阅结果，用户通过且已授权实施后才能进入增量交付。

已有明确批准继续沿用。用户只要求方案评审时，返回发现和依据；明确要求整理已确认方案时，直接整理并完成文档审阅。

## 使用事实与验证方案

技术设计要回答：怎样实现已确认目标，候选方案能否保证这些行为。先判断已有材料是否足以支撑当前设计。已核实的事实直接沿用，缺少依据的关键前提先查清，再据此选择方案；不因切换阶段重做已经完成的调查。

选择复用能力时，对照本次场景检查输入输出、实际行为、接入条件和业务差异。已有证据足够时直接沿用，不足时补查；名称相同、目录相似或存在生成代码，不能证明适合复用。影响方案成立的未知项先调查或验证，不能用建议补成事实。

先说明本次要查证的问题及其影响。例如，“附件现在怎样归档”属于现状缺口，应补查并检查是否影响原需求；“按评估项分组后，现有转换器能否处理这份数据”用于验证候选结构，要用具体输入和预期结果检查。提出新方案会带来新问题，不需要为每个方向另写调研报告。

直接查证小问题；需要独立探索时，使用共享的[调研提示词](../../references/investigation-prompt.md)，提供已有事实、候选方案和待验证假设。得到足以比较方案的证据后回到设计讨论。静态推断、原型验证和真实联调的结论分别说明，不能互相代替；已明确允许延后验证的事项，保留验证时点和失败后的影响。

新证据推翻现状时，说明影响并修正相关理解；涉及业务行为变化，回到需求讨论。调查结果用于当前决定，完整方案获批后，将采用的契约、机制、限制和必要证据写入 plan，重要取舍写入 ADR。独立审阅仍查验原始依据，不把主代理或调查子代理的结论当作免检事实。

据此说明各仓库新增、修改、复用或迁移什么。外部系统负责的行为写清接口责任与依赖，不替协作方承诺尚未确认的能力。

## 逐轮形成方案

按决定之间的依赖讨论：先确定规则由谁负责、对象和状态属于谁，再讨论接口配合与失败恢复。每轮展示可行选择、具体行为和代价，并给出建议。使用宿主提问工具取得重要决定，未收到回答时保留未决。

用 Spec 的场景和反例检验模型。共享规则要有业务依据，真实的权限、时序和生命周期差异必须保留。沿用能满足需求的现有结构；不要为抽象偏好改造无关模块。

涉及职责边界、公共契约、数据含义或生命周期的重要选择，必须加载 architecture-decisions，在用户决定后保存 ADR。正文同时说明选择及主要理由，不能只留 ADR 链接。

用户回答后更新方案、图源和后续问题。新证据改变业务行为时回到需求讨论；只改变实现结构时在本阶段处理。阻塞契约或模型的未决问题必须解决，不能把它移到风险章节后宣布方案完成。

## 写到什么程度

plan 确定整体方案和主要切片，增量交付再细化当前切片的开发步骤。技术设计必须把实施者共同依赖的约定写具体：

| 内容 | 实施者必须能读到 |
| --- | --- |
| 模块与改动 | 仓库、现有组件或代码位置、新增职责、复用依据及调用关系 |
| 接口与事件 | 操作或接口名、调用方、输入输出、字段含义、成功与失败结果 |
| 数据与状态 | 关键字段、标识与关系、状态归属、转换条件、读写时点 |
| 关键机制 | 本次涉及的权限、事务、幂等、并发、重试等如何落实规则 |
| 兼容与交接 | 旧数据和在途流程如何处理、依赖顺序、上线与回退安排 |
| 切片与验证 | 可验证能力、前置依赖、输入输出、完成标准和检查方式 |

不涉及的机制不凑章节。涉及的机制不能只写“考虑幂等”“做好异常处理”“按现有逻辑实现”。例如，重复回调会修改状态时，要写清用什么标识识别同一操作、哪些状态允许更新、重复或过期回调返回什么。方案不必提供逐行实现代码，但不能把关键设计留给实施者猜。

## 文档输出

写作前加载可用的 writing-clearly-and-concisely。使用 Markdown，默认写入本需求的 `.rivo/issues/<slug>/plan.md`。沿用 Spec 的目录，已有方案原位修改，用户或项目指定路径优先。跨仓库代码分别修改，方案仍集中保存。

先解释总体做法，再按运行过程展开细节。文字讲清规则怎样被实现，图帮助读者理解协作。SVG 放在对应段落，图中的关键约定同时写入正文。即使只读 Markdown 文本，也必须能理解设计。

每个模块章节写明本模块需要遵守的约定，可以简短重述共同规则。完整共享契约在一处定义，链接只用于进一步查证，不以“见 Spec”“同上”“类似另一个模块”代替当前解释。用有意义的标题和表格帮助 AI 定位，不靠反复超链接拼接正文。

```markdown
# <需求名称>：技术方案与交付安排

## 总体方案与范围
先说明本期采用什么做法、解决什么问题，再解释现状与关键变化。
列出涉及的仓库和外部依赖，嵌入现状与目标 SVG。

## 模型与重要选择
解释各对象的职责、关系和状态归属，以及为什么这样划分。
用业务场景检验设计，说明收益、代价和独立 ADR 对应的决定。

## 接口、数据与运行过程
给出实施所需的字段和契约，按请求或事件顺序说明各方动作。
写明成功、拒绝、重复和失败时的行为，嵌入时序或状态 SVG。

## 模块改动
按模块说明改动位置、输入输出、复用依据和关键机制。
解释模块如何保证相关业务规则，不只列文件名或类名。

## 交付切片
每片交付一项可以运行和验证的能力。
写明范围、依赖、提供和消费的接口、完成标准与验证方式。
切片组合后应覆盖完整需求；逐步编码操作留到实施阶段。

## 验证、兼容与发布
将验收场景对应到检查，覆盖本次关键失败路径。
说明兼容、迁移、发布顺序、回退方式和外部协作条件。

## 剩余问题与依据
说明问题的具体影响、解决方式和可继续的范围。
不能把影响模型或共同契约的空缺留到实施时自行决定。
集中列资料依据，避免打断正文阅读。
```

## 独立审阅

读取 [Plan 审阅提示词](references/plan-document-reviewer-prompt.md)，提供 plan、Spec、原始约束、工程依据、用户决定和图源。审阅者独立读取文件，报告写入 `reviews/plan-<round>.md` 并注明被审版本。

修复实质问题后，由新的审阅者复审当前文件和前轮问题。措辞偏好不阻塞通过；改变规则或重要选择的修复，先取得用户决定。反复无进展时查清缺少的证据或请用户裁决模型分歧。

## 完成条件

方案落实 Spec 的规则，关键契约足以实施，切片可继续细化，独立审阅通过，用户审阅通过。只有再具备实施授权，才能加载 incremental-delivery。方案通过不代表实现完成，也不能据此更新知识库中的系统现状。
