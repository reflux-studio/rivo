# Technical Design

开始时声明：“正在使用 rivo:technical-design，形成可实施的技术方案。”同一阶段已声明时不重复。写作时使用可用的 `writing-clearly-and-concisely` 技能。

读取 Spec，形成技术模型、契约和交付安排，写入 `plan.md` 并完成自审。承接已有决定、图源和工程约束；缺少 Spec 时先使用 requirements-definition 完成需求文档。

## 工作步骤

在主任务清单中追踪以下步骤，沿用已有进度。无任务工具时用对话短清单。

- 读取 Spec、决定和图源，核实工程现状与复用依据。
- 对尚需用户判断的重要取舍，展示候选结构、行为、成本和建议，等待回应后继续依赖部分。
- 验证关键假设，讨论取舍，更新图示与确认记录。
- 回述总体方案，引用已有确认或委托；尚未决定的内容明确标注。
- 写入 plan.md，同步受影响的 ADR 和需求。
- 对照 Spec 自审并修正 plan。
- 交付可实施的设计及未决项，或衔接增量交付。

整理已有设计时直接写入 plan 并自审。用户只要求评审时，返回发现、依据和建议。

## 协作方式

按模块或关键机制查证，展示候选、建议及其行为、成本和协作后果。AI 处理技术事实和常规实现细节；重要取舍交给用户判断，再展开依赖它的设计。

沿用已有确认，记录当前结论与提议。需求缺口明确影响范围，解决依赖问题的同时继续独立调查。

## 核实工程依据

沿实际调用和数据流核实相关模块、组件、接口、状态与外部依赖。复用需要实际语义、使用方、业务差异和依赖证据；不能仅凭相同名字、目录规范或类似代码认定它们属于同一个能力。

从总体做法讲起，说明新增、修改、复用和迁移的实际对象。执行范围只覆盖一个仓库时，也要交代其他系统提供的契约与协作条件。关键假设用权威契约、代码或小实验验证，标明证据范围。

## 选择实现模型

把业务规则映射到职责、接口、数据关系、状态归属和生命周期。检查多个入口是否在重复维护同一约束、特殊分支是否来自错误的对象边界、状态是否被放在了不合适的位置。

提出候选结构后，用需求场景和有区分力的反例推演。说明它怎样保证规则、为何比现状更合适，以及新增的间接层、迁移和理解成本。保留真实的权限、时序或生命周期差异，不以消除所有 if 或最大化复用为目标。现有结构已足够时直接沿用。

在 plan 中写明实现模型并引用 Spec 的业务规则。记录重要选择的理由；需要集中比较或长期追踪时，使用 architecture-decisions 记录 ADR。

## 契约与关键机制

说明何时可调用、输入输出的关键语义、成功与失败意味着什么、数据何时生效、失败怎样恢复。按实际风险展开权限、事务、并发、幂等、重复、顺序、重试、缓存失效等机制，说明本次设计采用哪些机制、怎样保证规则。

界面任务说明交互如何落实到组件和状态，包括加载、提交、刷新与恢复。数据变化说明关系、约束、读写路径和历史兼容。涉及迁移或发布时明确依赖次序、在途状态、回退条件和剩余限制。多个模块共享的契约集中维护，其他位置引用。

## 展示与修订

需要用户判断结构变化时，使用可用的 Archify，按 [架构图协作参考](../requirements-definition/references/architecture-diagrams.md) 继承本需求的 before/target，深化同一个 target 并刷新 compare。保留可恢复的确认版本；新的候选不能静默覆盖已确认快照。工具不可用时说明替代方式。

新证据改变需求含义时，带着原约定、证据、后果和建议回到相关需求问题；仅实现结构变化时在本阶段处理。按已有授权推进，未决定部分不阻塞独立工作。同步受影响的 Spec、决定、方案和图源，保留改变的理由。

## Output Location

默认写入本次目标项目根目录的 `.rivo/issues/<slug>/plan.md`，沿用当前需求的 slug 和已选主交付根目录。用户指定或项目配置声明的路径优先；已有方案原位更新，包括旧的 `system-design.md`。输入资料的位置不决定输出位置，所需目录在实际写入时创建。

## Plan Structure

开头注明方案状态、Spec 路径、决定来源和确认依据；图示附阅读入口和可恢复的版本。用以下结构写清设计，区分目标能力与已实现现状。

```markdown
# <需求名称>：技术方案与交付安排

## 总体做法与范围
目标、关键变化、工程现状依据、涉及模块及外部依赖。

## 技术模型与关键选择
职责、关系、状态归属与生命周期；怎样表达业务规则。
候选检验、采用理由、适用边界及相关 ADR（如有）。

## 契约与流程
接口和事件的关键语义，模块协作、状态生效与失败恢复。

## 模块设计
按实际模块说明改动、复用依据、组件或文件、数据与关键机制。
共享契约集中说明；复杂模块可链接附属设计。

## 交付切片
每个可验证能力的范围、前置依赖、交付契约与完成标准。

## 验证、兼容与发布
验收场景及风险的验证方式；适用的迁移、发布次序与回退安排。

## 风险与未决项
具体后果、现有依据、影响范围和解决方式。
```

## Plan 自审

写完 plan 后，由当前代理重新读取 Spec，逐项核对：

1. **需求覆盖：** 每条规则和验收是否有对应机制、交付切片和验证方式？补齐遗漏。
2. **可实施性：** 各切片是否写清改动对象、依赖、输入输出和完成标准？用具体安排替换“处理异常”“后续补充”等占位描述。
3. **契约一致性：** 各模块的名称、类型、接口、事件、状态和生效时点是否一致？核实引用的代码与外部契约。
4. **交付次序：** 依赖是否能按顺序满足？验证、兼容、迁移和发布安排是否覆盖本次风险？

直接修正文档问题；缺少需求决定时返回对应问题，更新 Spec 和 plan。自审完成后交接方案，并简述修正和剩余未决项。

## 完成与交接

plan 确定主要切片、共同契约和依赖，增量交付细化当前切片的执行步骤。

交付保存后的 plan、Spec、图源、验收依据和自审结论。有实施授权时加载 incremental-delivery 并声明用途；用户指定的设计或评审请求在本阶段交付。项目知识中的系统现状依据实际实现更新。
