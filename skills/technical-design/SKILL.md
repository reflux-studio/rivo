# Technical Design

形成能解释需求规则、可评审和实施的技术方案，并直接保存为 plan.md。承接已有需求、决定、图源与工程约束；只要求整理、评审或草稿时按范围完成，已有充分依据无需重新讨论。

## 协作方式

按当前模块或关键机制查证依据，展示候选及建议，说明行为、成本和协作后果，接收回应后再展开依赖它的设计。技术事实和常规实现细节由 AI 调查处理；重要取舍缺少既有决定时交给用户判断，不把设计工作变成产品必须作答的问题。

已有确认直接沿用。讨论中可保存局部设计或提议，完整文档不能代替尚未发生的讨论；用户明确要求先出草稿时遵循其范围。需求缺口只阻塞相关设计，继续独立调查。

## 核实工程依据

沿实际调用和数据流核实相关模块、组件、接口、状态与外部依赖。复用需要实际语义、使用方、业务差异和依赖证据；不能仅凭相同名字、目录规范或类似代码认定它们属于同一个能力。

从总体做法讲起，说明新增、修改、复用和迁移的实际对象。执行范围只覆盖一个仓库时，也要交代其他系统提供的契约与协作条件。关键假设用权威契约、代码或小实验验证，标明证据范围。

## 选择实现模型

把业务规则映射到职责、接口、数据关系、状态归属和生命周期。检查多个入口是否在重复维护同一约束、特殊分支是否来自错误的对象边界、状态是否被放在了不合适的位置。

提出候选结构后，用需求场景和有区分力的反例推演。说明它怎样保证规则、为何比现状更合适，以及新增的间接层、迁移和理解成本。保留真实的权限、时序或生命周期差异，不以消除所有 if 或最大化复用为目标。现有结构已足够时直接沿用。

将实现模型直接保存在方案中，业务含义引用 Spec。重要选择可以在方案中保留理由；需要集中比较或长期追踪时，可使用 architecture-decisions 形成 ADR。选择记录不替代对当前技术结构的说明。

## 契约与关键机制

说明何时可调用、输入输出的关键语义、成功与失败意味着什么、数据何时生效、失败怎样恢复。按实际风险展开权限、事务、并发、幂等、重复、顺序、重试、缓存失效等机制，解释保证如何成立；不为每个模块填满机制清单。

界面任务说明交互如何落实到组件和状态，包括加载、提交、刷新与恢复。数据变化说明关系、约束、读写路径和历史兼容。涉及迁移或发布时明确依赖次序、在途状态、回退条件和剩余限制。多个模块共享的契约集中维护，其他位置引用。

## 展示与修订

需要用户判断结构变化时，使用可用的 Archify，按 [架构图协作参考](../requirements-definition/references/architecture-diagrams.md) 继承本需求的 before/target，深化同一个 target 并刷新 compare。保留可恢复的确认版本；新的候选不能静默覆盖已确认快照。工具不可用时说明替代方式。

新证据改变需求含义时，带着原约定、证据、后果和建议回到相关需求问题；仅实现结构变化时在本阶段处理。按已有授权推进，未决定部分不阻塞独立工作。同步受影响的 Spec、决定、方案和图源，保留改变的理由。

## Output Location

默认写入本次目标项目根目录的 `.rivo/issues/<slug>/plan.md`，沿用当前需求的 slug 和已选主交付根目录。用户指定位置或项目配置（CLAUDE.md 等）中声明的路径优先；已有文件的位置不构成约定；修订已有方案时原位更新，包括旧的 `system-design.md`，不另建竞争版本。输入资料的位置不决定输出位置，所需目录在实际写入时创建。

## Plan Structure

按实际影响范围裁剪。开头注明方案状态、需求与决定来源、确认依据；图示附阅读入口和可恢复的版本。待定能力不能写成已实现现状。

```markdown
# <需求名称>：技术方案与交付安排

## 总体做法与范围
目标、关键变化、工程现状依据、涉及模块及外部依赖。

## 技术模型与关键选择
职责、关系、状态归属与生命周期；怎样表达业务规则。
候选检验、采用理由、适用边界及相关 ADR（如有）。

## 契约与流程
接口和事件的关键语义，模块协作、状态生效与失败恢复。

## 模块设计
按实际模块说明改动、复用依据、组件或文件、数据与关键机制。
共享契约集中说明；复杂模块可链接附属设计。

## 交付切片
每个可验证能力的范围、前置依赖、交付契约与完成标准。

## 验证、兼容与发布
验收场景及风险的验证方式；适用的迁移、发布次序与回退安排。

## 风险与未决项
具体后果、现有依据、影响范围和解决方式。
```

## 完成与交接

方案确定主要交付切片、共同契约与依赖；增量交付沿用这些边界并细化当前任务。无需在方案中预写全部实现代码或远期逐行操作；没有 plan 的小任务可直接在交付时拆分。

逐段讨论后回述总体方案，取得或引用已有确认，直接保存并核对：需求是否被覆盖、规则能否由机制保证、关键假设有无证据、验收和相关发布安排是否可执行。用实际对象和具体后果表达，不靠“保证一致性”等承诺填满模板。

交付可实施范围、方案版本、图源、验收依据和剩余限制。有实施授权时交给增量交付；只要求设计或评审时返回结果。确认目标不等于已经实现，不提前覆盖知识库现状。
