# 技术设计

把已确认的需求变成可以实施的方案，写入 `plan.md`，交给子代理和用户审阅。

开始时说明：“正在使用 rivo:technical-design，形成可实施的技术方案。”同一阶段已经说明过，就不重复。

## 工作步骤

先读取已通过子代理和用户审阅的 Spec。缺少 Spec 或审阅结果时，回到 requirements-definition 完成需求阶段。

把以下步骤加入主任务清单，已有进度直接沿用。没有任务工具时，在对话中列出短清单。

1. 阅读 Spec、相关决定和图源，核实工程现状及可复用的能力。
2. 按决定之间的依赖逐轮讨论，展示方案、行为、成本和建议。
3. 验证关键假设，根据回答更新方案、图示和确认记录。
4. 展示完整方案，说明重要取舍和未决问题，等待用户批准。
5. 获批后写入 `plan.md`，同步已确认的 ADR 和需求变化。
6. 启动审阅子代理对照 Spec 检查，修复问题，复审直到通过；遇到反复无进展的问题，按[审阅与分歧](../using-rivo/SKILL.md#审阅与分歧)处理。
7. 请用户审阅 plan，通过且已获实施授权后，再进入增量交付。

用户明确要求把已确认的方案写入 plan 时，直接按这些结论写入，再完成子代理和用户审阅。用户只要求评审时，返回问题、依据和建议。

## 逐轮讨论方案

沿用需求阶段的[决策树协作](../requirements-definition/SKILL.md#决策树协作)。本轮只讨论前提已经明确的问题：先确定各部分的职责和接口约定，再展开实现机制和交付切片。说明候选方案的行为、成本和对协作方的影响。

AI 负责查证事实和处理常规实现细节，重要取舍由用户决定。收到回答后，修改模型、图示和下一轮问题；未受影响的确认继续沿用。

关键能力还没验证，或仍在等待外部决定时，说明它会影响哪些后续工作。可以继续调查其他问题，但不能把推荐方案当作已经选定的方案。

## 核实工程依据

沿实际调用和数据流检查模块、组件、接口、状态和外部依赖。判断能否复用时，核实它实际做什么、谁在用、有哪些业务差异、依赖什么。名字相同、目录相似或代码相近，都不足以证明它们是同一种能力。

先解释总体做法：

- 新增什么，修改什么，复用什么，迁移什么。
- 涉及哪些模块和仓库。
- 其他系统要提供什么接口或协作条件。即使本次只修改一个仓库，也要说清这些依赖。
- 哪些假设已经通过接口约定、代码或小实验验证，证据能支持到什么程度。

## 选择实现模型

说明业务规则由哪些部分负责，接口如何配合，数据和状态归谁管理、经历哪些变化。

检查多个入口是否在重复维护同一条规则，特殊分支是否来自对象划分不当，状态是否放错了位置。提出候选结构后，用需求场景和反例检验：

- 它怎样保证业务规则？
- 相比现状解决了什么问题？
- 会增加多少间接调用、迁移和理解成本？
- 哪些权限、时序或生命周期差异必须保留？

现有结构足够时就沿用。不要为了消除所有 if 或追求最大复用而改造。

将实现模型写入 plan，并引用对应的 Spec 规则。记录重要选择的理由；需要集中比较或长期记录时，使用 architecture-decisions 保存 ADR。

## 接口与关键机制

写清接口或操作的约定：何时可以调用，输入输出意味着什么，怎样判断成功或失败，数据何时生效，失败后如何恢复。

根据本次风险，展开权限、事务、并发、幂等、重复请求、顺序、重试或缓存失效等机制。说明采用哪些机制，以及它们如何保证规则。

- **界面：** 交互如何对应到组件和状态，如何加载、提交、刷新和恢复。
- **数据：** 对象关系、约束、读写路径，以及旧数据如何兼容。
- **迁移与发布：** 依赖顺序、进行中的任务如何处理、何时回退，还有哪些限制。

多个模块共用的接口约定集中写在一处，其他地方引用。

## 图示与方案修改

讨论职责、接口、流程或状态时，使用 Archify。按[架构图协作参考](../requirements-definition/references/architecture-diagrams.md)沿用本需求的现状图和候选图，边讨论边完善。保存用户已确认的版本，新候选不能悄悄覆盖它。

未安装 Archify 时，说明“当前环境未安装 Archify，使用 Mermaid 替代”，然后继续。按实际选择写 ASCII、Mermaid 或 PlantUML，无需征求降级许可。已经安装但无法使用时，说明实际原因。用户明确不需要图时，遵从用户要求。

新证据改变需求含义时，回到对应需求问题，说明原约定、新证据、后果和建议。只改变实现结构时，在设计阶段处理。重要变化获批后，更新相关 Spec、决定、方案和图源，再完成子代理和用户审阅。等待期间可以继续不依赖该决定的调查。

## 文档输出

写文档时，如果有 `writing-clearly-and-concisely` 技能，就加载并使用。

默认保存到目标项目的 `.rivo/issues/<slug>/plan.md`，与本需求的 Spec 放在同一个目录。

- 用户或项目指定了路径，就按指定路径保存。
- 已有方案时，直接修改原文件，包括旧的 `system-design.md`。
- 输入资料放在哪里，不影响 plan 的保存位置。缺少目录时，在写入时创建。
- 涉及多个仓库时，沿用需求阶段选定的项目集中保存文档。

## 文档内容

开头说明 Spec 路径和方案依据，分清已确认的决定和未决问题。图示附上阅读入口，以及能恢复的已确认版本。分清计划提供的能力和已经实现的能力。

```markdown
# <需求名称>：技术方案与交付安排

## 总体做法与范围
目标、关键变化、工程现状依据、涉及模块和外部依赖。

## 技术模型与关键选择
各部分的职责和关系，状态归属与生命周期，以及如何保证业务规则。
候选方案的检验结果、采用理由、适用范围和相关 ADR（如有）。

## 契约与流程
接口和事件的含义，模块如何协作，状态何时生效，失败如何恢复。

## 模块设计
各模块的修改、复用依据、组件或文件、数据和关键机制。
共享的接口约定集中说明，复杂模块可以链接附属设计。

## 交付切片
每项可验证能力的范围、前置依赖、对外保证的行为和协作约定，以及完成标准。

## 验证、兼容与发布
如何验证验收场景和风险，如何迁移、发布和回退。

## 风险与未决项
具体后果、已有依据、影响范围，以及如何解决。
```

## 子代理审阅

写完 plan 后，加载 [Plan 审阅提示词](references/plan-document-reviewer-prompt.md)。填入 plan、已批准的 Spec、用户确认过的设计决定和工程依据，启动独立审阅子代理。

审阅者读取文档和依据，将报告写入本需求的 `reviews/plan-<round>.md`，返回 `Approved` 或 `Issues Found`。发现问题时，指出位置，并说明为什么会影响实施。

- 主代理修复问题后，启动新的审阅子代理，提供修订后的文档和前轮报告，复审直到通过；遇到反复无进展的问题，按[审阅与分歧](../using-rivo/SKILL.md#审阅与分歧)处理。
- 措辞偏好和可选改进不阻塞通过。
- 修复涉及需求或重要方案变化时，先请用户决定，再同步文档并复审。

用户只要求修改表述时，直接修改文档并重新审阅；结论有变化时，回到对应讨论。

## 交付与下一步

交付 plan、Spec、图源、验收依据和子代理审阅结论。plan 确定主要切片、各部分共用的行为和协作约定，以及依赖关系；增量交付阶段再细化当前切片的执行步骤。

子代理通过后，请用户审阅 plan。用户也审阅通过，并且已授权实施，才能加载 incremental-delivery。用户只要求设计或评审时，完成本次结果就结束。项目知识中的系统现状，等实现后再按实际情况更新。
