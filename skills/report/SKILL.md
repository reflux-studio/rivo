# /rivo:report —— 人话主讲

把一份产物（PRD / plan / 整体 diff / 现状）用人话讲给用户，让 ta 在听 + 打断里**重建认知、当场纠偏**——像现实中同事主讲技术方案，而不是甩一句"请 review"。

**它不是评审收敛门**：产物质量由机器侧 `/rivo:review` 自审收敛把关，report 只负责手动模式下把已收敛的产物讲给人听。生命周期 skill（issue / spec / plan / code）在 review 收敛、commit 后于**手动模式**走 report 主讲，讲完 skill 自然结束、工作流暂停，由用户决定是否继续下一步——不需要单独的"请批准 → OK"握手。**auto 编排下不触发 report**（auto 不主讲、不等批准）。

它**不落文件**：交流对象是此刻的用户，留下来的（用户的 override / 纠正）落进产物本身 + commit。

## 为什么不是"读文档"

一大份 spec / plan 没有人类可读性——现实里你不会读完同事的技术方案，而是让 ta 主讲、你在脑子里重建认知。report 就是那场主讲，不是更短的摘要。

## 怎么讲

1. **按"认知块"切，不按文档章节** —— 目标 / 关键决策 / 架构 / 风险 / 边界，切成用户需要理解的单元。
2. **决策先行** —— 每块先抛要用户判断的点（"我做了 X、否了 Y，因为 Z——你认吗？"），别先铺背景。
3. **一次一块、停下等反应** —— 用户"嗯"就继续，质疑就展开 / 改。ta 在反应里重建模型。
4. **自适应，深度 ∝ 参与的反比** —— 用户已在决策收敛里参与过的，一笔带过；只重点讲 **ta 没参与的**。讲给参与度 = 0 的外部干系人时，做完整主讲，并翻译成 ta 能懂的语言。
5. **暴露不确定，别推销** —— 主动说"我最没把握的是 X"。glib 的"都搞定了"只会更快骗到点头。
6. **必要时图文结合** —— 形状 / 架构 / 数据流 / 状态流转这类"怎么拼起来"的东西，纯文字讲不清就随手画个 ASCII 图（框 + 箭头 + 层级），图配着话讲，帮用户更快重建认知、当场判断。别为画而画——只在图比话省力时画。

## 讲什么

- **形状** —— 这一摊整体长什么样、怎么拼起来的（用户拍了一棵棵树，这里给森林）。
- **自填项** —— 我替用户默认 / 假设了什么（决策收敛没覆盖到的）。
- **不确定项** —— 我拿不准的、或被标出来要用户定的 tradeoff。

## 核心原则

- **主讲不是摘要** —— 交互、决策驱动、可当场打断，不是更短的 wall of text。
- **求校准不是求点头** —— 暴露判断点和不确定、能改变结果（用户可 override）才有意义。
- **即焚** —— 不落文件；用户的决定落进产物 + commit，那才是持久记录。

## 反例

**"把 plan 总结成三段漂亮的话、说一句'整体没问题，approve 吗'"** —— 这只是更短的"请 review"，还附带推销。主讲要把用户**没参与的决策和你最不托底的地方**顶出来，让 ta 真有东西可判、可推翻。
