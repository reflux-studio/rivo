# 交叉评审与自我修复

你既是作者又是评审，容易自我放行。派一个与你不同的模型，在独立上下文里评审产物，再据评审结果自我修复。

若 [using-rivo](../using-rivo/SKILL.md) 总纲尚未在上下文中，先读它。

## 获取必要的上下文

先判定要评审的产物与范围；若上游给定了审查项提示词，照提示词审。

## 发起评审

交叉评审按可信度从高到低分三档：

- **跨厂商**：装了诸如 codex-plugin-cc 等插件或 MCP 的，调外部模型审
- **同厂商不同模型**：如使用 subagent 派遣 Opus 模型审阅 Sonnet 产物
- **同模型兜底**：使用 subagent 派遣同一模型自审

检测用户的运行环境，按评审对象选档：

- **评审你（或本会话模型）产出的产物** → 选可信度最高的一档，离作者越远越好。
- **评审不是你产出的东西**（如设计稿、用户提供的文档）→ 不存在自我放行的问题，不必强求跨厂商；独立上下文照旧，按评审所需的能力选模型（如设计稿选视觉理解强的）。

派评审 agent 时，连同审查项提示词与 [review.md](templates/review.md) 模板一并交给它。

> 评审 agent 的职责限于找问题：判严重性与类型、定处理方式；解法与改动留给主线程。用 subagent 隔离上下文，保证它和作者不是同一双眼睛。

把评审 agent 产出的结果原样存到 `.rivo/issues/<issue-id>/reviews/<topic>-<round>.md`（不属于任何 issue 的产物，如宪章文档，落到 `.rivo/reviews/`），不替它增删——分级分类要由独立的它来下，才客观。

## 处理与重审

照评审结果逐条处理——这一步在主线程做，不在评审 agent 里：

- **本层问题**：直接修。
- **方向性问题**：修复需要改动上游产物（如 spec、plan）才能解决，或根本否定了当前产物所依据的前提。这类问题交用户拍板，或通过 **backtrack** 回根因层。不在本层硬补。

改完重新发起评审。只要还有高危未清，就再来一轮。

**终止条件**：如果同一类问题连续两轮无法收敛，或评审已超过三轮仍有高危发现，暂停并向用户报告评审僵局——包括已修复的、仍存在的、以及背后可能的方向性原因——由用户决定继续评审还是调整方向。

## 核心原则

- **先分级，再处理** —— 每条发现都标严重性（高 / 中 / 低危）与所属审查项；高危拦路，决定能否进下一步。
- **方向性问题往上游路由** —— 根在上游或方案本身的问题，交用户拍板或走 **backtrack** 回根因层。
- **评审必落文件** —— 每一轮都按 review 模板写成文件，有迹可循。
- **评审不收敛时主动上报** —— 连续两轮同类问题未收敛或三轮后仍有高危，暂停并向用户报告。

## 危险信号

- 「改了三轮还在冒新问题，再来一轮」—— 不收敛往往意味着方向本身错了，停下来向用户报告评审僵局。
- 「第二轮了，只看上一轮的问题就行」—— 每轮都独立审产物的所有方面，并防住修复本身引入的新问题，不只盯上一轮。
- 「这个问题我直接改掉」—— 修复前先问：是否需要用户拍板、是否要重议方案，不擅作主张。
- 「评审通过了，就不写文件了」—— 通过也要落文件，否则无从追溯审了几轮。
