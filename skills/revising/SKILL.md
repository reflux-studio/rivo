# 修订已确认的内容

产物之间有上下游关系：决定约束技术方案与测试方案（两者同级并互相核对），两份方案共同约束任务清单，任务清单约束代码与验证证据。

动手修订前，先看改动幅度：
- 核心模型和主线不变，只是调整局部决定、某个接口契约、测试预期或任务安排：按下面的流程从最上游逐层修订。
- 实施到中后期，发现底层模型或整体路子走不通、需要推翻重做：不要往当前目录里再叠一份平行的重构方案；与用户确认后先暂停或收尾当前需求，另开独立的重构需求。

## 流程

### 1. 确定从哪一层改起

| 要改变的内容 | 起点 |
| --- | --- |
| 范围、业务行为、验收标准，或 `decisions.md`、`adr/` 中的某项决定 | 决定 |
| `plan.md` 写明的结构、契约或发布安排，决定不变 | 技术方案 |
| `test-plan.md` 的测试预期、分层策略或老功能回归范围，架构不变 | 测试方案 |
| `task.md` 的任务划分、顺序、人工验收节点或共同约定，两份方案不变 | 任务清单 |

- 方案里要改的内容对应某条决定时，往上游追到“决定”
- 调整技术方案时，检查是否同时改变测试方案的预期、边界或回归范围
- 新事实需要核实时，先加载 `investigating`
- 用户已经做过决定、只是之前漏记的，补记后继续，不走修订流程
- 方案没写到、也不改变契约与测试预期的局部代码写法，在任务范围内决定并记进 `task.md` 即可

### 2. 取得用户的决定

向用户说明：

```markdown
原来的约定：<决定的编号、ADR 或 plan.md / test-plan.md 的版本与内容>
实际发现：<代码、运行结果或测量数据等证据>
具体后果：<照原约定做会发生什么>
处理建议：<怎样改，以及各选项的代价>
影响范围：<要改的产物、受影响的任务、已完成的工作和协作方>
```

改变决定由用户拍板，改变方案由用户确认。沉默不算同意。

### 3. 从起点逐层往下改

| 层 | 产物 | 做法 |
| --- | --- | --- |
| 决定 | `decisions.md`、`adr/` | 加载 `converging` 更新，沿依赖检查下游决定 |
| 方案 | `plan.md`、`assets/`、`test-plan.md` | 加载 `writing-plans` 在原处改写受影响部分，对应方案次版本号加一，并核对技术方案与测试方案一致 |
| 任务清单 | `task.md` | 在原处更新受影响的任务、引用的 `TC-xx` 与人工验收节点，标明需要重做或重新验证的任务 |
| 代码 | 代码、`evidence/` | 受影响的已完成任务按新方案重做，并重新通过验证与审阅 |

- 不跳层：起点以下的每一层都要核对，不需要改的也确认它与上游一致
- 上游确认后再改下游：决定定下后再改方案，方案确认后再改任务和代码

### 4. 核对并报告

- 在各层产物中搜索旧说法，清理残留
- 向用户报告：每一层改了什么，哪些核对过不需要改，哪些任务要重做或重新验证

## 修订期间

- 不依赖改动部分的任务继续推进
- 依赖改动部分的任务，等上游确认后再继续
- 原有的批准和实施授权继续有效，除非用户收回
- 局部修订由用户直接确认，不重新做全量方案审阅
