# 测试设计与分层

动手写代码前，先同时对照需求规则和技术方案定好测试预期和影响范围：根据需求规则定“应该表现成什么样”，防止照着刚写完的代码反推测试；根据技术方案和代码依赖定“底层改了什么、可能波及哪些老功能”，避免只测新增页面而漏掉回归。

## 输入

- **业务规则**：需求文档、PRD、已确认的业务规则、异常处理约定和验收标准
- **技术方案与代码依赖**：技术方案、接口契约、代码现状、公共依赖和方案里最脆弱的假设

## 流程

### 1. 用四类方法拆出关键测试点

穷举会带来大量重复用例，按四类方法把场景压缩到少而准的集合：

- **等价类划分**：把同类输入归为一类，每类只取一个代表值（例如金额校验覆盖正数、0、负数、超上限、非数字即可，不重复测多个正常正数）
- **边界值分析**：检查最容易出错的临界点——`0`、`-1`、`null`、空集合、单条与多条、分页首末页、字段最大长度 `N` 与 `N+1`、跨天与时区、数值精度
- **状态迁移与条件组合**：梳理不允许的状态跳转、重复点击或重放的幂等性，以及“角色权限 × 数据状态 × 配置开关”的组合条件
- **异常容错与老功能影响**：覆盖上游超时、部分失败回滚、水平/垂直越权、并发竞态、历史存量脏数据兼容，以及改动公共组件、共用表或跨端契约波及的老功能回归

### 2. 为每条测试点分配测试层级

避免把几十个参数边界全塞进慢而脆的端到端测试：

| 层级 | 覆盖重点 | 成本与定位 |
| --- | --- | --- |
| 单元测试 | 纯逻辑、计算规则、参数等价类、边界值、状态分支与异常捕获 | 毫秒级自动执行，大部分参数组合和边界放在这一层 |
| 集成测试 | 模块拼接、数据库事务、权限鉴权、跨服务与跨仓库真实契约 | 秒至分钟级自动执行，也是对接 MeterSphere、Etest 等测试平台的核心层 |
| 端到端测试 | 核心主干链路、关键交互渲染与跨模块串联 | 成本高，只验证关键链路连通与交互表现，不在此层穷举字段边界 |
| 人工验收 | 视觉布局、交互体验、文案可读性或真实设备兼容 | 仅用于需要人眼确认的关键节点 |

### 3. 按模块与回归范围写出测试方案

- 按 [测试方案模板](references/test-plan-structure.md) 组织，写入调用方或项目指定的位置（默认 `test-plan.md`）；团队有自己的模板或测试平台导入格式时优先沿用
- **按业务模块和老功能回归范围组织，统一编号 `TC-01..`**：不绑定临时的任务序号，调整任务拆分或顺序也不会让编号失效，同时方便同步到 MeterSphere、Etest 等平台
- **篇幅随改动大小调整**：小改动精简为几行紧凑表格，覆盖核心正常、边界、异常与直接受影响的回归点即可，不强求逐条铺开；大中型需求按模块与回归范围展开

### 4. 送审前自查

- 每项业务规则、异常约定和方案里最脆弱的假设是否都有对应条目
- 是否基于改动影响面圈出了老功能回归范围，而不是只测新增界面或新接口
- 每条预期结果是否客观、可断言，避免“展示正常”“处理成功”这类含糊表述
- 有没有把本该由单元测试覆盖的参数组合错放进端到端测试，或把跨服务契约只留在全 mock 的测试里

自查不能代替独立审阅。

### 5. 独立审阅

首次定稿前做一次全量独立审阅。之后的局部修订由决策方直接确认，不再重审：

1. 可加载 `dispatching-subagents`，按 [审阅提示词](references/reviewer.md) 派一个没有参与编写的独立审阅者检查漏测边界、漏测影响面与分层合理性
2. 按 [接收审阅意见](references/receiving-review.md) 逐条核实：属实的 P0 修完后交同一审阅者复核；明确拒绝同一等价类重复扩写、分层上移的过度设计，以及脱离前置硬约束的过度防御意见；未修的 P1、P2 说明原因
3. 宿主缺少子代理工具时如实说明缺口，不把自我检查算作独立审阅
