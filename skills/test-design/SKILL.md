# 测试设计

写代码前，先对照需求规则和技术方案定下测试预期和影响范围。需求规则决定“应该表现成什么样”，这样就不会照着刚写完的代码反推测试；技术方案和代码依赖决定“底层改了什么、会波及哪些老功能”，这样就不会只测新页面而漏掉回归。

## 输入

- **业务规则**：需求文档、PRD、已确认的业务规则、异常处理约定和验收标准
- **技术方案与代码依赖**：技术方案、接口契约、代码现状、公共依赖，以及方案里最脆弱的假设

## 流程

### 1. 拆出测试点

用经典测试设计方法把场景压到少而准，不穷举：

- **等价类划分、边界值分析**：每类输入取一个代表值，重点测临界点
- **状态迁移、判定表**：非法状态跳转、重复提交的幂等性，以及角色、数据状态、配置开关的组合
- **错误推测**：上游超时、部分失败回滚、越权、并发竞态、存量脏数据
- **影响分析**：改动公共组件、共用表或跨端契约时，圈出受波及的老功能

### 2. 按测试金字塔分层

参数组合和边界尽量放在单元测试；集成测试覆盖模块拼接、数据库事务、鉴权和跨服务契约；端到端测试只走核心主干和关键交互；人工验收只留给需要人眼确认的视觉、体验和文案。不要把几十个参数边界塞进又慢又脆的端到端测试。

### 3. 写出测试方案

- 按 [测试方案模板](references/test-plan-structure.md) 组织，写入调用方或项目指定的位置（默认 `test-plan.md`）。团队有自己的模板，或者项目接入了外部测试平台、有导入格式要求时，优先沿用
- 按业务模块和老功能回归范围组织，用稳定的 `TC-01..` 编号，不绑定任务序号，任务调序时编号不会失效
- 篇幅跟着改动大小走：小改动用一张紧凑的表覆盖正常、边界、异常和直接受影响的回归点；大中型需求按模块展开

### 4. 送审前自查

- 每条业务规则、异常约定和方案里最脆弱的假设，是否都有对应用例
- 是否按改动影响面圈出了老功能回归范围，而不是只测新界面或新接口
- 每条预期是否可以直接写成断言，没有“展示正常”“处理成功”这类含糊说法
- 有没有把该放单元测试的参数组合放进端到端测试，或者把跨服务契约只留在全 mock 的测试里

自查不能代替独立审阅。

### 5. 独立审阅

首次定稿前做一次全量独立审阅，之后的局部修订由用户直接确认，不再重审：

1. 加载 `dispatching-subagents`，按 [审阅提示词](references/reviewer.md) 派一个没有参与编写的审阅者
2. 按 [接收审阅意见](references/receiving-review.md) 逐条核实；属实的 P0 修完交同一审阅者复核
3. 宿主没有子代理工具时如实说明，不把自查算作独立审阅
