# 接收测试方案审阅意见

测试审阅者容易出于稳妥要求大量加测。调用方对照 PRD、决定记录、技术方案和底层约束逐条核实：真正的高风险盲区和回归范围必须补上，脱离实际约束的加测要拒绝。

## 分级

| 级别 | 含义 | 处理 |
| --- | --- | --- |
| P0 | 漏掉核心需求或关键回归范围；预期写错；并发幂等、越权、非法跳转、回滚或存量兼容等高风险盲区缺失 | 必须修 |
| P1 | 同一等价类明显重复、分层严重倒置，或预期含糊、无法写断言 | 默认修；代价明显高于收益时可不修，写明理由 |
| P2 | 编号、措辞或分组瑕疵，不影响执行和覆盖 | 不必修，顺手能改的改 |

没有 P0 即为通过。没修的 P1、P2 和拒绝理由在交付测试方案时一并说明。

## 核实与处理

对照需求、决定记录、技术方案、调查结论和代码约束核实每条意见：

| 核实结果 | 处理 |
| --- | --- |
| 盲区或回归遗漏属实 | 按级别补充或调整用例和分层，检查是否波及相关模块 |
| 预期规则本身不明确，或需要改范围 | 停下来请用户明确规则，再更新测试方案 |
| 缺少上下文造成的误会 | 拒绝，写明对应的规则、决定或调查证据 |
| 过度设计或过度防御（见下节） | 拒绝，写明等价类依据、前置约束或成本收益 |
| 用例没错，预期不够可断言 | 改清断言条件和输入边界，层级不变 |

## 过度设计与过度防御

下面两类意见核实后直接拒绝，免得测试套件越来越大、越来越脆：

- **过度设计**：为简单改动铺开几十条组合，把同一等价类拆成多条重复用例，或者把单元测试就能覆盖的字段边界放进端到端测试
- **过度防御**：针对类型检查、数据库外键或唯一约束、上游鉴权已经挡住的不可能状态写用例，最后只能靠大量 mock 才跑得通

拒绝时写明前置约束、等价类依据或分层理由。审阅者复核时仍坚持，且涉及真实的业务风险取舍，交用户决定。

## 复核

有 P0 时，修完交给同一个审阅者增量复核：
- 宿主支持时续用原审阅者会话，附上改动说明、被拒绝的意见与理由，只复核修复与波及范围
- 无法续用时派新的审阅者，附上前轮报告与改动摘要
- 复核结论追加到原报告末尾，直到没有 P0

## 用户与团队的评审意见

测试方案交用户或团队评审后带回的意见，先核实技术约束和现有用例覆盖，再交用户决定增删。同事的建议在用户采纳前不写进测试方案。
