# 接收测试方案审阅意见

独立测试审阅者容易因为稳妥习惯而要求扩写大量用例，调用方对照 PRD、决定记录、技术方案与底层约束逐条核实：真正的高危盲区和回归域必须补齐，脱离实际约束的用例膨胀和过度防御要明确拒绝。

## 分级

| 级别 | 含义 | 处理 |
| --- | --- | --- |
| P0 | 漏掉核心需求或 P0 回归域；预期写错；高危并发幂等、越权、非法跳转、回滚或存量兼容缺失 | 必须修 |
| P1 | 明显重复废用例、测试分层严重倒置或预期含糊无法写断言 | 默认修；代价明显高于收益时可不修，写明理由 |
| P2 | 编号、措辞或分组瑕疵，不影响执行与覆盖 | 不必修，顺手能改的改 |

结论：没有 P0 即为通过。没修的 P1、P2 与拒绝理由在交付测试方案时一并说明。

## 核实与处理

对照需求、决定记录、技术方案、调查结论与代码约束核实每条意见：

| 核实结果 | 处理 |
| --- | --- |
| 盲区或回归域遗漏属实 | 按级别补充或调整 `TC-xx` 与分层，并检查是否波及关联模块 |
| 预期规则本身不明确或要改范围 | 停下提交需求方明确规则后再更新测试方案 |
| 缺少上下文造成的误会 | 拒绝，写明对应规则、决定或调查证据 |
| 过度设计或过度防御的加测建议 | 拒绝，写明等价类依据、前置硬约束或成本收益比，不因高优先级标签盲从 |
| 用例没错，预期表述不够可断言 | 改清断言条件与输入边界，验证层级不变 |

## 识别并拒绝过度设计与过度防御

测试审阅意见符合下列特征时直接拒绝，防止测试套件膨胀变脆：

- **过度设计（用例膨胀与分层上移）**：要求为简单改动铺开几十条冗余组合、把同一等价类拆成多条重复输入反复测，或把单元测试毫秒级就能覆盖的字段边界硬塞进高成本端到端链路
- **过度防御（脱离威胁模型的假想场景）**：要求针对编译器类型检查、数据库外键/唯一约束或上游鉴权网关已物理阻断的不可能状态编写低收益分支用例，导致后续靠大量脆性 mock 才能勉强跑通

拒绝时写明具体的前置约束、等价类代表值依据或分层考量；复核时若审阅者坚持且涉及真实业务风险偏好，交由需求方裁决。

## 复核

有 P0 时，修完交给同一个审阅者增量复核：
- 宿主支持时续用原审阅者会话，附上改动说明、拒绝的意见及理由，只复核修复与波及范围
- 无法续用时派新的独立审阅者，附上前轮报告与改动摘要
- 复核结论追加到原报告末尾，直到无 P0 通过

## 需求方与团队评审意见

测试方案经需求方或团队评审带回的意见，先核实技术约束与现有用例覆盖，再交需求方拍板是否增删；其他同事的建议在确认前不直接写入测试方案。
