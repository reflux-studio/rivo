# 团队协作

这份技能说明一支产研团队如何把一个需求从提出推进到上线。Team Lead 读它来推进流程，其他角色读它来查协作规则。

## 角色

- **Product**：负责产品方案和 UAT，产出 spec 和 uat 记录。
- **Designer**：负责界面的交互与视觉，产出 ui-spec，界面有变化时才出场。
- **Engineer**：负责技术方案、编码、测试和发布，产出 plan、代码和测试记录。
- **Reviewer**：负责评审所有承载判断和取舍的产物。
- **Team Lead**：负责开工单、判断工单类型、照流程表逐步推进、把需要用户拍板的事收口给用户。它不生产交付物，也不评判产物好坏。

每个角色的立场和行为边界写在 `agents/` 各自的定义里，这里只列分工。

## 工单类型

接到需求，Team Lead 先判断类型，照该类型的流程表推进。再小的需求也是需求——改一行文案也走产品需求的完整流程。

- **产品需求**：新增或改变用户可感知的功能。
- **缺陷**：已有功能的表现和预期不符。
- **技术任务**：用户不可感知的工程改进——重构、依赖升级、性能优化。

三类工单的流程形状：

```
产品需求  产品方案 → 〔界面设计〕 → 技术方案 → 编码 → 测试 → UAT → 发布 → 复盘
缺陷      复现 → 定修复预期 → 〔技术方案〕 → 编码 → 测试 → 发布 → 复盘
技术任务  定目标 → 技术方案 → 编码 → 测试 → 发布 → 复盘
```

〔〕里的步骤按条件出现；每个产出步骤后面都跟着对应的评审步骤，图中省略，完整步骤见各流程表。拿不准算哪类，按产品需求走，它的流程最全。

## 产品需求流程

| 步骤 | 负责角色 | 产物 | 完成的定义 |
| --- | --- | --- | --- |
| 产品方案设计 | Product | spec（含验收标准） | 产物完成 |
| 产品方案评审 | Reviewer | 评审意见 | 评审通过，用户确认定稿 |
| 界面设计（仅界面的交互或视觉有变化时） | Designer | ui-spec | 产物完成 |
| 界面设计评审（同上条件） | Reviewer | 评审意见 | 评审通过 |
| 技术方案设计 | Engineer | plan（含现状梳理与影响面分析） | 产物完成 |
| 技术方案评审 | Reviewer | 评审意见 | 评审通过，用户确认定稿 |
| 编码 | Engineer | 代码 | 产物完成 |
| CR | Reviewer | 评审意见 | 评审通过 |
| 测试 | Engineer | 测试记录 | 对照 spec 的验收标准逐条验证通过，附证据 |
| UAT | Product 带用户 | uat 记录 | 用户确认满足需求 |
| 发布 | Engineer | 已上线的交付物 | 按 PROJECT.md 的交付约定发布并验证 |
| 复盘 | 全员 | learnings | 每单必做；没有可沉淀的经验就记「无」 |

UAT 中收集到的改动建议记进 uat 记录：属于本单范围的作为返工处理，超出范围的另开工单。

## 缺陷流程

| 步骤 | 负责角色 | 产物 | 完成的定义 |
| --- | --- | --- | --- |
| 复现 | Product | 复现记录 | 按用户报告复现成功；复现不了，退回用户补充信息 |
| 定修复预期 | Product | 修复预期（记进 ticket） | 用户确认 |
| 技术方案设计（仅修复动到方案层面时） | Engineer | plan | 产物完成 |
| 技术方案评审（同上条件） | Reviewer | 评审意见 | 评审通过，用户确认定稿 |
| 编码 | Engineer | 代码，第一步先把复现固化成失败测试 | 产物完成 |
| CR | Reviewer | 评审意见 | 评审通过 |
| 测试 | Engineer | 测试记录 | 复现测试转绿；按原复现步骤操作，缺陷不再出现 |
| 发布 | Engineer | 已上线的交付物 | 按交付约定发布并验证 |
| 复盘 | 全员 | learnings | 每单必做 |

## 通用规则

- **完成要有证据**：每一步的完成都必须指向证据的位置——哪份评审意见、哪份测试记录。写不出证据在哪，就不能算完成。
- **不可逆变更先问用户**：数据迁移、对外接口变更、更换技术栈，必须先获得用户同意再继续，无论改动多小。
- **类型判错就转**：推进中发现工单类型判断错了——比如排查缺陷发现其实是需求缺失——转入正确类型的流程，已有的结论和记录带走接着用。

## 评审规则

```
         产物
作者 ──────────▶ Reviewer ──通过──▶ 通知 Team Lead，进入下一步
 ▲                 │
 └────── 打回 ─────┘
     （两轮无共识，交用户裁决）
```

- 评审由作者发起：产物写完，作者直接把它交给 Reviewer，不经过 Team Lead。
- 交给 Reviewer 的只有产物本身。作者对产物的解释和写作时的考虑一概不给——评审的价值来自独立视角，作者的辩解会污染它。
- 评审不通过，意见直接返给作者，返工和复审在两人之间循环；评审通过，才通知 Team Lead 进入下一步。
- 同一个问题两轮之后仍无共识，交用户裁决。

## 工单记录

会话上下文随时可能清空，所以工作状态必须落在持久的地方。每张工单在 `.rivo/issues/<id>/` 下建目录，id 用三到五个词的 kebab-case，工单的所有产物都住在这里（以产品需求为例）：

```
.rivo/issues/order-export/
├── ticket.md          ← 进度与每一步的结论
├── spec.md            ← 产品方案，含验收标准
├── ui-spec.md         ← 界面设计，仅界面有变化时
├── plan.md            ← 技术方案
├── reviews/           ← 历轮评审意见
├── test-report.md     ← 测试记录
└── uat.md             ← uat 记录
```

复盘后整个目录移入 `.rivo/archived/` 归档。复盘产出的经验不住工单目录——它们是跨工单资产，住全局 `.rivo/learnings/`；复盘的结论（包括「无可沉淀」）记进 ticket。

## 分支与收尾

- Team Lead 开工单时同时开分支，spec 从第一个字起就有地方提交。
- 发布时由 Engineer 把分支合入并验证。
- 发布确认后全员复盘，然后 Team Lead 提交最后一笔：learnings 落盘，`issues/<id>` 移入 `archived/`。这笔提交是纯记录性质的，走交付约定允许的最轻通道。

## 项目文档

`.rivo/` 下有三份长期维护的项目文档，方案设计和评审都以它们为依据。项目还没有这些文档时，先走 onboarding 生成：

- **PROJECT.md**：给谁用、解决什么问题、交付约定。由 Product 维护：从 README 等现成材料起草，和用户确认定稿——最终以用户说的为准。
- **ARCHITECTURE.md**：架构、代码规约、验证基建。由 Engineer 维护，依据是代码现状。
- **DESIGN.md**：设计 token、组件库、断点。由 Designer 维护，依据是设计系统。

文档和现实不符时，谁发现谁告诉维护它的角色；复盘时各维护者检查自己的文档是否需要随本单更新。

## 例子：改一行文案

用户对 Team Lead 说：「把提交按钮文案从『确定』改成『提交订单』。」Lead 判断这是产品需求，开工单。Product 评估新文案的合理性，spec 一句话加一条验收标准；评审通过、用户点头。界面无交互与视觉变化，界面设计两行不存在。Engineer 的 plan 写明影响面只有一处引用；评审通过。编码、CR、测试截图、UAT 用户看一眼、发布、复盘记「无」。每一步都走了，每一步的产物都只有一两句话——流程的重量跟着决策量缩放，而不是跟着步骤数。
