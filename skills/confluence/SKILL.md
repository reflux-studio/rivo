# 方案讨论

开始时声明：“正在使用 rivo:discussing-designs，和你讨论这次改动的目标与做法。”

用户主导目标和方向，AI 负责查证、追问、提出建议并协助落实。先理解用户已有的思路和理由，帮助其检验、补全方案；尚无方向时一起探索，不要求用户先完成设计。已有 PRD 是输入，需求理解和验收最终进入技术方案，不另写一份 Spec。

**完整方案必须展示并获得用户批准。讨论尚未收敛时，不写成最终 plan，不开始产品代码实现。** 调查实验只在允许范围内进行，结果标明是验证材料。

## 从当前问题开始

读取用户请求、PRD、现有 plan、note、ADR、评审意见和相关实现中与本次问题有关的部分。已有决定和调查继续沿用；用户只要求评审或重新讨论一个选择，就处理该问题，不重做整个需求。

展开具体方案前，先理解或询问用户是否已有思路。用户主动讲过就承接，不重复问；用户希望先读材料，就读完后再请其补充想法，不能把暂时没说当作没有方向。用户明确还没有思路或已委托 AI 提出做法时，再从目标和约束出发探索。

梳理用户的目标、方案思路、理由、不希望采用的做法和已给出的委托。简述你的理解，只追问会影响判断的缺口；已经明确的决定不重问，未说过的偏好不代填。区分已确定的选择、需要查证的前提和仍开放的问题。

采用 Rivo 完成交付时，讨论后留下技术方案和实施任务，经过相应审阅再实施。需求简单就把文档写短，不省略文档与审阅。单独讨论或评审一个问题，仍只完成用户指定的工作。

用宿主任务工具建立或沿用本次清单；没有时在会话中维护短清单：明确范围、查证现状、讨论候选、呈现完整方案、审阅和确认、交回结果。只保留本次实际要做的工作。

## 查清目标和事实

沿用户给出的思路核对它要解决的问题、本期行为变化与成功标准。PRD 有歧义或遗漏时，用具体场景讨论，不逐段翻译原文；缺少方向时，从用户的目标和约束出发提出可行做法。

加载 investigating，沿本期场景查清入口、参与方、数据变化、实际调用和结果，将机制与依据整合到 note。类型或接口存在不代表已经接入；选择复用能力前，核对输入输出、实际行为、接入条件和业务差异。

新方案带来新问题时继续调查或实验，不因“现状已经调研完”就跳过验证。证据足以回答当前问题后回到讨论，不扩大成无关的全仓扫描。技术前提与业务规则互相影响时，一起修正理解。

解释系统关系、流程或状态时，加载 using-archify，在讨论中展示现状与候选 SVG。图应帮助用户判断当前问题，不能等文档写完才补。

## 按决定的依赖展开

沿用户的思路找出决定后续判断的问题，例如审批单位、数据归属和对外责任。先查证已有方案能否成立，指出团队评审可能追问的前提、代价和失败场景。有反例或更合适的做法时，说明证据与差异，交给用户判断；不能为了采用自己的推荐而改写用户的目标。

每轮围绕一个关联问题展开，带上场景、依据、可行做法和建议，再取得决定。候选做法应包含用户提出且可行的方向，选项不是封闭菜单。用宿主提问工具交流；没有适用工具时在会话中提问。

收到回答后，回述确定的规则，更新后续问题，并用正常、拒绝、重复操作或失败恢复等相关场景检验。不能用一次问卷或固定问题轮数代替讨论。用户关闭问题、没有回答或保持沉默，都不构成批准。

重要职责、共享契约、数据含义或生命周期选择，加载 architecture-decisions 比较并记录 ADR。调查、验证、命名和普通代码细节由 AI 主动处理，不把能查明的问题转成问卷。用户明确委托 AI 选择时，在该范围内给出选择及理由；委托不扩展到未授权的重要取舍或重大不可逆操作。

方案应覆盖需求范围、功能点、整体结构、关键数据与接口、影响面、外部协作，以及适用的验证、发布和回退安排。先解决最复杂、最不确定的部分；不要详写常规接线，却把核心交互留空。

## 收敛与审阅

呈现完整方案及重要理由，明确相对现状的变化。核心规则或共同契约仍不清楚时，继续讨论或请用户调整范围；不能只列入“待确认”就宣布方案完成。用户允许延后的验证，说明验证时点和失败后的影响，不写成已经成立。

用 [方案讨论审阅提示词](references/design-reviewer-prompt.md) 启动新的独立审阅者，提供本轮完整结论、原始请求、用户决定和调查依据。报告保存到本需求的 `reviews/design-<round>.md`。审阅的是设计能否成立，不要求先存在 plan。

修复后重新审阅。涉及重要取舍的修改先与用户讨论；审阅者不能替用户决定。反复审阅没有新进展时，查清证据或将模型分歧交给用户，不能靠增加轮次推进。

向用户讲清完整方案、重要理由和审阅结果，重点解释用户尚未参与的判断、AI 补充的建议，以及仍不确定的地方。按需要理解的主题交流，给用户纠正和改变方案的机会，不用一份长文加“是否批准”代替讨论。已经明确批准的内容沿用；因审阅发生变化的部分重新说明并取得决定。用户可以一并批准方案和授权实施，不重复索取已有授权。

## 重新讨论已有方案

评审意见或实施发现改变前提时，先说明原结论、新证据和受影响的行为。按问题调用 investigating、architecture-decisions 或 using-archify，重写受影响的设计说明和图，不在旧结论后不断追加补丁。

**设计结论变化后必须重新独立审阅，并交给用户确认改变的决定。** 旧报告不能覆盖新方案。核对受影响的 plan、task、外部契约和已完成实现；通过 writing-designs、planning-tasks 更新并完成相应复审，再继续依赖这些结论的工作。仍有效的部分继续沿用，不重启整个需求。

讨论笔记和正文允许按新结构重写；已有 ADR 的历史理由和审阅报告应保留，不能改写成一直如此。

## 结果与交接

本次方案忠实表达用户意图、有可靠依据、独立审阅通过、用户批准后，按请求交回结果。继续交付时加载 writing-designs 留下技术方案，再编排实施任务；只讨论或评审，到此结束。

材料默认集中在目标项目的 `.rivo/issues/<slug>/`，沿用已有需求目录和用户指定位置。跨仓库选定一个文档目录。写作使用可用的 writing-clearly-and-concisely；没有必要的文件不预建空壳。

## 常见错误（Red Flags）

| 你在想 | 应当怎么做 |
| --- | --- |
| “用户只要最后批准就行” | 从用户的思路出发，让重要判断在讨论中形成。 |
| “用户方案有问题，我直接换成自己的” | 查证反例，讲清影响，再与用户决定。 |
| “问过一轮，方案已经明确” | 用完整场景检查尚未解决的决定。 |
| “先定稿，未知项实施时再猜” | 解决关键缺口或取得明确的范围调整。 |
| “方案简单，直接编码” | 文档可以短，方案、任务与审阅仍要完成。 |
| “评审通过过，这次变化不用再审” | 审阅当前结论及其关联影响。 |
