# 独立代码审阅

把“代码质量与规范（写得好不好）”和“需求与方案符合度（做对没有）”拆给**两名独立审阅者并行检查**，各自只看本方向需要的材料、各自出具结论。不让代码整洁掩盖需求漏做，也不让功能跑通掩盖重复实现、放宽断言或只跑 mock 而跳过真实集成的问题。

## 流程

### 1. 送审前先跑自动检查

先跑通当前代码版本的静态检查（编译、类型检查、Lint）以及单元测试、轻量集成测试，再发起代码审阅——既不浪费审阅上下文去抓低级编译或语法错误，也把测试代码与实测输出一并交由审阅者核验。

### 2. 并行委派两名独立审阅者

1. 加载 `dispatching-subagents`，按 [审阅者提示词](references/reviewer.md) **并行派发两名没有参与本次编码的独立审阅者**，按场景统一选用**单项改动模式**或**整体模式**：
   - **审阅者 A（代码质量与规范）**：只传真实代码差异（如 `git diff` 含未提交与未跟踪文件）、仓库规范、参照样板与组件库要求
   - **审阅者 B（需求与方案符合度）**：传真实代码差异、需求/设计/测试预期依据（含引用用例 `TC-xx`），以及实测命令与原始输出；不只传执行者的口头摘要
2. 两名审阅者只读不写，各自返回本方向的报告；需要归档时，由调用方汇总写入目标审阅报告（或分别保存为两份报告，避免并行写同一文件冲突）
3. 宿主缺少子代理工具时如实说明缺口，不把自我检查算作独立审阅

### 3. 核实与处理意见

按 [接收审阅意见](references/receiving-review.md) 对照真实需求、设计与代码逐条核实两份报告：

- 属实的 **P0**（需求漏做、行为错误、违反契约或组件硬约束、测试未落地、放宽断言，或只用全 mock 跳过真实集成）必须修复，重跑受影响的自动检查后交回**提出该 P0 的同一审阅者**复核（如果修复改动较大、影响另一方向关注面，一并交另一名审阅者复核），直到两个方向都无 P0
- 明确识别并拒绝为未发生扩展硬抽接口的过度设计，以及对已保证前提重复判空或加异常捕获的过度防御意见
- 缺少上下文造成的误判给出事实依据并记录；未修的 P1、P2 和拒绝理由记入交付或任务记录
