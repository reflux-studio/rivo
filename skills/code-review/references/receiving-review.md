# 接收代码审阅意见

审阅者只看到提供的 diff 和材料，可能因为缺少业务背景而误判，也可能出于习惯要求“多加一层抽象”“再判一次空”。调用方对照真实需求、已有决定和代码逐条核实，再决定修还是拒。

## 分级

| 级别 | 代码质量（A） | 需求符合度（B） | 处理 |
| --- | --- | --- | --- |
| P0 | 违反组件库或仓库硬约束、严重破坏结构、安全或稳定性隐患 | 需求没满足、行为错误、违反契约、测试没落地或验证虚假、与决定冲突 | 必须修 |
| P1 | 没复用已有组件或代码、明显重复、过度设计 | 局部边界处理不完整、影响测试可信度或文档一致性 | 默认修；代价明显高于收益时可不修，写明理由 |
| P2 | 局部瑕疵 | 局部瑕疵 | 不必修，顺手能改的改 |

两份报告都没有 P0 即为通过。没修的 P1、P2 和拒绝理由记入交付或任务记录，验收时一并交出。

## 核实与处理

对照需求、技术方案、测试方案和实际代码核实每条意见：

| 核实结果 | 处理 |
| --- | --- |
| 代码问题属实 | 按级别修复，重跑受影响的验证 |
| 任务或交付约定本身写错 | 先更正对应任务或文档约定再继续 |
| 意见暴露技术方案或测试方案有误 | 按方案修订规则从受影响的上游改起 |
| 缺少上下文造成的误会 | 拒绝，写明理由和代码或决定依据 |
| 过度设计或过度防御（见下节） | 拒绝，写明依据，不因对方标了高优先级就照改 |
| 同意问题，不同意级别 | 按核实后的级别处理，写明理由 |

## 过度设计与过度防御

用奥卡姆剃刀判断：效果相当时，保留假设更少、机制更少的写法。下面两类意见核实后直接拒绝：

- **过度设计**：要求把只有一种实现、也没有扩展计划的逻辑抽成策略工厂、通用适配器、配置开关，或者包一层只有几行的辅助函数
- **过度防御**：要求对类型已收窄的值、校验层已拦截的字段或上游契约已保证的前提反复判空、套 `try/catch`。这类代码增加噪声，还会把真实的错误吞掉

拒绝时附上调用链、类型定义或上游校验的位置。审阅者复核时仍坚持，且确实有真实的边界风险，交用户决定。

## 复核

有 P0 时，修完交回提出它的审阅者复核；修复改动较大、波及另一方向时，也交另一名审阅者看：
- 宿主支持时续用原审阅者会话，附上修复范围、拒绝的意见及理由
- 无法续用时派新的同方向审阅者，附上前轮报告，只复核修复与波及范围
- 审阅者对拒绝的意见仍然坚持，或意见涉及已有决定：交用户裁决

两个方向都复核通过为止。同一个问题反复修不好时，停下来查根因，再报给用户。
