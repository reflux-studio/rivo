# 接收代码审阅意见

执行者和审阅者只看到提供的 diff 与材料，可能因缺少业务背景提出误判，也可能出于惯性要求“多加一层抽象”或“再判一次空”。调用方对照真实需求、已有决定和代码逐条核实，再决定修还是拒。

## 分级

| 级别 | 含义 | 处理 |
| --- | --- | --- |
| P0 | 需求没满足、行为错误、契约违背、验证虚假或与架构决定冲突 | 必须修 |
| P1 | 未复用已有组件/代码、明显重复或过度抽象、影响可维护性 | 默认修；代价明显高于收益时可不修，写明理由 |
| P2 | 局部瑕疵 | 不必修，顺手能改的改 |

结论：两名审阅者的报告都没有 P0 即为通过。没修的 P1、P2 和拒绝理由记入本次交付或任务记录，验收时一并交出。

## 核实与处理

对照需求、技术方案、测试方案和实际代码核实每条意见：

| 核实结果 | 处理 |
| --- | --- |
| 代码问题属实 | 按级别修复，并重跑受影响的验证 |
| 任务或交付约定本身写错 | 先更正对应任务或文档约定再继续 |
| 意见暴露技术或测试方案有误 | 按方案修订规则从受影响的上游修订 |
| 缺少上下文造成的误会 | 拒绝，写明理由和代码/决定依据 |
| 过度设计或过度防御的建议 | 拒绝，写明真实约束、类型/契约保证或复杂度代价，不因对方标高优先级盲改 |
| 同意问题，不同意级别 | 按核实后的级别处理，写明理由 |

## 识别并拒绝过度设计与过度防御

不要为了“显得稳妥”或顺手讨好审阅者而往代码里塞多余复杂度，符合下列特征的意见核实后直接拒绝：

- **过度设计（面向未发生的扩展抽象）**：审阅者要求把当前只有单一实现、明确无扩展计划的逻辑硬抽成策略工厂、通用适配器、多余配置开关或几行包一层的空壳辅助函数
- **过度防御（重复校验与吞异常）**：审阅者要求对 TypeScript / 编译期类型已收窄的非空值、schema 校验中间件已拦截的字段或上游契约已保证的不变式反复判空、套多层无意义 `try/catch`——这不仅增加噪声，还容易把真实 Bug 吞掉掩盖掉

拒绝时附上具体调用链、类型定义或上游校验位置作为证据；如果审阅者复核时坚持且确有真实边界风险，再交需求方拍板。

## 复核

有 P0 时，修完交回提出该 P0 的原审阅者复核（若本次修复改动较大、影响另一方向的关注面，一并交另一名审阅者复核）：
- 宿主支持时续用原审阅者会话，附上修复范围、拒绝的意见及理由
- 无法续用时派新的同方向审阅者，附上前轮报告，只复核修复与波及范围
- 审阅者对拒绝的意见仍然坚持，或意见涉及已有决定：交需求方裁决

两个方向都复核通过为止。同一个问题反复修不好时，停下排查根因再报给需求方。
