# 评审界面设计文档

一份界面设计文档只有两种失败方式：照着它做出来的界面不是需求要的（场景缺失、超范围），或者照着它做不出来（状态没定义、选型没交代，工程只能猜）。评审就是在编码之前找出这两种失败。评审对象是文档；评审设计稿本身用 critiquing-designs。

## 工作流程

### 1. 建立评审依据

- 读上游输入：需求文档的场景与验收标准——界面是为它们服务的。
- 若项目里维护着长期设计文档（token、组件库、断点、业务组件清单），先读，它是选型与一致性的准绳。
- 个人偏好不构成依据。依据只有三样：上游输入、长期文档、下面的清单。

### 2. 通读抓理解

- 通读一遍后，尝试复述：这个界面给谁用、完成什么任务、由哪几块组成。
- 复述不出来，本身就是最严重的一条意见。

### 3. 逐节过检查清单

按下面的清单逐节检查。清单与界面设计文档的产出结构（见 writing-ui-specs）成对维护：那边加一节，这边加一组检查。

### 4. 组织意见与交付

按「意见的写法」（见 reviewing-specs，两边同一套写法）成文。交付形态取决于你对这份文档的位置：

- **有裁决权**（团队产物的把关评审）：给出结论——通过，或不通过附阻塞项。阻塞项清零才能通过。若这单工作有工单目录，意见存入其中的 `reviews/`。
- **无裁决权**（外来的规格文档）：同一份发现转为改进建议和澄清问题清单。

## 检查清单

### 需求覆盖

- [ ] 需求里的每个场景都有对应的界面定义吗？
- [ ] 有超出需求范围的设计吗——定义了需求里没有的东西？

### 设计稿索引与单一事实源

- [ ] 有设计稿时：每个区块都给了稿件节点链接吗？
- [ ] 有设计稿时：文档里抄了稿上能查到的值吗？抄写就是双写，稿一改文档就撒谎——标出来让它删。
- [ ] 没有设计稿时：视觉规格写全了吗？token、尺寸、断点。

### 布局与 Token

- [ ] 布局和断点与设计系统的定义一致吗？
- [ ] 引用的 token 在设计系统里真实存在吗？
- [ ] 新增的 token 写明为什么现有的不够用了吗？

### 组件选型与拆分

- [ ] 三层匹配走了吗？该用业务组件的地方自己拼了吗？该用组件库高级组件的地方用基础组件拼了吗？
- [ ] 新建组件有「为什么现有的不够用」的理由吗？该沉淀为业务组件的标了吗？
- [ ] 组件结构树和组件表对得上吗？
- [ ] 选型理由不显然的地方写了吗？

### 状态与交互

- [ ] 每个交互元素的状态全吗——默认、悬停、激活、禁用、加载、错误、空？
- [ ] 设计稿通常只画理想态：其余状态文档补齐了吗？
- [ ] 交互行为（点击、手势、过渡）定义了吗？

### 内容与边界情况

- [ ] 空状态、超长内容、截断规则定义了吗？
- [ ] 国际化文本、慢速网络、数据缺失考虑了吗？

### 响应式

- [ ] 每个断点下的行为写了吗？
- [ ] 断点与设计系统一致吗？

### 动效

- [ ] 有动效的地方，时长和缓动给了吗？

### 无障碍

- [ ] 焦点顺序、ARIA 标签、键盘交互、屏幕阅读器播报交代了吗？

### 越界检查

- [ ] 夹带代码接口了吗？Props 签名、事件类型、文件结构——那是技术方案的领地，出现即越界。

### 整体

- [ ] 概述能让没看过需求的人知道这个界面给谁用、完成什么任务吗？
- [ ] 前后自洽吗？结构树、组件表、状态表之间有没有互相打架？
- [ ] 比例失衡吗？有空节吗？

## 输出

```markdown
## 界面设计文档评审：[文档名]

### 结论
[把关：通过 / 不通过；反馈：总体评估一两句]

### 阻塞项
| # | 位置 | 问题 | 为什么 |
|---|------|------|--------|
| 1 | [节/条] | [描述] | [依据与后果] |

### 建议项
| # | 位置 | 建议 | 理由 |
|---|------|------|------|

### 澄清问题（反馈场景）
1. [问题] —— [为什么需要答案]

### 可靠的部分
- [确认没问题的节，一句话]
```

## 注意事项

- 评审产出意见，不产出修改——改是作者的事。
- 状态完整性是界面文档最常见的窟窿——设计者眼里只有理想态，逐个交互元素数一遍状态。
- 「这个设计好不好看」不在清单里——视觉品质的反馈走 critiquing-designs，对着稿说；这里只审文档能不能指导施工。
