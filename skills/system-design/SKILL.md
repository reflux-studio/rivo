# 编写技术方案

技术方案写清架构边界、核心模型和关键契约，篇幅控制在十分钟内读完。只写需要协作和拍板的设计，不把现状排查、方案辩论或界面细节搬进来。

## 流程

### 1. 核对事实与参照样板

- 先读原始需求、PRD、已确认的决定和调查结论；缺少会影响架构的工程事实时，先查清依赖的实际行为和接入条件
- 确认后端参照哪个已有模块或服务、前端参照哪个已有页面和组件库，写进方案的整体设计
- PRD 里已写明的按钮显隐、提示文案和常规表单校验留在 PRD，不搬进方案

### 2. 编写方案

- 按 [技术方案模板](references/plan-structure.md) 组织，写入调用方或项目指定的位置（默认 `plan.md`）；团队有自己的模板时用团队的
- 从第一性原理出发：先问这个问题本身该怎么解，再看现有做法和既定思路要不要沿用
- 用奥卡姆剃刀取舍：效果相当时选假设更少、机制更少的做法。要新增服务、抽象层或同步机制，先和最简单的直接做法比一比，写清为什么必须加
- 按高内聚、低耦合划分模块：每块职责单一，依赖方向清楚
- 没有变化的章节直接略过；已有接口只是照常调用或微调时，一行写清路径、用途和变化
- 写明本方案最脆弱的一条假设

### 3. 送审前自查

- 范围里的每个模块和已确认的决定是否都有对应设计
- 主场景、失败场景、异步时序和上线当天的初始数据能否走通
- 参照样板、组件库约定和跨系统契约是否写清楚
- 正文有没有混入排查过程、辩论记录或 PRD 的界面细则
- 图、表、示例是否与正文一致，同一份定义是否只维护一处

自查不能代替独立审阅。

### 4. 独立审阅

首次定稿前做一次全量独立审阅，之后的局部修订由用户直接确认，不再重审：

1. 加载 `dispatching-subagents`，按 [审阅提示词](references/reviewer.md) 派一个没有参与编写的审阅者
2. 按 [接收审阅意见](references/receiving-review.md) 逐条核实；属实的 P0 在原处改写，交同一审阅者复核
3. 宿主没有子代理工具时如实说明，不把自查算作独立审阅

交付方案时附一段简短说明：方案怎样落实了已有决定、参照了哪处现有实现、没修的 P1 和 P2 及拒绝理由，以及方案最依赖的前提假设。
