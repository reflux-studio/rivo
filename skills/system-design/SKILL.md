# 编写技术方案

技术方案用来写清架构边界、核心模型和关键契约，篇幅控制在十分钟内读完。只写清楚需要协作与拍板的设计，不把现状排查流水、辩论过程或界面细节搬进来。

## 流程

### 1. 核对事实与参照样板

- 先读原始需求、PRD、已确认的决定和调查结论；缺少会影响架构的工程事实时，先查清依赖的实际行为与接入条件
- 确认后端参照哪个已有模块或服务、前端参照哪个已有页面及组件库，写进方案的整体设计，避免实施时重新造轮子
- PRD 里已经写明的按钮显隐条件、提示文案和常规表单校验留在原 PRD，不搬进技术方案

### 2. 编写方案

- 按 [技术方案模板](references/plan-structure.md) 组织，写入调用方或项目指定的位置（默认 `plan.md`）；团队有自己的模板时用团队的
- 控制篇幅，没有变化的章节直接略过；已有接口如果只是照常调用或微调，一行写清路径、用途和变化即可
- 如果要新增服务、抽象层或同步机制，先对比最简单的直接做法说明为什么有必要，并写明本方案最脆弱的一条假设

### 3. 送审前自查

- 范围里的每个模块和已确认决定是否都有对应设计
- 主场景、失败场景、异步时序和上线当天的初始数据能否走通
- 参照的样板代码、组件库约定和跨系统契约是否写清楚
- 正文有没有混入现状排查过程、方案辩论流水或 PRD 里的界面细则
- 图、表、示例是否与正文一致，同一份定义是否只维护一处

自查不能代替独立审阅。

### 4. 独立审阅

首次定稿前做一次全量独立审阅。之后的局部修订由决策方直接确认，不再重审：

1. 可加载 `dispatching-subagents`，按 [审阅提示词](references/reviewer.md) 派一个没有参与方案编写的独立审阅者检查
2. 按 [接收审阅意见](references/receiving-review.md) 逐条核实：属实的 P0 在原处改写并交同一审阅者复核；明确识别并拒绝为未发生的需求提前抽层的过度设计，以及为已保证前提重复加校验的过度防御意见；未修的 P1、P2 说明原因
3. 宿主缺少子代理工具时如实说明缺口，不把自我检查算作独立审阅

交付方案时一并交出简短说明：方案怎样落实了已有决定、参照了哪处现有实现、没修的 P1/P2 与拒绝理由，以及方案最依赖的前提假设。
