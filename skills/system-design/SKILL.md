# System Design

形成工程师能理解、协作方能依赖的技术方案，详细程度与当前交付范围匹配。

## 落到现有工程

理解目标、已作出的选择和已有能力。核查可复用模块的实际语义，不能只凭名称判断复用。说明新增、修改和复用的能力，以及各自职责；有必要时落实到组件、模块和目录。

重要架构选择未定时，先比较选择或标明其影响，不用详细方案掩盖缺失的决定。

## 明确契约

根据协作需要描述接口、事件、组件和数据边界：输入输出、前置条件、成功含义、失败与重试、权限、幂等和一致性保证。只讨论适用维度，但不能把契约缩减为类型定义。

说明数据由谁持有、何时改变、是否保留历史，以及跨边界变化怎样传递。检查正常行为和会改变结果的边界场景。

让协作方能据此独立实施和验证。内部算法、辅助函数和逐行代码留给实现，除非某个机制是契约成立的关键。

## 让方案可以评审

把变化、依据、重要取舍、协作依赖和未决事项放在容易找到的位置。使用示例或图帮助读者判断，不重复已有材料。

邀请用户和相关负责人关注业务后果、责任划分和关键机制。保留已明确的决定与授权，不把整理文档变成重复审批。

明确兼容、迁移、发布次序和必要的回退方式。以当前切片为单位细化实施，远期部分保留边界和依赖，不预写大量可能失效的实现代码。

## 保持协作承诺

使用已有方案、接口文档或其他合适载体。契约可以调整，但要说明原因、影响和过渡办法；仅改变内部实现时不必重写整份方案。

发现业务概念或架构假设不成立时，回到相应问题修正，再更新受影响的设计。方案的价值是支持判断和协作，不是覆盖所有实现细节。

使用 [技术方案模板](references/system-design.md) 作为可评审的起点，删去无关部分或沿用团队模板。重点补足协作方会依赖的信息，内部细节按证明契约所需的程度展开。
