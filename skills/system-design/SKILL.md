# System Design

让工程师读完能够判断改动、依据、影响和可行性，并能据此协作实施。

## 承接需求和决定

使用已有需求与交互约定、ADR 和现状依据，不重复询问已确认内容。关键行为或方向未定时，说明缺口并先讨论；不要用详尽的实现设计掩盖缺失的前提。

开始时识别当前需要打磨的问题和依赖。事实不足就继续调查，重点核实准备复用的能力、调用方、业务差异和集成条件。接口存在或名称相似不足以证明复用可行。

## 分段形成设计

先讲总体做法和主要改动，再按问题依赖展开组件、数据流、接口及运行机制。每段交代具体对象、改动理由、影响面和未决项，邀请用户判断尚未确定的取舍，确认或获委托后继续依赖部分。

不靠一次生成完整文档替代协作。小而明确或已有充分决定的任务可以直接整理；没有未决选择时不为章节逐项求批。草稿可随讨论保存，结论变化时更新相关内容。

重要结构选择需要比较可行方案并保留理由；实施细节在已经确定的边界内展开。设计发现业务含义或架构假设不成立时，回到具体问题，更新受影响的决定。

## 讲清改动与保证

用页面、组件、模块、接口和字段的实际名称说明新增、修改、复用和迁移。解释契约的行为含义：何时可调用、成功表示什么、数据何时生效，以及相关的失败、重试、权限和兼容处理。

关键机制写到足以判断保证能否成立；内部函数和逐行实现留给编码。远期部分保留边界和依赖，当前切片细化到可实施。明确验收、联调、发布依赖和适用的回退方式。

流程或结构对比有助于决策时，使用可用的 Archify 技能；沿用相同概念和标识，展示现状、目标与变化理由。没有工具时用图表或文字完成。图、原型与实际实现的证据分别标明。

## 组织技术方案

使用统一的 [技术方案模板](references/system-design.md)，或映射到团队已有格式。根据调查得到的影响范围裁剪，不能根据当前仓库或执行者职责提前排除其他系统。只负责一部分实现时，仍说明外部能力、契约和未决依赖。

详细设计按实际模块展开。复杂部分可拆附属文档，主方案保留完整流程、共同决定、协作契约与交付安排，避免重复定义需求和接口。接口字段以既有权威来源维护，方案解释关键语义和理由。

## 写得可判断

先给结论，再给依据。以“把共用区块移到通用层，两条业务线调整引用并回归”这样的具体表达代替“增强复用能力”。未查证的结论写成有条件的判断，并指出确认方式。

完整方案由讨论结果整理而成。记录已确认和仍待决定的部分，便于团队评审；团队的新意见同步到相应需求、ADR 或设计，保留重要变化的理由。

## 后续衔接

方案足以指导实施且已有实施授权时，使用 [incremental-delivery](../incremental-delivery/SKILL.md) 拆分任务并交付。行为前提不清楚时回到 [requirements-clarification](../requirements-clarification/SKILL.md)，重要取舍变化时回到 [architecture-decisions](../architecture-decisions/SKILL.md)，独立部分继续推进。只要求设计时交付方案及未决项，不自动进入实施；长任务同步当前阶段、结论与下一步到已有进度记录。
