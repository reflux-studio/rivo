# 接收技术方案审阅意见

独立审阅者依据有限材料挑刺证伪，既能发现真实的设计漏洞，也可能因缺少业务规模约束或出于保守习惯提出过度要求。调用方对照原始需求、已确认决定、ADR 与工程现状逐条核实，再决定改还是拒。

## 分级

| 级别 | 含义 | 处理 |
| --- | --- | --- |
| P0 | 照方案做会做错或做不下去；核心假设不成立；遗漏需求；与 ADR 或决定冲突 | 必须修 |
| P1 | 明显过度设计、漏写参照样板或影响评审与联调质量 | 默认修；代价明显高于收益时可不修，写明理由 |
| P2 | 局部瑕疵，不影响理解和执行 | 不必修，顺手能改的改 |

结论：没有 P0 即为通过。没修的 P1、P2 与拒绝理由在交付方案时一并向需求方说明。

## 核实与处理

回到技术方案、决定记录、ADR、调查笔记与代码事实核实每条意见：

| 核实结果 | 处理 |
| --- | --- |
| 设计漏洞或事实错误属实 | 按级别在原处改写受影响段落，不留纠错补丁句，并检查波及的图与表 |
| 缺少上下文造成的误会 | 拒绝，写明决定编号或调研证据 |
| 过度设计或过度防御的建议 | 拒绝，写明当前规模、成本与上游契约依据，不因对方标了高优先级就盲目采纳 |
| 需要补定核心决定或改范围 | 停下提交给需求方拍板后再更新方案 |
| 文字引发歧义，设计本身没错 | 改清原句表述，设计不变 |

## 识别并拒绝过度设计与过度防御

审阅意见只要符合以下两类特征，核实后直接拒绝，不放进方案制造多余复杂度：

- **过度设计**：要求在当前业务规模和明确范围内额外抽离抽象层、插件化扩展点、独立消息队列、配置开关或多层中转服务，且没有本期必须成立的多态或异步诉求支撑
- **过度防御**：要求针对类型系统、基础设施强约束或上游接口契约已经明确保证不会发生的情形，在方案里堆叠重复校验、双重补偿任务或低收益容错链路

拒绝时写明“为什么以当前规模与契约无需这套机制”，而不是含糊敷衍；如复核时审阅者坚持认为这里存在真实风险取舍，交给需求方裁决。

## 复核

有 P0 时，修完交给同一个审阅者增量复核：
- 宿主支持时续用原审阅者会话，附上修改内容、被拒绝的意见与理由，只复核改动和波及范围
- 无法续用时派新的独立审阅者，附上前轮报告与本次改动说明
- 复核结论追加到同一份审阅报告末尾，直到无 P0 通过

## 需求方与团队评审意见

方案提交需求方或团队评审带回的意见，先核对涉及的代码行为与真实约束（查不清时先补充调查），整理核实结果和建议交给需求方决定；其他同事的建议在获得拍板前不直接改写进方案。
