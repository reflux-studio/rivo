# 接收技术方案审阅意见

审阅者只凭有限的材料挑错，能发现真实的设计漏洞，也可能因为不了解业务规模，或出于保守习惯，提出过度的要求。调用方对照原始需求、已确认的决定、ADR 和工程现状逐条核实，再决定改还是拒。

## 分级

| 级别 | 含义 | 处理 |
| --- | --- | --- |
| P0 | 照方案做会做错或做不下去；核心假设不成立；遗漏需求；与 ADR 或决定冲突 | 必须修 |
| P1 | 明显过度设计、漏写参照样板，或影响评审与联调 | 默认修；代价明显高于收益时可不修，写明理由 |
| P2 | 局部瑕疵，不影响理解和执行 | 不必修，顺手能改的改 |

没有 P0 即为通过。没修的 P1、P2 和拒绝理由在交付方案时一并说明。

## 核实与处理

回到方案、决定记录、ADR、调查笔记和代码核实每条意见：

| 核实结果 | 处理 |
| --- | --- |
| 设计漏洞或事实错误属实 | 按级别在原处改写受影响的段落，不留纠错补丁句，并检查波及的图和表 |
| 缺少上下文造成的误会 | 拒绝，写明决定编号或调查证据 |
| 过度设计或过度防御（见下节） | 拒绝，写明当前规模、成本和上游契约依据 |
| 需要补定核心决定或改范围 | 停下来交用户决定，再更新方案 |
| 设计没错，文字引起歧义 | 改清原句，设计不变 |

把 P0 挪进待决事项不算修复。

## 过度设计与过度防御

用奥卡姆剃刀判断：满足本期需求的前提下，机制越少越好。下面两类意见核实后直接拒绝：

- **过度设计**：在当前规模和范围内，要求额外加抽象层、插件扩展点、消息队列、配置开关或中转服务，而本期并没有必须成立的多态或异步需求
- **过度防御**：类型系统、基础设施约束或上游契约已经保证不会发生的情况，要求再加重复校验、补偿任务或容错链路

拒绝时写明为什么在当前规模和契约下不需要这套机制。审阅者复核时仍坚持，且确实涉及风险取舍，交用户决定。

## 复核

有 P0 时，修完交给同一个审阅者增量复核：
- 宿主支持时续用原审阅者会话，附上修改内容、被拒绝的意见与理由，只复核改动和波及范围
- 无法续用时派新的审阅者，附上前轮报告与本次改动说明
- 复核结论追加到同一份报告末尾，直到没有 P0

## 用户与团队的评审意见

方案交用户或团队评审后带回的意见，先核实涉及的代码行为和真实约束（查不清时先补调查），把核实结果和建议交给用户决定。同事的建议在用户采纳前不写进方案。
