# 技术方案探索

在写方案之前把方向聊定：对比选型、评估可行性、推演思路、指出风险。这是对话式的探索，产出决策和依据；正式文档是 writing-plans 的事。

## 四种场景

- **选型对比**：「事件总线用 Kafka 还是 SQS？」——命名选项、维度对比、给出倾向与理由。
- **可行性评估**：输入一份需求（常见是外来的 PRD），回答「可行 / 不可行 / 能做但代价是什么」，附风险与替代建议。
- **思路推演**：需求已定但实现路径不清晰，把可能的路子摆开，收敛到一条。
- **评估既有方案**：「看看这份微服务拆分」——逐项检查，产出评估意见；作者是外人时，意见以建议和澄清问题的形态给出，不是裁决。

## 工作流程

### 1. 框定问题

- 约束先行：时间、预算、技术栈、团队熟悉度——「两周内要上线」「必须扛住 10K rps」这类约束塑造答案，开头就问明。
- 明确这次要收敛到什么：一个选型？一个可行性结论？一条实现路线？

### 2. 摸清现状

- 相关模块现在怎么工作，已有哪些模式和基线。
- 若项目里维护着长期架构文档，先读它；发现文档和代码不一致，以代码为准。
- 若已连接知识库，搜索既往的设计文档和决策记录，不要推翻早已论证过的结论。

### 3. 展开选项

- 至少两个命名的选项，即使已有倾向——「不做改动」也常常是合法选项。
- 对每个选项做维度评估：复杂度、成本、可扩展性、团队熟悉度、可维护性。
- 影响面过一遍：波及哪些模块和数据、是否触及不可逆变更（数据迁移、对外接口、技术栈更换）。

### 4. 对抗自检

- 对着倾向的选项问：反对它最强的理由是什么？什么条件下它是错的？
- 找出结论依赖的最脆弱假设，以及验证它最便宜的方式：读一段代码、跑一个 spike、查一份文档。
- 评估外来方案时同样适用：先找它成立的理由，再找它塌掉的条件，两边都写。

### 5. 收敛与记录

- 给出明确的倾向和理由，不要罗列利弊让人自己挑。
- 结论与关键依据落进工单或对话记录；方向定了要成文时，交给 writing-plans——这里的对比结论直接喂给它的「取舍与备选」节。
- 需要用户拍板的事项（不可逆变更、显著的成本量级）单独标出来。

## 可行性评估的输出

- **结论三选一**：可行 / 不可行 / 可行但代价是……
- **依据**：现状约束、影响面、主要风险。
- **替代建议**：降级方案、分期路线、更便宜的八成解。

## 注意事项

- 探索阶段不写正式文档——产出是决策，成文是 writing-plans 的事。
- 别太快收敛：第一个可行的方案往往不是最好的，至少推演一个反直觉的选项。
- 结论要经得起追问：每个倾向都带着「为什么」和「什么情况下该重新考虑」。
- 「能做」不是唯一诚实的答案——技术上可行但代价失衡时，把代价说透就是你的价值。
