# 调查与笔记

从实际入口追到结果，用能区分真假的证据回答问题，把查明的机制和依据按主题写进调查笔记。

这项工作可以由当前会话直接做，也可以交给子代理独立完成。交给子代理时，只需告诉它资料目录和要回答的问题；查阅已有资料、查证代码和更新笔记都由执行调查的一方完成。

## 流程

### 1. 确定问题与查阅已有资料

先明确本次要回答什么问题、答案会影响哪个判断，以及允许调查的范围。

动手查代码前先看已有沉淀：
- 项目的知识库或架构文档
- 调查目录（默认 `research/`）中已有的笔记

如果已有文档覆盖了该问题，核实它与当前代码是否一致。读过项目知识库时，记下所读版本（提交号或修改时间），方便后续对照。

### 2. 沿行为查证

- 从入口追到结果，检查调用方、数据变化、配置、存储和失败路径
- 找到类型、接口或文件不代表能力已经接通，要看实际调用链
- 准备复用已有接口、服务或组件前，先核对它的输入输出、实际行为和接入条件
- 涉及界面改动时，对照设计稿和项目实际使用的组件库、同类页面，列出设计元素分别对应哪个现有组件、哪处样板代码，哪些确实需要新建
- 区分文档声明、代码推断、模拟实验和真实运行；证据冲突时回查来源和版本

### 3. 结束调查

- 能回答问题并说明限制，就结束调查
- 仍有缺口时，说明影响和下一项有效检查，不扩大成全仓扫描
- 为验证假设写的实验代码或临时脚本用完即删，不留作正式实现

### 4. 更新调查笔记

- 位置：调用方或项目指定的位置优先，默认放在 `research/<主题>.md`
- 结构：按 [调查笔记模板](references/note-structure.md) 组织
- 按被调查的对象（系统、协议、机制或页面组件映射）分文件，不按日期建文件
- 命中已有主题时，直接在原文件改写受影响的内容，不另建新文件，也不按日期追加流水
- 一次性的排障日志、抓包数据和对比输出与长期调查笔记分开存放，不混入 `research/`

### 5. 报告结论

返回三件事：
- 直接结论和关键依据
- 尚未查明的部分
- 哪些已有认识需要更正

如果新证据与已有的设计结论或已写好的代码冲突，报告原结论、新证据和具体影响，不擅自改写方案或产品代码。
