# 调查与笔记

开始时声明：“正在使用 rivo:investigating，查清这个问题并更新调查笔记。”

围绕当前问题建立可复用的认识。调查结果应解释实际机制、适用范围和依据，维护到同一份 note 中。技能提供调查方法，不承担需求定稿或实施授权，也不另建阶段清单。

## 确定问题与已有认识

先说明需要回答什么、答案会影响哪个判断，以及允许调查的项目和操作范围。读取 note、已有项目知识和相关资料，核实已有结论是否适用于本次问题。PRD、代码、运行结果和他人建议各自提供不同证据，不互相代替。

调查可以发生在任何阶段。已有事实直接沿用；新候选方案需要新验证时，明确假设、输入与预期结果。用户只要求查证时，返回发现和笔记，不自动开始设计或改业务代码。

## 沿行为查证

从实际入口追到结果，检查调用方、数据变化、配置、存储和失败路径。找到类型、接口或文件不等于该能力已经接入。要复用一项能力时，核对输入输出、实际行为、接入条件和业务差异。

用能够区分假设成立与否的场景验证。分别说明代码推断、实验观察和真实运行结论；静态分析不能冒充真实联调。证据冲突时回查来源和版本，不能只选择最方便推进的一条。

小问题直接查证，需要独立探索时读取 [调查委派提示词](references/investigation-prompt.md)，提供已有认识、明确缺口和允许范围。子代理返回证据，由当前笔记维护者核对并整合，避免多人分别追加矛盾结论。

能够回答问题且说明限制后结束；仍有缺口时说明影响和下一项有效检查，不扩成无关的全仓扫描。调查建议不等于用户决定，实验代码也不自动成为正式实现。

## 像专题 Wiki 一样组织 note

按本需求涉及的机制或问题组织，例如“字段转换”“附件存储”“SDK 接入”“配置生效”。每个主题从职责和结论开始，再说明运行链路、数据与配置、边界、依据与待核实项。

```markdown
# <主题或需求>：调查笔记

## 调查范围
本次关心的系统、问题和适用版本。

## <机制或问题>
当前认识：负责什么，实际怎样工作。
关键链路与契约：入口、调用、数据与配置，必要时使用图和字段表。
适用边界：已验证到哪里，哪些是推断或尚未确认。
依据：代码、配置、实验或运行结果及其适用版本。
待核实：尚缺什么证据，它会影响哪个判断。
```

按主题写完整句子，链接放在对应主题末用于追溯。字段一行一个，单元格保持短句，解释放在表外。需要图示时加载 using-archify；写作继续使用可用的 writing-clearly-and-concisely。

不按日期罗列“今天读了哪些文件”，不为每次调查另建报告，不照搬整仓目录或会议流水。note 保存项目机制和验证结论，目标方案写进 plan，实施安排写进 task，重要取舍写进 ADR。

## 更新与检验

有新发现时先读当前主题，重写受影响的说明、表和图。原结构不适合时可以重新组织整份笔记；清除失效断言，仍适用于其他版本的结论保留其范围。历史证据单独留存，不把前后矛盾的说法堆在一起。

每次更新后重新核对结论与原始证据，检查相关主题有无冲突，说明哪些原认识被改变。调用方据此重新审阅受影响的设计、方案、任务或实现，不能把“笔记已更新”当作它们仍然有效的证明。

需要改变业务含义或重要选择时，把原结论、新证据与影响交回 discussing-designs 或当前协作者；未获决定不修改目标承诺。可供其他需求复用的事实，通过 knowledge-management 合入已有项目知识，避免维护两份相同 Wiki。

## 保存与返回

默认保存到目标项目的 `.rivo/issues/<slug>/note.md`。沿用当前需求的目录；独立调查使用 `.rivo/issues/<topic>/note.md`，用户或项目指定位置优先。已有笔记原位维护，跨仓库集中保存，写入时再创建目录。

返回直接结论、关键依据、尚未查明的部分，以及哪些已有材料需要修订。只完成当前调查，不自行宣布方案通过或推进交付阶段。
