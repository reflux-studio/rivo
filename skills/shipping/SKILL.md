# 发布

按清单发布改动：发布前逐项核对，执行发布，发布后验证，回滚条件在发布前定好。

## 工作流程

### 1. 读交付约定

- 若项目里维护着长期文档记有交付约定（怎么合分支、走不走 PR、CI 有什么要求、发布到哪），照它执行。
- 没有成文约定的，问一次用户，把答案沉淀下来，下次不再问。

### 2. 发布前核对

逐项过，不跳：

- [ ] 全量测试通过，CI 是绿的（若已连接 CI，引用这一次的流水线结果）。
- [ ] 代码评审通过，测试与 UAT 都已放行。
- [ ] 发布放行已获用户确认。
- [ ] 有数据库迁移的：迁移在非生产环境验证过，有回退脚本。
- [ ] 有 feature flag 的：开关状态确认过，默认值正确。
- [ ] 回滚方案写好了——**在发布之前决定什么情况下回滚，不在出事之后现场讨论**。

### 3. 执行发布

- 按交付约定合入分支、走发布通道。
- 有 staging 的先发 staging，冒烟验证再上生产；支持灰度或金丝雀的优先用。
- 发布后立即验证：关键用户路径手动走一遍；若已连接监控，观察错误率与延迟一段时间（十五分钟量级），确认与发布前基线一致。

### 4. 发布后收尾

- 确认指标平稳，没有新增报错。
- 更新变更记录（changelog 或 release note，按项目惯例）。
- 发布结果和验证证据记录在案；关联的工单收口。

### 5. 触发回滚时

- 命中预先写好的回滚触发条件——错误率超阈值、关键路径失败——立即执行回滚，不恋战。
- 回滚本身也要验证：确认系统回到发布前的状态。
- 回滚后的问题排查走 systematic-debugging，修好重新走发布流程，不打补丁硬顶。

## 产出结构

发布记录是过程性记录：结论与证据（流水线链接、验证结果）记进工单的进度，changelog 或 release note 按项目惯例发布，不在工单目录新设文件。

```markdown
## 发布记录：[版本或工单名]

**时间：** [时间]　**通道：** [直推 / PR #n / 流水线链接]

### 核对
- [x] 测试全绿：[CI 链接]
- [x] 评审 / 测试 / UAT 放行
- [x] 用户确认发布

### 验证
- 关键路径：[走查结果]
- 监控：[错误率与延迟，对比基线]

### 回滚预案
- 触发条件：[错误率 > X% / 关键流程失败]
- 回退方式：[revert 提交 / 切回旧版本 / 迁移回退脚本]
```

## 注意事项

- **每次发布都跑核对清单**，包括「就改了一行」的发布——清单防的就是「我忘了」。
- 「合并了」不等于「发布完成」；发布完成的定义是**上线并且验证过**。
- 若已连接源码托管，核对本次发布包含的改动清单，确认没有夹带预期之外的提交。
- 交付约定一旦成文，本技能永远照约定执行；想改约定是另一件事，和用户明确后更新文档。
