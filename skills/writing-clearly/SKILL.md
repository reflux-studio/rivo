# 写清楚

开始时声明："正在使用 rivo:writing-clearly，把这段文字写到读者能直接读懂。"

**核心原则：** 读者手里只有这段文字，读完就能理解和行动。读者是人还是模型都一样：模型从人类文字中学会阅读，写不清楚的东西它同样会读错。

## 按体裁选形式

| 体裁 | 例子 | 形式 |
| --- | --- | --- |
| 解释 | plan.md、知识库、ADR 的理由 | 连贯段落，讲清前因后果 |
| 操作 | 技能流程、审阅提示词、部署步骤 | 编号步骤，每条讲一件事 |
| 对照 | 字段、参数、配置项、错误码 | 表格，一行一个对象 |

解释型内容：
- 一段讲一件事，第一句说出结论，后面给理由和细节
- 段落之间有因果或先后，读者不用自己补连接词
- 项目符号只用于真正并列、互不依赖的短条目

操作型内容：
- 每一步是一个能完成的动作
- 不直观的规则带半句原因，让读者能处理没写到的情况
- 原因只写半句，不展开成段落

表格：
- 单元格只写短语
- 原因和例外写在表旁

## 句子

以下几条改编自 Strunk 的 *The Elements of Style*，只保留适用于中文的部分：
- **主动、正面地说**：写"订单超时后系统原路退款"，不写"退款操作将会被执行"
- **只在读者确实会误入时写"不要"**：其余情况把该怎样做写清楚
- **具体**：写"30 分钟""每分钟一次"，不写"一段时间""定期"
- **删掉多余的词**："进行处理"写成"处理"
- **并列的内容用相同句式**
- **术语第一次出现时解释**，全文用同一个名字叫同一个东西

## 引用与代码

- 路径、代码位置和出处放进引用块，写在相关段落之后，不打断句子
- 同一份定义只用一种形式给出，不同时用表格、JSON 和伪代码重复
- 可复制的配置不含未说明的占位值

## 图

图是嵌入 Markdown 的 SVG：
- 画图用 archify 技能；宿主没有 archify 时，按 [手写 SVG](references/hand-drawn-svg.md) 画
- 图源和 SVG 存在一起，在对应段落用相对路径嵌入
- 替代文字概括图的结论，例如 `![审批以模板为单位，全部通过后活动归档](assets/approval/after.svg)`
- 结构、流程或状态有变化时，画 before 和 after 两张图，同一对象位置相近，读者只看变化的部分
- before 只画核实过的对象和关系
- 只读正文也能理解；不用 ASCII 图，中文下会错位
- 画完打开看一眼：文字溢出、连线遮挡，只有看了才知道

## 去掉 AI 腔

写完后按 [AI 腔清单](references/ai-patterns.md) 过一遍，改掉命中的句子。

## 修订

修订后的文本只陈述当前的做法，读起来像第一次就写对了：
1. 删除错误的内容，在原处重写受影响的段落、表格和图；结构不合适时重写整节
2. 被放弃的做法只在读者确实需要知道时，作为理由写进取舍说明或 ADR
3. 批量替换或改名后，全文搜索旧说法

## 对照示例

解释型内容，笔记体：

```markdown
## 订单超时
- `ORDER_TIMEOUT=30m`，见 `config/order.yaml`
- `closeExpired()` 每分钟扫 `status=PENDING`
- 关闭后释放库存（`stock.release`）
- 注意：支付回调晚到 → 退款
```

每一行都是真的，但读者不知道 30 分钟从什么时候算，为什么晚到的回调要退款而不是恢复订单。

连贯写法：

```markdown
## 订单超时

买家下单后有 30 分钟付款时间，从订单创建时算起。后台每分钟扫描一次待支付订单，把超时的关闭并释放库存，这批商品立即可以再售。

关闭之后仍可能收到支付成功的回调，因为支付渠道的通知最多会晚到几分钟。此时库存可能已经卖给别人，恢复订单无法保证有货，所以统一原路退款并通知买家。

> 配置：`config/order.yaml` 的 `ORDER_TIMEOUT`；实现：`closeExpired()`、`stock.release`
```

## 常见错误

| 你在想 | 应当怎么做 |
| --- | --- |
| "审阅说这句有歧义，补一句说明" | 重写原句，让它本身没有歧义。 |
| "加一句'不要……'防止误解" | 把正面的规则写清楚。 |
| "列成要点更清楚" | 先看体裁：解释写成段落，操作写成步骤。 |
| "给模型看的，写得机械点没关系" | 模型读错的地方和人一样，照样写清楚。 |
| "图已经画了，正文可以省" | 正文独立成立，图帮助理解。 |
