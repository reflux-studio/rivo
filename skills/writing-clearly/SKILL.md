# 写清楚

开始时声明："正在使用 rivo:writing-clearly，把这份文档写成人能从头读懂的样子。"

**核心原则：** 一个没参与讨论的读者，手里只有这份文档，从头读到尾能读懂：做什么、为什么、怎样验证。

## 句子和段落

以下几条改编自 Strunk 的 *The Elements of Style*，只保留适用于中文的部分：

1. **一段讲一件事。** 第一句说出这段的结论，后面给理由和细节。段落之间有因果或先后，读者不用自己补连接词。
2. **主动、正面地说。** 写"订单超时后系统原路退款"，不写"退款操作将会被执行"。规则写成该怎样做；只有读者确实会误入的做法，才写不该怎样。
3. **具体。** 写"30 分钟""每分钟一次""回调最多晚到几分钟"，不写"一段时间""定期""可能存在延迟"。
4. **删掉多余的词。** "进行处理"写成"处理"，"实现了对订单的关闭"写成"关闭订单"。
5. **并列的内容用相同的句式。**
6. **术语第一次出现时解释**，全文用同一个名字叫同一个东西。

## 形式

- **段落是主体。** 项目符号只用于真正并列、互不依赖的短条目。
- **要对照查阅的内容集中成表：** 字段、参数、配置项、错误码，一行一个对象。单元格只写短语，原因和例外写在表旁的段落里。
- **路径、代码位置和出处放进引用块，** 写在相关段落之后，不打断句子。
- **代码块要增加信息。** 同一份定义只用一种形式给出；可复制的配置不含未说明的占位值。

## 图

图是嵌入 Markdown 的 SVG。图源和 SVG 存在一起，在对应段落用相对路径嵌入，替代文字概括图的结论：

```markdown
![审批以模板为单位，全部模板通过后活动归档](assets/approval/after.svg)
```

- 画图用 archify 技能。宿主没有 archify 时手写 SVG，用 `prefers-color-scheme` 适配明暗主题。
- 结构、流程或状态有变化时，画 before 和 after 两张图。同一对象在两张图里位置相近，读者只看变化的部分。
- before 只画核实过的对象和关系。
- 只读正文也能理解。不用 ASCII 图，中文下会错位。

## 去掉 AI 腔

写完后按 [AI 腔清单](references/ai-patterns.md) 过一遍，改掉命中的句子。

## 修订

修订后的文本只陈述当前的做法，读起来像第一次就写对了：

1. 删除错误的内容，在原处重写受影响的段落、表格和图；结构不合适时重写整节。
2. 被放弃的做法只在读者确实需要知道时，作为理由写进取舍说明或 ADR。
3. 批量替换或改名后，全文搜索旧说法。

## 对照示例

同一段内容，笔记体：

```markdown
## 订单超时
- `ORDER_TIMEOUT=30m`，见 `config/order.yaml`
- `closeExpired()` 每分钟扫 `status=PENDING`
- 关闭后释放库存（`stock.release`）
- 注意：支付回调晚到 → 退款
```

每一行都是真的，但读者读完不知道 30 分钟从什么时候算，为什么晚到的回调要退款而不是恢复订单。

连贯写法：

```markdown
## 订单超时

买家下单后有 30 分钟付款时间，从订单创建时算起。后台每分钟扫描一次待支付订单，把超时的关闭并释放库存，这批商品立即可以再售。

关闭之后仍可能收到支付成功的回调，因为支付渠道的通知最多会晚到几分钟。此时库存可能已经卖给别人，恢复订单无法保证有货，所以统一原路退款并通知买家。

> 配置：`config/order.yaml` 的 `ORDER_TIMEOUT`；实现：`closeExpired()`、`stock.release`
```

## 常见错误

| 你在想 | 应当怎么做 |
| --- | --- |
| "审阅说这句有歧义，补一句说明" | 重写原句，让它本身没有歧义。 |
| "加一句'不要……'防止误解" | 把正面的规则写清楚。 |
| "列成要点更清楚" | 有因果和先后的内容写成段落。 |
| "图已经画了，正文可以省" | 正文独立成立，图帮助理解。 |
