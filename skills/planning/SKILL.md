# 做技术方案

把一个明确的目标做成能直接施工的技术方案。三步：确定目标 → 做调研 → 写方案。

## 确定目标

方案回答「怎么做」，前提是「做什么」已经清楚。目标有什么用什么：需求规格（spec，前端再加 ui-spec）、缺陷的复现材料、或需求方的直接描述。读目标时主动挑刺——spec 也会有漏洞和矛盾；目标模糊或自相矛盾，先要求澄清再动手，别带着歧义设计。

## 做调研

- **内部现状**：目标涉及的模块当前怎么实现、现有架构撑不撑得住，圈出改动点和影响面。项目有架构文档就先读（rivo 全局契约 `ARCHITECTURE.md`），方案要在它的模块边界和依赖方向内做，真要突破就记成架构决策并给足理由。脱离现状设计出来的方案是空中楼阁。
- **外部技术**：要引入新库 / 框架时联网查现成方案和业界做法；模型对库的记忆有滞后，定下用哪个前先核实它最新的用法。不涉及外部技术就跳过。
- **过往经验**：团队有经验沉淀就翻相关条目（rivo 里是 `.rivo/learnings/`），沉淀过的坑别再踩一遍。

## 写方案

按契约 → 拆解 → 留痕推进：

1. **先定契约**：接口、数据模型、模块边界先定下来，实现照着走，契约一改就同步它的影响面。前端任务里，ui-spec 要复用的组件引用 DESIGN.md 已有的，新增组件由你补上 Props / 事件 / 类型契约（ui-spec 只给意图，类型归你）。
2. **拆到能开工**：组件和改动点拆到实现者照着不用再猜的粒度，影响面（要改的代码、数据迁移、配置）一条不漏地列出来。
3. **留下取舍**：每个关键决策写清选了什么、放弃了什么、为什么，让实现者和后来者看得懂约束。

缺陷的修复方案多一条：根因要有复现证据背书（最好是一个失败测试），给不出就把根因标为推断，让评审知道这条最薄；修复要对准根因，不是只压症状。

## 产出

按 [plan.md](../../templates/plan.md) 模板写（rivo 里落到 `.rivo/issues/<id>/plan.md`），覆盖目标的全部需求。

## 核心原则

- **够用就好**：够用的简单方案胜过完备的复杂方案，多出来的复杂会在实现和维护里反复还债，别为设想中的扩展性提前加抽象层。
- **分清可逆与否**：可逆的快做、错了再改；数据模型、对外契约、技术栈这类难回头的，想透了再定、留好退路。
- **大胆重构，小心设计**：现有架构真撑不住才重构，且重构本身要细设计、做足影响面控制，不借这次需求夹带。

## 危险信号

- 「上游定了，照着做就行」：是需求本身的问题就上报，别在方案层闷头硬凑。
- 「需求简单，不用调研」：再简单也先读代码、圈影响面。
- 「这库我熟，直接上」：模型对库的记忆有滞后，先核实版本和现有用法。
- 「方案差不多了，先开工」：不可逆的设计定版要等用户拍板。
