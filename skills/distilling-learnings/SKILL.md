# 复盘沉淀

从刚结束的交付里提炼「下次会做得不一样」的东西。输入是过程产物，不是印象；产出是改变未来行为的指令，不是感想。

## 工作流程

### 1. 扫过程产物找摩擦

复盘的原料全在工单目录里，逐样过：

- 评审意见：打回了几轮？打回的都是什么类型的问题？
- 测试记录：不通过项是怎么漏到测试阶段的？
- UAT 记录：用户的落差反馈暴露了什么理解偏差？
- 排查记录：根因的「推断」最后对了吗？
- ticket 进度：卡过哪里、用户纠正过什么、类型判断转过向吗？

### 2. 判断有没有可沉淀的

- 一次顺畅的交付很可能没有教训——**「无可沉淀」是合法结论**，记一句归档，不硬挤。
- 摩擦不等于教训：偶发的失误不必沉淀，会重复发生的模式才值得。

### 3. 提炼

每条经验过三道门，过不了就扔：

- **有根因**：知道为什么发生，不是只知道发生了。
- **有事实支撑**：能回指过程产物——哪轮评审、哪条测试记录。
- **下次可执行**：是改变行为的指令，不是感想。「以后小心点」不合格；「这个项目的网关会吞错误堆栈，排查接口问题先看网关日志再看应用日志」合格。

### 4. 分流去向

三个去向，各归各家，不双写：

- **全队通用的项目经验** → `learnings/`，一条一文件，INDEX.md 加一行索引。
- **属于某份长期文档的** → 直接更新那份文档：架构变了改 ARCHITECTURE，交付约定变了改 PROJECT，设计体系变了改 DESIGN——由各文档的维护者动手。
- **属于某个角色的工作方式** → 各角色沉淀进自己的私有记忆（按各自记忆职责的分类）。

同一条经验只住一个家：能进长期文档的不进 learnings，learnings 装的是文档没有合适章节安放的经验。

### 5. 收口

- 「无可沉淀」或分流完毕后，复盘结束，工单可归档。

## 产出结构

`learnings/` 下一条一文件，文件名用短 kebab-case：

```markdown
# [一句话标题：网关吞堆栈，排查先看网关日志]

**情境**：[什么情况下会遇到]
**教训**：[发生了什么、根因是什么]
**下次**：[具体怎么做]
**出处**：[工单 id + 哪份过程产物]
```

INDEX.md 每条一行：`- [标题](文件名.md) —— 一句话钩子`。

## 注意事项

- learning 的读者是未来的会话——对这单的来龙去脉一无所知的读者。写到不带上下文也能执行。
- 定期修剪：过时的删掉，被长期文档吸收的删掉。一份塞满陈旧条目的 INDEX 比没有更糟——它稀释信任。
- 复盘不追责，只找模式。「谁的错」不是有效产出，「什么机制让它下次不发生」才是。
