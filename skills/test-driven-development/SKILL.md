# 测试驱动开发

开始时声明：“正在使用 rivo:test-driven-development，用失败测试驱动当前行为的实现。”同一阶段已经说明过，就不重复。

围绕用户或调用方能观察到的行为，先写失败测试，再实现，最后改善代码结构。

每轮只处理一个行为，按测试实际运行的结果报告进度。

**先运行测试并看见它因目标行为缺失而失败，再写该行为的实现。环境错误、编译错误或未经运行的测试都不能冒充这个证据。**

## 选择下一项行为

从需求、接口约定或可复现的缺陷中确定预期，不要照着待测代码反推。规则有冲突时先讨论清楚，不能用测试替业务作决定。

选择能验证目标行为的测试层级，优先沿用已有测试的范围和边界。只模拟本次测试范围以外的依赖。检查结果和承诺的行为，不复制实现算法，也不只检查是否调用了 mock。

## 红、绿、重构

1. 写出表达下一项行为的测试。
2. 运行并确认它因行为缺失而失败。环境错误不算红灯；意外通过时检查测试是否能区分错误行为。
3. 完成满足该行为的最小合理实现，运行相关测试；只有实际通过才能进入重构。
4. 在测试保护下改善结构，再验证受影响行为。测试未通过时先解决当前问题，不进入下一个行为。

保持每轮改动足够小，便于定位失败原因。修复缺陷时保留能重现原问题的回归测试。不要先批量写完实现，再将补测描述成 TDD。

## 适用边界

先核实稳定的行为预期，再开始 TDD。视觉改动用视觉检查，文案用审校，环境配置用相应验证。准确说明实际采用的方法。

报告真实检查与未覆盖范围，区分模拟、集成与运行环境的证据。已有检查通过后，只有新改动、失败或未解决问题才需要扩大或重复测试。遵循用户明确的验证范围与委托。

## 返回结果

将实现和实际验证结果返回给当前任务，继续下一个行为或进入审阅。预期有冲突时，回到需求或设计讨论。一轮测试通过，不代表整项交付完成。
