# Test-Driven Development

开始时声明：“正在使用 rivo:test-driven-development，用失败测试驱动当前行为的实现。”同一阶段已声明时不重复。

以可观察行为建立反馈，按小步完成红、绿、重构。

每轮聚焦一个行为，完成失败测试、实现和验证，再检查结构。按实际运行结果报告进度。

## 选择下一项行为

预期来自需求、契约或可复现的缺陷，不能由待测实现反推。规则有冲突时先澄清，不让测试替业务作决定。

选择能覆盖目标行为的合适层级，优先复用已有测试边界。只模拟当前验证范围以外的依赖，断言结果与保证，避免复制实现算法或只检查 mock 调用。

## 红、绿、重构

1. 写出表达下一项行为的测试。
2. 运行并确认它因行为缺失而失败。环境错误不算红灯；意外通过时检查测试是否能区分错误行为。
3. 完成满足该行为的最小合理实现，运行相关测试。
4. 在测试保护下改善结构，再验证受影响行为。

保持每轮改动足够小，便于定位失败原因。修复缺陷时保留能重现原问题的回归测试。不要先批量写完实现，再将补测描述成 TDD。

## 适用边界

先核实稳定的行为预期，再开始 TDD。视觉改动用视觉检查，文案用审校，环境配置用相应验证。准确说明实际采用的方法。

报告真实检查与未覆盖范围，区分模拟、集成与运行环境的证据。已有检查通过后，只有新改动、失败或未解决问题才需要扩大或重复测试。遵循用户明确的验证范围与委托。

## 后续衔接

将实现与真实验证结果交回当前任务，继续下一项行为或进入既定审阅。预期发生冲突时把问题交回需求或设计讨论；本轮测试通过不代表整项交付完成。
