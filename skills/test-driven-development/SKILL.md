# 测试驱动开发

先运行测试，看见它因目标行为缺失而失败，再写实现。测试未运行，或因编译、环境问题中断，都不能证明它检验了目标行为。

围绕用户或调用方能观察到的行为推进，每轮只处理一个行为。

## 流程

### 1. 选择下一项行为

- 预期优先来自已有的测试用例清单（如单元测试或集成测试用例），单独使用时来自需求、接口约定或可复现的缺陷，不照着待测代码反推
- 预期不明确或互相冲突时，暂停该行为的实现，报告原约定和冲突
- 选择能验证目标行为的测试层级，只模拟本次范围以外的依赖
- 修改了跨仓库接口或 SDK 消费方时，除了单元测试，还要跑真实的类型检查和构建，不用全 mock 的测试掩盖契约断裂

### 2. 红

1. 写出表达这项行为的测试
2. 运行，确认它因行为缺失而失败
3. 意外通过时，检查测试能否区分错误行为

### 3. 绿

1. 写满足该行为的最小合理实现
2. 运行相关测试，实际通过才进入下一步

### 4. 重构

1. 在测试保护下整理结构
2. 再验证受影响的行为
3. 测试没通过先解决，不进入下一个行为

保持每轮改动足够小，失败时容易定位。修复缺陷时，保留能重现原问题的回归测试。

## 适用边界

- 纯数据库迁移、基建脚手架、配置改动或页面静态布局不硬套红-绿-重构，按对应的迁移检查、构建、环境或页面检查验证
- 如实区分模拟、集成与真实运行环境的证据，说明未覆盖的范围
- 已有检查通过后，只有新改动或未解决的问题才需要重复运行
