# Test-Driven Development

让测试成为对行为的可执行预期，在实现前得到反馈。

## 确定预期

从需求、契约、真实缺陷和领域约束中选择下一项行为。预期必须有独立于待测实现的依据。关键规则有冲突时先澄清，不让测试替业务作决定。

选择最小且有意义的验证层级。单元测试适合局部规则，集成与契约测试验证边界，端到端测试检查关键路径。只模拟不属于当前验证目标的依赖。

## 红、绿、重构

1. 写一个表达具体行为的测试。
2. 运行它，确认失败来自尚未满足的行为，而非环境、拼写或无关错误。意外通过时检查测试能否区分正确与错误。
3. 实现满足当前行为的最小合理改动，运行相关测试。
4. 在测试保护下改善结构，再验证受影响行为。

让循环足够小以定位原因。验证边界、失败路径和重试等适用情形，不用测试数量代替质量。修复缺陷时保留能重现原始问题的回归测试。

## 解释验证范围

断言可观察结果和真正的约束，避免仅断言内部调用次序或复制算法。相同的实现与测试假设可能一起错误；关键规则用业务示例或其他独立依据交叉检查。

临时探索尚无稳定行为契约时，可以先调查；进入保留实现前补上适当验证。视觉与运行环境问题使用对应观察手段，不伪造红绿循环。

区分测试通过、集成验证和生产行为。报告实际运行的检查与未覆盖部分；修改实现或测试后，更新受影响的验证证据。
