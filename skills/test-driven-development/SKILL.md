# 用测试驱动行为

预期来自用户需求、已批准的契约或可复现缺陷，不从现有实现反推。测试不能替用户决定业务规则；预期冲突时先查依据，必要时由当前任务处理设计变化。

选择能观察目标行为的测试层级，沿用合理的项目边界。只模拟范围之外的依赖，验证输出和效果，不复制实现算法，也不只断言调用了 mock。

## 红、绿、重构

1. 为下一项行为写测试并运行，确认它因目标行为缺失而失败。意外通过时检查测试能否区分错误行为。环境或编译失败不能算行为红测。
2. 写满足该行为的最小合理实现，运行相关测试，实际通过再继续。
3. 在测试保护下改善结构，重新验证受影响行为。失败先解决，不用更多改动掩盖问题。

修复缺陷时留下能重现原问题的回归测试。代码已经存在时不为制造红测删除有效工作，可用隔离基线或可控故障验证测试辨别力，并准确说明证据。

## 边界

视觉改动用视觉检查，文案用审校，配置用对应验证，不为低收益断言增加形式上的测试。模拟通过不代表真实集成；如实报告命令、结果、版本和未覆盖部分。必要环境不可用时保留受阻状态，不虚称验证通过。

已有检查通过后，只有新改动或未解决问题才需要再测；共同契约变化覆盖相关调用方。遵循用户明确的验证范围，仍有重要缺口时说明影响。

方法完成后继续当前任务的审阅与交付，不另设进度或审批。
