# 把需求澄清成 spec

把一个诉求澄清成可验证的需求规格。**审稿 / 澄清的过程就是写 spec 的过程**，只回答「做什么 / 为什么」，怎么实现留给技术方案。

## 确定输入

输入有什么用什么：现成 PRD（产品 / 策划写好的）、需求方的对话、或一个已复现坐实的缺陷。

动笔前先看现状，不脱离现有实现空谈需求：探索代码库，定位这是改已有还是纯新增——改已有，弄清现状的业务逻辑、交互形态、影响面；纯新增，判断是否依赖现有能力。项目有全局契约（rivo 里是 `.rivo/PROJECT.md`）和经验沉淀（`.rivo/learnings/`）就先读，带着现状去问才问得到点子上。

## 怎么做

### 有现成 PRD：先审再转

PRD 是外部输入，你审它、转成 spec，不照单全收：

- **缺口**：场景 / 状态 / 异常分支 PRD 漏没漏？补问。
- **越界 / 低价值**：要的有没有超范围或价值存疑？标出回确认。
- **矛盾 / 模糊**：自相矛盾或没法验证的点，回产品 / 需求方。

审出的问题落进 spec 的「待确认与来源缺口」，原始 PRD 指针记在「来源材料」。

### 没有 PRD：挖根因、按轮收敛

- **挖根因**：表面诉求未必是真需求，用户说要加个按钮，真正缺的可能是另一种交互。先问「什么场景、什么痛苦」，再判断他要的方案对不对。
- **按轮收敛**：问题按轮组织，一轮只放一小组紧密相关的问题，用上一轮的回答收窄下一轮，不一股脑全抛。每个问题附你的建议答案，让用户在锚点上拍板；问题同时落进「待确认与来源缺口」，不在场的用户也能成批看到、成批回答。尽量用 ASCII 图辅助对齐，这些图直接进 spec。

### 输入是缺陷：定「修成什么样」

已坐实的症状就是现状基线，你定「这算不算缺陷、该修成什么样」——用户视角的期望正确行为，根因不归你。spec 通常薄得多，小节按需取用；发现其实是设计如此或需求缺失，如实上报，别硬按缺陷写。

### 边澄清边落盘

spec 全程是活草稿：聊清一个实体就补领域模型，定下一段流转就补流程图 / 状态机，达成一个决策就记进对应小节。别攒着聊完再回忆补，到「需求定版」门才冻结。

## 产出

按 [spec.md](../../templates/spec.md) 模板写（rivo 里落到 `.rivo/issues/<id>/spec.md`）。两点必须做到：

- **结构，不只孤立行为**：别只写「点按钮 → 变 XX 状态」，否则下游容易写出面向过程的代码。领域实体的关系、关键对象的状态流转、业务主流程，用图钉死。
- **未定项显式标**：拿不准的内嵌 `[NEEDS CLARIFICATION: ...]`，澄清前不臆测；依赖外部、当下关不掉的，标阻塞方与影响面。

## 核心原则

- **挖根因，不照单做**：先弄清场景和痛苦，再定做什么。
- **价值优先，可验证优先**：规格从真实用例里长出来，不为设想中的未来堆当下复杂度；每条需求都能写成一条「做到没有」可判定的 AC，「提升体验」这种得拆成可测指标。
- **边做边写，文件是记忆**：对话会丢，聊定一条就写一条。
- **守产品侧边界**：只答做什么 / 为什么，对话滑向技术选型、接口设计就拉回（即便用户主动聊起），已形成的实现共识记到 spec 的「移交 plan 的线索」单独收着。

## 危险信号

- 「用户说怎么做我就怎么做」：先问场景与痛苦，别替他把方案定了。
- 「聊完再统一补 spec」：聊到后面就忘了，当场落盘。
- 「顺手把技术方案也定了」：滑向选型 / 接口就拉回，那归技术方案。
- 「上游 / 老 spec 写过，照搬」：带挑刺的眼光读，照搬会把上游的错也一起搬进来。
- 凭记忆向用户转述需求 / 代码事实：现场打开对照，转述出错比不答更糟。
