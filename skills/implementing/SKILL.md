# 照方案实现

照既定方案把需求变成可运行的代码。方案是协作的唯一依据（rivo 里是 plan.md），接口、数据模型、组件契约、模块边界都在里头。**全程 TDD**：动手实现都先写测试，再简单的改动也不例外，简单代码一样会错。

## 了解上下文

- 通读方案和验收标准（rivo 里是 plan.md 和 spec 的 AC），按方案定的契约施工。
- 动手前先打开要改的模块、要调的函数、要复用的逻辑，看它现在怎么写，别凭印象。给的上下文不够就去读源码。
- 团队有经验沉淀就翻相关条目（rivo 里是 `.rivo/learnings/`），沉淀过的坑别再踩。

## 怎么做

红-绿-重构，一个 AC 一轮：

1. **红**：先写一个能复现需求的失败测试，对照它要覆盖的 AC 写，描述期望的外部行为。
2. **绿**：写最小的代码让测试通过——只动该动的，不顺手重构无关代码、不加没人要的灵活性、不为不会发生的场景写防御。
3. **重构**：在绿灯保护下整理代码，每步都让测试保持绿。

一以贯之的约束：

- **不硬编码**：API 路径、配置、环境相关的值不写死。
- **守代码规约**：命名、目录、错误处理、测试范式照项目规约走（rivo 全局契约 `CONVENTIONS.md`），别带自己的风格。
- **（前端）照 ui-spec + 设计稿**：按 ui-spec 的组件组合实现、复用 DESIGN.md 组件；要精确视觉时回查 ui-spec 记的设计稿来源，别凭印象还原。

## 产出

按 AC 组织的代码与测试：每条 AC 做成一组小步、绿灯收尾、可单独回退，不同 AC 不混在一起。门禁全绿才算完：测试、类型检查、lint 全通过，警告清零，不留「在我机器上能跑」的黑箱。

是否、何时真的 `git commit` 听用户与项目约定，别擅自动用户的提交历史；脏工作区、多人协作时尤其先问。

## 核心原则

- **忠于方案，不自行发挥**：接口、数据模型、组件契约、模块边界按方案定的来；方案不清楚就问它的作者，不自己假设一个看似合理的版本填上。
- **测试验证正确性，不反推实现**：写通用、正确的解，不为某个测试输入硬编码或打补丁让它过。测试是靶子，不是实现目标。
- **测真实行为，不拿 mock 凑数**：测的是它实际怎么跑，不是把桩写得刚好通过。
- **越写越绕，多半是上游的问题**：逻辑怎么都顺不下来，根源常在领域模型划分或方案的契约，别在实现层加 `if` 硬凑，这是该上报回方案层的信号。

## 危险信号

- 「先写实现，测试回头补」：补的测试只给现状背书，红在前。
- 「测试不过，把断言改宽点」：要改实现，不是改靶子。
- 「这段难测，mock 掉就行」：mock 过了界就测不到真实行为，守住该测的边界。
- 「这块顺手也重构了吧」：本次只动该动的，重构夹带进来放大风险。
- 「契约没写清，我按合理的来」：别脑补一个版本，回方案作者问清楚。
- 「这库我熟，直接写」：模型对库的记忆有滞后，引用已有代码或第三方库前先核实版本与现有用法。
