# Write Spec

独立接收需求材料，或承接调用方的结论、来源、确认依据、未决项与位置。无需启动完整交付流程。

## 调用边界

用户直接要求整理材料或先出草稿时按请求写作，未知项如实保留。被需求或设计阶段调用时，先承接本次已对齐的范围与确认依据，只整理该范围；讨论未收敛且用户未要求整份草稿时，不自行扩写为完整文档。缺少必要决定就交回当前问题，不能把“写作可独立使用”当作跳过调用方讨论条件的理由。

## 写作与核对

1. 新建或实质修订前读取 [Spec 模板](references/spec.md) 及已有目标文档。
2. 按模板整理目标、非目标、角色、行为、UI 形态、规则、约束与验收。已有权威 PRD 在对应章节引用，只补充澄清、差异和遗漏。
3. 对照模板逐项检查元信息、章节和表格字段，核对验收是否对应行为、建议与确认是否分明、是否夹带未决定的实现选择。
4. 交回文档位置、主要变化和未决项。被调用时继续原问题；独立写作完成后结束。

采用模板的主结构，细节按实际范围裁剪，不适用处简短说明；用户指定其他格式时按其要求。被调用时步骤嵌入当前清单项，不另建竞争清单。

## 内容边界

区分草稿、部分确认与已确认，附真实讨论或委托依据。未知内容保留缺口，不靠编造填满模板。需要澄清新需求时交回调用方；独立请求中需要进一步讨论时使用 [requirements-definition](../requirements-definition/SKILL.md) 处理具体问题。

技术限制解释其用户后果，组件拆分和算法留在技术方案中。已有图示引用其阅读入口、图源版本和确认状态；修改文字不改变图源。写作本身不意味着需求得到批准。
