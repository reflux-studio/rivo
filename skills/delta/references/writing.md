# 知识库写作标准

知识库的读者是刚入职的同事，或者替他分析项目的 AI。标准只有一条：读者从首页开始，从头读到尾，能够理解系统现在是什么样、各部分怎样协作、为什么这样设计，改动时要守住哪些约束。

## 怎样写

首页 README.md 用连贯的文字讲清系统全貌：它做什么、由哪些部分组成、一次典型的操作怎样流过这些部分，然后把读者引到各个主题。每个主题一个文件，按读者理解的顺序展开，先讲这部分负责什么，再讲它怎样工作、有哪些规则和约束，以及这些规则背后的理由。

正文以连贯的段落为主体。段落之间要有因果和先后，读者读到一条规则时，应当同时知道它为什么存在、违反了会怎样。术语在第一次出现的地方用一两句话解释清楚，不另外维护术语表。字段、配置项、命令这类需要逐项对照的内容，集中成一张表，一行一项。

路径、文件位置和来源需求放进 Markdown 引用块，写在对应段落之后，不打断正文。来源写实际文件位置和原需求目录。

涉及结构或流程时配图，图是嵌入 Markdown 的 SVG；正文仍然要讲清图里的关键关系，只读文字也能理解。不使用 ASCII 图。

知识库记录的是现状，不是历史。讨论过程、被放弃的方案、实施中踩过的坑，留在归档的需求目录里；只有读者改动系统时必须知道的理由，才写进正文。

## 对照示例

同一段内容，笔记体写法：

```markdown
## 订单超时
- `ORDER_TIMEOUT_MIN=30`，见 `config/order.ts`
- job：`jobs/expire.ts`，每分钟跑
- 状态 PENDING → CANCELLED，释放库存（`inventory.release`）
- 支付回调晚到：走退款（ADR-004）
- 注意幂等
```

每一行都是真的，但新同事读完仍然不知道：超时从什么时候算起，为什么晚到的支付要退款而不是恢复订单，"注意幂等"指的是哪一步。

连贯写法（需求归档后的样子）：

```markdown
## 订单超时

用户下单后，订单处于"待支付"状态，并暂时占住所需的库存。如果 30 分钟内没有完成支付，系统会取消订单并把库存还回去，避免热门商品被未付款的订单长期锁住。检查由一个每分钟运行一次的后台任务完成，所以实际取消时间可能比 30 分钟晚一分钟以内。

取消和支付可能同时发生：支付平台的回调偶尔会在订单已被取消之后才到达。这时库存可能已经被别人买走，恢复订单无法保证有货，所以系统对这笔款项直接发起退款。后台任务和支付回调都可能修改同一个订单，两者都以"订单当前仍是待支付"为前提更新状态，谁先成功谁生效，另一方看到状态已变就放弃，因此同一订单不会被取消两次，也不会既取消又发货。

> 超时时长：`config/order.ts`；后台任务：`jobs/expire.ts`；库存释放：`inventory.release`
> 来源需求：[order-timeout](../archived/order-timeout/)
```

## 修订原则

修订知识库时，修订后的文本只陈述当前的正确做法，读起来应当像第一次就写对了。删除失效的内容，在原处重写受影响的段落，不在原文旁追加补丁句，也不因为一次纠正新增"不要……""而不是……"一类的否定句。批量替换或改名之后，先全文搜索残留。

仍然适用于其他版本或范围的旧规则不是错误内容，保留下来，并写明它适用于哪个版本或范围。
