# 基础验收

两道验收的第一道：不带用户，自主把系统跑起来，验「跑起来对不对」。带真实用户确认价值兑现是第二道 `running-uat`。

## 了解上下文

- 拿验收标准（AC，rivo 里在 spec）当靶子，逐条验，不读实现。
- 按项目的环境说明把环境跑起来（rivo 全局契约 `TESTING.md`），备齐依赖服务与种子数据。环境起不来是头号阻塞，先解决；环境说明没覆盖的坑，验完回头补进去。

## 怎么做

- **逐条对照 AC 验行为**：每条 AC 亲手点、亲手跑，按可观察的行为判定，✅ 通过、⚠️ 有缺陷（功能在但行为偏离）、❌ 未实现。AC 没有「差不多」，偏差就是缺陷。正常路径 + 空态、错误态、边界都覆盖，不只走最顺的那条。
- **涉及 UI 必须跑起来看**：UI 的正确性在屏幕上、不在代码里，实际点、实际填、实际提交，截图 / 录屏为证，不拿读代码或看设计稿代替。
- **多源取证**：截图、录屏、网络面板、控制台、e2e 断言，用可复现的证据下判断。

## 产出

行为级测试报告按 [verification.md](../../templates/verification.md) 模板写（rivo 里落到 `.rivo/issues/<id>/verification.md`）：逐条 AC 的判定（✅/⚠️/❌）、操作路径、观察结果、证据。报缺陷必须给得出稳定复现的步骤，复现不稳的标「疑似」。每条不符，判断它是缺陷（实现没做到 AC）还是规格问题（实现忠于 AC、但 AC 本身有问题），如实记进报告。

## 核心原则

- **没验过就是没做到**：默认它不工作，要亲手跑出来的行为证据才算数。
- **黑盒独立**：不读实现，读过代码会不自觉觉得「它应该能工作」，你只认点下去实际发生了什么。

## 危险信号

- 「代码看着对，应该能跑，不用真点」：没跑就是没验。
- 「先看看实现怎么写的再验」：读了就丢了黑盒独立。
- 「happy path 过了就行」：空态、错误态、边界也得逐一点到。
- 「环境起不来，先按代码推断」：环境是头号阻塞，先解决再验。
