# 分层验证与回归测试

用最短的反馈路径证明改动真的可用。如实分清“已经跑过并证明”和“还没覆盖”的部分，不拿口头推测或全 mock 测试代替集成验证。

## 1. 从快到慢

按测试金字塔从下往上跑，遵循快速失败：前一层有阻塞问题，就不往后跑。

1. 静态检查：编译、类型检查、Lint、生成的协议或类型文件是否同步
2. 单元测试
3. 集成与契约测试：模块拼接、数据库事务、权限、跨服务和跨仓库的真实调用
4. 端到端测试与人工验收：核心主干链路、真实页面和交互

## 2. 回归范围

- **自动测试全量跑**：合入或验收前，全量跑静态检查、单元测试和集成测试。机器跑不费人力，专门拦“后面的改动把前面改坏了”
- **端到端和人工测试按影响面跑**：不再把参数边界走一遍，只跑三类路径：跨模块的核心主干、全部 P0 冒烟场景、本次改动和公共依赖波及的老功能
- **局部修改后定向复测**：人工验收、代码审阅或最终验证触发修改后，只复测受影响的范围。纯样式或文案只复查对应页面和构建；改了业务逻辑，先补上或更新对应的自动测试，再重跑受影响的检查
- **外部测试平台**：如果项目接入了外部测试平台，在授权范围内按项目约定（如 `AGENTS.md`）触发或同步，保留平台报告链接

一次加了多项优化（例如索引、缓存、批量查询）时，用消融实验确认每一项的实际收益，没有收益的复杂度在报告里指出来。

## 3. 证据

- 没有在当前最新代码上实际跑过、看到完整结果，就不说“通过”。代码再改动后，之前的结果作废
- 写清每次运行的条件：全 mock、内存替身、测试环境，还是真实联调环境。全 mock 不能算集成已打通
- 截图、命令日志和回归输出放进指定的证据目录；临时脚本和测试脏数据用完即删，不留在仓库里

## 4. 验证报告

面向验收、合入前检查或团队归档时，按 [验证报告模板](references/test-report.md) 写出 `test-report.md`（位置由调用方或项目指定），把各层结果、用例与回归核对、缺陷复测、证据索引和未覆盖的范围一次写清。
