# 把 UI 落成 ui-spec

把这次需求的 UI 意图落成 ui-spec。**看设计稿的过程就是写 ui-spec 的过程**，看一遍、落一份，稿只拉一次。你不写代码，ui-spec 只是意图；组件的 Props 类型、API 这些契约归技术方案，实现归实现者。

## 了解上下文

- **有设计稿**：打开它（图 / Figma 节点 / 本地 HTML），边看边落。
- **没有设计稿**：你就是设计者，直接决定 UI 的样子和组成——产出的是组件组合，不是一张图。
- 先备好项目的设计系统约定（rivo 全局契约 `DESIGN.md`）：组件清单、token，组合时优先复用。

## 怎么做

### 审设计稿，对 spec 核

设计稿是外部输入，你审它、转它：

- **覆盖**：spec 要的状态 / 场景（空 / 错误 / 权限 / 边界），设计稿是否都画了？漏的记进审稿结论。
- **越界**：设计稿有没有超出产品范围的交互 / 页面？有就标出。
- **体验质量**：点击区 < 44×44px、对比度低于 WCAG AA、主操作不突出等可定位问题，标出。

### 边看边落盘

ui-spec 全程是活草稿：看清一个视图就落一个，别攒着回忆补。尤其**设计稿来源**那行（节点 id / 链接 / 文件路径）要当场记，它让实现时能回查到稿上那一块取间距 / 色值，不必再到处翻稿。

## 产出

按 [ui-spec.md](../../templates/ui-spec.md) 模板写（rivo 里落到 `.rivo/issues/<id>/ui-spec.md`）。每个视图必须写清两样：

- **组件组合**：复用 DESIGN.md 哪些组件（写明），新增哪些（给名称、用途、「现有的为什么替代不了」，只到意图不写 Props 类型）。绕过设计系统的硬编码样式标出。
- **全部状态**：正常 / 空 / 加载 / 错误 / 无权限 / 边界各态、关键交互与流转，别只画正常态。

## 核心原则

- **看稿即写**：审设计稿的过程就是落 ui-spec 的过程，看一遍、落一份，稿只拉一次。
- **复用优先于新增**：组件库膨胀很贵，能复用就复用，新增要给「现有的为什么替代不了」。
- **守在意图层**：管 UI 长什么样、用哪些组件、有哪些状态，不碰 Props 类型和代码。
- **交互服从任务**：服务于用户完成任务的最短路径，不为视觉炫技加动效或步骤；B 端容错低，视觉正确是可测的（间距 / 色值 / 字号对得上号，不靠「感觉对了」）。

## 危险信号

- 「看完整体再统一补 ui-spec」：看到后面就忘了，看清一个视图当场落一个。
- 「设计稿来源以后再补」：来源那行当场记，否则实现时满地找稿或靠猜。
- 「新增个组件更顺手」：先查 DESIGN.md 现有的能不能用。
- 「只画正常态就够了」：空 / 错误 / 边界态是下游最容易漏的，必须落清楚。
