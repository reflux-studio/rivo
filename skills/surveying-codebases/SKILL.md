# 勘测代码库

从真实代码归纳出工程认知并落成文档，让之后的方案设计和评审有准绳可依。勘测是事实记录：代码是什么样就记什么样，评价和改进主张不属于这份产出。

## 工作流程

### 1. 建立地图

- 从外围读起：README、构建与依赖配置（package.json、pyproject.toml 一类）、目录树。
- 目标是先知道「这里有什么、从哪进入」，再决定往哪深入。

### 2. 分维度勘探

三个维度互不依赖；若环境支持并行执行，可以分头同时勘探，各路只回结论不回过程——勘探是读密集的活，并行的收益最高：

- **架构**：模块划分与各自职责、数据流向、存储方案、分层方式、对外接口。
- **代码规约**：命名习惯、目录组织、错误处理范式、状态管理惯例、注释与测试的风格。
- **验证基建**：怎么装依赖、怎么跑起来、单元测试和端到端测试怎么执行、CI 里跑了什么。

### 3. 以代码为准

- 一切结论归纳自实际代码。项目里已有的说明文档只当线索，断言要回代码里核实；文档与代码冲突的，以代码为准，并把冲突记下来。
- 惯例要有出处：一处是写法，三处才是惯例。每条规约至少能指出两三个体现它的文件。
- 读不出确定结论的（比如某个模块看不出为什么这么设计），标注「推断」或列为待确认问题，不编造确定性。

### 4. 落成文档

产出 `ARCHITECTURE.md`，三节：

- **架构**：模块地图（配 ASCII 图）、数据流、存储、分层、对外接口。
- **代码规约**：逐条列，每条附出处文件。
- **验证基建**：安装、启动、测试、CI，每条都是可直接执行的命令。

### 5. 核验

- 验证基建那一节的每条命令**亲手跑一遍**——写在文档里的命令必须真的能跑，这节是全文档里唯一能当场证伪的部分，不核验等于没写。
- 规约每条回指出处；架构图对照两三条真实调用路径走一遍。

## 产出结构

```markdown
# ARCHITECTURE

## 架构
[模块地图（ASCII 图）、各模块职责、数据流、存储、对外接口]

## 代码规约
[逐条惯例，每条附出处：命名、目录、错误处理、状态管理、测试范式]

## 验证基建
[安装 / 启动 / 测试 / e2e / CI，每条是可执行的命令，全部亲手验证过]

## 待确认
[读不出结论的推断项，标注来源]
```

## 注意事项

- 勘测记录事实，不做评论——「这里该重构」是另一件事的产出，不进这份文档。
- 别把一个文件的怪癖当全库惯例，也别把新旧并存的过渡状态记成单一规则（「新代码用 X，`legacy/` 下仍是 Y」是准确的记法）。
- 检验标准：拿着这份文档、不重读全库，能不能直接开始设计方案？能，才算勘测完成。
- 文档落成后随代码演进增量更新（复盘时同步），不推倒重跑全量勘测。
