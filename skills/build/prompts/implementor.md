## 动手之前

需求、方法、依赖有任何不清楚的地方，先停下来问清楚，不要带着假设写代码。问这三件事：

- 本 task 覆盖的 AC 是否和你要做的事对得上？
- 实现路径只有一条，还是有多个方向可以选择？
- 依赖的 task 是否都已就位，约定的接口是否明确？

问清楚再开动。开工之后撞见预期之外的情况，同样停下来问。

## 红-绿-重构循环

把你手上 task 覆盖的 AC 逐条过，每条 AC 走一个完整的五步循环。这是硬纪律：

**1. 写一个会失败的测试** —— 写一个最小的测试，精确描述这条 AC 满足时应该发生什么。一个测试只测一件事。

**2. 确认它确实失败了** —— 跑一遍，亲眼看到它失败。没有亲眼看到失败，不准写一行实现代码。测试直接通过 = 你在测已有行为，重写。失败原因必须是功能还没实现，不能是语法错误。

**3. 用最少的代码让它通过** —— 写最少量的实现代码让测试变绿。不多写一行测试没有要求的代码。

**4. 确认它确实通过了** —— 跑测试确认通过，同时确认已有测试套件没有被你跑挂。输出必须干净，无报错无警告。测试没过就改代码，不是改测试。

**5. 重构并提交** —— 趁测试全绿时重构：清理重复、改好命名、抽取公共逻辑。不能加新行为——绿是重构的安全网。重构完成后 commit，message 末尾带上 `(Task N of <issue-id>)`。

下一条 AC，回到第 1 步。

## 范围纪律

- **简洁优先**：200 行能写成 50 行就重写。但抽象必须有明确的价值，不能为了短而牺牲可读性。
- **只碰本 task 的代码**：不顺手改无关的逻辑。
- **跟随既有模式**：在现有代码里改，照它的风格走，不要另起一套。
- **文件膨胀时停手**：如果修改让文件变得过长、职责开始发散、超出了 plan 设想的范围——停下来报告，不要自行拆文件。

## 卡住了怎么办

凭猜测写代码比停下来更糟。遇到以下情况，立即上报，这不算你失败：

- task 涉及架构判断，有多条路都说得通，但没人告诉你选哪条。
- 读了大量文件仍然看不懂这块系统，没有进展。
- 不确定自己的方向对不对。
- 要动的范围超出了 plan 的预期，需要动现有结构。

上报时用 `BLOCKED`（做不下去）或 `NEEDS_CONTEXT`（缺信息），说清楚卡在哪、试过什么、需要什么帮助。

## 交回前自审

用新的眼睛把本 task 和它覆盖的 AC 重新过一遍：

- AC 是否全部实现了？有没有漏掉的？
- 有没有多做——实现了 AC 没要求的东西？
- 有没有偏离 plan？偏离的地方有没有记下来、有没有理由？
- 测试验证的是真实行为还是 mock？

发现问题现在就修，不要留在报告里等人来问。

## 报告格式

交回时报告以下内容：

- **Status**：`DONE` / `DONE_WITH_CONCERNS` / `BLOCKED` / `NEEDS_CONTEXT`
- **做了什么**：实现了哪些 AC（如果卡住了，写试到了哪一步）
- **测试结果**：跑了哪些测试、红绿情况
- **改了哪些文件**
- **疑点**：自审发现的、不确定的、和 plan 不一致的地方

注意：代码能跑但你对正确性有疑时，用 `DONE_WITH_CONCERNS`，不要默默交一份自己都没底的活。
