# 实现

基于给定的技术方案和任务拆解，执行和构建代码。

若 [using-rivo](../using-rivo/SKILL.md) 总纲尚未在上下文中，先读它。

## 获取必要的上下文

1. 读取项目全局说明：`.rivo/PROJECT.md`、`.rivo/ARCHITECTURE.md`，了解项目全貌
2. 从当前 issue 目录 `.rivo/issues/$issue_id` 读 `spec.md`、`plan.md`、`tasks.md`，理解需求、技术方案与任务拆解；若存在 `ui-contract.md` 一并读取——派活和批次规划需要知道哪些 task 对接已实现的 UI
3. 从 `.rivo/learnings/` 目录下读取可能涉及到的学习经验

## 任务分配

### 1. 分析依赖，规划批次

基于 `tasks.md` 提取依赖关系，把任务分成批次：一个任务的全部依赖完成后，它才能进入执行批次。

```
第 1 批（无依赖）：T1, T5
第 2 批（依赖 T1）：T2
第 3 批（依赖 T2）：T3, T4
第 4 批（依赖 T3 / T5）：T6, T7
第 5 批（依赖 T6, T7）：T8
第 6 批（依赖 T1–T8）：T9
```

### 2. 按批次调度 subagent

使用 [implementor.md](prompts/implementor.md) 提示词派遣 subagent。

> **注意事项**：
> 1. 按难度选模型：简单或机械性的任务用便宜快速的模型，复杂问题用更强的模型。
> 2. 同一批次内、改动文件互不重叠的任务可以并行；可能碰同一文件的任务即使依赖上互不阻塞，也串行执行，避免提交相互踩踏。
> 3. 派活时把 task 全文与必要上下文一次贴齐，implementor 不需要再去翻 `.rivo/` 产物。

### 3. 逐任务审查（两级门禁）

subagent 返回后，按状态分流。**返回成功不等于 task 完成**——必须走完两级独立审查，全绿才算。

#### 3a. 状态分流

- subagent 返回成功 → 进入两级审查。
- subagent 返回失败 → 分析失败原因：
  - 如果是任务描述不清或约束冲突，修正提示词，重试。
  - 如果失败指向 spec 本身不可实现 → 暂停，用 **backtrack** 回 `clarify` 层。
  - 如果失败指向 plan 方案缺陷 → 暂停，用 **backtrack** 回 `plan` 层。

#### 3b. 两级独立审查

每级审查派遣独立的 reviewer subagent（用**不同模型**，隔离上下文）。审查对象限定为本 task 的提交——按 commit message 里的 Task 标记圈定 diff，不混入并行 task 的改动。implementor 交回前的自审是作者自查，替代不了这两级独立审查。

**第一级：spec 合规审查**
- 职责：对照本 task 覆盖的 AC 逐条验证——实现是否完整、是否过度实现、是否偏离 spec 与 plan 的约定。
- 审查提示词：[spec-compliance-reviewer.md](prompts/spec-compliance-reviewer.md)
- 通过 → 进入第二级。
- 不通过 → implementor 修复后重新审查，直到通过。

**第二级：代码质量审查**
- 职责：审查正确性（分支、边界、异常、并发）、安全（注入、越权、密钥）、测试覆盖（真测试非 mock 凑数）、规范（命名、目录、遵循 PROJECT 约定）。
- 审查提示词：[code-quality-reviewer.md](prompts/code-quality-reviewer.md)
- 通过 → 标记 task 完成。
- 不通过 → implementor 修复后重新审查，直到通过。

> 两级全绿本 task 才算完成。任一审查未通过，不得进入下一个 task。

批次之间做集成验证：当前批次所有 task 两级全绿后，跑一遍受影响的集成测试，确保 task 间接口对接正确，再进下一批。

### 4. 全局回归

所有 task 完成后，按 `PROJECT.md` 定义的命令运行项目已有的测试套件（单元测试、集成测试等），验证无回归。有测试失败就修复后重跑，全部通过为止。

## 全局终审

所有 task 两级全绿后，用 **review** 技能再做一次全局交叉评审——审跨 task 接口一致性、整体回归、是否有全局性遗漏。与逐 task 审查不同，全局终审看的是 task 之间的衔接和整体一致性。

> 审查项提示词：[final-reviewer.md](prompts/final-reviewer.md)

## 收尾

问题收敛后，总结本次实现的 task 覆盖情况与测试结果，提示用户进入 `/rivo:verify` 做人工验收。

## 核心原则

- **先写测试，再写代码** —— 派活时不替 implementor 放宽红-绿纪律，再简单的 task 也不例外。
- **commit 跟着红绿循环走** —— 每条 AC 在绿灯收尾时提交一次，message 末尾带 `(Task N of <issue-id>)`；一个 task 对应一段连续、可整体回退的提交序列，不同 task 的提交不混在一起。
- **派活前备齐上下文** —— task 全文与相关约束一次贴齐，implementor 不需要自行翻 `.rivo/` 产物，避免上下文偏差。
- **按难度选模型** —— 机械性任务用便宜快速的模型，需要判断的任务用更强的模型。
- **全部门禁必须通过** —— 测试、类型检查、lint 全部通过才算完成，警告也要清零。
- **逐 task 两级审查** —— 实现完成不算完：spec 合规审查 + 代码质量审查，两级全绿本 task 才算完成。任一未通过不进下一个 task。
- **全局终审** —— 所有 task 两级全绿后，再做一次全局交叉评审，审跨 task 接口、回归、整体一致性。

## 危险信号

- 「这个 task 太简单，跳过写测试吧」—— 简单代码同样会出错，先写测试再写代码，对所有 task 一视同仁。
- 「几个 task 的改动一起 commit 省事」—— 提交混在一起就无法按 task 回退，每个提交只属于一个 task。
- 「测试过了，lint 有几个警告不影响」—— 门禁必须全部通过，警告同样需要清零。
- 「implementor 说逻辑越写越绕，加个 if 让它先过」—— 代码腐化往往始于这类妥协。根源多半在上游领域模型划分有误，回 **plan** 修正，不在实现层硬补。
- 「implementor 返回了 DONE，这个 task 就过了」—— 返回成功只是实现完成，必须走完两级独立审查才标记完成。
- 「spec 审查过了，代码质量差不多就行」—— 两级是独立门禁，一级通过不替代另一级。spec 合规不等于代码写得好。
- 「全绿了，我自己看一眼就发版」—— 自己的眼睛做不了终审，定稿后必须交叉评审。
- 「200 行能写成 50 行，但能跑就先这样」—— 简洁优先，但抽象必须有充分理由，不能为了简洁牺牲可读性。
