# 执行测试

对照验收依据逐条执行验证，每条留下可指认的证据，产出测试记录。记录的标准：别人不用重跑，就能核对你的结果。

## 工作流程

### 1. 列核对表

收集这次改动的验收依据，逐条列成核对表：

- **功能需求**：需求文档的验收标准，按编号逐条（AC-1、AC-2……）。
- **缺陷修复**：原复现步骤加修复预期——按原步骤操作，缺陷应不再出现。
- **技术任务**：完成标准逐项——性能指标、迁移完成率、测试全绿。

### 2. 定验证方式

- 每条标注怎么验：自动化测试（写明测试名）、手动操作（写明步骤）、数据核对（写明命令或查询）。
- 有自动化测试的条目也要真的跑——引用的是这一次的运行结果，不是「上次是绿的」。

### 3. 逐条执行，留证据

- 证据要可指认：测试输出、截图、命令和它的返回、日志片段。「我看了没问题」不是证据，证据是别人能核对的东西。
- 不通过就记不通过，附上实际现象与预期的差异。没有「基本通过」。
- 发现验收依据之外的问题，另立一条如实记录，不混进核对表——它是新的缺陷上报，不是这次验证的项目。

### 4. 回归

- 全量测试套件跑一遍：确认改动没有弄坏别的东西。
- 若已连接 CI，以 CI 的全量结果为准并引用它。

### 5. 产出测试记录

若这单工作有自己的工单目录，存为其中的 `test-report.md`；否则按用户指定的位置保存。

## 产出结构

```markdown
## 测试记录：[工单名]

**日期：** [日期]　**环境：** [本地 / staging / 生产，分支或版本]

### 逐条验证
| 依据 | 验证方式 | 结果 | 证据 |
|------|---------|------|------|
| AC-1 | 自动化：`test_export_csv` | ✅ 通过 | [测试输出] |
| AC-2 | 手动：[步骤摘要] | ✅ 通过 | [截图] |
| AC-3 | 手动：[步骤摘要] | ❌ 不通过 | [实际现象 vs 预期] |

### 回归
- 全量套件：[N 通过 / M 失败]，[CI 链接或本地输出摘要]

### 额外发现
- [验收依据之外发现的问题，如有]

### 结论
[全部通过 / 不通过项列举]
```

## 注意事项

- 环境如实记录——「在我机器上通过」和「在 staging 通过」是两个不同的结论。
- 测试记录只陈述事实，不解释原因——不通过项的定位是排查（systematic-debugging）的事，别在记录里猜根因。
- 核对表来自验收依据，不临场发明验证项；觉得依据本身缺了条目，退回给定它的人补，补了重新验。
