# 入场

团队进入一个项目，先建立三份长期文档，之后所有方案和评审以它们为准绳。已有文档的项目跑它做增量校准——只补缺的、改错的，不推倒重来。

## 分工

| 文档 | 怎么来 | 谁负责 |
| --- | --- | --- |
| ARCHITECTURE.md | surveying-codebases 勘测代码库 | Engineer |
| DESIGN.md（仅有前端界面时） | surveying-designs 勘测设计体系 | Designer |
| PROJECT.md | 读 README 等现成材料起草，和用户确认补齐 | Product |

三路对称：都是先读事实源起草，再补缺口。互不依赖，同时进行。

## 流程

1. **Team Lead 检查现状**。项目根没有 `.rivo/` 就建骨架：`issues/`、`archived/`、`learnings/`（含空的 INDEX.md）。已有文档的看哪些缺失或和现实脱节，只派对应的路；全新项目三路全派。
2. **Engineer 勘测代码库**，产出 ARCHITECTURE.md——架构、代码规约、验证基建三节。验证基建的每条命令亲手跑通，是这份文档的完成条件。
3. **Designer 勘测设计体系**（项目有前端界面才有这一路），产出 DESIGN.md——token、组件库、业务组件清单、断点。
4. **Product 起草项目定位**，产出 PROJECT.md。先读现成材料——README、文档、包描述——把「给谁用、解决什么问题、什么算价值」起草出来；再和用户确认修正，并补齐材料里读不出的：
   - 交付约定：分支怎么合、走不走 PR、发布到哪、发布前要过什么。
   - 质量取舍：什么必须稳、什么可以快。

   第一次合作把这几样一次问齐，不零敲碎打。草稿以用户确认为准——README 也会过时。
5. **收口**。勘测产物不走评审——它们是事实记录，把关靠核验（命令跑过、结论有出处），已内置在勘测技能里；把各文档的要点和标为「推断」「待确认」的项摆给用户过目，PROJECT.md 由用户确认定稿。三份就位，团队可以接活。

空项目没有代码可勘测：勘测的两路改为按各自文档的覆盖项逐项问用户，不编造。

## 完成的定义

- ARCHITECTURE.md 落盘，验证基建节的命令全部亲手跑通。
- DESIGN.md 落盘（仅前端），每个 token 和业务组件有出处。
- PROJECT.md 经用户确认。
