# 写 task.md

task.md 按可验收的结果安排实施，说明任务顺序、共同契约和完成条件。执行者读方案和代码后决定具体做法，任务不必展开成逐文件的编码教程；需要限定修改范围时，仍应列出相关文件。

## 拆分方法

- **按结果拆**：每项任务交付一项能单独检查的结果，写清用户或调用方能观察到什么
- **对应模块**：每项任务注明服务于需求总览中的哪些模块。一项任务可以覆盖多个模块的共用机制，一个模块也可以拆成几项任务
- **不单列配套工作**：配置、脚手架和测试归入需要它们的任务
- **风险先行**：先排影响后续结构的任务，让风险最高的假设最早被验证
- **标明依赖**：没有依赖、也不改同一处的任务可以并行
- **共同约定集中写**：接口名、字段、状态语义、代码风格、工作分支，用 plan.md 中的实际值。单项任务只写特有契约
- **验收可检查**：写场景和预期结果，或指向 plan.md 的验证安排

拆分时发现 plan.md 缺契约，按 implementing-plans 的“实现与方案不一致时”处理，不在 task.md 里补定。

## 结构

```markdown
# <需求名称>：实施方案

依据：plan.md <版本>，adr/<编号范围>。代码仓库、分支与已有授权。

## 共同约定

所有任务都要遵守的契约和工程约定。

## 任务

| 任务 | 对应模块 | 可验证结果 | 依赖 |
| --- | --- | --- | --- |
| T1 <名称> | <F1 等> | <做完后能观察到什么，必须遵守的特有契约> | 无 |

## 验收

逐任务审阅、整体审阅，以及 plan.md 中要求的验证步骤。

## 实施记录

按任务记录实现选择、没修的 P1 和 P2、被拒绝的意见和方案变更的处理结果。
```

## 自查

- 逐节对照 plan.md，每个模块、契约和验证安排都落在某项任务或共同约定里
- 任务之间没有矛盾的契约

覆盖完整即开工。
