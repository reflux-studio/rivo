# 接收执行者与审阅者的意见

执行者和审阅者只看到提供的 diff 与材料，可能因缺少业务背景提出误判。主代理对照真实需求、已有决定和代码逐条核实，再决定如何处理。

## 分级

| 级别 | 含义 | 处理 |
| --- | --- | --- |
| P0 | 需求没满足、行为错误、契约违背、验证虚假或与 ADR/决定冲突 | 必须修 |
| P1 | 未复用已有组件/代码、明显重复或过度抽象、影响可维护性 | 默认修；代价明显高于收益时可不修，写明理由 |
| P2 | 局部瑕疵 | 不必修，顺手能改的改 |

结论：没有 P0 即为通过。没修的 P1、P2 和拒绝理由记入 `task.md` 对应任务的审阅记录，交付时列给用户。

## 核实与处理

对照 `plan.md`、ADR、`task.md` 和实际代码核实每条意见：

| 核实结果 | 处理 |
| --- | --- |
| 代码问题属实 | 按级别修复，并重跑受影响的验证 |
| `task.md` 约定问题 | 主代理更新 `task.md` |
| 意见暴露方案本身有误 | 按 `SKILL.md` 的「实现与方案不一致时」处理 |
| 缺少上下文造成的误会 | 拒绝，写明理由和代码/决定依据 |
| 同意问题，不同意级别 | 按核实后的级别处理，写明理由 |

## 复核

有 P0 时，修完交给同一个审阅者复核：
- 宿主支持时续用原审阅者会话，附上修复范围、拒绝的意见及理由
- 无法续用时派新的审阅者，附上前轮报告，只复核修复与波及范围
- 审阅者对拒绝的意见仍然坚持，或意见涉及已有决定：交用户裁决

复核通过为止。同一个问题反复修不好时，停下分析根因并报给用户。
