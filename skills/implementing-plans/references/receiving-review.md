# 接收执行者与审阅者的意见

执行者和审阅者都刻意不带主线程的上下文，他们的意见不一定成立，分级也可能偏差。主代理逐条核实，再决定怎样处理。

## 核实与处理

对照 plan.md、ADR、task.md 和实际代码核实每条意见：

| 核实结果 | 处理 |
| --- | --- |
| 代码问题属实 | 交执行者修复 |
| task.md 问题属实 | 主代理改 |
| 执行者报告的方案问题属实 | 按实施技能的偏离分流 |
| 缺少上下文造成的误会 | 拒绝，写明理由和证据 |
| 表述不清 | 重写表达，做法不变。plan.md 的措辞也属于修改定稿方案，加载 writing-plans 处理 |
| 同意问题，不同意级别 | 写明分级异议和理由 |
| 只是措辞偏好 | 不改 |

## 各轮之间

有阻塞问题：
1. 不论修复、拒绝还是下调分级，都派新的审阅者全量重审
2. 被拒绝的意见和分级异议连同理由交它复核
3. 审阅者接受理由，这条即告处理
4. 仍然坚持，或涉及 ADR 的决定：交用户裁决，之后不再重复提出

没有阻塞问题：
- 本轮通过
- 被拒绝的非阻塞意见和分级异议不再复核，连同理由记进 task.md 实施记录，验收时列给用户

## 三轮上限

同一任务或同一次整体审阅连续三轮未通过，停下，不开第四轮：
1. 分析根因，报给用户
2. 根因是修订方式在制造新问题：说明根因和改法，用户知情后继续
3. 其他根因（方案不可行、三方库或环境限制、执行者能力不足、漏掉分叉、ADR 矛盾）：由用户决定下一步
4. 用户决定或知情后，该对象重新计轮

## 向用户说明偏离

需要用户决定或确认的偏离，用这个格式：

```markdown
原来的约定：<ADR 或 plan.md 中的内容，注明编号或版本>
实际发现：<代码、运行结果、测量数据等证据>
具体后果：<照原约定做，什么场景下会发生什么>
处理建议：<修订方案、调整决定或补充调查，以及各自的代价>
影响范围：<受影响的任务、已完成的工作和协作方>
```
