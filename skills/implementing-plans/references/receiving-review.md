# 接收执行者与审阅者的意见

执行者和审阅者依据任务材料提出意见。主代理对照原始需求、已有决定和实际改动逐条核实，再决定如何处理。

## 分级

| 级别 | 含义 | 处理 |
| --- | --- | --- |
| P0 | 需求没满足、行为错误、缺少必要的验证，或与 ADR、用户决定、plan.md 契约矛盾 | 必须修 |
| P1 | 影响质量或可维护性，但行为正确 | 默认修；修复代价明显高于收益时可不修，写明理由 |
| P2 | 瑕疵，例如命名、风格 | 不必修，顺手能改的改 |

结论：没有 P0 即为通过。没修的 P1、P2 记进 task.md 实施记录，验收时列给用户。

## 核实与处理

对照 plan.md、ADR、task.md 和实际代码核实每条意见：

| 核实结果 | 处理 |
| --- | --- |
| 代码问题属实 | 按级别交执行者修复 |
| task.md 问题属实 | 主代理改 |
| 执行者报告的方案问题属实 | 按 implementing-plans 的“实现与方案不一致时”处理 |
| 缺少上下文造成的误会 | 拒绝，写明理由和证据 |
| 同意问题，不同意级别 | 按你认为的级别处理，写明理由 |

## 复核

有 P0 时，修完交给同一个审阅者复核：
- 宿主支持时续用原审阅者的会话，把修复内容、拒绝的意见和理由发给它。它已经读过代码，复核只看改动和波及范围
- 无法续用时，派新的审阅者，附上前轮报告，只复核修复和波及范围
- 审阅者对拒绝的意见仍然坚持，或意见涉及 ADR 的决定：交用户裁决

复核通过为止。同一个问题反复修不好时，停下分析原因，报给用户。

## 请用户决定方案变更

需要用户决定或确认方案变更时，说明以下内容：

```markdown
原来的约定：<ADR 或 plan.md 中的内容，注明编号或版本>
实际发现：<代码、运行结果、测量数据等证据>
具体后果：<照原约定做，什么场景下会发生什么>
处理建议：<修订方案、调整决定或补充调查，以及各自的代价>
影响范围：<受影响的任务、已完成的工作和协作方>
```
