# 收敛

开始时说明正在使用 `rivo:converging`，并用一句话说明本次要做什么。同一项工作中不重复声明。

用户决定方向和重要取舍，AI 查事实、提问题、给建议，并记录决定及其理由。能通过调查查明的事实先自行核实，沉默或跳过问题不视为同意。

一个回答可能引出新的问题。用 ADR 记录重要决定及其依赖，按依赖顺序继续讨论。

**产出：** `adr/`、`note.md` 和 before 图。不写 plan.md，不改产品代码。

## 流程

### 1. 了解需求和现状

读材料：
- 用户的请求和给出的材料
- 项目知识库（默认 `.rivo/knowledge/`）。把它的版本（提交号或修改时间）记进 note.md，收尾合并时要用
- 团队规约：CLAUDE.md、AGENTS.md、CONTRIBUTING.md 等
- 继续已有需求目录时：`adr/`、note.md、方案和审阅报告

问用户：
- **思路**：已有什么设想？
- **理由**：为什么这样想？

用户已经说明的思路和理由直接沿用；还没有思路时，从目标和现状一起探索。

确认现状：
- 加载 investigating 调查相关现状
- 加载 writing-clearly 画出 before 图
- 和用户确认"现在是什么样"，再讨论做法，避免基于不同的现状描述做决定

### 2. 按轮提问

每轮讨论前提已经确定、现在就能回答的问题。下文把这组问题称为“前沿”。

每轮开头一行说明进度：已确定哪些事，本轮还有几个问题。

每个问题写明：
- **场景**：什么情况下要做这个选择
- **依据**：查到的事实，各选项的代价
- **建议答案**

控制每轮范围：
- 前沿问题一次问完，先问影响后续选择较多的问题
- 提问工具一次放不下时，按工具上限分批发出，仍算同一轮
- 依赖本轮其他答案的问题，留到下一轮
- 讨论中冒出的旁支问题，留到下一轮，免得打断本轮

应对回答：
- 回答打开了新方向：先调查，再提解法
- 认为用户的方向有问题：带着证据和影响提出来

### 3. 记录本轮决定

用户答完一轮后，先记录决定，再准备下一轮问题：
1. 按 [adr.md](references/adr.md) 的判定标准检查每个回答。达到门槛的写成或更新 ADR，其余暂记 note.md 的“已确认的方案细节”，注明决定来源，写 plan.md 时纳入
2. 更新了已有 ADR 时，沿"依赖"检查下游 ADR 是否仍成立。不成立的同样交用户决定
3. 根据新决定和“引出的问题”整理下一轮可以回答的问题

### 4. 确认可以写方案

三条都满足才结束讨论：
1. **本期问题已处理**：每份 ADR 的"引出的问题"都已回答、被用户划出本期，或经用户同意延后并写明影响和解决时点；核心设计缺口（见 writing-plans）不能延后。标成“方案细节”的，答案要已经记在 note.md 的“已确认的方案细节”里；只是留到写方案时再定的，不算已回答
2. **场景走得通**：拿主场景和本需求的失败场景对照已有决定走一遍。发现缺少事实就调查；发现尚未确认的行为规则或关键取舍就继续提问
3. **用户确认理解一致**：简短复述完整做法和关键理由，说明各场景依据哪些 ADR 或已确认的方案细节，用户确认

把三条的检查结果和日期写进 note.md，状态行改为“讨论结束”。向用户说明接下来会编写技术方案、组织独立审阅，再交给用户确认，然后加载 writing-plans。

## 重开已有决定

评审、实施或验收中发现某份 ADR 要改时，回到这里：
1. 向用户说明原决定、新证据和影响，取得决定
2. 按 adr.md 更新或替换 ADR
3. 按“记录本轮决定”检查依赖该决定的其他 ADR
4. 继续讨论新问题，满足上述三条结束条件后加载 writing-plans 修订方案，由用户确认

如果用户已经做过决定，只是缺少记录，按 adr.md 补写后继续原来的方案编写或实施工作。
