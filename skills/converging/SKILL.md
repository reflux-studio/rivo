# 讨论需求与做法

用户决定方向和重要取舍，AI 查事实、提问题、给建议，并记录决定及理由。能通过代码或配置查明的事实先自行核实，沉默或跳过问题不视为同意。

**产出：** `decisions.md`、`adr/`。调查结论由 `investigating` 写进 `research/`。本阶段不写 `plan.md`，不改产品代码。

## 流程

### 1. 了解需求与确认方向

先读材料：
- 用户的请求、PRD、设计稿和给出的材料
- 项目知识库（默认 `.rivo/knowledge/`）。把读到的版本（提交号或修改时间）记进 `decisions.md` 的依据
- 团队规约：`CLAUDE.md`、`AGENTS.md`、`CONTRIBUTING.md` 等
- 继续已有需求目录时：`decisions.md`、`adr/`、`research/`、方案和审阅报告

确认方向起点：
- 设计方案前，先询问用户是否已有方向思路或模块拆解；如用户回复没有，才允许你先查清现状并自行设计候选方案
- 用户已经给出的拆解和思路直接作为讨论起点，核对有无遗漏和边界冲突
- 按 [决定记录模板](references/decisions.md) 建立 `decisions.md`：明确要做的写进“范围”，候选做法和待查问题写进“待决事项”，用户明确排除的写进“不做的事”

### 2. 找出依赖并调查

先处理会约束多个模块的问题。各模块分头做决定，容易对同一个字段或接口定出两套规则。

- 找出跨模块共用的数据定义、接口、权限、发布条件，以及共用改动可能影响、不能破坏的老功能
- 加载 `investigating` 查清现状，验证候选做法是否可行；涉及界面时，一并查清设计稿元素与本地组件库、同类样板页面的对应关系
- 调查改变了拆解或依赖时，更新 `decisions.md` 的范围
- 现状复杂时画现状图，先和用户确认“现在是什么样”，再讨论怎么改

### 3. 按轮讨论取舍

把需要拍板的问题按依赖排好：每轮只问前提已经确定、现在就能回答的问题；依赖本轮答案的问题留到下一轮。

每轮开始前重读 `decisions.md`。如果新问题与已有决定冲突，先指出原决定再问，不默默覆盖。

每个问题按编号写清三项：
- **场景**：什么情况下要做这个选择
- **依据**：查到的事实，各选项的代价
- **建议**：推荐选哪个、为什么

控制每轮范围：
- 当前能回答的问题一次问完，先问影响模块多的
- 能在代码或知识库里查到的事实自己查，不拿去问用户
- 认为用户的方向有问题时，带着证据和具体后果提出来

### 4. 记录本轮决定

用户答完一轮后，先记录，再准备下一轮：
- 每个决定在 `decisions.md` 记一行，注明来源；已解决的待决事项从表里移走
- 达到 [ADR 模板](references/adr.md) 门槛的决定另写一份 ADR，`decisions.md` 的那一行链接过去
- 没有实质选项的工作只保存调查结论，模块、依赖和 ADR 不要求一一对应
- 更新已有决定时，沿依赖检查下游决定是否仍然成立

### 5. 确认可以写方案

三条都满足才结束讨论：
1. `decisions.md` 的待决事项都已回答、划出本期，或经用户同意延后并写明影响和解决时点。会改变主流程、跨系统契约或数据落点的问题不能延后
2. 拿主场景、异常与失败处理（超时、幂等、并发、部分失败）、权限边界、上线初始/存量数据兼容以及不能破坏的老功能沿模块走一遍，能走通并把关键验收标准记入 `decisions.md`
3. 简短复述完整做法和关键理由，用户确认理解一致

用户确认后，加载 `writing-plans` 进入方案阶段。

## 改变已有决定

方案批准前，决定可以随讨论直接改写。方案批准后要改变范围或某项决定时，加载 `revising` 处理（如果底层模型需要推翻重做，则另开重构需求）。用户决定过、只是漏记的，补记后继续。
