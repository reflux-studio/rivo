# 收敛

开始时声明："正在使用 rivo:converging，和你一起把这次需求的做法讨论清楚。"

**核心原则：** 用户定方向和决定，AI 查事实、提问题、给建议，并把每个定下的分叉当场写成 ADR。

讨论是一棵决策树，每个回答都可能打开新的分叉，`adr/` 就是这棵树。

**产出：** `adr/`、`note.md` 和 before 图。不写 plan.md，不改产品代码。

## 流程

### 1. 对齐起点

读材料：
- 用户的请求和给出的材料
- 项目知识库（默认 `.rivo/knowledge/`）。把它的版本（提交号或修改时间）记进 note.md，收尾合并时要用
- 团队规约：CLAUDE.md、AGENTS.md、CONTRIBUTING.md 等
- 继续已有需求目录时：`adr/`、note.md、方案和审阅报告

问用户：
- **蓝图**：已有什么思路？
- **理由**：为什么这样想？

用户没有蓝图时，一起探索。

对齐现状：
- 加载 investigating 调查相关现状
- 加载 writing-clearly 画出 before 图
- 和用户确认"现在是什么样"，再开始提问。对现状理解不一致，后面的决定都会建在错的前提上

### 2. 按轮提问

每轮问决策树的**前沿**：前提都已确定、现在就能回答的问题。

每轮开头一行说明进度：已定下哪些分叉，本轮问几个。

每个问题写明：
- **场景**：什么情况下要做这个选择
- **依据**：查到的事实，各选项的代价
- **建议答案**

控制每轮范围：
- 一轮最多 5 个问题，先问牵动后续分叉最多的。再多用户记不住前面的问题
- 依赖本轮其他答案的问题，留到下一轮
- 讨论中冒出的旁支问题，留到下一轮，免得打断本轮

应对回答：
- 回答打开了新方向：先调查，再提解法
- 认为用户的方向有问题：带着证据和影响提出来

### 3. 收轮

用户答完一轮，先收轮，再问下一轮：
1. 按 [adr.md](references/adr.md) 的判定标准检查每个回答。达到门槛的写成或更新 ADR，其余留给 plan.md
2. 更新了已有 ADR 时，沿"依赖"检查下游 ADR 是否仍成立。不成立的同样交用户决定
3. 从新决定和"引出的问题"算出下一轮前沿

### 4. 检查出口条件

三条都满足才结束讨论：
1. **没有未决分叉**：每份 ADR 的"引出的问题"都已回答，或被用户划出本期
2. **场景走得通**：拿主场景和本需求的失败场景对照已有决定走一遍。需要 AI 自行假设的地方，就是还没问的分叉
3. **用户确认理解一致**：简短复述完整做法和关键理由，每个场景一行写明由哪份 ADR 覆盖，用户确认

然后宣布："所有问题已确认，接下来用 writing-plans 写技术方案，独立审阅通过后交给你确认。"并加载 writing-plans。

## 重开已有决定

评审、实施或验收中发现某份 ADR 要改时，回到这里：
1. 向用户说明原决定、新证据和影响，取得决定
2. 按 adr.md 更新或替换 ADR
3. 按收轮检查下游
4. 新引出的问题照常提问，出口条件满足后加载 writing-plans 修订方案，由用户确认

只为补记漏记的决定而来时，按 adr.md 补写后直接回去。

## 常见错误

| 你在想 | 应当怎么做 |
| --- | --- |
| "这个问题问用户就行" | 能查到的事实先自己查，只把决定交给用户。 |
| "眼下没问题可问了，讨论结束" | 逐条过出口条件，尤其是场景走查。 |
| "这个决定不大，先不记" | 收轮时按判定标准检查，达到门槛就写。 |
| "先整理一份讨论快照" | `adr/` 就是记录，满足出口条件后直接进 writing-plans。 |
| "用户没反对，就当同意了" | 只有明确的回答才算决定。 |
