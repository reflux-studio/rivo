# 讨论需求与做法

开始时说明正在使用 `rivo:converging`，并用一句话说明本次要做什么。同一项工作中不重复声明。

用户决定方向和重要取舍，AI 查事实、提问题、给建议，并记录决定及理由。用户已经给出的拆解和做法是讨论的起点。

**产出：** note.md 中的需求总览、`adr/`、必要的现状图。不写 plan.md，不改产品代码。

## 流程

### 1. 整理需求总览

读材料：
- 用户的请求和给出的材料
- 项目知识库（默认 `.rivo/knowledge/`）。把读到的版本（提交号或修改时间）记进 note.md，收尾合并时要用
- 团队规约：CLAUDE.md、AGENTS.md、CONTRIBUTING.md 等
- 继续已有需求目录时：note.md、`adr/`、方案和审阅报告

按 [需求总览模板](references/requirements.md) 写进 note.md：
- **沿用用户的拆解**：用户已经划分模块时，核对遗漏、边界和依赖；没有时按可观察的结果拆
- **分清三类输入**：明确的范围、候选做法、待查事实。“同事之前接过一版”是调查线索，查过才算结论
- **范围以用户的最新说法为准**：用户取消的内容记为排除项。旧 PRD、设计稿和代码现状与它冲突时，查清影响再问用户
- **模块写结果**：技术改造、数据迁移和上线准备也可以是模块，写清它服务于哪项结果

### 2. 找出依赖并调查

先处理会约束多个模块的问题。各模块分头决定，容易对同一个字段或接口得出不同的定义。

- 找出跨模块共用的数据定义、接口、权限和发布条件
- 加载 investigating 查清现状，验证候选做法是否可行
- 调查改变了拆解或依赖时，更新需求总览
- 现状复杂时加载 writing-clearly 画现状图，先和用户确认“现在是什么样”，再讨论做法

### 3. 按轮讨论取舍

每轮讨论前提已经确定、现在就能回答的问题。每个问题写明：
- **场景**：什么情况下要做这个选择
- **依据**：查到的事实，各选项的代价
- **建议**：推荐哪个，为什么

控制每轮范围：
- 当前能回答的问题一次问完，先问影响模块多的
- 依赖本轮其他答案的问题，留到下一轮
- 能查明的事实自己查，不拿来问用户
- 认为用户的方向有问题时，带着证据和影响提出来

### 4. 记录本轮决定

用户答完一轮后，先记录，再准备下一轮：
- 达到 [ADR 模板](references/adr.md) 门槛的决定写成 ADR；其余记进 note.md 的“已确认的做法”，注明来源
- 没有实质选项的工作只保存调查结论，例如核对已有字段对应哪个 key。功能、依赖和 ADR 不要求一一对应
- 更新已有 ADR 时，沿“依赖”检查下游决定是否仍成立
- 决定改变了模块边界或依赖时，更新需求总览

### 5. 确认可以写方案

三条都满足才结束讨论：
1. **本期问题已处理**：需求总览里的待决问题都已回答、被用户划出本期，或经用户同意延后并写明影响和解决时点。会改变主流程、跨系统契约或数据落点的问题不能延后
2. **场景走得通**：拿主场景和失败场景沿模块走一遍，包括上线当天的初始数据和外部入口。缺事实就调查，缺决定就继续问
3. **用户确认理解一致**：简短复述完整做法和关键理由，用户确认

用户确认后，说明接下来会写技术方案、组织独立审阅，再交用户确认，然后加载 writing-plans。用户只要求讨论时到此结束。

## 重开已有决定

评审、实施或验收中发现某个决定要改时，回到这里：
1. 向用户说明原决定、新证据和影响，取得决定
2. 按 ADR 模板更新或替换 ADR，检查依赖它的决定和模块
3. 满足上面三条后，加载 writing-plans 修订方案

讨论期间，不依赖这个决定的工作继续进行。用户做过决定、只是缺少记录时，补写后继续原来的工作。
