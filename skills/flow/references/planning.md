# 写 task.md

task.md 是粗粒度的实施方案。它告诉执行者要交付什么、按什么顺序、守住哪些契约、怎样算完成；怎样实现由执行者读方案和代码后自己决定。写到修改哪些文件、每一步怎么编码的实施方案，信息量就等于代码，篇幅会和技术方案一样长。

## 拆分方法

每项任务交付一项可以单独检查的结果，说清用户或调用方能观察到什么。配置、脚手架和测试归入需要它们的任务，不单列。

先排会影响后续结构的任务，让风险最高的假设最早被验证。标明任务之间的依赖；没有依赖、也不会改动同一处的任务可以并行。

多项任务共用的约定写在"共同约定"里，例如接口名、字段、状态语义、代码风格和工作分支，使用 plan.md 中的实际值。单项任务只写它特有的契约。拆分时发现 plan.md 缺少契约，按实施技能中的偏离分流处理，不在 task.md 里补定。

验收写可以检查的场景和预期结果，或指向 plan.md 中的验证安排。

## 结构

```markdown
# <需求名称>：实施方案

依据：plan.md <版本>，adr/<编号范围>。代码仓库、分支与已有授权。

## 共同约定

所有任务都要遵守的契约和工程约定。

## 任务

| 任务 | 可验证结果 | 依赖 |
| --- | --- | --- |
| T1 <名称> | <做完后能观察到什么，必须遵守的特有契约> | 无 |

## 验收

逐任务审阅、整体审阅，以及 plan.md 中要求的验证步骤。

## 实施记录

按任务记录实现选择、被拒绝的非阻塞意见、分级异议和偏离处理。
```

## 自查

写完逐节对照 plan.md，确认每项需求、契约和验证安排都落在某项任务或共同约定里，任务之间没有矛盾的契约。覆盖完整即开工。
