# 接收执行者与审阅者的意见

执行者和审阅者都刻意不带主线程的上下文，他们提出的问题不一定成立，分级也可能偏差。主代理逐条核实，再决定怎样处理。

## 核实与处理

对照 plan.md、ADR、task.md 和实际代码核实每条意见：

- 属实的，修复。代码问题交给执行者；task.md 的问题由主代理改。执行者报告的方案问题属实时，按实施技能中的偏离分流处理。
- 因为缺少上下文而产生的误会，拒绝，写明理由和证据。
- 由表述不清引起的，改写表达，做法不变。task.md 由主代理直接改；plan.md 的措辞即使只改表达，也是对定稿方案的修改，加载 course 处理。
- 同意问题、但不同意分级的，写明分级异议和理由。

## 各轮之间

报告里有阻塞问题时，不论修复、拒绝还是下调分级，都由新的审阅者全量重审，并把被拒绝的意见和分级异议连同理由交给它复核。审阅者接受理由，这条意见即告处理；仍然坚持，或者意见涉及某份 ADR 的决定，交给用户裁决，此后的审阅不再重复提出。用户支持主代理的，该意见即告处理，这一轮没有其他阻塞问题即为通过。

报告里没有阻塞问题时本轮即为通过，被拒绝的非阻塞意见和分级异议不再复核，连同理由记进 task.md 的实施记录，请用户验收时一并列出。

## 三轮未通过

同一任务或同一次整体审阅连续三轮未通过，停下来分析根因，把分析报给用户，不开第四轮。

根因是修订方式在制造新问题的，说明根因和改法，用户知情后继续。其余根因都由用户决定下一步，例如方案内容不可行、三方库或环境限制、执行者能力不足、讨论漏掉了分叉、ADR 之间有矛盾。用户决定或知情后，该对象重新计轮。

## 向用户说明偏离

实现偏离 ADR 或 plan.md 的内容、需要用户决定或确认时，用下面的格式：

```markdown
原来的约定：<ADR 或 plan.md 中的内容，注明编号或版本>
实际发现：<代码、运行结果、测量数据等证据>
具体后果：<照原约定做，什么场景下会发生什么>
处理建议：<修订方案、调整决定或补充调查，以及各自的代价>
影响范围：<受影响的任务、已完成的工作和协作方>
```
