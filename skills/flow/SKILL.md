# 实施任务

开始时声明：“正在使用 rivo:implementing-tasks，完成当前实施、审阅或验证工作。”

主代理按用户确定的方向组织任务、查证问题和说明进展，执行者实现并自查，独立审阅者检查真实改动与证据。方向分歧交回用户，主代理和审阅者都不能代替其作决定。每项任务都要审阅，最终还要验证组合行为和原始目标。

**实施必须有用户授权。实现完成只表示待审；实现或依据变化后，必须重新审阅和验证受影响部分。** 用户只要求代码评审或验证，就处理指定范围，不自动修改实现或重启方案讨论。

## 核对当前依据

读取原始目标、会话决定、已有 plan、task、note、ADR、审阅报告和实际改动。开始正式实施前，核实 plan 已通过独立审阅和用户审阅，task 已通过独立审阅。报告需对应当前内容，文件存在不等于通过。

单独审阅或验证按已有要求和实际改动检查，不把补齐实施批准或过程文件作为检查前提。材料缺失影响判断时，在结果中说明具体证据缺口；本次检查不授权修复或启动后续流程。

准备实施时，缺少方案文档就加载 writing-designs，缺少任务安排就加载 planning-tasks，缺少决定就加载 discussing-designs 讨论具体缺口；技术事实不清楚时加载 investigating。需求简单可以写短方案和任务，不跳过审阅。已有批准和实施授权继续沿用，不重复索取；用户沉默或关闭问题不是批准。

用宿主任务工具建立或沿用总清单，没有时在会话列出：核对依据、派发当前任务、接收实现和自查、独立审阅、修复复审、整体验证、交接。各任务完成条件成立后再更新进度。

## 派发与检查

1. 从 task 提取当前任务的完整上下文，按 [任务简报](references/task-brief.md) 补齐工作区、授权、依赖和验收。
2. 按 [执行者提示词](references/implementer-prompt.md) 启动新的执行者，提供适用技能。执行者只完成本任务，不嵌套派发。
3. 接收实现、验证与自查结果，核对完整修改和未完成内容。适用行为采用 test-driven-development；异常定位使用 systematic-debugging。
4. 按 [审阅者提示词](references/reviewer-prompt.md) 启动不同于执行者的独立审阅者，检查完整任务改动、调用影响、约定与证据。
5. 修复后重新验证，并启动新的审阅者复审；带上当前依据、前轮报告和本轮差异。
6. 当前任务实现、适用验证和独立审阅均通过后，再推进依赖任务。

独立任务确实不会互相覆盖修改或依赖未完成契约时可以并行。默认逐项推进，不以多开子代理代替任务划分。

给执行者实际规则和契约，不只发路径或章节编号。给审阅者真实代码版本或快照，包括未提交和未跟踪文件；多个仓库分别说明。无需为了审阅而提交代码。

## 变化与重新评审

发现偏差时先判断：是实现没有遵守约定，还是原来的约定需要改变。原规则仍成立的实现缺陷直接修复、验证、独立复审；可选改进不阻塞交付。

新事实影响设计时，加载 investigating 查清机制并更新 note，说明原约定、新证据、后果和影响范围。涉及业务含义、模型、公共契约或重大不可逆操作，必须取得用户决定；不能把“代码已写好”当作批准。

先向用户说明新证据如何影响其原方案，以及建议调整的部分，不用已经写好的代码倒逼接受。通过 discussing-designs 重新讨论受影响的问题，重要选择加载 architecture-decisions，结构或流程变化加载 using-archify。方案由 writing-designs 重写相关内容并完成独立与用户审阅，任务由 planning-tasks 更新并独立复审。

**修改实现、方案或任务后，旧审阅结论不能直接沿用到受影响工作。** 检查正在执行和已完成的任务，将更新后的依据交给相关执行者，重新验证关联行为。只暂停依赖变化的部分，无关工作继续按有效约定推进。

修订正文要整合新结论，必要时重写，不靠追加说明掩盖冲突。保留历史 ADR、审阅和验证证据。反复复审没有新进展时，查清争议或请用户裁决设计分歧，不以增加轮次碰运气。

## 整体验证与交接

所有任务完成后，启动新的独立审阅者检查组合行为、原始功能范围、外部协作、兼容和发布安排。单个模块通过、构建通过或任务勾完，都不能代替这次检查。

验证用户可观察的结果，区分静态推断、模拟验证和真实集成。环境错误不算行为测试失败；无法取得必要证据时，说明未完成范围。约定需要用户验收的事项等待用户验收。

交付说明实际改动、版本、审阅与验证结果、剩余外部依赖和发布事项。在已有授权内完成提交或交接；实施授权不自动包含发布、合并或其他重大不可逆操作。

可复用的新事实通过 knowledge-management 更新现有项目知识，只有已实现并核实的能力才能写成系统现状。全部交付事项完成后才归档；不能用归档表示未完成事项已经解决。

## 文件与记录

代码在各自项目修改，过程文件沿用本需求的 `.rivo/issues/<slug>/`，用户指定位置优先。task 维护当前任务约定和实施结果，note 保存调查认识，plan 保存目标方案。

审阅报告按 [审阅记录](references/review-report.md) 写入 `reviews/<task>-<round>.md`，终审按同样方式逐轮留存；日志、截图和验证材料放在 `evidence/`。派发简报从当前任务提取，不再新增一套长期任务文档。写作使用可用的 writing-clearly-and-concisely。

继续任务时，从文件、报告、真实改动与会话中核对进展和批准，不增加状态台账，也不推测缺失的授权。

## 常见错误（Red Flags）

| 你在想 | 应当怎么做 |
| --- | --- |
| “执行者自查过，可以完成任务” | 独立审阅真实改动和证据。 |
| “修复很小，不必再审” | 对修复及关联影响重新审阅。 |
| “方案变了，只改后续任务即可” | 检查已完成和在途实现是否仍成立。 |
| “每个任务都通过，需求就完成” | 对照原始目标验证组合行为。 |
