# 验收标准写法

## 前提 / 动作 / 结果

适合存在明确前置条件和操作的行为：

```text
Given [用户、数据和系统状态]
When [用户动作或系统事件]
Then [可观察结果]
```

一个场景存在多个重要结果时，可以写多个 Then，但不要把互不相关的行为塞进同一条。

## 核对表

适合简单功能、规则或多项静态要求：

```text
- [ ] 用户可以……
- [ ] 当……失败时，系统显示……
- [ ] 未授权用户不能……
```

## 应覆盖什么

- 核心正常路径；
- 最重要的错误路径；
- 权限和角色差异；
- 空数据和边界输入；
- 重复提交、取消、重试或超时等适用行为；
- 不应发生的副作用；
- 兼容旧行为的要求。

## 常见问题

- **不可观察**：“系统正确处理请求”。应写用户、接口或数据能观察到什么。
- **无法判定**：“页面加载要快”。应给阈值、基线或明确测试方式。
- **指定实现**：“使用 Redis 缓存”。除非技术选择本身是外部硬约束，否则写目标结果。
- **只写正常路径**：没有错误、权限和边界行为，实现的人只能自行决定。
- **一条太大**：同时覆盖多个独立场景，失败时无法判断哪部分未完成。
- **照抄要求**：验收标准应比要求更可执行，而不是换一种说法重复。
