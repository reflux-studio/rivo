# 知识文档

优先沿用项目已有模板、主题划分和导航。没有现成模板时，按读者要理解或执行的事情组织，不按本次会话过程编排。文件长短不决定是否拆分，主题能否独立理解才是依据。

## 选择阅读主线

| 文档用途 | 可以怎样展开 |
| --- | --- |
| 机制说明 | 能力与场景、系统中的位置、工作方式、约束与理由、使用和维护 |
| 研究发现 | 要回答的问题、主要发现、适用人群与条件、依据与限制、对后续判断的启示 |
| 操作指南 | 适用场景、前置条件、操作步骤、结果检查、失败处理 |
| 契约参考 | 用途与适用版本、精确定义、示例、兼容与限制 |

这些是阅读顺序，不是必须填满的槽位。已有团队格式优先，内容不需要的章节不凑。

## 把关系讲清楚

新同事从头读到尾，应当能理解现在怎样工作、为什么有这些约束，以及修改时要注意什么。用连贯段落解释因果和流转，字段或规则需要对照时用表格，结构和流程适合时配图。

例如，仅写“缓存：十分钟；失效：发布后；异常：回源”，读者还不知道这些规则怎样配合。可以写成：

> 配置发布后，服务先使旧缓存失效，再读取新版本。正常读取的结果缓存十分钟；缓存不可用时直接读取来源，因此仍能拿到配置，但请求耗时会增加。

这只是表达示例，实际机制必须有来源支撑。

## 保留边界与来源

- **只写已核实的认识**：未知部分说明范围，目标和建议保留其原有性质
- **注明适用条件**：系统版本、环境、样本和时间可能影响结论，仍适用于旧范围的内容不直接删除
- **来源集中且可追溯**：指向原始材料、有效决定与核实证据。正文讲清内容，文件名和行号不代替解释
- **不搬排查流水**：排查过程留在原工作记录，知识保留复用所需的结论和理由
- **核对合并基线**：他人新增的知识保持原样，有冲突先协调，不能用旧副本覆盖当前文件
- **归档后检查链接**：引用使用材料的实际位置，移动后核实引用目标仍存在
