# 设计测试用例

开始时说明正在使用 `rivo-testing:designing-tests`，并用一句话说明本次要做什么。同一项工作中不重复声明。

通过宿主发现公共 `rivo:using-rivo`，读取测试工作约定。公共包不可用时说明依赖缺失并停止领域执行。输入可以是用户给定的需求、规则、设计、接口和待测对象，不要求其他领域插件或完整源码。

测试预期来自需求和已确认规则。接口、设计和实现可以帮助识别入口与观察方式，不能替代业务依据。

## 流程

### 1. 核对依据和范围

读取当前材料，记录来源与版本：
- 要验证哪些用户任务、接口或业务结果，哪些不在本次范围
- 哪些规则已经确认，哪些仍有歧义或冲突
- 实际入口、运行环境、依赖、账号和测试数据是否可用
- 当前最可能失败、失败后影响最大的地方是什么

材料不可读或规则不清时，写明影响，只暂停依赖部分。已有团队材料可以直接引用，不复制成另一套需求。

### 2. 按风险选择场景

从入口追到可观察结果，覆盖与本次任务有关的正常、异常、权限、兼容和恢复场景。按问题选择方法：

| 情况 | 做法 |
| --- | --- |
| 一组输入按同一规则处理 | 用等价类选有效与无效的代表值，检查各类是否确实得到不同处理 |
| 范围、长度、数量或时间有临界点 | 检查边界本身和边界两侧；先核对包含关系与单位 |
| 多个条件共同决定结果 | 用决策表列条件组合与预期，删去有依据的不可能组合 |
| 行为取决于当前状态 | 覆盖允许与禁止的状态迁移，以及重复、取消和中断后的行为 |
| 数据跨页面、服务或异步流程流转 | 沿数据流核对读取、写入、传递和下游结果，关注失败后的状态 |

这些方法用来找遗漏，不要求每项需求套齐全部方法。高风险组合需要单独检查，不能因为单个条件测过就视为组合已覆盖。

### 3. 写可执行的用例

按 [用例模板](references/cases.md) 记录场景和覆盖关系：
- 每条用例有稳定 ID、需求依据、风险和验证方式
- 前置条件写明账号、权限、数据、依赖和必要状态
- 操作给出实际输入与步骤，预期写可观察的输出和最终状态
- 有持久化或下游承诺时，安排刷新、重查或下游检查，不只看成功提示
- 有设计依据时，加入对应窗口、数据与状态下的视觉及交互预期

例如规则是“只接受 1 至 10 的整数”时，可以检查 1、10、范围内代表值、0、11、小数和其他类型。范围两端是否包含、类型不符如何反馈，都要有依据；规则没有说明时先问负责人。

### 4. 核对缺口

沿主场景和失败场景走一遍，检查用例能否区分正确与错误：
- 验证只检查了字段存在，还是检查了正确的值和行为
- 需求或风险是否都有对应场景，无法覆盖的原因是什么
- 自动化或人工执行需要什么工具、数据和观察条件

业务预期有歧义交需求负责人，设计或技术问题交对应负责人，通过公共 `rivo:collaborating` 发起请求。测试提出证据和建议，不批准或修改他人的需求、设计或技术方案。

### 5. 交付测试设计

按公共 `rivo:writing-clearly` 说明覆盖、风险、未决问题和执行条件。用户要求继续执行时加载 `rivo-testing:testing`；只做测试设计时到此结束。

## 修订用例

预期需要改变时，先核对负责人确认的新依据，再使用公共 `rivo:revising` 更新受影响用例。保留可恢复版本和原失败证据，在原处写清当前预期，不能为了匹配实现改规则。执行结果另记，不混进用例定义。
