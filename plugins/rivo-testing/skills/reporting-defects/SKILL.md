# 报告缺陷

开始时说明正在使用 `rivo-testing:reporting-defects`，并用一句话说明本次要做什么。同一项工作中不重复声明。

通过宿主发现公共 `rivo:using-rivo`，读取测试工作约定。公共包不可用时说明依赖缺失并停止领域执行。缺陷输入可以来自用户反馈、实际测试或已有记录，不要求其他领域插件。

报告要让负责人理解差异、按步骤复现，并知道需要处理什么。测试负责事实和质量判断，产品实现由开发修改，业务预期由需求负责人确认。

## 流程

### 1. 核对依据并复现

对照需求、设计或已确认规则，先记录：
- 依据来源与版本，以及实际待测版本和环境
- 账号、权限、数据与初始状态
- 触发问题的步骤和输入，是否稳定复现

安全且有授权时重复操作，保留日志、截图或查询结果。无法复现时保留原现象和本次检查条件，不把“未复现”写成“已修复”。预期缺失或冲突时先交需求负责人确认，不能从当前实现倒推预期。

### 2. 写清差异和影响

按 [缺陷模板](references/defect.md) 写记录：
- 标题说明触发条件与可见现象，步骤只保留复现所需内容
- 预期引用依据，实际写观察到的结果，原因假设另行说明
- 描述影响哪些用户、数据或流程，给出严重程度及理由
- 证据能定位到相应操作和版本，敏感数据按授权处理

沿用团队已有严重程度定义。没有定义时说明具体影响，不能只留下一个没有解释的等级。

### 3. 交对应负责人

通过公共 `rivo:collaborating` 核对工单里的实际参与方，发起开发修复请求或需求确认请求：
- 请求带缺陷记录和所需反馈，详情留在独立记录中，工单只留精简索引
- Agent 联系遵循已有授权和真实通信能力；真实 IM 等外部消息需要相应授权
- 接收方、权限或材料不足时保留待处理状态和解除条件，不声称已经送达
- 重发前查看现有请求与回复，避免同一缺陷反复通知

使用已有缺陷系统时引用其中的记录，不维护第二份相互独立的处理状态。

### 4. 跟踪修复与复测

记录负责人回复和修复版本，加载 `rivo-testing:testing` 核对实际运行版本并复测：
- 验证原步骤的预期，再按影响回归
- 复测失败继续反馈新的版本和证据
- 受阻或无法观察时保留缺口，不提前关闭
- 保留原失败、每次回复与后续运行的链接

测试可以协助定位，但不修改产品代码或需求，也不替负责人接受剩余风险。交付时说明真实的交接与复测状态，不能把收到回复等同于问题已经解决。

## 更正记录

原记录有误时，保留可恢复版本，原处改写本次事实，说明更正依据。新的运行另记，不把原失败改成通过；业务预期变更先核对负责人确认的依据。
