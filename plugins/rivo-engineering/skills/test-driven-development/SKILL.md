# 测试驱动开发（TDD）

先写测试，看着它失败，再写最小的代码让它通过。

核心原理：**没看着测试失败过，你就不知道它测的是不是对的东西。**

## 什么时候用

TDD 是推荐纪律，不是强制流程：是否采用，在动手之前自己判断。行为能预先说清、可以先写断言的工作（新功能、缺陷修复、行为变更）收益最大；探索性原型、生成的代码、配置文件和保持行为的既有代码重构，收益可能不抵成本。

无论用不用 TDD，交付底线不变：实现必须带上能证明行为的自动化测试。

**一旦决定采用，下面的规则没有「就这一次跳过」**——中途想跳过是合理化，不是判断；判断只发生在动手之前。

## 铁律

```
没有先失败过的测试，就没有生产代码
```

先写了代码？删掉，重来。不留作「参考」，不边写测试边「改编」它，不看它——删除就是删除，照着测试重新实现。

## 红-绿-重构

```
红：写一个失败的测试
 │
 ▼
验证红——它因对的理由失败了吗？ ──否（报错，或直接通过）──▶ 修测试，重新验证
 │ 是
 ▼
绿：写最小实现
 │
 ▼
验证绿——本条通过，全套仍绿吗？ ──否──▶ 改代码（不改测试）
 │ 是
 ▼
重构（保持全绿，不加行为） ──▶ 下一条
```

### 红——写失败的测试

写一个最小的测试，表达「应该发生什么」。

好的样子——名字清晰、测真实行为、一次一件事：

```typescript
test('失败的操作重试 3 次', async () => {
  let attempts = 0;
  const operation = () => {
    attempts++;
    if (attempts < 3) throw new Error('fail');
    return 'success';
  };

  const result = await retryOperation(operation);

  expect(result).toBe('success');
  expect(attempts).toBe(3);
});
```

坏的样子——名字模糊、测的是 mock 不是代码：

```typescript
test('重试能用', async () => {
  const mock = jest.fn()
    .mockRejectedValueOnce(new Error())
    .mockRejectedValueOnce(new Error())
    .mockResolvedValueOnce('success');
  await retryOperation(mock);
  expect(mock).toHaveBeenCalledTimes(3);
});
```

要求：一个行为、名字说清行为、用真代码（万不得已才 mock）。

### 验证红——看着它失败

**必做，永不跳过。** 跑这一个测试，确认三件事：

- 它是**失败**，不是报错。
- 失败信息符合预期。
- 失败的原因是功能还不存在，不是拼写错误。

测试直接通过了？你在测已经存在的行为，改测试。测试报错了？修到它「正确地失败」为止。

### 绿——写最小实现

写刚好让测试通过的代码：不加测试之外的功能（可配置的重试次数、没人要的回调都等它们自己的测试），不顺手重构别处，不超出测试范围「改进」。

### 验证绿——看着它通过

**必做。** 确认：本条测试通过；其他测试没被弄坏；输出干净，没有报错和警告。

测试没过？改代码，不改测试。别的测试坏了？现在就修，不留到以后。

### 重构——清理

只在全绿之后：去重、改名、提取辅助函数。保持测试全绿，不添加行为。

## 选测试的层级与类型

写测试之前先选对层级：

```
      /   端到端   \    少、慢、高置信——只留关键用户路径
     /    集成      \   适量、中速——跨模块的行为
    /     单元       \  多、快、聚焦——大多数逻辑住这层
```

- 按对象选类型：API 端点用业务逻辑单测加 HTTP 层集成测试；数据处理看输入校验、转换正确性、幂等性；前端用组件测试和交互测试。
- 该测的：业务关键路径、错误处理、边界情况、安全边界、数据完整性。
- 不必测的：平凡的取值方法、框架自身的行为、一次性脚本。

## 为什么顺序不能反

**「我写完代码再补测试验证」**——事后写的测试立即通过，而立即通过什么都证明不了：可能测错了东西、可能测的是实现不是行为、你从没见过它抓住任何问题。

**「我已经手动测过所有边界了」**——手动测试是临场的：没有记录、代码一改就得重来、压力之下必有遗漏。「我试的时候是好的」不等于系统化验证。

**「删掉几小时的工作太浪费」**——沉没成本谬误。时间已经花掉了，现在的选择是：删掉按 TDD 重写（再花几小时，高置信），或者留着补测试（半小时，低置信，大概率带着 bug）。真正的浪费是留着一份你无法信任的代码。

**「事后测试也能达到同样目的」**——不能。事后的测试回答「它做了什么」，事先的测试回答「它该做什么」。事后测试被你的实现锚定：你测你写出来的，不是需求要求的；你验证你记得的边界，不是被逼着发现的边界。

## 常见借口

| 借口 | 现实 |
|------|------|
| 「太简单了不用测」 | 简单代码也会坏。测试只要三十秒。 |
| 「我之后会补测试」 | 立即通过的测试什么都证明不了。 |
| 「已经手动测过了」 | 临场 ≠ 系统化。没记录、不能重跑。 |
| 「删掉太浪费了」 | 沉没成本谬误。留着没验证的代码才是负债。 |
| 「留着当参考，先写测试」 | 你会照抄它——那就是事后测试。删除就是删除。 |
| 「我得先探索一下」 | 可以。探索完扔掉，从 TDD 重新开始。 |
| 「这测试很难写」 | 难测 = 难用。听测试的话，简化设计。 |
| 「TDD 拖慢速度」 | TDD 比事后排错快。捷径 = 在生产环境里排错。 |

## 危险信号——出现这些情况就停下，重新开始

- 代码写在测试前面。
- 测试一写出来就通过。
- 说不出测试为什么失败。
- 打算「以后」补测试。
- 「就这一次」「这次不一样，因为……」。
- 「留着当参考」「改编现有代码」。

## 例子：修一个缺陷

缺陷：空邮箱被表单接受了。

```typescript
// 红
test('拒绝空邮箱', async () => {
  const result = await submitForm({ email: '' });
  expect(result.error).toBe('Email required');
});
// 验证红：FAIL——expected 'Email required', got undefined ✓ 因对的理由失败

// 绿
function submitForm(data: FormData) {
  if (!data.email?.trim()) {
    return { error: 'Email required' };
  }
  // ...
}
// 验证绿：PASS，全套仍绿 ✓
```

重构：需要校验多个字段时再提取校验逻辑，现在不动。

## 完成前核对

- [ ] 每个新函数/方法都有测试。
- [ ] 每个测试都看着它失败过，且因对的理由失败。
- [ ] 每轮写的都是让测试通过的最小代码。
- [ ] 全部测试通过，输出干净。
- [ ] 测试用的是真代码，mock 只在万不得已处。
- [ ] 边界情况和错误路径有覆盖。

有一格勾不上？你跳过了 TDD，回去重来。

## 卡住的时候

| 问题 | 解法 |
|------|------|
| 不知道怎么测 | 先写你希望存在的 API 调用，先写断言。还不行就问用户。 |
| 测试太复杂 | 设计太复杂。简化接口。 |
| 什么都得 mock | 代码耦合太紧。用依赖注入。 |
| 测试准备工作巨大 | 提取辅助函数；还是大就简化设计。 |

## 与排查的衔接

发现 bug？先写一个复现它的失败测试，然后走循环——测试既证明修复有效，也防止回归（systematic-debugging 的第四阶段会把你送到这里）。**没有测试，不修 bug。**

## 最后一条

```
生产代码 → 存在一个先失败过的测试
否则 → 不是 TDD
```

用不用 TDD 在动手前决定；写到一半开始「变通」它，就是没在用。
