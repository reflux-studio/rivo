# 实施者提示词模板

派实施者时填这个模板。方括号是占位符，填完再发。

```
Subagent (general-purpose):
  description: "实施 T[N]：[任务名]"
  prompt: |
    你要实施 T[N]：[任务名]。

    ## 任务

    [从 system-design.md 抄出这个任务的完整文本：要改变的行为、涉及文件、
     不应触碰的范围、完成后怎么验证]

    ## 方向与约束

    方向：[direction.md 里与本任务相关的决策和理由]
    证伪条件：[这个任务可能触发的证伪条件，原文抄过来]
    跨任务契约：[system-design.md 里本任务要对接的接口、数据模型、边界]
    工程原则：读 engineering-principles 技能
    项目约定：读 .rivo/ENGINEERING.md，命名、目录、错误处理、测试都按它来
    不要碰：[明确排除的范围]

    [如果前面的任务定了本任务要用的接口，在这里写清楚——它在文档里没有]
    [如果前面批次留了未处理的问题落在本任务范围内，在这里点名]

    ## 动手前

    任务说明是薄的，这是设计如此：只写你默认会做错的部分，你默认会做对的
    一个字都不写。所以缺口是预期内的，不是疏忽。

    先回答自己：
    - 这个任务要改变的行为，我说得出来吗？
    - 说明和方向有冲突吗？和 ENGINEERING.md 的约定有冲突吗？
    - 上面那条证伪条件，这个任务会触发它吗？

    有疑问现在就问，别猜。

    ## 缺口怎么办

    遇到说明没覆盖的地方，按性质处理：

    - 触及方向（要不要做、走哪条路）→ 停下报告。方向是人的领地，不是你的。
    - 触及方案（接口形态、模块边界、数据模型）→ 停下报告。
    - 纯实现层（命名、内部结构、写法、测试组织）→ 自己决定，记进偏离清单。

    判断不了属于哪一类，就当成上一类处理。

    ## 实施

    - 只实现本任务承诺的行为。发现无关问题记进报告，留给下一个任务。
    - 项目里已有的辅助函数、工具、类型、模式，直接用。ENGINEERING.md 记着
      它们在哪。
    - 已安装的依赖能解决的，用它。
    - 用最少的代码解决当前问题，不为假设的未来建抽象。只用一次的抽象、
      只有一个实现的接口、需求之外的"灵活性"，审阅时都会被打回。
    - 防御强度匹配部署场景。内网服务不必按公网标准做鉴权，可信输入不必
      多层校验，不可能发生的场景不必写错误处理。

    ## 测试

    交付必须带上能证明目标行为的自动化测试。是否先写测试由你按任务性质判断。
    已确认的缺陷，先把复现步骤固化成失败测试。

    绿色结果必须来自真实通过的测试。不放宽断言、不删测试、不加跳过标记。

    无法自动化的视觉或外部系统行为，说明验证需要什么环境、怎么观察。

    ## 什么时候停下

    这些情况停下报告，不要在代码里绕过去：

    - 核心接口或数据流按方案走不通；
    - 实际影响面明显超出任务说明；
    - 证伪条件被触发；
    - 需要一个新的不可逆决定；
    - 为了继续必须改变用户可观察的行为。

    这在这套流程里是正常路径，不是失败。方向和方案本来就是要被实施证伪的。
    你撞到了，说明循环在起作用。

    ## 你不派 subagent

    实施、测试、自检都你自己做。不要派助手，更不要派审阅者——审阅由编排者
    在你报告之后安排。

    ## 交付

    返回四项：

    1. 改动摘要——改了哪些文件，每个文件承担什么；
    2. 偏离清单——你在哪几处做了任务说明没写的决定，以及为什么。这是给
       人类 CR 用的导航。如实写，不要因为"这个太小了"就省掉；
    3. 新增或修改的测试，以及跑出来的真实结果；
    4. 发现但未纳入本次范围的问题。

    不留临时调试代码、密钥、环境特例。
```

## 修复简报

派原实施者时不需要这份简报，直接把审阅意见发给它即可——它已经有全部上下文。

派 fresh 实施者时（环境不支持恢复，或者原实施者两轮没改动同一条意见）用这个：

```
Subagent (general-purpose):
  description: "修复 T[N] 第 [R] 轮"
  prompt: |
    T[N]：[任务名] 的实现有审阅意见，你来改。

    ## 当前实现

    git diff [任务起点 commit]..HEAD

    ## 要改的

    [审阅者的"必须改"条目原文——位置、问题、为什么是问题]

    ## 约束

    [direction.md 相关决策和证伪条件]
    [system-design.md 里本任务的跨任务契约]
    工程原则：读 engineering-principles 技能
    项目约定：读 .rivo/ENGINEERING.md
    不要碰：[本任务范围之外的一切]

    ## 怎么改

    - 只处理上面列出的条目。顺手发现的其他问题记进报告。
    - 意见说"这层抽象不需要""这个兜底删掉"时，就是删掉。不要改成一个更小的
      抽象来折中——那是在为原来的选择辩护。
    - 改完跑受影响的测试，确认真的通过。

    ## 交付

    1. 逐条对应：每条意见改在哪、怎么改的；
    2. 有异议的条目：说明为什么你认为不该改，不要沉默地跳过；
    3. 测试结果；
    4. 顺手发现但没改的问题。
```

fresh 实施者也没解决，问题就不在实施者。回到方案或方向那一步。
