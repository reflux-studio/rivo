# 技术方案结构

按需取用。**每一节都过一遍准入测试：不写这一节，模型默认会做对吗？会，就删掉它。** 章节存在不是写它的理由。

## 摘要

- 要解决的目标；
- 一句话说明怎么做；
- 主要影响范围；
- 需要批准的不可逆决定（如有）。

## 输入

- `direction.md` 和 `context.md` 的地址与版本；
- 从方向继承下来的证伪条件；
- 不应改变的行为。

现状不在这里重写——它在 `context.md` 里，只在方案需要引用某个具体事实时点名。

## 方案概览

整体结构、数据流和控制流。图能提高理解时用图，但图不替代关键的文字契约。

## 跨任务契约

**只写实施者各自定会定歪的部分。** 多个任务要对接的东西必须在这里定死，否则每个 fresh subagent 会各定一套：

- 接口签名、事件与协议；
- 数据模型、索引、迁移方式；
- 状态机和生命周期；
- 模块职责边界与依赖方向；
- 跨模块的错误处理与幂等约定。

单个任务内部的实现细节不写——那是实施者的自由裁量区，写了就是把代码写两遍。

## 明确不改变的部分

防止实施范围无意扩大。列出这次不碰的模块、接口和行为。

## 复用关系

项目里已有的、这次应该拿来用的辅助函数、工具、类型和模式，指出它们在哪。

`.rivo/ENGINEERING.md` 里已经记过的不必重复——它对实施者默认可见。

## 任务清单

```markdown
- [ ] T1 <要改变的行为>
      范围：<涉及文件> / 不碰：<不应触碰的范围>
      验证：<完成后怎么验证>
- [ ] T2 …（依赖 T1）
- [ ] T3 <不可逆：动 schema，实施前先评审，自己单独一批>
```

不可逆任务醒目标出。

## 批次

和人协商的结果：哪些任务合成一批、哪些单独一批。一批结束做一次人类 CR。

## 风险与不可逆决定

只列真实存在的。不可逆决定单独写：为什么现在必须做、怎么迁移和回滚、怎么验证没有破坏外部消费者、批准状态。

没有不可逆决定就不写这一节。

## 开放问题

需要人拍板的，附默认假设和推荐答案。
