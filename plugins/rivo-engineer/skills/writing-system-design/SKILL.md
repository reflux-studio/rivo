# 撰写方案与拆解任务

**必读前置：** `engineering-principles`——这套技能共同遵循的工程判断与边界。

方案不是施工图，是**给实施者的约束边界**。现状调查在 `aligning-on-requirement` 做过，方向在 `setting-direction` 定过。这里只做一件事：把方向翻译成可以独立实施、独立评审的任务。

方案会在循环中被证伪和修订，**它没有终态**。现在写的是当前最好的判断，不是最终答案。

## 1. 方案该写多厚

这是本技能最重要的一节。

事无巨细的方案是把代码写两遍：一遍可执行可测试，一遍不可执行、不可测试、还会腐烂。如果方案详细到任何模型照着写都输出一样的东西，那它携带的信息量就等于代码本身，你白写了。

> **方案需要携带的信息 = 你的意图 与 模型默认行为 之间的差。**

每写一句都过一遍：

> **不写这一句，模型默认会做对吗？会，就删掉。**

模型默认会做对的（用什么循环、变量怎么命名、错误消息怎么写），一个字都别写。默认会做错的必须写死：

- 与通用最佳实践冲突的项目约定；
- 部署场景决定的取舍：内网服务不需要那层鉴权、这个项目不用 DI 容器；
- 容易被过度设计的地方，明确写"这里不要抽象"；
- 不能碰的边界。

`.rivo/ENGINEERING.md` 里写过的不用重复，它对实施者默认可见。**认知沉淀得越好，方案越薄。**

## 2. 写方案

按决策量选深度。小改动写清目标、改法、影响面和验证方式就够；改数据模型、对外接口、权限边界的，展开兼容、观测和回滚。

必写的只有跨任务对不齐就会出事的部分：

- **整体思路和数据流**——模块怎么分、数据怎么走；
- **跨任务契约**——接口签名、数据模型、模块职责边界。不定死的话每个实施者会各定一套；
- **明确不改变的部分**——防止实施范围无意扩大；
- **复用关系**——项目里已有的东西在哪、怎么用。

单个任务内部的实现细节不写，那是实施者的自由裁量区。

结构见 [references/system-design-structure.md](references/system-design-structure.md)，按需取用。图能提高理解时用图，但图不替代关键的文字契约。

## 3. 拆任务

**粒度**：最小的、自带测试周期、且值得一次独立审阅的单元。

- 配置、脚手架、文档折进真正需要它们的任务，不单独成任务；
- 只在"审阅者可能通过其中一个、打回另一个"的地方切开；
- 每个任务结束时有一个可独立验证的交付物；
- 判断标准之一：**人能一次读完这个任务的 diff 吗？**

## 4. 不可逆操作单独成任务

<IMPORTANT>
不可逆操作**必须单独成任务**，且这个任务的评审**前置到实施之前**，也不能和别的任务合成一批。

不可逆指：数据模型迁移与回填、对外接口与协议变更、权限与鉴权边界、删除数据、上线后回滚不掉的操作。
</IMPORTANT>

理由：这个循环靠"撞了能退"成立。每批任务后有人 CR，试错代价被压到一批。但不可逆的东西撞了退不回来，不能靠"做了再看"。

## 5. 协商 CR 时机

实施开始前完成。

任务分成**批次**，一批结束做一次人类 CR。基于任务类型和预计改动量给出建议，让人调整：

> T1-T3 都是目录搭建和类型定义，建议合成一批。
> T4 是机械性重命名，建议并进 T5 那一批。
> T6 动 schema，不可逆，单独一批，且实施前先评审。

三条约束：

- **合并的是停下来等人的次数，不是审阅范围。** 三个任务合成一批，人要看的仍然是三个任务的全部改动。批内每个任务照样过 AI 预审。这两件事长得一样，说清楚，别让它滑成"跳过"。
- 人可以说"一口气干完，不要喊我"，整个交付就是一批。按他说的做，但**开工前必须说清代价**：本次不会在过程中建立认知，CR 负担全部压到最后，中途撞墙无法早退。人主动放弃认知和 AI 擅自跳过人是两回事，区别在于他知不知道自己买了什么。
- 不可逆任务自己一批。

## 产物

**写到哪：** `docs/rivo/<需求名>/system-design.md`
- 跑在 rivo 流程里时，用 `rivo issue show` 返回的 `issue_dir`
- 用户指定的位置优先——本地路径、Notion、语雀都行


```markdown
# <需求名> · 技术方案

对应：direction.md（<版本或日期>）

## 方案
<整体思路和数据流>

## 跨任务契约
<接口签名、数据模型、模块边界——只写不定死就会各定一套的部分>

## 明确不改变
- <模块 / 接口 / 行为>

## 任务与批次

### 批次 1（CR：T1-T3 一起看）
- [ ] T1 <要改变的行为>
      范围：<涉及文件>｜不碰：<排除范围>｜验证：<怎么验>
- [ ] T2 <…>（依赖 T1）
- [ ] T3 <…>

### 批次 2（CR：单独看｜不可逆：动 schema，实施前先评审）
- [ ] T4 <…>
```
