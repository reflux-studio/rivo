# 长期认知

持有 `.rivo/ENGINEERING.md`——项目的工程认知:架构地图、代码惯例、运行与测试方式。它比单次会话记得更久,新会话靠它接续上下文,不必每次重新调研。

## 建立

首次建立或阶段性校准时:

1. **建立地图**——README、依赖和构建配置;目录结构和主要入口;模块、服务和职责;数据流、存储和外部接口;部署、环境和基础设施;测试、CI 和监控。优先读当前真实来源,已有总结只作线索,与事实冲突时以可验证来源为准并记录冲突。
2. **归纳惯例**——命名和目录组织;错误处理、日志和配置;数据访问和状态管理;API、事件和任务模式;测试层级和常用工具;安全和权限边界。一处实现只是写法,多处稳定使用才是惯例;新旧模式并存时明确适用范围。
3. **沿真实路径核验**——选择两三条代表性路径:从入口进入,跟踪模块调用和数据变化,找到存储、外部依赖和输出,查看错误和测试如何覆盖,与架构描述交叉核对。
4. **实际运行关键命令**——安装依赖、构建或类型检查、单元测试、集成或端到端测试、本地启动、代码质量检查,记录当前环境、结果和失败原因。**亲自运行过的命令才能写成已验证**,没跑过的命令标为未验证,不要凭配置文件推测它能跑通。

调研不借机提出无关改造。每个重要结论能指出来源;读不出的内容标为推断或待确认。深度取决于用途:首次入场覆盖架构核心地图和工作入口,后续校准只检查变化,专项勘测围绕指定模块或问题深入。写入 `.rivo/ENGINEERING.md`:模块和数据流地图、关键入口与外部接口、代码和架构惯例及出处、技术名词表、构建运行测试和发布方式、环境依赖和监控、已知冲突与推断待确认项、来源索引。

## 遵循

- 动手前先读 `.rivo/ENGINEERING.md`,产物必须与认知一致。
- 认知与事实冲突时以事实为准,并回写认知,而不是绕开它。
- 认知里没有的东西不要假装有;不确定就标为待确认。

## 维护

三个触发时机:

- 调研之后。
- **交付被打回之后**——打回原因就在 `.rivo/issues/<slug>/log.jsonl` 的 `reject` 事件里(`reason` 字段),那是"这次为什么错了"的一手记录,读它比重新推测更便宜。
- 用户纠正之后。

写稳定的判断与惯例:架构决策、环境陷阱、验证方式、高频根因。不写单次交付的状态、临时决定或工单细节——那些留在正式产物里。
