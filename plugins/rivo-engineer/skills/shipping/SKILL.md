# 发布

发布完成不是“代码合并了”，而是目标修订进入目标环境并通过发布后验证。

## 1. 读取交付约定

从用户提供的交付约定、项目认知或发布平台读取：

- 分支和 PR 规则；
- CI 与质量要求；
- 目标环境和发布时间；
- 审批人；
- 数据迁移、灰度和回滚方式；
- 发布后需要观察的指标。

约定缺失且会影响风险时，向用户确认并更新相应配置。不要每次发布都重新询问已经确定的规则。

## 2. 发布前核对

确认：

- 实现和技术方案指向相互匹配的当前修订；
- 实现已经通过评审节点；
- 所有工程验证和适用的用户验收已通过；
- CI 对当前提交是绿色；
- 不可逆变更和项目要求的审批已经获得；
- 数据迁移在非生产环境演练过；
- 外部 API、事件或配置变更有兼容方案；
- 回滚条件、负责人和具体操作已经确定；
- 本次发布没有夹带未声明提交。

## 3. 选择发布方式

按风险使用：

- 直接发布；
- 预发布环境验证后发布；
- 灰度、金丝雀或分批发布；
- 功能开关；
- 双写、影子流量或兼容期；
- 维护窗口内迁移。

不要为了形式增加复杂发布机制，也不要对高风险迁移使用不匹配的轻量流程。

## 4. 执行发布

- 记录发布开始时间、目标修订和通道；
- 按顺序执行构建、迁移、部署和配置变更；
- 每一步核对实际结果，不以命令退出码之外的猜测判断成功；
- 需要人工操作时逐项记录，避免遗漏和重复执行。

## 5. 发布后验证

立即执行：

- 关键冒烟验证；
- 核心用户路径；
- 数据读写和后台任务；
- 关键外部集成；
- 版本、配置和迁移状态检查。

监控可用时，对照发布前基线观察错误率、延迟、资源、队列、关键业务指标和日志。观察时间按系统风险决定，不固定写死。

## 6. 回滚

是否回滚不是发布现场的即兴决定：回滚条件、负责人和操作在发布前已经确定并获得批准（见第 2 节）。命中已批准的条件时按预案执行并立即通知用户；预案没有覆盖的情况，报告用户拍板，不自行决定。

回滚后验证：

- 服务和关键路径恢复；
- 数据状态一致；
- 旧版本与新配置兼容；
- 用户影响停止扩大。

回滚后的排查使用 `systematic-debugging`。修复后重新走评审、测试和发布。

## 7. 收尾

将以下内容写入用户指定的发布记录，并把结论同步到交付状态：

- 发布修订、环境和通道；
- 审批与发布时间；
- 迁移结果；
- 冒烟验证和监控证据；
- 回滚状态；
- 尚需继续观察的事项。

未指定后端时，发布记录写进 `rivo issue show` 返回的 `issue_dir`（文件名 `release.md`）。按项目惯例更新发布说明或变更记录。
