# 敏捷开发循环

**必读前置：** `engineering-principles`——这套技能共同遵循的工程判断与边界。

方案不可能在动手前穷尽。这个循环的前提是：**方向和方案会在实施中被证伪**，撞墙是正常路径。

你是编排者。实施和审阅都派给 subagent，**你不写代码**。

## 为什么派遣

- 写的人审不出自己的问题。审阅者带着实施时的上下文，就会沿着实施者的思路复核，而不是重新判断。
- 前一个任务的上下文会污染下一个。实施者拿到的应该是你构造的输入，不是你这场会话的历史。
- 你要跨十几轮存活。被单个任务的细节填满，你就会忘记自己走到哪了。

没有 subagent 能力时退化为同会话顺序执行，**明确告诉用户质量会下降**。

## 批次

任务按 `system-design.md` 里协商好的 CR 预算分成**批次**。一个批次是一组连续任务，最少一个。

```
批次内，逐个任务：
    派实施者 → 提交 → 派审阅者预审 → 有问题就让实施者改 → 预审通过
    → 批内下一个任务（不停，不问人）

批次末尾：
    人类 CR，范围是整批的全部改动
    通过 → 关闭批次，开始下一批
    打回 → 分类处理，需要重做时退回批内某个提交

全部批次完成：
    派整体审阅者 → 人类整体 CR → 收尾
```

**批内每个任务都要预审。** 预审是 AI 做的，不占人的时间，没有理由省。合并省掉的是**停下来等人的次数**，不是审阅本身。三个任务合成一批，人要看的仍然是三个任务的全部改动。

不可逆任务**自己单独成一批**。

人说过"一口气干完，不要喊我"时按他说的做，整个交付就是一批。开工前必须已经说清代价，那在 `writing-system-design` 里完成。

## 开工前

读齐 `context.md`、`direction.md`、`system-design.md`、`.rivo/ENGINEERING.md`。确认任务清单和 CR 预算已经和人确认过，不可逆任务的评审已经前置做过，当前不在主干分支上或已得到用户明确同意。

## 派实施者

用 [implementer-prompt.md](implementer-prompt.md) 填空。

- **派遣前记下当前 commit**（`git rev-parse HEAD`）。预审要看的 diff 从这里起算，退回也退到这里。
- **一次只派一个。** 并行实施者会冲突。
- **不要把会话历史粘进去。** 实施者需要的是本任务、它要碰的接口、项目约定。把前三个任务的总结贴进第四个任务，只会让它在一堆无关信息里找线索。
- **前面批次留下的未处理问题**，如果落在这个任务碰的范围里，在派遣时点名。
- **不要为了"确保它做对"把任务说明写厚。** 说明该多厚在 `writing-system-design` 里定了：只写模型默认会做错的部分。写厚了就是把代码写两遍，而且那一遍不可执行、不可测试、还会腐烂。

实施者返回改动摘要、偏离清单、测试结果。

## 任务完成就提交

<IMPORTANT>
每个任务预审通过后**立刻提交**。

提交是**退回时的落点，不是"通过"的标志**。人类 CR 还没做，但代码必须已经在 git 里分好段——三个任务攒成一次提交，打回时就没法只退掉第二个。
</IMPORTANT>

提交后更新 `system-design.md` 里的任务状态。

## 预审与修复

派审阅者（[task-reviewer-prompt.md](task-reviewer-prompt.md)，fresh subagent，diff 从派遣前记的 commit 起算）。

预审有问题时：

1. **派谁修**——运行环境能恢复已派遣的 subagent 就派原实施者，它知道自己为什么那么写，改动更小、更不容易碰坏旁边的东西。不能恢复就派 fresh 实施者，用 [implementer-prompt.md](implementer-prompt.md) 的修复简报填空。
2. **复审**——改完派 **fresh 审阅者**，只看这一轮改的部分。审阅永远 fresh，没有例外。
3. **同一条意见 2 轮没解决就换 fresh 实施者**，不管环境能不能恢复。审阅意见里最常见的是"这层抽象不需要""这个兜底删掉"，两轮改不动同一条，通常是它在为自己原来的选择辩护，或者折中成了一个更小的抽象。fresh 实施者没有沉没成本。
4. **换了 fresh 还是没解决**，问题就不在实施者。按下面「打回」的表格判断是方案没说清还是方向不成立，回到对应那一步。

<IMPORTANT>
**你不亲自改代码。** 你只构造修复简报，判断修没修好。

自己动手看起来更快，但你改完之后，这个任务的实施上下文就进了你的会话，后面所有审阅都失去独立性。
</IMPORTANT>

预审通过不等于通过。它只是把明显的问题挡掉，别浪费人的注意力。

## 批次末尾：人类 CR

<HARD-GATE>
未经人类明确表态，禁止关闭当前批次、禁止开始下一个批次、禁止收尾。

"看起来没问题""预审都过了"不是表态。
</HARD-GATE>

主动要人 CR，前置汇报整批改动：

- 改了什么，涉及哪些文件，分成了哪几个提交；
- **偏离清单**——实施者在哪几处做了任务说明没写的决定；
- 预审发现了什么、怎么修的；
- 对后续任务的影响。

**偏离清单是导航，不是摘要。** 它让人的注意力先落到那几处，不代替人读代码。人只批准了一份摘要，认知就没有发生，这个循环也就没有存在的理由了。

看到这些念头，就是在给自己找理由：

| 想法 | 现实 |
| --- | --- |
| "这批改动很小" | 小改动一样携带架构决定。请人看。 |
| "上一批人看过类似的" | 类似不是相同，而且认知靠每一批累积。请人看。 |
| "预审和测试都过了" | 它们证明行为对，证明不了架构对、可读性对。请人看。 |
| "人已经等很久了，先往前推" | 你省下的时间会在最后加倍还回去。请人看。 |

## 打回：按性质分类

不要一律当成"实现没写好"：

| 反馈性质 | 落到哪 | 回到 |
| --- | --- | --- |
| 实现没对上方案 | 无需改文档 | 本循环，重做对应任务 |
| 方案不成立 | 改 `system-design.md` | `writing-system-design` |
| 方向不成立（证伪条件中了） | 改 `direction.md`，`adr.md` 追加一条 | `setting-direction` |
| 可复用的偏好 | 写进 `.rivo/ENGINEERING.md` | 继续，不打断 |

**最后一行是这个循环唯一的复利来源。**

人在 CR 里说"这里不需要这层抽象""内网服务不用做这个鉴权""不要为不可能的输入写兜底"，这类反馈落进 `ENGINEERING.md`，下一轮实施者开工就带着它。这次交付变好是次要的，下次交付起点更高才是这个循环存在的理由。

判断标准：这条反馈只对本次需求成立，还是对这个项目一直成立？后者才写进认知。

`adr.md` 只记转向，一条一行：`原本想走 X，撞了 Y，所以改走 Z`。追加，不覆盖。活文档只留最新版，**转向的理由留全部历史**。

**同一处连续 2 次被打回，回 `setting-direction` 重定方向。** 两次都没做对，问题不在实现层。

## 退回代码

- **先问人。** 这是破坏性操作。
- 说清楚退到哪个提交，哪些已经过了 CR 的任务会被一并退掉。
- 退回后从那个提交重新开始该任务。

## 全部批次完成

派整体审阅者（[final-reviewer-prompt.md](final-reviewer-prompt.md)，fresh subagent，看全量改动）。

它审的和单任务预审不同：每个任务单看都合格，合起来结构可能已经变形。

发现问题按上面的分类处理。通过后请人做整体 CR，同样不能代判。

## 收尾

1. **交验证方案给用户**：验证入口、要准备的环境和数据、按什么步骤操作、期望看到什么。
2. 写实现交接到 `docs/rivo/<需求名>/implementation.md`（rivo 流程里用 `issue_dir`，用户指定的位置优先）：实现修订、对应的方向与方案、改动摘要、新增或修改的自动化测试、验证时需要准备的环境与账号、本次发现但未纳入范围的问题。
3. 用户验证通过后用 `longtermism` 沉淀：从 `adr.md` 提炼值得跨交付留下的决策，把本次 CR 沉淀的可复用偏好合并进 `.rivo/ENGINEERING.md`。

需要真正上线时用 `shipping`。它是独立的一步，不属于这个循环。

## 产物

| 文件 | 谁写 | 怎么留 |
| --- | --- | --- |
| `context.md` | `aligning-on-requirement` | 原地改，只留最新 |
| `direction.md` | `setting-direction` | 原地改，只留最新 |
| `system-design.md` | `writing-system-design` | 原地改，含任务状态 |
| `adr.md` | 本技能 | 追加，只记转向 |
| `implementation.md` | 本技能 | 收尾时一次写成 |

偏离清单和逐条 CR 意见**不落盘**。它们活在会话和 commit message 里，写成文件只会变成没人回头翻的垃圾。
