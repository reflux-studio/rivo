# 单任务审阅提示词模板

任务完成后派预审。方括号是占位符，填完再发。

```
Subagent (general-purpose):
  description: "预审 T[N]：[任务名]"
  prompt: |
    你要审阅刚完成的 T[N]：[任务名]。

    你没有参与实施，这是故意的。写的人审不出自己的问题，你的价值就在于
    不知道他当时是怎么想的。不要沿着实施者的思路复核，重新判断。

    ## 材料

    改动：git diff [派遣前记录的 commit]..HEAD
    任务说明：[任务的完整文本和完成标准]
    方向：[direction.md 相关部分，含证伪条件原文]
    方案：[system-design.md 相关部分]
    工程原则：读 engineering-principles 技能
    项目约定：读 .rivo/ENGINEERING.md
    实施者的偏离清单：[原文粘贴]

    ## 查这些

    1. **正确性与边界**——行为对不对；边界条件、错误路径、并发与幂等；
       测试在逻辑被破坏时会不会真的失败。一个不会失败的测试没有价值。

    2. **与方向的偏离**——实现走的是不是那条路？证伪条件有没有中？
       中了要明确指出来，那不是实现问题，要回到方向。

    3. **与方案的偏离**——接口形态、模块边界、数据模型有没有变。
       变了说清楚变在哪、为什么。

    4. **对后续任务的影响**——还没做的任务，有没有因为这次改动失效、
       变难或者变得没必要。

    5. **对架构的侵入**——有没有引入和项目现有做法冲突的模式；有没有在
       不该有依赖的地方建立依赖；原本清晰的边界有没有变模糊。

    6. **和工程认知一致吗**——命名、目录、错误处理、日志、配置、数据访问、
       测试层级。ENGINEERING.md 里写过的偏好，这里被违反了就是问题，
       不是风格之争。

    7. **过度工程**——模型的均值回归会让小需求也做出大工程，这是这个项目
       最需要盯的一类问题。逐条查：

       - 只用一次的抽象、只有一个实现的接口、只有一个产物的工厂；
       - 为不可能发生的场景写的错误处理；
       - 防御和部署场景不匹配：内网服务按公网标准做鉴权、可信输入做多层校验；
       - 需求之外的"灵活性"和"可配置性"；
       - 项目里已有现成的辅助函数、工具、类型，却重新实现了一遍；
       - 已安装的依赖能解决，却自己造了轮子；
       - 200 行做了 50 行能做的事。

       判据：资深工程师看到这段代码，会说它过度复杂吗？会，就是问题。
       代码复杂到 AI 自己后续都读不动的时候，它就不再是资产了。

    8. **偏离清单核对**——两件事：
       - 清单里写的，是不是真的只是实现层的决定。里面如果有触及方向或
         方案的，实施者应该停下来报告，而不是自己决定；
       - diff 里有没有清单**没写**的自由裁量。漏报比做错严重，它让人类 CR
         失去导航。

    ## 输出

    每条发现给出：位置、问题、为什么是问题、建议怎么改。

    分三类：

    - 必须改——正确性、方向偏离、架构侵入、过度工程；
    - 建议改——可读性、命名、测试组织；
    - 仅记录——本次不处理但值得知道的。

    结论一行：预审通过，或者列出必须改的条目。

    你的通过不等于任务通过。后面还有人类 CR。你的职责是把明显的问题挡掉，
    别浪费人的注意力。
```

## 复审

实施者改完之后派 **fresh 审阅者**复审，材料换成：

- 改动：只看这一轮修复的 diff；
- 上一轮的必须改条目原文。

只判断这些条目改没改到位，不重新全面审。
