# 实现改动

## 1. 读齐当前输入

开始前读取：

- 当前技术方案或明确的改动目标；
- 对应的 requirement、ui-design 或技术完成标准；
- 项目工程认知和代码惯例；
- 尚未关闭的评审发现；
- 测试、发布和不可逆操作要求。

确认所有地址指向当前修订。上游存在尚未判断影响的新修订时，先完成影响判断再实现。

## 2. 建立实施计划

把工作拆成可验证的小段：

- 每段改变一个清晰行为或结构；
- 明确需要修改的文件和不应触碰的范围；
- 确认前置依赖；
- 为每段选择自动化验证方式。

## 3. 实现与测试

推荐用 `test-driven-development` 驱动实现：先写失败的测试，再写最小实现。是否采用由你按任务和代码现状判断；无论是否采用，交付必须带上能证明目标行为的自动化测试。

已确认缺陷先把复现步骤固化成失败测试。无法自动化的视觉或外部系统行为，提前说明测试节点验证需要怎样的环境和观察方式。

## 4. 控制范围

- 只实现 requirement 和技术方案承诺的行为；发现无关问题时记录，另行处理。
- 绿色结果必须来自真实通过的测试——不放宽断言、不删除测试。
- 交付中不留临时调试代码、密钥或环境特例。

## 5. 方案失效时停止

出现以下情况时暂停实现：

- 核心接口或数据流无法按方案成立；
- 实际影响面明显超出方案；
- 上游验收标准存在矛盾；
- 需要新的不可逆决定；
- 为继续实现必须改变用户可观察行为。

更新相应产物并重新评审，不在代码中悄悄绕开。

## 6. 完成实现

运行受影响的单元测试、必要集成测试和项目要求的静态检查，确认没有夹带无关修改。随后输出实现修订、环境入口、已完成测试和测试节点验证所需信息。

交付时返回：

- 实现地址和修订；
- 对应技术方案或改动目标；
- 改动摘要；
- 新增或修改的自动化测试；
- 测试节点验证需要准备的环境、账号和数据；
- 实现中发现但未纳入本次范围的问题。

rivo 可用时，把这份实现交接写进 `rivo issue show` 返回的 `issue_dir`（文件名 `implementation.md`）；未安装 rivo 时，发布到项目惯用的交接文档位置，或直接返回给用户。代码本身仍以源码仓库中的实现为事实源。
