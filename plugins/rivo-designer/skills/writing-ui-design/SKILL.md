# 撰写 UI Design

ui-design 的读者是实现者和评审者。它可以以 Figma、原型、HTML、图片或文档为主，但必须让下游知道哪个来源是事实、当前修订是什么，以及设计源没有表达的行为约束。先把体验决定收敛完整，再发布交接。

向用户或需求的所有者澄清决策时，沿决策依赖分轮提问、把默认假设摆到台面，每题附推荐答案；能从设计源和代码查证的事实自行查证。

## 1. 读取依据

- 当前 requirement 及修订；
- 项目设计认知（设计系统）：已有组件、token、页面模式和交互惯例；
- 现成设计源及其修订；
- 品牌、平台和设备约束。

requirement 缺少关键产品行为时，向需求的所有者提问——业务规则的答案属于意图层。

## 2. 判断设计源

- **可直接采用的正式设计**：已经覆盖 requirement、状态、边界和工程交接，不因为来自外部团队或格式不同就重做；直接作为 ui-design 进入交叉评审和独立验证。
- **没有现成设计**：从用户任务和设计系统开始提出方案。
- **需要补全且可直接编辑**：在原设计源中迭代，保留关键决定。
- **需要补全但只读**：输出定位明确的评论、修改要求或增量说明，不复制整份设计。
- **外部 AI 设计平台**：把问题转写成可执行修改指令，等待新修订后重新检查。
- **运行中的现有界面**：区分当前事实与本次要改变的部分。

各类设计来源的处理方式见 [references/design-sources.md](references/design-sources.md)。

如果用户只要求评价一份现成设计，而不是产出或补全 ui-design，直接以设计视角独立审阅并给出评论，不必产出新的 ui-design。

## 3. 建立用户任务

从任务开始，而不是从页面组件开始：用户从哪里进入、当时知道什么、核心动作和判断是什么、完成和失败后发生什么、哪些角色或设备会改变路径。复杂流程先用步骤图或线框验证结构，再投入视觉细节。

## 4. 设计层级并寻找更简路径

确认首屏最重要的信息和动作、主次操作的区分、危险操作的提示与恢复，以及用户对当前位置和系统状态的理解。提出至少一个更简单的路径，确认当前复杂度确有必要。

## 5. 补齐状态和边界

对每个关键区域检查：默认、加载、空态、错误、无权限、禁用、成功反馈、超长内容、大数据量、响应式变化，以及重复提交、取消、返回和中断恢复。完整检查框架见 [references/interaction-checklist.md](references/interaction-checklist.md)。

## 6. 映射设计系统

按优先级匹配：已有业务组件 → 组件库组件 → 现有 token 和布局模式 → 新组件或新 token。新增约定时说明为什么已有能力不够，以及它是否值得进入长期设计认知。

同时覆盖可访问性与平台行为：键盘、焦点、标签、对比度、点击区域、屏幕阅读器语义和平台原生习惯。

## 7. 组织并撰写

选择主事实源：精确布局、尺寸和颜色由设计工具表达时引用设计源；行为、状态切换和边界规则在文档中补充；只有文字设计时，文档本身承担结构、组件和状态的完整表达。

按变化规模组织——局部调整只写受影响区域和前后行为；新页面或新流程用完整结构；大型改版按用户任务拆分。推荐结构见 [references/ui-design-structure.md](references/ui-design-structure.md)。

写清交互和反馈：什么触发状态变化、操作过程中用户看到什么、成功和失败后发生什么、是否可以取消或撤销、动效的目的和可跳过性。

## 8. 标明实现自由度

区分：必须忠实实现的用户行为；必须使用的设计系统约定；实现者可以自行决定的内部实现；仍需需求的所有者或用户确认的内容。API、数据库和代码拆分属于机制层，留给 system-design。

## 9. 发布

确认 requirement 中所有相关场景都有体验答案、状态和边界足够完整、实现者无需猜测用户行为，然后把 ui-design 写进 `rivo issue show` 返回的 `issue_dir`，并注明对应的 requirement 修订。
