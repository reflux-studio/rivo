# 长期认知

持有 `.rivo/DESIGN.md`——项目的设计认知:设计系统、组件、token 和交互惯例。它比单次会话记得更久,新会话靠它接续上下文,不必每次重新巡查。

## 建立

首次建立或阶段性校准时:

1. **定位事实源**——设计文件和组件库;主题、token 和全局样式配置;前端组件和业务组件;页面骨架、布局和响应式断点;运行中的主要界面。优先读当前真实来源,已有总结只作线索,与事实冲突时以可验证来源为准并记录冲突。
2. **调研内容**——颜色、字体、间距、圆角、阴影等 token;主力组件库、版本和二次封装层;被多个场景复用的业务组件;重复出现但尚未进入设计系统的组件和模式;表单、表格、筛选、导航和反馈模式;响应式和设备差异;无障碍和交互惯例;新旧设计并存的边界。
3. **核验**——token 从真实配置或设计变量读取,截图只能提供线索;组件确认真实存在,并指出使用位置;一处写法不算惯例,至少找到多个一致实例;设计文件和代码冲突时同时记录,谁覆盖谁交给负责人裁决。

巡查不借机提出无关改造。每个重要结论能指出来源;读不出的内容标为推断或待确认。深度取决于用途:首次入场覆盖设计系统核心地图,后续校准只检查变化——退化、漂移和新出现的可复用模式,专项巡查围绕指定页面或流程深入。写入 `.rivo/DESIGN.md`:事实源索引、token 和主题、组件库与业务组件、布局断点和交互模式、无障碍惯例、迁移中或不一致区域、建议收编进设计系统的组件和模式提案、推断与待确认项。

## 遵循

- 动手前先读 `.rivo/DESIGN.md`,产物必须与认知一致。
- 认知与事实冲突时以事实为准,并回写认知,而不是绕开它。
- 认知里没有的东西不要假装有;不确定就标为待确认。

## 维护

三个触发时机:

- 调研之后。
- **交付被打回之后**——打回原因就在 `.rivo/issues/<slug>/log.jsonl` 的 `reject` 事件里(`reason` 字段),那是"这次为什么错了"的一手记录,读它比重新推测更便宜。
- 用户纠正之后。

写稳定的判断与惯例:确认的 token 取值、新收编的组件、被推翻的假设。不写单次交付的状态、临时决定或工单细节——那些留在正式产物里。
