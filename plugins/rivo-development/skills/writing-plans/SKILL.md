# 写技术方案

开始时说明正在使用 `rivo-development:writing-plans`，并用一句话说明本次要做什么。同一项工作中不重复声明。通过宿主发现公共 `rivo:using-rivo`，读取开发工作约定；缺少公共包时说明依赖缺失，不自动安装或假装执行。

把已确认的做法写成技术方案。读者没有参与讨论：用户要据此向同事解释，团队要据此评审，开发、联调和发布要据此对照。

## 流程

### 1. 核对设计依据

- 读取用户给定需求、设计、技术决定、ADR、调查和项目规约。共享需求先读工单，核对参与方、实际位置及产物归属
- 技术决定记录里没有 ADR 的小决定也要落实。从这些材料提炼本期做法，不把查证过程和选择理由搬进方案
- 缺少技术事实时加载公共 `rivo:investigating`。材料不可读时说明缺口，只暂停依赖它的部分
- 仍有未处理的设计问题时，按下文“何时回到技术讨论”处理；业务歧义通过公共 `rivo:collaborating` 交需求负责人，无人负责时交用户处理

### 2. 写技术方案

- **位置**：沿用用户给定材料、工单登记或公共领域约定，不另建第二份有效方案
- **结构**：按 [技术方案模板](references/plan-structure.md) 组织；团队有自己的模板时用团队的
- **表达**：加载公共 `rivo:writing-clearly`
- **模块对应**：详细设计的模块名称和顺序与需求总览一致，评审者看到总览就能找到对应章节
- **定义完整**：协作方要对照实现的内容写出实际定义，条目多时放进随方案维护的附件
- **工程边界明确**：写清契约来源、模块职责、扩展点与主流程的关系和存量适配。界面任务登记设计来源、版本及定位

用户同意进入写方案，就是这次写作的授权，不逐条请示。输入可以来自人类同事，不要求其他领域插件参与。

### 3. 送审前自查

- 范围里的每个模块是否都有对应设计，每条技术决定是否都已落实
- 主场景和失败场景沿模块能否走通，包括上线当天的初始数据
- 协作方需要的定义是否完整交付，引用的附件是否已写好
- 正文是否讲清本期做法，必要背景与查证细节是否分开
- 图、表、示例是否与正文一致，同一份定义是否只维护一处
- 批量替换或改名后，在方案、附件和 ADR 中搜索旧说法

自查不能代替独立审阅。

### 4. 独立审阅

首次定稿前做一次全量独立审阅。批准后的修订由用户或有权负责人确认，不默认重审全文：每次修订都重审，成本会远超修订本身。

1. 加载公共 `rivo:dispatching-subagents`，按 [审阅提示词](references/plan-reviewer.md) 安排未参与写作的审阅者
2. 给出当前方案及原始需求、决定、调查、附件和模板的实际位置。报告按公共约定或用户指定位置保存，不覆盖旧报告
3. 按 [接收审阅意见](references/receiving-review.md) 核实和处理；有 P0 时修复后交同一审阅者增量复核

宿主或授权不支持独立审阅时，说明缺口，交用户决定如何继续，不把自查称为独立审阅。

### 5. 交用户和团队评审

审阅通过后，交出方案和一份简短说明：

- 方案怎样落实了已确认的需求和技术决定
- 审阅中没修的 P1、P2，拒绝了哪些意见及理由
- 还需要用户或其他负责人判断的地方

用户或团队带回意见时，按接收审阅意见先核实事实，在已有决定权和授权内处理。其他负责人的材料由对方修改。

### 6. 完成

用户或有权负责人批准后，标明定稿及版本，本次方案工作完成。

- 批准方案不等于授权实施
- 已有实施授权继续沿用；授权覆盖时加载 `rivo-development:implementing-plans`，否则到此交付

## 修订已有方案

批准前，在写作授权内按评审意见修改。批准后加载公共 `rivo:revising`，核对当前版本、决定权和依赖影响，再更新技术方案及附件。

- **在原处重写**：正文只写当前的做法，读起来像第一次就写对了。修改过程只进修订记录
- **版本递增**：确认后次版本号加一，修订记录加一行；改写前确保原内容可从提交或快照恢复
- **说明覆盖范围**：原审阅没有覆盖的新内容，在交付说明里交代影响和验证结果，不引用旧报告证明新内容通过
- **通知受影响方**：需要修改其他产物时，通过协作交其负责人处理

## 何时回到技术讨论

写作中遇到以下情况，回到 `rivo-development:converging` 处理后再继续：

- **核心设计缺口**：会改变主流程、跨系统契约或数据落点的未定问题。把它列进待决事项，不等于设计已经完成
- 达到 ADR 门槛、而有权人尚未决定的取舍

用户想先看未完成的稿子时可以成文和送审。状态写“草稿（设计未完成）”，在受影响章节标出缺口；解决后才能确认定稿并进入相关实施。

某个取舍找不到记录时先查来源：已经决定、只是漏记的，补记；AI 自己补定的重要取舍，交有权人决定。技术方案只维护开发负责的做法，不代改需求、测试用例或质量报告。
