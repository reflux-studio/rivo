# 写技术方案

开始时说明正在使用 `rivo-development:writing-plans`，并用一句话说明本次要做什么。同一项工作中不重复声明。通过宿主实际发现公共入口 `rivo:using-rivo` 并读取其领域约定；不能仅凭路径存在判断可用。缺少公共包或无法发现入口时，说明依赖缺失并停止领域执行，不自动安装。

## 写作

1. 读取用户给定需求、设计、技术决定、调查和项目规约；共享需求先读工单。材料不可读时说明缺口，只暂停依赖它的部分。
2. 缺少技术事实时加载公共 `rivo:investigating`；业务歧义通过公共 `rivo:collaborating` 交已登记的产品负责人，无人负责时请用户处理。需要新的重要技术取舍时回到 `rivo-development:converging`。
3. 按 [技术方案模板](references/plan-structure.md) 或团队模板写方案。位置遵循公共领域约定，用户或项目给定位置优先。说明行为、契约来源、职责、扩展点、存量适配、失败处理和发布安排。界面任务引用实际设计来源、版本和定位。
4. 加载公共 `rivo:writing-clearly`，自查范围、决定、主路径和失败路径、契约与发布安排。用户同意写方案即为写作授权。

## 审阅与确认

组织独立方案审阅，审阅者核对需求、技术决定、真实约束和方案的完整性，并提供依据和影响。通过宿主发现公共 `rivo:dispatching-subagents` 安排审阅；宿主或授权不支持独立审阅时明确缺口，不称已完成独立审阅。核实意见并修正属实问题，必要时让审阅者复核，随后交用户或有权负责人确认。已有确认和实施授权沿用，不重复询问；确认方案不自动授权实施。

存在核心设计缺口而用户希望先看稿时，标明“草稿（设计未完成）”及受影响部分，不能视为定稿。测试意见可以作为输入，但开发方案由有权负责人确认，不要求其他领域插件参与。

## 修订

批准后修改时加载公共 `rivo:revising`，确认有效版本、决定权及影响。保留可恢复的原版本，在授权范围内更新技术方案及其附件，通知其他产物负责人处理各自产物。方案正文保持当前有效做法；修订记录说明版本、变化与理由。
