# 协作配置示例

协作配置是全员的共同约定：每个成员发布产物、请求审批、选择沟通深度之前都以它为准。它是写给成员读的普通文档，不是机器解析的 schema；建立和调整走 `onboarding`，由 Team Lead 代表团队与用户确认。

项目配置默认保存在 `.rivo/PROFILE.md`；跨项目的全局偏好（沟通习惯、默认审批口味）用宿主的持久化方式保存，项目配置优先。

```markdown
# 协作配置

## 用户与沟通

- 用户是前端工程师：技术内容直说，业务背景需要解释。
- 默认先给结论和取舍，实现细节按需展开。

## 产物位置

- requirement：POPO 文档《订单中心需求集》，评审意见写在文档评论里。
- 代码评审：GitHub PR 逐行评论，结论汇总在 PR 描述。
- 其余产物与记录（ui-design、system-design、实现交接、交叉评审、独立验证、异常调查、UAT、发布、交付状态、复盘）：`.rivo` 默认工作区。

## 审批点

- 发布、数据迁移、删除数据必须本人确认。
- requirement 定稿必须本人确认。

## 分支与发布

- 从 main 切 `feat/<slug>`，PR squash 合并。
- 发布走 GitHub Actions：staging 验证后手动晋级 production。

## 验证独立性

- 首选跨供应商模型做独立验证；不可用时降级为同宿主独立上下文，并在验证结论中注明降级。

## 宿主映射

- Team Lead、Product、Designer、Engineer、Verifier 由 multica 的独立 Agent 承担。
- 每个 Agent 预装自己的角色技能和 `collaborating`。
- Verifier 与产物作者使用独立上下文；权限允许读取事实源、运行验证和在隔离位置实验，不允许直接修改被验证产物。
- Agent 无法访问某个外部后端时，由 Team Lead 记录限制并改用可执行的交接方式。
```

只记会改变团队行为的内容；宿主能自己判断的（比如包管理器用哪个）不写。
