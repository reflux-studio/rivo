# 技术方案验证检查表

## 目标与约束

- 是否引用当前 requirement、ui-design 或技术目标修订？
- 功能、性能、可靠性、安全、成本和期限约束是否完整？
- 方案是否解决当前目标，而不是扩张到假设的未来？

## 现状真实性

- 关键模块、调用关系、数据流和依赖是否从代码或运行结果核实？
- 是否把猜测写成事实？
- 对现有行为和爆炸半径的判断是否有证据？
- 抽查关键断言时能否在代码或配置中找到对应位置？

## 方案完整性

- 模块、接口、数据模型、状态变化和错误路径是否足够明确？
- 是否覆盖迁移、兼容、并发、重试、幂等和失败恢复等适用问题？
- UI 与后端、服务与数据库、同步与异步边界是否清楚？
- 是否说明不变的部分，避免实现者扩大改动范围？

## 取舍

- 是否至少考虑过现实可行的替代方案？
- 选择理由是否结合当前约束，而不是泛泛列优缺点？
- 是否存在明显更简单、复用现有能力更多的方案？
- 新依赖、新服务和新抽象是否有足够收益？

## 风险与交付

- 不可逆变更是否醒目标明并等待批准？
- 发布、灰度、观测和回滚是否与风险匹配？
- 数据迁移和外部接口变化是否有兼容策略？
- 实施步骤是否有顺序、依赖和每步验证方式？

## 可测试性

- 每个目标能否映射到自动化或手工验证？
- 是否说明需要新增或修改哪些测试层级？
- 性能、可靠性或安全目标是否有可执行验证方法？

## 典型严重发现

- 关键现状断言与代码不符。
- 方案无法覆盖上游验收标准。
- 数据或接口变化没有迁移、兼容或回滚策略。
- 实施者仍需自行决定核心接口和数据流。
