# 需求验证检查表

## 问题与价值

- 能否一句话说清谁遇到了什么问题？
- 是否说明不解决的实际影响？
- 目标是结果还是预先指定的功能清单？
- 项目定位、用户证据或业务背景是否支持这项工作？
- 是否存在更小、更直接或价值更高的替代方案？

## 目标与范围

- 目标是否具体且彼此一致？
- 非目标是否覆盖最容易被误解的相邻范围？
- Must-have 是否真的缺一不可？
- 是否把未来想法混进当前承诺？
- 依赖、期限和不可改变的约束是否明确？

## 用户行为

- 用户角色是否足够具体？
- 核心场景是否覆盖开始条件、操作和结果？
- 是否覆盖权限差异、空态、错误、取消、重复操作和边界输入？
- 要求是否描述用户可观察结果，而不是越界指定 UI 组件或技术实现？

## 验收标准

- 每条标准是否能独立验证？
- 是否明确前置条件、动作和预期结果？
- “快速、友好、稳定、支持”等词是否被具体化？
- 是否包含关键失败路径和不应发生的行为？
- 验收标准是否足以让 Engineer 建立测试证据？

## 事实与来源

- 已确认事实、推断和开放问题是否分开？
- 外部 PRD 中的原始要求与团队补充是否可区分？
- 高风险假设是否有负责人和解决方式？
- 重要决定能否追溯到用户、数据或上游材料？

## 典型严重发现

- 两种合理解释会产生不同产品行为，却没有决定。
- 核心验收标准无法判断真假。
- 需求与已确认的项目目标直接冲突且未说明。
- 关键假设被写成事实，错误时会推翻整个方案。
