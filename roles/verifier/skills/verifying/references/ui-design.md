# 界面设计验证检查表

## 需求覆盖

- requirement 中每个相关场景是否有体验答案？
- 是否擅自增加需求之外的业务能力？
- Product 已确定的术语、优先级和行为是否被正确表达？

## 用户路径

- 用户能否看出当前位置、可执行动作和下一步？
- 核心任务是否存在不必要步骤、重复确认或隐蔽入口？
- 危险操作是否有足够提示和恢复方式？
- 成功、失败和处理中状态是否给出及时反馈？

## 状态与边界

- 默认、悬停、焦点、禁用、加载、空态、错误和成功状态是否适用且完整？
- 超长文本、大数据量、窄屏、慢网络和权限差异是否有明确行为？
- 表单校验、重复提交、取消和返回后的状态是否清楚？

## 设计系统

- 是否优先使用现有组件、token 和布局模式？
- 新组件或新 token 是否真的有必要？
- 同类元素的层级、间距、交互和文案是否一致？
- 设计源与文字补充是否互相冲突？

## 可访问性

- 键盘能否完成核心路径？
- 焦点顺序和焦点可见性是否合理？
- 颜色是否被用作唯一信息载体？
- 标签、错误信息、点击区域和对比度是否足够？

## 工程交接

- Engineer 是否能知道组件、状态、断点、资源和行为，而不需要猜？
- 哪些内容由设计源表达，哪些由补充说明表达，是否分工清楚？
- 仍留给 Engineer 的实现自由度是否明确？

## 典型严重发现

- 核心需求场景没有对应界面或交互。
- 错误、权限或空态缺失，Engineer 无法决定正确行为。
- 设计稿与 requirement 在关键产品行为上冲突。
- 核心路径无法通过键盘完成且没有合理原因。
