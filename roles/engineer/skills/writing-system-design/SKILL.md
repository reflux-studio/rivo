# 撰写 System Design

system-design 是 Engineer 对实现和验证作出的承诺：实现者不再猜核心接口、数据流、影响面或验证方式；评审者能检查方案建立在真实现状上。方案不能建立在对代码库或运行行为的猜测上——先调查，再收敛，再撰写。

需要用户或上游拍板的决策使用 `frontier-questioning` 分轮批量提问，每题附推荐答案；代码、配置和运行行为属于事实，自行调查。

## 1. 识别输入类型

- **产品或体验交接**：读取 requirement、ui-design 和各自修订。
- **纯技术任务**：先明确目标、完成标准和不应改变的行为。
- **现成技术方案**：核实断言、缺口和适用约束。
- **已观察异常**：先使用 `systematic-debugging` 得到复现和根因证据，再进入方案。

## 2. 明确目标和质量属性

除功能目标外，确认对当前决策有影响的质量属性：性能与容量、可用性与故障恢复、一致性与数据正确性、安全与合规、兼容与迁移、成本与期限、可观测性。只处理真实场景要求的维度。

## 3. 调查现状

从仓库外围建立地图，再深入受影响路径：入口、模块和调用链；数据如何进入、变化、存储和输出；已有接口、抽象和扩展点；现有测试、监控和部署方式；最近相关变更；工程认知中适用的架构约束。

关键断言要能指出代码、配置、日志或运行结果。调查方法见 [references/current-state-investigation.md](references/current-state-investigation.md)。

## 4. 找影响面

检查直接和间接影响：API、事件和数据模型；前端、后端、任务、缓存和存储；权限、审计和敏感数据；迁移、回填和历史数据；旧客户端和外部消费者的兼容；测试、监控、发布和回滚。明确哪些部分保持不变，防止实现范围无意扩大。

## 5. 形成候选方案

至少考虑：复用现有模式的最小方案；结构更合理但成本更高的方案；不改代码或延后处理的替代方案（若现实可行）。比较当前约束下真正重要的维度。详细方法见 [references/tradeoff-guide.md](references/tradeoff-guide.md)。

## 6. 验证关键假设

高风险未知项优先用最小实验验证：打开真实代码和依赖文档、写小型 spike 或查询、运行性能基准、验证第三方 API、检查数据分布、在非生产环境演练迁移或回滚。实验结论与推断分开；无法验证但可接受的风险写明监控和退路。

## 7. 撰写方案

按决策量选择深度——小改动写目标、现状、改法、影响面和验证方式即可；数据迁移、公共接口、安全或高可用改动展开兼容、观测、发布和回滚；多个可独立实施的目标拆分或分阶段。推荐结构见 [references/system-design-structure.md](references/system-design-structure.md)。

- **已验证的现状**：只保留影响方案的事实，关键断言附证据；说明为什么现有模式不能直接满足目标。
- **方案与边界**：整体思路和数据流、受影响模块及职责、接口和数据模型、状态转换与失败恢复、与现有能力的复用关系、明确不改变的部分。图能提高理解时使用，但图不替代关键文字契约。
- **取舍**：现实考虑过的替代方案、未采用原因、当前选择接受的代价，以及哪些条件变化时需要重新评估。
- **风险与不可逆变更**：数据迁移、外部兼容、权限与隐私、性能与容量、监控盲区、回滚限制。不可逆变更醒目标明，列出需要的批准。
- **实施步骤**：按依赖顺序，每步说明改什么、影响哪里、完成后如何验证、能否独立提交或回滚。
- **测试与发布**：每个目标映射到单元、集成、E2E、性能或数据验证；发布策略与风险匹配，提前定义回滚条件。

## 8. 发布

确认核心接口和数据流已经决定、不可逆变更已识别、上游缺口已解决；仍会迫使实现者猜测的缺口作为待处理发现，在解决或有留痕地跳过之前不发布当前版本。随后按 `collaborating` 的产物发布约定发布，并注明对应的上游版本。
