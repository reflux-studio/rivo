# 系统化排查

乱枪打鸟的修复浪费时间还制造新 bug，快速补丁只是把问题埋深一层。

核心原理：**先找到根因，才允许动手修。修症状就是失败。**

## 铁律

```
没有完成根因调查，就没有资格提出修复
```

## 什么时候用

任何技术问题：测试失败、线上 bug、行为异常、性能问题、构建失败、集成问题。

**越是下面这些时刻，越要按流程走**：

- 时间紧（紧急最容易诱发瞎猜）。
- 「有个明显的快速修复」摆在眼前。
- 已经试过好几个修复了。
- 上一个修复没起效。
- 你并不完全理解这个问题。

问题看起来简单不是跳过的理由——简单 bug 也有根因，流程对简单 bug 走得也快。

## 需要的输入

任何一样都有帮助，越多越准：

- 报错信息或堆栈——**原文，不要转述**，确切的文本很重要。
- 复现步骤。已经有黑盒复现记录的，从它开始，不重复劳动。
- 最近改了什么：部署、依赖升级、配置变更——头号嫌疑人。
- 日志或截图。
- 预期行为 vs 实际行为。
- 范围语境：「staging 好的、线上坏」「只有大 payload 出问题」——一句话砍掉一半搜索空间。

用户报告只代表“已报告”。稳定复现或取得等价证据后才是“已确认”；确认后再判断属于实现缺陷、产品设计缺陷、环境问题还是外部依赖，标记为“已归类”。

## 四个阶段

每个阶段完成之前，不进下一个。

### 阶段一：根因调查

在考虑任何修复之前：

1. **把报错读完**。不跳过报错和警告——里面常常就写着答案。堆栈读到底，记下行号、路径、错误码。
2. **稳定复现**。能可靠触发吗？确切步骤是什么？每次都发生吗？复现不了就继续收集数据，不猜。
3. **查最近的变更**。什么改动可能导致它？diff、最近的提交、新依赖、配置差异。若已连接源码托管，列出触碰相关路径的最近提交；若已连接监控，拉取问题时段的错误率和指标，对照部署时间线。
4. **多组件系统先插桩取证**。系统跨多层（CI → 构建 → 签名，API → 服务 → 数据库）时，先在每个组件边界加日志——进来什么、出去什么、环境和配置有没有传到——跑一次拿到「断在哪一层」的证据，再去调查那一层。不带证据就挑一层开始猜，是排查最大的时间黑洞。
5. **回溯数据流**。报错在调用栈深处时：坏值从哪来？谁用坏值调了这里？一路向上追到源头。修在源头，不修在症状处。

### 阶段二：模式分析

- **找能工作的同类**。同一个代码库里，和坏掉的这处相似但能用的代码在哪？
- **完整读参考实现**。在照一个模式实现时，把参考读完——每一行，不略读。部分理解保证出 bug。
- **列出所有差异**。能用的和坏掉的之间，差异逐条列，再小也列，不断言「这个不可能有关」。
- **理解依赖**。它需要什么组件、配置、环境？做了什么假设？

### 阶段三：假设与验证

- **一次一个明确的假设**：「我认为根因是 X，因为 Y」——写下来，具体，不含糊。
- **最小改动验证**：一次只动一个变量，不同时修多处。
- **验证完再继续**：成立，进阶段四；不成立，换新假设——**不在旧修复上叠新修复**。
- **不懂就说不懂**：不装懂，去问、去查，不硬编一个解释。

### 阶段四：实施修复

1. **先建失败的测试**。最简复现，能自动化就自动化（写法见 test-driven-development）。没有失败的测试，不动手修。
2. **单一修复**。只改根因指向的那一处，不带「顺路改进」，不捆重构。
3. **验证**。测试转绿了？其他测试没坏？问题真的消失了？
4. **修复无效就停**。数一数试了几个修复：不到 3 个，带着新信息回阶段一重新分析；**3 个及以上，停下来质疑架构**。
5. **三连败 = 架构问题**。信号：每个修复都在别处暴露新问题、修复动辄要「大规模重构」、修一处坏一处。这不是假设失败，是模式本身错了——停止修复尝试，把架构疑点带给用户讨论。

## 危险信号——出现这些情况就停下，回到阶段一

- 「先快速修一下，回头再调查」。
- 「改改 X 试试看」。
- 一次改了好几处，跑测试碰运气。
- 「跳过测试，我手动验一下就行」。
- 「多半是 X，我修了」——没追过数据流就提方案。
- 「我不完全理解，但这样也许能行」。
- 「再试一个修复」（已经失败两次以上时）。

## 常见借口

| 借口 | 现实 |
|------|------|
| 「问题很简单，不用走流程」 | 简单问题也有根因。流程对简单问题走得很快。 |
| 「紧急情况，没时间走流程」 | 系统化比乱试快——乱试才是最慢的路径。 |
| 「先试这个，不行再调查」 | 第一个修复定下整个基调。从一开始就做对。 |
| 「修好了再补测试」 | 没测试的修复站不住。先有失败的测试才叫证明。 |
| 「一次多修几处省时间」 | 分不清哪个起效，还会引入新 bug。 |
| 「参考太长，我照大概意思改」 | 部分理解保证出 bug。读完。 |
| 「我看到问题了，让我修」 | 看到症状 ≠ 理解根因。 |
| 「再试一次」（已败两次以上） | 三连败 = 架构问题。质疑模式，别再修了。 |

## 快速参照

| 阶段 | 关键动作 | 完成标准 |
|------|---------|---------|
| 一、根因调查 | 读全报错、稳定复现、查变更、插桩取证 | 知道坏在哪、为什么 |
| 二、模式分析 | 找能用的同类、逐条比差异 | 找到关键差异 |
| 三、假设验证 | 单一假设、最小实验 | 假设被证实或更新 |
| 四、实施修复 | 失败测试、单一修复、验证 | 测试转绿、问题消失 |

## 真的「没有根因」时

调查确实指向环境性、时序性或外部因素的：记录你调查了什么，实现恰当的处理（重试、超时、报错信息），加上监控和日志供下次追查。但要诚实——**九成五的「找不到根因」是调查没做完。**

## 产出结构

```markdown
## 排查记录：[问题摘要]

### 复现
- **预期**：[应该发生什么]
- **实际**：[实际发生了什么]
- **步骤**：[如何复现]

### 根因
[为什么会发生——验证过的写结论，没验证的标「推断」]

### 修复
[改了什么、为什么这个改动解决的是根因]

### 防回归
- [固化的失败测试]
- [加上的防护或监控]
```

## 注意事项

- 若已连接项目管理工具，先搜相关的已知问题和历史工单，别重复排查。
- 「重启就好了」不是根因，是把问题推迟到下一次发作。
- 排查中发现实现符合既有设计，但结果仍不合理时，如实上报产品设计缺陷——那不是技术修复能单独解决的事。
- 当前存在正式交付时，按 `collaborating` 的产物发布约定把排查记录写入指定后端；未指定时写入交付目录的 `investigation.md`。
