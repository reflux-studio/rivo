# Rivo 技能体系审阅

审阅日期：2026-09-30。对象：本地 HEAD `356b684`（清单版本 0.8.4）及四个未提交的技能文件改动。对照了 `v0.8.0`、相关修改提交、0.8.1 审阅记录和当前会话中的 APC 方案样本。

本轮只审阅，未修改技能、方案或产品代码。报告中的文件位置以 Rivo 仓库根目录为基准。用户最近明确的写作原则是：不重复解释、不要求读者跳转；通过选材和组织一次讲清。同一概念在后文继续使用不算重新解释。

## 结论

Rivo 有可保留的流程骨架：用户决定需求和重要取舍，AI 查证；方案批准与实施授权分开；实施发现错误前提要返回修订；验收后核实知识并归档。调查、TDD 和排障对证据的要求也基本一致。

主要问题在骨架之间的连接。什么算重要决定、什么只是实现选择、什么需要记录、什么必须写入供人评审的方案，没有形成稳定的边界。结果是讨论不断产生材料，方案负责全部承接，实施又把写进方案的内容当成需要确认的约定。写作补丁随后试图通过段落、列表和标题控制体积，无法消除上游制造的负担。

不能把所有问题都归因于 v0.8.0 的文字重构。首次方案审阅、逐任务轻审、粗粒度任务和不另设状态文件，是该版本明确做出的流程选择。审阅次数和讨论节奏若要改变，需要重新讨论收益与代价。真正可以直接判定的缺陷，是相同规则在不同阶段不一致、规则与示例相反，以及修复结果无法可靠追溯。

## 1. “重要决定”的判定过宽，普通选择会被升级为流程约束

`skills/converging/references/adr.md:7–12` 要求：有多个可行选项，并且会引出问题或推翻后造成返工，就写 ADR。这个条件并不能区分重要架构决定与普通工程选择。组件拆成一个还是两个、内部辅助函数放在哪个文件，也可能满足两条。

`skills/converging/SKILL.md:60–70` 随后检查每个回答、追踪 ADR 依赖并要求问题闭合。`skills/writing-plans/SKILL.md:108–115` 又把达到 ADR 门槛而未由用户决定的选择交回讨论。局部选择一旦被记成 ADR，就获得了影响后续流程的权重。

这会增加提问、记录和确认，也给方案增加必须承接的材料。它不证明当前每份 ADR 都多余，但规则本身缺少重要性的筛选条件。0.8.1 审阅记录已经指出此风险，当前判据仍未变化。

修正方向：先按影响判断是否需要用户决定，例如业务行为、跨系统契约、重要成本或不可轻易改变的约束；再判断决定如何记录。不能从“需要写 ADR”反推出“必须让用户决定”。用户已经授权 AI 选择的范围也应继续有效。

## 2. 方案与实施的分工，会随方案写得多细而改变

`skills/writing-plans/SKILL.md:31–32` 要求普通细节纳入正文；方案结构要求给出类、组件和配置落点。`skills/implementing-plans/SKILL.md:69–73` 则区分“plan.md 写明的内容”和“方案没写到的纯实现选择”：前者修订后由用户确认，后者允许执行者决定。

由此产生一个不稳定边界：同样是不改变外部行为的组件拆分，没写进方案时执行者可以决定，写进去以后就可能被当成方案变更。方案越详细，实施越容易需要来回确认；为避免遗漏继续加细节，又进一步扩大需要确认的范围。

修正方向：确认权限应取决于变化的语义和影响，不能取决于它是否曾经出现在 plan.md 中。方案说明本期做法和需要共同遵守的契约；不影响这些约定的实现调整由 AI 处理并保持必要记录。重要决定变化仍由用户确认。无需新增文档阶段。

## 3. “核心设计缺口”只补进方案阶段，尚未统一初次设计与实施修订的处理

`skills/writing-plans/SKILL.md:100–104` 规定，核心缺口补齐前不能定稿，也不能进入实施。`skills/implementing-plans/SKILL.md:22` 和 `78–82` 允许方案修订期间继续不依赖变化的任务。

初次设计未完成时不开始实施，与已有方案实施中暂停受影响任务，都是合理行为。但新规则没有明确区分这两种状态。已经实施到一半时发现材料转换方式不成立，重新进入 writing-plans 后，模型可能全停，也可能按实施规则继续。草稿状态还没有说明它基于哪份已经批准的方案、哪些范围仍有效。

同一处缺口也需要区分原因。能通过实验确定的文件形态应先查证；查证后存在多个可行方案，才需要做取舍。现有 converging 和 investigating 有这个原则，核心缺口处理却概括为“由用户决定”，增加了把技术事实也交给用户回答的可能。

修正方向：阶段之间共用相同的判断顺序——先分清事实缺失与决定缺失，再确定受影响范围，最后决定可继续的工作。初次未获批与已有获批范围的修订需要明确区分，不必为此新建复杂状态文件。

## 4. 审阅依赖“第几次”，而不完全依赖当前内容和版本

`skills/writing-plans/SKILL.md:71` 明确只在首次定稿前全量独立审阅，后续修订由用户确认。历史提交 `2a1beab` 的理由曾是“方向在这一轮就会暴露”；0.8.1 删除了这项过满判断，但保留了审阅次数。

这个选择能减少审阅成本，但其代价需要正视：方案通过后新增权限模型或数据迁移，用户同意新的业务方向，并不等于新技术设计已经经过独立核验。当前规则要求报告影响和验证范围，能提高透明度，却不能替代缺失的技术审查。0.8.1 报告已经把它列为待验证的流程选择。

实施也有相似边界：`skills/implementing-plans/SKILL.md:59–61` 在用户验收反馈后要求修复、重跑验证，再请验收，没有明确什么变化会使此前的整体审阅结论失效。

修正方向不是恢复每次改字都全量送审，而是讨论按影响复核：纯表达修订沿用结果；改变权限、共享契约、数据迁移等内容时，仅复核变化及波及范围。若用户仍选择后续仅由本人确认，应明确这是一项成本取舍，不把历史审阅表述为覆盖当前全部设计。

## 5. 复核落盘只修了方案审阅，实施审阅仍有同样的证据缺口

`skills/writing-plans/references/receiving-review.md:37` 和对应审阅提示词要求每轮复核追加到原报告，注明版本或快照。实施侧的 `references/reviewer.md:46–48` 只说明复核范围，`references/receiving-review.md:27–34` 只要求复核通过，没有要求保存该轮结论及对应代码版本。

触发场景：某任务审阅不通过，执行者修复，原审阅者在会话里确认通过，随后上下文切换。报告仍可能只保存第一次“不通过”，恢复工作时无法区分修复已核验、仅已修改，或根本没复核。实施报告本身有版本字段，但首次报告中的版本不能代替后续复核的版本。

这是明确的跨阶段修补不完整。应统一“审阅对象、结论、版本、仍未关闭的问题”这几个含义；方案和代码各保留自己的检查重点。统一不意味着把所有提示词移入一个大文件，也不应迫使执行者层层跳转才能知道如何工作。

## 6. 写作规则开始改善结构，但仍存在形式约束与示范之间的冲突

未提交改动把功能点改为事后检查项，移除了仓库改动汇总，并明确先选材后编辑。这些应保留。“每个事实只写一处”和“不让读者跳转”并不矛盾；如果无法同时满足，应先移动或合并相关内容，不应恢复重复解释。

仍有三类问题：

- `skills/writing-clearly/SKILL.md:25–26,40–42` 用句数、条目数、代码名数量和朗读长度控制表达。这些条件只能提示可能的难读，不能决定是否拆分。它们会把没有必要拆开的内容变成碎片。
- `plan-structure.md:36,50` 将问题式标题和一句话现状说明写得过于绝对。标题不一定需要是问句；与本期决定直接相关的约束也不一定一句就能说清。应依据内容作用取舍，不制造新的统一腔调。
- 示例没有贯彻正文要求。`plan-structure.md:102–104` 把多种结果塞进一个单元格，回调请求只写“审批中心回调载荷”，具体定义在示例之外的调查材料中；第 117 行仍要求使用“上面的回调接口”。短了，但读者又需要自己找信息。

正文禁链接与通用规则允许随文链接也需要明确适用范围。AI 技能的调用导航与面向人的方案叙述不是同一种阅读任务；不应把所有内部导航都禁掉，也不能用工具能跳转为人类方案保留理解上的跳转。

修正方向：保留不重复、不跳转和一次讲清，删除机械计数；示范通过重新选材和组织变短，不能通过省略必要定义变短。不要用某份 APC 方案的句式逐条反向生成通用写作规则。

## 7. 整体实施审阅对原始范围的回查不够明确

方案审阅的输入明确包含原始请求、PRD 与用户决定。实施审阅模板的明确输入则是 task、plan、ADR、note、代码与验证证据；虽然第 17 行泛指“需求和决定依据”，整体检查第 31 行只具体要求与 ADR、plan 和共同约定一致，第 34 行检查方案想达到的效果。

如果需求在成文或后续修订中被无意遗漏，任务、测试和代码可以全部与错误的方案一致，整体审阅仍可能看不到遗漏。用户批准方案不能自动解释为用户有意删除了所有未被写入的原始需求。

修正方向：整体审阅要能对照原始需求及经用户批准的范围变更，区分有意调整与意外遗漏。无需新增一份 Spec 或逐项追踪矩阵；保持原始依据和范围变更可获取，在最终交付时核对即可。这里是输入与检查要求不充分，不能据此断言过去每次交付都漏了需求。

## 8. 知识维护仍按文件形状决定组织方式

`skills/knowledge-management/references/knowledge.md:15–17` 规定，已有知识库如果是单个多节 README，就把本次涉及的主题拆成文件，并把原位置改为导读链接。

这个动作不是核实知识的必然结果。一篇按阅读顺序组织的说明，可能因此被拆成需要往返导航的若干片段。它也与“只改本次涉及的知识，其余保持原样”的保守维护目标存在张力。

不重复、不跳转的原则并不要求整个知识库只有一个文件。问题在于分割应依据能否独立解释一个主题，而不能仅因为当前载体是 README。修正方向是保留现有阅读结构，确实形成独立主题时再拆分；目录导航用于找主题，不代替主题内部的解释。

合并基线要求本身值得保留。最新方案结构不再要求在 plan 记录知识库版本，而知识参考第 50 行仍提到“plan.md 的现状一节”，属于次要的跨文件残留；note 已有记录要求，因此不是归档必然受阻。

## 9. 宿主缺少能力时，没有明确的继续与停止边界

`skills/using-rivo/SKILL.md:93–104` 列了子代理调用方式；方案和实施都依赖独立审阅，实施还要求每项任务启动新执行者。但没有说明子代理不可用、达到并发上限或审阅者失败时，哪些工作可以由主代理继续，哪些结论必须保持未完成。

实际后果是不同宿主或模型可能选择全停，或者自行审查后仍宣称独立审阅完成。当前文档没有授权后者，本轮也没有观察到它已发生；缺的是失败分支。0.8.1 报告已经记录此项，尚未形成明确处理方式。

修正方向：工具能力不足不改变质量含义。允许继续的调查或实现与尚未完成的独立审阅分别报告；不能把自查改名为独立审阅。是否采用其他审阅方式由已有授权和用户要求决定，不应默认增加审批步骤。

## 10. Rivo 自身的行为回归没有成为可复用产物

README 第 111 行已经要求执行规则变化后用具体需求试用。现有受跟踪文件中没有可复用的行为测试场景、预期动作或相应结果集；0.8.1 的审阅报告明确说没有模型行为试用。

这不证明仓库外从未试用。APC 本身就是实际样本，但连续在同一需求上修改规则，容易只解决该样本刚暴露的症状，不能说明简单需求、实施修订、恢复会话和知识收尾仍然正常。

需要验证的是动作和结果，而非模型会不会复述规则。以下场景可构成小规模回归集，无需建设复杂测试平台：

| 场景 | 应观察的行为 |
| --- | --- |
| 普通局部改动 | 不把普通实现选择升级为用户决策和 ADR |
| 跨系统方案缺转换契约 | 先查证或讨论；不靠移入待决项认定设计完成 |
| 有初始账号缺口的新权限流程 | 能发现上线第一天走不通，并明确初始化方式 |
| 已批准方案修订一个接口 | 暂停依赖任务，保留无关任务的已有授权，审阅覆盖范围明确 |
| 修复审阅问题后恢复会话 | 能从记录确定修复和复核分别完成到了哪里 |
| 同一设计在材料中多次出现 | 成文时只在合适位置解释一次，不以跳转补救拆散的结构 |
| 已有单文件知识库 | 不因文件形状自动拆分，保留其他工作写入的内容 |
| 子代理不可用 | 不虚称独立审阅完成，也不阻塞无关的可继续工作 |

本轮只做了这些规则路径的静态推演，没有启动模型执行这些案例。未来行为试用应包含较弱模型，并区分模型试用与独立审阅；不能用一次强模型审阅代替执行验证。

## 哪些需要保留，哪些需要重新决定

九个技能不必全部推倒重写。调查应回答事实，讨论应处理取舍，方案应表达做法，实施应兑现行为，知识应解释已核实的现状，这些职责可以保持。

| 技能 | 本轮判断 |
| --- | --- |
| using-rivo | 入口与授权原则清楚；需要统一阶段间约定和能力不足的处理 |
| converging | 事实先查证、沿依赖讨论可保留；重要决定门槛和结束条件需要重新校准 |
| investigating | 证据分类、端到端调查、禁止据搜索命中判断已接入，均应保留 |
| writing-plans | 人类阅读目标清楚；与决定记录、实现细节、修订审阅的边界需要重整 |
| writing-clearly | 选材与因果组织可保留；撤掉机械格式限制，并使示例符合原则 |
| implementing-plans | 按可验收结果拆任务、发现错误前提返回处理可保留；确认权限和复核记录需统一 |
| test-driven-development | 目标行为、真实红绿、模拟边界与非代码验证区分清楚；本轮未发现同等级结构性缺陷 |
| systematic-debugging | 从复现到假设检验、区分实验与正式修复、报告约定冲突，职责清楚 |
| knowledge-management | 核实已实现现状、合并而非覆盖、验收后归档可保留；撤掉按文件形状自动拆分的规则 |

“前沿问题一次问完”是 v0.8.0 的明确选择，本轮不建议把它直接替换成任意固定数量上限。它是否造成用户负担，应观察真实答复和遗漏情况；优先减少不值得用户决定的问题，比规定每轮三问或五问更接近根因。

## 修正顺序

先确定少数共用原则：哪些决定属于用户、哪些工作属于 AI；哪些内容供人理解、哪些保存查证依据；审阅结论覆盖什么版本和范围。然后按实际执行路径同步调整主技能、参考文件、子代理提示词和示例。

对写作，先选本期做法，再确定每个问题一次讲完的位置，最后才修句子。对流程，先区分事实、决定与实现选择，再安排调查、确认和记录。对质量控制，先明确当前变化需要什么证据，再决定核验范围。不要继续按“文档太长就加短句规则、漏某项就给所有方案加一节”的方式扩展。

本轮不建议新增阶段、增加一种中心状态文件、恢复全面重复审阅，或把所有公共内容抽进必须层层打开的总规范。共用原则需要一致，单独加载的技能和角色提示词仍应具备完成自身工作的必要信息。

## 检查范围与限制

已通读九个主技能及全部参考文件，检查 README、两份插件清单、marketplace、启动 hook、图源与既有审阅报告，并核对相关 Git 历史。APC 方案仅作为当前产物样本，不在本轮重新核验其 Java、前端代码或在线 PRD 的真实性。

本地检查结果：5 个 JSON 解析通过；2 个 SVG XML 解析通过；9 个技能的名称与目录一致且有 description；Markdown 围栏检查通过；排除代码示例后 35 个本地链接有效；两份插件清单版本一致，均为 0.8.4；两个 shell 文件通过 bash 语法检查；启动 hook 在普通目录和含 .rivo 的目录中，以 Claude、Cursor、通用输出分支共六种本地环境运行，JSON 和入口注入符合脚本预期；git diff --check 通过。

hook 检查是本机脚本模拟，不代表真实宿主安装和生命周期验证。未运行 Windows hook、真实 Claude Code/Codex 安装测试、模型行为回归或新的图形布局检查。未复现所有历史会话，也不能据此确定每次偏离来自规则、模型还是当时上下文。结论覆盖当前体系的静态结构、具体冲突和已有样本，不声称穷尽实际执行中的全部问题。
